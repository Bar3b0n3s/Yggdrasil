# Game debugging

Use this skill when a game built through automation does something unexpected: a script error, a test that fails, a ball that falls through the track, a sound that is silent, a replay that no longer verifies. `docs.get {topic: "reference/Automation"}` has every method's params and results, and `reference/Validation` every validation code (the topics `game-building` lists under "Documentation"; Architecture §13.7 of the repository describes the observability design). Methods are written `domain.verb` as `engine_client` calls them; the MCP bridge proxies the tool-flagged ones as `domain_verb` (`log.read` is the tool `log_read`) and reaches every other method through `engine_call {method, params}`. Work in a loop: **observe, form one hypothesis, check it with the narrowest query, fix through automation, re-run the deterministic check.** Never edit project files by hand to try something (see `game-building`).

## Pages

Four reference pages beside this file hold the error tables, the native module's rules and the 2D checks; each is a `docs.get` topic and a file in this skill's directory:
- `skills/game-debugging/error-codes` ([error-codes.md](error-codes.md)): the JSON-RPC errors, the engine `ErrorCode` values, the script error kinds and the MCP bridge errors, each with its fix.
- `skills/game-debugging/validation-codes` ([validation-codes.md](validation-codes.md)): every `project.validate` code with its severity, what it means and its fix.
- `skills/game-debugging/native-module` ([native-module.md](native-module.md)): a game's C++ module: why it does not run, its build diagnostics and refusals, native components, fatal stops, what a module reaches, and its provenance and format rules.
- `skills/game-debugging/sprites-2d` ([sprites-2d.md](sprites-2d.md)): 2D games: a sprite or tilemap that does not show, sort, animate, light or look sharp, and a 2D body, tilemap collider or 2D callback that does not behave, with the 2D collider overlay and `physics2d.bodyInfo`.

## The observability loop

1. **Read what the engine already told you.** Every response carries `_meta.diagnostics` (`newErrors`, `newWarnings`, `newScriptErrors`, `firstNew`) and `_meta.playState`. Start there. `_meta.revision` counts changes to the addressed open scene (the active one, or the request's `scene` target) and the project settings only: creating or writing assets and scripts leaves it unchanged, so `ifRevision` guards the scene and the settings, not asset files. A revision names one state of one scene, so a revision read in one open scene never matches another.
2. **Logs and events, by cursor.** `log.read {cursor, minLevel: "Warn", contains?, limit?}` returns structured entries with source locations and entity context, oldest first, at most `limit` per call, and `nextCursor`. Page by passing exactly the returned `nextCursor` as the next `cursor` until a read returns no entries; never compute or guess a cursor (from `seq` numbers or entry counts), which skips entries without an error. `cursor: ""` starts at the oldest entry held, `cursor: "end"` returns only the cursor of the next entry (to watch from now on), and `dropped` counts entries overwritten before the read could see them. `events.read {cursor, types?: ["ScriptErrorRaised", "AssetImportFailed", "PlayStateChanged", "AssetReloaded", "SceneChangedOnDisk", "SceneOpened", "SceneActivated", "SceneClosed", "DiagnosticsChanged", "GpuDeviceLost"]}` pages the same way and tells what happened in order.
3. **Script errors.** `script.errors {since}` lists deduplicated errors with kind, script, line, column, callback, entity, slot (the faulting behaviour's place in its entity's Script list), tick, count and traceback; `nextCursor` continues, `evicted` says older ones were dropped. `tick` is the session's tick the latest occurrence's callback ran in, as `Time.GetSessionTick()` reads it there (`Time.GetTick()` too in a session whose world never paused; after a world pause `Time.GetTick()`, the world's clock, is behind it): in the fixed step the zero-based index of the tick being run (0 in the first `OnFixedUpdate`, so a fault in the first tick of `play_step {ticks: 2}` reads tick 0 while `_meta.tick` is then 2), in the frame phase (`OnUpdate`, `OnLateUpdate`) the ticks completed. A failing instance is disabled at its first error, whatever `pauseOnError` says, and only it: it runs no further callback (its tasks are cancelled) until a hot reload of its script, so a line that faults every tick still reads `count: 1`, while the entity's other script slots and every other instance keep running; `count` counts the occurrences of the same error (script, line, message), one per faulting instance. With `Scripting.PauseOnError` (or `play_start {pauseOnError: true}`) the editor also pauses ordinary play at the first error. The list is the current play session's: a new play session (`play.start`, `input.record`, `input.replay`) forgets the earlier sessions' errors and keeps the cursor, so a cursor taken before the start reads exactly the new session's. A `script.eval` that raises is the caller's error: it is answered with `ScriptError` (-32006, the located error with its traceback in error data `scriptError`) and logged, and never enters this list nor its response's `_meta.diagnostics` (`newScriptErrors`, `firstNew`), which count the game's errors only.
4. **Ask the running game.** `script.eval {context: "Play", entity: "/Game", code: "return self.Board:ToAscii()"}` evaluates in the play VM with `self` bound to the instance of the entity's first script slot (`script: "<Name>"` binds it to the slot whose behaviour has that `Script.Define` name; NotFound at `/script` when none has) and returns the value plus captured prints. The value is JSON (nil, booleans, numbers, strings and tables of them), and a vector, `Color` or `Quat` at any depth comes back as the array of its components (`[x, y, z]`, `[r, g, b, a]`, `[x, y, z, w]`), as `graph.liveValues` reads them (only `script.eval` converts them: a `play.waitFor` predicate or a replay expectation returning one fails with its Script error); any other value (an `Entity`, a function) fails with an error naming its type and place, so unpack it (`return e.Name`). `context: "Edit"` is read-only. During a recording, evaluate only reads: a write through an engine API (a component, an entity, `SetActive`, a session `Random` draw) invalidates the recording, and a write to a Luau table (`self.Score = 0`, `self.Board:FillRows(...)`) is neither detected nor recorded, so once that write shows in a checkpoint, the final hash or an expectation the recording no longer reproduces itself and `input.record`'s `stop` refuses it, event-free or not.
5. **Where things are.** `scene.tree {format: "Text", root?, depth?}` gives the compact outline (ids, components, positions); `scene.query {where: {name?, tag?, component?, path?}}` finds entities; `entity.get {entity, components: "all"}` shows values; `entity.bounds {entities}` gives world AABBs, the quickest check for gaps and overlaps. For UI, `ui.tree {format: "Json", target?, width?, height?}` gives every canvas and element in scene pixels with its rectangle, clip and `visible` flag: an element that does not show is hidden (outside the scene image or its clip), disabled, outside every canvas (`UI_ELEMENT_WITHOUT_CANVAS`) or drawn under a later one (`skills/game-building/ui`).
6. **What changed.** `scene.diff {against: "Saved"}` lists RFC 6902 changes per entity since the last save (or `against: "Revision", revision`); `edit.history` lists the undo steps. Each open scene has its own command history: `scene.open` and `scene.new` without `keepOpen` replace the active scene and clear its history (earlier undo steps are gone), but undo indices keep increasing for the editor's lifetime, so an index never names a later command; an `undoIndex` of 0 means the call recorded no command (a `project.validate` that fixed nothing, a dry run, a batch op).
7. **Look.** `viewport.screenshot {view: "Game" | "Scene", width, height, target?, annotate: {labels: "all", colliders: true, bounds: true, axes: true}}` draws names, short ids, colliders and bounds over the frame so you can tie pixels to entities (UI elements get yellow outlines and labels in scene pixels). For the game view pass the project window's size (`width: 720, height: 900` for a 720 × 900 game), which the PNG keeps unless `maxDimension` caps its larger side: the default is 640 × 360 whatever the window, which misframes a portrait game and scales screen text by the wrong height; `target: "Play"` renders the play scene, where runtime entities such as a pool exist; `debugView` shows a data view instead of the lit image: `Albedo`, `Normals`, `Roughness`, `Metallic`, `Emissive`, `AO`, `ShadowCascades`, `Overdraw` or `LightCount` (`Lit` is the default). `ShadowCascades` colours each surface by its cascade: 1 red, 2 green, 3 blue, 4 yellow, blended across the blend bands; black is no surface, no shadow-casting `DirectionalLight`, or beyond the shadow distance (`ShadowDistance` or the camera's far clip), into which the last cascade fades. `LightCount` colours each pixel by the lights its light cluster holds: 0 black, 1–2 blue, 3–4 cyan, 5–8 green, 9–16 yellow, 17–32 orange, more red. Needs an editor with `renderer: "vulkan"`.
8. **Physics.** `physics.bodyInfo {entity}` reports the body (type, layer, sensor, colliders, velocities, sleeping, bounds, contacts since which tick, grounded, ground normal and, for a character, the collider it stands on, `groundCollider`, and whether it is squeezed, and by what, `squeezed` and `squeezedBy`, and its centre of mass, `centerOfMass`, which a `MassProperties` moves) of the play session; `Physics.GetSurface` reads that collider's friction and surface velocity from a script. A missing body means a physics validation error kept it from being created. `physics.jointInfo {entity}` reports a joint (M37): the bodies it joins, `created` (false for one refused by `PHYSICS_JOINT_INVALID`, broken, disabled or not made yet), `broken`, its angle, position or distance, its force and torque of the last step and its motor; the collider view and `viewport.screenshot`'s colliders annotation draw each joint (teal in force, orange broken, crimson refused: colours no collider category uses).
9. **Timing and load.** `stats.get` reports frame and per-pass timings, dropped simulation time, entity, body and voice counts, the Luau heap and its limits, the committed bytes of the heap the C runtime allocates from (`processHeapCommittedBytes`, Windows only; the heaps a graphics driver keeps of its own are not in it), and the GPU device losses the editor recovered from (`deviceLosses`). Its `memoryAllocationCount` (the device's native allocations; the log warns once per view above 2,000) still counts what the frame released until the frame's garbage collection frees it at its end, so a request that renders a lot shows a peak that a `stats.get` in a later frame no longer reads. Its `views` are the editor's displayed viewport panels, and only displayed panels render: a headless editor displays the Scene view only, so `game` is unavailable there, and `play.step {render}` renders the play scene through the Scene view. A view's `passes` list only the passes its frame recorded, each with `drawCalls`, `dispatches` and `triangles`: entities of one mesh and one material are one instanced draw (`ForwardOpaque` with 64 identical crates counts 1), `PointShadows` appears while a shadow-casting point light is in view, `LightClusters` while a point or spot light is, and `Skinning` while a skinned or morphed mesh is drawn (one dispatch per deformed entity, each in a draw of its own); `shadowedPointLights` and `droppedPointShadows` (beyond the budget of four), like `shadowedSpotLights` and `droppedSpotShadows`, count the frame's shadows. With SSR on, a view also reports the trace's area in its completed GPU frame `ssrAreaFrame` (empty while none recorded SSR): `ssrTiles` (the trace image's 8 x 8 tiles), `ssrTracedTiles` (those holding a glossy pixel, the only ones traced and composited) and `ssrTracedPixels`, at half resolution (`ssrHalfResolution`, the project's `Rendering.SsrHalfResolution`) of the half-size trace image, so a game sees what its reflections cost: a mostly rough view traces few tiles. Each view also reports its planar reflections (M42): `planarReflections` drawn (at most 4), `droppedPlanarReflections` past the cap or whose GPU objects, or the view's probe constants, could not be created (they show the probes and SSR), `culledPlanarReflections` out of view, seen from behind or in a debug view, and `planarReflectionEntities`, the drawn mirrors in slot order, mirror k's whole cost being the row `PlanarReflection<k>`; `Application.GetStats()` gives scripts `PlanarReflections` and `DroppedPlanarReflections` in every configuration. A mirror that shows no reflection: check that its glass is in view and faces the camera with its `Normal`, and `project.validate`'s `RENDER_REFLECTION_INVALID`. `play.state` reports mode, tick, `stateHash`, lockstep owner, whether the session was modified, recording, and `stopped`/`stopError` after a fatal stop.
10. **Audio.** `audio.stats` lists the device, group volumes and every voice (clip, entity, volume, pitch, spatial position, cursor, and `fadeVolume`, the level a fade moved it to; `next` and `inNext` for an intro and its loop, whose cursor is the section's it plays), and `music`, the session's music (`Audio.PlayMusic`): the request's clip, intro, volume and loop, its `voice` (the handle of one of the voices) and `fadingVoices`. No voice means nothing played; a voice at volume 0 points at the mixer or attenuation, one at `fadeVolume` 0 at a fade. Music that restarts at a doorway is a scene's `AudioSource`, or a `PlayMusic` of another clip: the same clip keeps its `voice` handle across `Scene.Load`; an empty `music.voice` with a clip means the voice ended (`Loop` false) or could not start (logged).
11. **Reproduce deterministically.** `play.start {lockstep: true, seed}` and `play.step {ticks, input}` reproduce a bug tick by tick; equal seeds and inputs must give equal `stateHash` values. A test that fails only sometimes is a determinism bug (unordered iteration, wall time, unseeded randomness, `^` with a non-trivial exponent: see `luau-gameplay`).

### Common situations

- **A replay no longer verifies.** `input.replay {path, verify: true, strictHash: true}` reports each `Expect` outcome, `finalTick`, `stateHash`, `stopReason`, `checkpointsChecked` and `checkpointFailed`; a failed verification (also the expected failure of `withoutInput: true`) is error -32003 `Validation`, whose data `replay` holds that outcome with `passed: false` and, at a differing checkpoint, `checkpointFailed: true`, `finalTick` at that checkpoint and `checkpointsChecked` counting it. The usual failure is "replay verification failed at checkpoint tick N: expected state hash X, observed Y" (`checkpointFailed: true`, playback stopped at N): checkpoint N is the first whose state hash differed and every earlier one matched, so the divergence lies in the 60 ticks before N; bisect only there (a final-hash mismatch with every checkpoint matched lies after the last checkpoint). In `test.run` the replay's `Checkpoint@<tick>` or `FinalStateHash` row fails with both hashes. Either failure carries a hint: the world differs from the recording, because a serialized component of the scene (the look's included: `PostProcess`, `Environment`, lights, `Camera`, `Text`), a script, the game's native module, an asset or the engine changed since it was recorded, or the play is not deterministic (a locale change the playback did not repeat among its causes: a `Loc.SetLocale` the recording's input did not cause). A replay recorded with a start fingerprint (format 3) also names what changed: `changes` lists each entity, component and directly referenced asset (a script, a material) that differs from the recording, the first ending the message; a replay upgraded from format 2 names nothing until it is recorded again, and a change of the native module's code (`Native/`) is never named. `checkpointsFailed` counts the differing checkpoints and `firstFailedCheckpointTick` names the first: without `continuePastCheckpoint` playback stops there, so they are 1 and `finalTick`; `continuePastCheckpoint: true` (with `strictHash`) plays on past every differing checkpoint and counts them all. An edit of the scene's look changes every checkpoint, so its replays fail at their first. The session then stays paused at the replay's last tick (or where playback stopped): read its state with `script.eval {context: "Play"}`, `scene.query` or `entity.get`, and end it with `play.stop`. A hash mismatch after an intended change (an engine fix, gameplay, the look) means re-recording with `test.run {record}` (`skills/game-building/replays`, "Re-recording replays"); otherwise compare `play.step` hashes tick by tick against a fresh recording within that window to find the first divergent tick.
- **A replay is refused: "the replay was recorded in the locale 'X', but the session started in 'Y'".** A version 5 replay starts in its header's `Locale` (the locale its recording started in), and every engine path (`input.replay`, `test.run`, an export's `--feature-test`) starts it there; the refusal comes before a tick runs, so a test host or a session started by hand in another locale (`play.start {locale}`, the Runtime's `--locale`, which `--replay` refuses) is the cause. A replay upgraded from version 4 or earlier has a null `Locale` and plays in the project's `Localization.Locale`. A mismatch after a locale change during play reaches the next checkpoint through the state hash's locale block instead (the hint above).
- **A recording is refused: "does not depend on its input".** `input.record {action: "Stop"}` or `test.run {record}` fails with `Validation` when the recording, replayed without its input events, still passes its verification (every checkpoint, the final hash and every expectation, whatever script errors that run raised); `input.record` puts that run's outcome in error data `inputCheck`, and nothing is written. That happens only when the input never shows in the world at a checkpoint (one every 60 ticks), at the end or in an expectation: a recording shorter than 60 ticks that ends idle, input that changes only script state, or play after the last checkpoint that a restart undoes (a longer recording that ends with a restart is accepted, its checkpoints having seen the play, but its final hash then proves only the restored state). End the recording while the played state is still in the scene, record again, and confirm with `input.replay {path, verify: true, strictHash: true, withoutInput: true}` that the new replay fails without its input. An accepted `test.run {record}` reports its replay in the `recording` block, whose `inputCheck.divergedAtTick` is where the run without input first differed (`input.record`'s `inputCheckTick`). A recording written with a `warnings` entry ("its final state hash does not depend on its input") passed the check only at its checkpoints: its run without input reached the recorded final hash, so end it while the played state is still in the scene.
- **A recording is refused: "while taking the recording's start fingerprint".** A recording fingerprints every asset its scene references (format 3), so `input.record {action: "start"}` fails with the asset's own error, or `test.run {record}` with `Validation` ("recording invalidated: ..."), naming the asset, when one cannot be hashed: its source no longer imports. Nothing is recorded or written. Fix the source (`asset.info` shows its diagnostics; while the editor knows the asset is in error, play of a scene that references it is refused with `InvalidState` naming it), or remove the reference, then record again. A playback is never refused for this: a replay whose hash differs names the error as its change ("not known, because the playback's start fingerprint could not be taken").
- **A recording is refused: "does not reproduce itself".** Before its input check, `input.record {action: "Stop"}` replays a recording with input events with its input (`verify`, `strictHash`, its `expect`) and refuses with `Validation` at `/path` naming the first failure in tick order: a checkpoint (`the state hash at checkpoint tick <t> is <observed>, recorded <expected>`), an expectation (`expectation <i> at tick <t> (/expect/<i>/luau) is false`, or `failed: <message>`), the final hash, where playback stopped, or the playback's first script error. Error data `verification` holds the playback's outcome; nothing is written, the recording has ended and the session is the verification's, paused where it stopped. The usual causes: a `script.eval` or `play.waitFor` that wrote script state during the recording, an expectation that does not hold with the recording's own input (check it first with `script.eval {context: "Play"}` at its tick), and a script that reads the host or iterates entity keys with `pairs` (`luau-gameplay`). Record again without them.
- **Play is refused: "references the asset ..., and it is in error".** `play.start`, `input.record` and `input.replay` refuse only a scene that references an asset in error (an import that failed, a scan error), directly or through its prefabs' meshes and materials, its materials' textures, its scripts' required modules or its Script fields' assets, and the message names the first such asset and its error. Another scene it names (a Script field holding the next level) is not checked: a load of a broken level fails in the script when `Scene.Load` runs. Fix that asset (`asset.info` shows its diagnostics) or remove the reference; every other scene of the project plays, and `test.run` is never refused for it. An `ASSET_BAKE_DEFERRED` warning is no asset error: an editor launched with `renderer: "none"` imported an HDR environment that no cooked bake in `Library/Cache` covers, so its scenes play and test there (an environment is not simulation state, so the hashes match a GPU editor's) while the environment does not load, unless an earlier bake of it is still in use, until an editor with a GPU bakes it (an editor launched with `renderer: "vulkan"` does when it first loads it: a scene that shows it, or `asset.reimport`); an export from the renderer-none editor refuses it with the GPU hint.
- **`test.run` refuses: "is open with unsaved changes".** A selected suite is bound to an open scene with unsaved changes, active or not, or a selected replay plays it, and runs play saved scene files: `scene.save` it (`scene.save {scene: <its path>}` for another tab), then run again.
- **A request changed the wrong scene.** Without `scene`, a request addresses the active scene. `scene.list` shows which open scene is active and each one's `id`; name the scene (`scene: "<project path>"` or its `id`) or `scene.activate` it first, and `edit.undo {scene}` takes the change back in the scene that recorded it. A target naming no open scene is NotFound at `/scene`, its hint listing the open scenes; an `id` names nothing once its scene was closed or replaced. During play, a target naming another open scene than the played one addresses that edit scene, and `target: "play"` with it is InvalidArgument at `/scene`.
- **One of an entity's scripts misbehaves.** `GetScript()` returns the first slot's instance only: ask for a behaviour by its `Script.Define` name, `GetScript("<Name>")`, or list them with `GetScripts()`. Callbacks run in (`ExecutionOrder`, canonical entity order, slot) order, so a slot that must run before another needs the lower `ExecutionOrder`. A `script.errors` row's `slot` names the faulting slot; the entity's other slots keep running. A native fault (`script` `native:<System>`, `callback` `NativeStep`) has no behaviour: its `slot` 0 names none. `entity.get {entity, components: ["Script"]}` shows the `Scripts` list.
- **A graph behaviour misbehaves** (a `.graph` Script asset). `graph.read {graph}` first: a `GRAPH_INVALID` finding, an `incomplete` one included, keeps the graph from importing, so its slots run nothing. Its script errors name a line of its transpiled text, which `graph.read {graph, luau: true}`'s `lineNodes` maps to the node; in play, `graph.liveValues {entity, script?}` reads each node's last value, the members and the instance's errors by node, without changing the state hash. A `Script.Get`, `Script.Set` or `Script.Call` reads, writes or calls a member named by a string: a misspelt member reads nil from a table, while a member an engine value lacks (`unknown Entity member 'X'`), a method the object lacks (`attempt to call missing method 'X' of table`) or an object that is nil (`attempt to index nil`) is a run-time error located at that node; a renamed method is not renamed at its callers (`Script.Call`'s `Method` strings, Luau's `:Name()`), so check them after `graph.setMembers {rename}`. `skills/game-building/graphs` has the rest.
- **A `test.run {record}` is refused because a row did not pass.** The message lists the selected rows that did not pass, `<suite>/<case> (<status>)`. A `replay:<path>/...` row is a committed replay the filter also selected: give the recording suite a name that no replay path contains (`Record.<Name>`) and record with exactly that filter.
- **A soak fails a scene.** The milestone gate plays every scene of a game in `Projects/<Game>` for 10,000 lockstep ticks without input and fails it on growing entity, body, voice or allocation counts, a growing memory or script heap, or a new script error (`OnStart` included). Reproduce it: `play.start {lockstep: true}` without a seed, `play.step` to tick 10,000, `script.errors` (the session's errors, item 3), and `stats.get {views: false}` past ticks 5,000 and 9,500 (an editor launched with `headlessGameView: true` and `renderer: "vulkan"` renders the game view the soak samples); a per-lock `Scene.Instantiate`, pooled entities with bodies, a looping or late game-over sound and unbounded histories are the usual causes.
- **A test case fails.** `test.run {filter: "<suite>/<case>"}` reruns one case; its row has the failure messages with file and line, and `Test.ExpectScriptError` claims expected errors. A failed `Test.ExpectEqual` or `Test.ExpectNear` shows its message followed by `(got <actual>, expected <expected>)` (and `, epsilon <e>`), so pass the actual value first. Add `print` calls or `Test.GetStateHash()` checkpoints, then remove them.
- **A result too large to answer inline.** A response over 48 KB is `{path, truncated: true, summary}`: read the file with the bridge's `result_read {path, pointer?, offset?, length?}` (one page with `nextOffset`, or the JSON value at a pointer such as `/cases/0`; `engine_client.load_offloaded` outside the bridge), never with another file tool; it also reads a test run's `jsonPath` and `junitPath` reports. A `test.run` result names its failing rows in `failedCases` and counts every status in `counts`, inline. A `docs.get` topic too long for one response comes back as its first page with `nextOffset` and its sections; ask for a `section` or page on with `offset`.
- **A ball falls through or bumps.** `entity.bounds` on the neighbouring pieces shows gaps; `project.validate` reports `PHYSICS_ADJACENT_STATIC_BODIES` and layer problems; `physics.bodyInfo` shows the layer and contacts; check `Physics.Collisions` pairs the layers.
- **A collision callback does not arrive.** A collider merged into an ancestor's compound body gets its own `OnCollisionEnter` (and its own `OnTriggerEnter` when its body passes through a sensor) only when its entity has a Script naming a script; the other side's callback names the body's owner (`contact.OtherCollider` is the collider). Pieces of one body whose contacts share a normal (coplanar pieces, the seam between two edge-to-edge bricks) report the event to one piece only, an accepted limit of Jolt's manifold reduction: a piece that must get its own event at a seam keeps its own `Static` body. An enter needs touching shapes, or the step the solver bounces one off the other: a pass within Jolt's 2 cm speculative distance reports nothing. A callback that reads an entity another callback destroyed this tick works, but a write to it raises `entity <id> was destroyed`.
- **A script or asset change does nothing.** Lockstep, recording, replay and test sessions defer script and asset reloads (sound effects, textures, meshes, sprite sheets, tilemaps, string tables) until the session ends, so an `asset.setProperties` of a sound effect, sprite sheet, tilemap or string table, or an `asset.import` that replaces a texture or model, shows only after `play.stop` and a new `play.start`, while `asset.getProperties` (the tool `asset_get_properties`) reads a native asset's values from its file at once; ordinary play reloads scripts at the next safe point and assets at the next frame. A material (a `.material`) is the exception: only drawn, it reloads at once in every session, so its change shows in the next `play.step`'s frame and `viewport.screenshot`, changes no state hash and does not mark the session `modified` (a recording stays valid); a glTF's materials reload with the glTF, so they wait too. To try component values in a running session, `entity.update {target: "Play"}` changes the play scene alone. A reload refused for type errors (with `BlockPlayOnTypeErrors`) or compile errors keeps the old code and reports a `type` or `compile` error with callback `Reload`.
- **A light casts no shadow.** Check `CastShadows` on the light and on the occluding `MeshRenderer`, and `ReceiveShadows` on the surface. A view shadows at most 16 point lights (the four most important at full resolution, the rest at half) and 16 spot lights, the most important it sees (`Intensity` × the brightest `Color` channel over the squared distance from the camera); `stats.get`'s `droppedPointShadows` and `droppedSpotShadows` count the rest, and `project.validate` warns `RENDER_POINT_SHADOW_BUDGET` and `RENDER_SPOT_SHADOW_BUDGET` for a scene with more than 16 enabled: turn `CastShadows` off on the less important ones. A light that holds a shadow keeps it until another is a quarter more important. A light that is not shaded at all is past `Rendering.MaxShadedLights` (`stats.get`'s `maxShadedLights`; `RENDER_LIGHT_LIMIT_EXCEEDED`). A point light whose `Range` is not above twice its `SourceRadius` (at least 0.05 m) is never shadowed, nor counted. Spot shadows share an atlas (`droppedSpotShadows`). Screenshots in play before and after `entity.update {target: "Play"}` toggles `CastShadows` show what the shadow does.
- **Many lights.** `debugView: "LightCount"` (item 7) shows how many lights each pixel's 64-pixel tile and depth slice holds. A point or spot light reaches every cluster its `Range` sphere touches, and a directional light every cluster, so wide orange or red areas mean ranges larger than the look needs.
- **An export is refused.** `project.export` refuses script type errors, asset errors (also of content `Export.Exclude` leaves out, `Assets/Tests/**` included), missing build scenes, an `Export.Version` that is not `major.minor.patch` (each part at most 65535), an `Export.Icon` that is not a square PNG of at least 256 × 256, and an existing output directory that holds anything but an earlier export. Fix what the error names (`script.check`, `asset.info`, `project.validate`), or export into another directory.
- **`project.upgrade` refuses.** A material, sound effect, replay, sprite sheet, tilemap, string table or graph with a member its reader does not know (or a graph whose lists are out of their canonical order) fails the upgrade at its file and pointer instead of losing the member; any open scene with unsaved changes is refused, the error naming every one (save them first), while no open scene is needed.
- **The editor died.** The bridge reports `EditorCrashed {exitCode, lastLogLines, crashReportPath, autosaveAvailable}`; read the crash report, then `editor_launch {recover: true}` if an autosave exists: it reopens every autosaved scene as an unsaved open scene.
