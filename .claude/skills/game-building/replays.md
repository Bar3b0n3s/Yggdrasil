# Replays, recording suites and re-recording

A reference page of the `game-building` skill (`skills/game-building`), for its step "7. Replays", which says what a replay records and proves.

## Replays

- **Record every replay from a recording suite** ("Recording suites" below): re-recording is then one `test_run {record}`, and the input plan stays readable through `script_read`. `input_read_replay {path}` returns a replay's events in `play_step`'s input form, a page at a time, so a replay made with `input_record` can be re-recorded from its own events.
- **A UI replay that drags, scrolls or types comes from a recording suite too.** Besides `Test.InjectMouse` (a button, at an optional position), `Test.InjectKey` and `Test.InjectGamepad`, which click and navigate, a case moves the pointer with `Test.InjectMouseMove(position)`, turns the wheel with `Test.InjectScroll(delta)` (wheel steps, y up-positive) and types with `Test.InjectText(text)` (committed UTF-8 characters), each queued for the next unapplied tick like every `Test.Inject*` event; positions are view coordinates, which are the scene pixels `ui_tree` reports unless the output is upscaled. Drag a slider by a press on it, a move along it on a later tick and a release; move the pointer over a scroll view before its wheel steps (the wheel scrolls the scroll view under the pointer); click a text input to focus it before typing. The recording holds the `MouseButton`, `MouseMove`, `Scroll` and `Text` events that `input_record` records from the same `play_step` input.
- `input_record` suits a quick check of planned input, written to a scratch replay (it plays the saved scene: the skill's "Pitfalls"). In Edit mode, `input_record {action: "Start", scene?, parameters?, seed?}` starts a lockstep session at tick 0 (default seed: the session seed) and records. Drive it with `play_step` input, then `input_record {action: "Stop", path: "Assets/Tests/Replays/Check.replay", expect: [{tick: 600, luau: "return (Scene.FindByName('Game') :: Entity):GetScript().Lines >= 1"}]}`: an expectation that only the input satisfies, at a tick no later than the last. Expectations are compiled, never type-checked: run the exact expression with `script_eval {context: "Play"}` before `stop`. Once you have checked it, `asset_delete {asset: "Assets/Tests/Replays/Check.replay"}`: every replay left below `Assets/` counts as committed (the games suite fails one that `Testing.Replays` leaves out), and a committed replay comes from a recording suite.
- **`stop` verifies with the input.** Every recording is first replayed with its input (`verify`, `strictHash`, its `expect`). Unless that playback reproduces every checkpoint, the final hash and every expectation, without stopping early or raising a script error (at teardown, in `OnDestroy`, too), `stop` refuses with `Validation` ("replayed with its input, the recording does not reproduce itself: <reason>", the first failing checkpoint, expectation, final hash, stop or script error, with its tick), writes nothing and ends the recording; error data `verification` holds the playback's outcome.
- **Evaluate only reads while recording** (`luau-gameplay`, "Recording", lists the mutating APIs). A `script_eval` or `play_wait_for` that calls a mutating engine API invalidates the recording at once; one that writes script state (a `self` field, a board table) is neither detected nor recorded, so `stop` refuses the recording once that write shows. A hot reload or a play-scene edit during the recording invalidates it too: `stop` then fails, writes nothing and names the reason.
- **The input check.** A recording with input events is then replayed without them before it is written. When that run reproduces every checkpoint, the final hash and every `Expect` (whatever script errors it raises), the outcome does not depend on the input: `stop` (and `test_run {record}`) refuse it with `Validation` ("does not depend on its input") and write nothing. That happens only when the input never shows in the world at a checkpoint, at the end or in an `Expect` (`game-debugging` lists the cases), so give the first input well inside the first 60 ticks, end every recording while the played state is still in the scene (pieces placed, score shown, a life lost), and keep an `Expect` for what only the input causes. A check that differed only at checkpoints but reached the recorded final hash writes the recording with a warning (`warnings`): only its checkpoints prove the play. After `stop` the session is the check's, paused at the replay's final tick (or where the check stopped); `inputCheckTick` names the first checkpoint that differed. Inspect the recorded run before `stop`, or replay the written file.
- Verify with `input_replay {path, verify: true, strictHash: true}`: every `Expect` must hold, every checkpoint must match when playback reaches its tick (the first that differs stops it there, `checkpointFailed`, naming the tick and both hashes) and the final hash must match. `checkpointsChecked` counts the checkpoints compared, the one that failed included, so a passing replay compared all of them. A failure's `changes` name what changed since the recording (entities, components, directly referenced assets), the first one ending its message. `Testing.Replays` makes every test run verify them; each replay's entry in the run's `suites` reports the same count as `checkpointsChecked` and the tick of a checkpoint that differed as `failedCheckpointTick`.
- **Replay twice.** Verify each new replay twice that way: the two `stateHash` values must be equal (the transcript keeps both).
- `input_replay {path, verify: true, strictHash: true, withoutInput: true}` plays the replay with none of its input events. It must fail for a replay with events, as an error like every failed verification (-32003 `Validation`; `game-debugging` reads its data). When it passes, re-record the replay (the games suite checks this for every committed replay).
- After `input_replay` the session stays paused where playback ended: inspect it (`script_eval {context: "Play"}`, `entity_get`), then `play_stop`.

## Recording suites

A replay is recorded by a test-only **recording suite** that plays like a player: an **autopilot** where hand-written input is impractical (steering a physics ball), or a single case that injects a **planned input list** at fixed ticks (a Tetris opening). Record its run, then verify the replay without it:

1. Add it to `Testing.Suites`, bound to the scene, with `Modes: ["Editor"]`, so exported builds never run it.
2. Its single case reads the scene and injects input with `Test.InjectAction` (a UI with the pointer, wheel and typing injections above): an autopilot follows the level's waypoint entities with a PD controller every tick until the goal is reached; a planned case taps each action at its tick. It must only read the scene and inject input: never move entities, write components or draw from the session's `Random` stream, so the run equals a player pressing the same inputs. End it with `Test.Expect` on what only the input causes, while the played state is in the scene, with no restart at its end (cover restarts in another suite).
3. **Name it so that no replay path contains its name** (`Record.Opening`, not `Opening`, whose filter would also select `Assets/Tests/Replays/Opening.replay`), and record with exactly that filter: `test_run {filter: "Record.Opening", record: "Assets/Tests/Replays/Opening.replay"}`. The filter must select exactly one suite, and every selected row must pass: a refused recording names the selected rows that did not pass (a `replay:<path>/...` row is a committed replay the filter also selected). The editor verifies the candidate in fresh ordinary gameplay without the test driver, every checkpoint and the final hash included, then runs the input check ("Replays" above), before it writes the file. The result's `recording` block describes the replay written, its `inputCheck.divergedAtTick` saying where the run without input first differed, with `expectations` and the input check's `warnings`.
4. The replay is then verified **without** the suite by `input_replay {verify: true, strictHash: true}` and by every test run through `Testing.Replays`, which proves that plain input reproduces the play. Level 2 and 3 suites set `Parameters` (such as the carried timer), which the replay header stores. A recording made by `test_run` carries an `Expect` only when you pass `expect: [{tick, luau}]` with `record`, which it verifies with and without the input; its checkpoints and the input check make it prove its gameplay anyway, and the suite's own `Test.Expect` asserts it at record time.

`luau-gameplay` ("Recording") has a planned-input suite (`Record.Opening`) and an autopilot suite for a rolling-ball level.

## Re-recording replays

When an engine change legitimately alters simulation results (a physics fix, a new serialized field, a changed default), or the scene (the look included: a `PostProcess`, light or `Camera` value) or the game's native module changes after recording, replay hashes change and their verification fails, its hint saying that the world differs from the recording:
- Re-run each recording suite with `test_run {filter, record}` through automation, so provenance and the transcript record the new replay; verify it twice and run the input check again ("Replays" above).
- After a gameplay change, re-record a replay when it must cover the new behaviour: a matching hash only means the worlds matched at each checkpoint and at the end, and script state that never reached the world is not compared.
- The review of the change states why the hashes changed. A verifier's hash never replaces a recorded one by hand.
- A replay of format version 1 (no `Checkpoints`, so verified by its final hash only) or 2 still verifies; `project_upgrade` rewrites it as version 3 with no start fingerprint (and, from version 1, no checkpoints), and re-recording it adds them.
- An engine change that alters the canonical form of project files also runs `project.upgrade` on every affected game (`project_upgrade {dryRun: true}` first, then `project_upgrade {}` through the bridge; `changes` gives each rewritten file with its reason; its refusals are in `game-debugging`; or `Editor --headless --project <Game> --upgrade`, which appends its own `cli` transcript lines: `project.refreshAssets` for its deferred asset scan, then `project.upgrade`), so the audit and the byte-identical re-save test stay green; the same change regenerates FeatureTest and re-records the affected replays.
