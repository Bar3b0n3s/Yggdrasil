# Game building

This is the workflow an agent follows to build a game with this engine, from an empty project to an exported build. Write gameplay with the `luau-gameplay` skill, and diagnose with `game-debugging`. Tools are named `domain_verb` as the MCP bridge proxies them; a method without a tool (`prefab.revert`, `project.refreshAssets`, `play.state`, `stats.get`) is reached through `engine_call {method, params}`, and `engine_client` calls every method by its `domain.verb` name.

Everything a builder reads is served by `docs_get`, which needs a connected editor: launch or attach first ("1. Launch"). `docs_get {}` lists every topic with its size.

- **Reference:** `reference/Automation` (every method with its params and results), `reference/Components` (every component field with its range and default), `reference/FileFormats`, `reference/Validation`, `reference/ScriptAPI` and `reference/BuiltinAssets` (every `engine://` asset).
- **JSON schemas** of the file formats: `reference/Schemas/<Format>`, such as `reference/Schemas/Project` (every `.eproj` field) or `reference/Schemas/SoundEffect`.
- **Scripting:** `scripting/Engine.d.luau` (the declarations the type checker uses) and the script templates `templates/Scripts/Behaviour`, `templates/Scripts/Module` and `templates/Scripts/Test`.
- **Native module:** `native/NativeApi.h`, the C++ interface a game's module includes ("4. Scripts").
- **Long topics:** a topic too large for one response returns its first page with `nextOffset` and its sections; `{topic, toc: true}` returns only the sections (with `section`, its subsections). ## Ground rules

- **Only through automation.** Every engine-consumed file of a game (the root `<Game>.eproj` and `.luaurc`, everything under `Assets/`, every `.meta` and a native module's sources under `Native/`) is written by the editor through an automation method: never with a text editor, a shell or a file-copy tool. `Scripts/AuditProvenance.py` rejects any other origin (§13.12).
- **Provenance and transcript are committed.** In the game's project directory, `<Game>/` below (`Projects/<Game>/` for a demo, `Tests/Projects/Breakout/` for the M16 dry run), the editor records each write in `<Game>/Automation/Provenance.json` (`{Path, XXH64, Method, RequestId, Client, TranscriptLine}`; `RequestId` is null only for a `ui` write), and the MCP bridge appends every request to `<Game>/Automation/BuildLog.jsonl` and passes its line number on, so each entry names the transcript line of the request that wrote it. Never edit either by hand; never delete the transcript.
- **Windowed UI writes do not count.** A file saved from the editor's own UI is recorded with method `ui`, which the audit rejects for demo games. Use the UI to look, not to author.
- **`Library/` is a cache** (import cache, autosave, lock, offloaded results, screenshots). It and `Build/` (export output) are gitignored, as are `*.bak` files; none is committed or audited.
- **Documentation is exempt.** `<Game>/AGENTS.md` and a `README.md` are written directly (no automation method writes them); describe the game's scenes, actions, scripts and tests there when you finish. The unit suite type-checks every `luau` fence of `AGENTS.md` against the documentation's stub modules, not the game's (it does not lint them): a fence is either code you already ran through `script_write` and `script_check`, or carries `skip="<reason>"`, as a snippet that requires the game's own modules must.
- **A missing capability is an engine change.** When automation cannot do what the game needs, add the method (the `add-automation-method` skill) or the script API (`add-script-api`) with its tests before continuing. Never work around it by hand.

## 1. Launch

- `editor_launch {project: "Projects/<Game>", create: true, template: "Empty"}` creates and opens the project (templates: `Empty`, `Basic3D`). A relative project path (`"Projects/<Game>"`, `"Tests/Projects/Breakout"`) names a directory below the repository root, whatever the bridge's working directory, and the transcript records it that way. Without `create` it opens an existing one, always through a transcribed `project.open` on a launcher-state editor (never `--project`), so whatever opening writes, such as the `.meta` files of new sources, is attributed to that request. The bridge launches the Release editor headless with `renderer: "none"`; pass `renderer: "vulkan"` for screenshots and a Dist export's smoke test, which a `renderer: "none"` editor refuses (`Unsupported`) and leaves unrun. A rendering editor holds the machine-wide GPU lock that every checkout shares until it exits, so `editor_shutdown` it when the rendering work is done; a launch waits while a gate (`CI.py`) or another GPU run holds it (`LockUnavailable` after 30 min, naming the holder).
- If the user already has the project open with "Allow AI automation" on, `editor_launch` attaches to that editor instead (§13.8). `EditorAlreadyOpen {pid}` means an editor without automation holds the project: ask the user to allow automation, then `editor_attach`. Every attach and every launch begins with a transcribed `session.info` (a launch sends it right after its `project.open` or `project.create`), so the transcript shows where each session starts and the result reports the session with its open scene. Request ids restart with every launch or attach and skip the bridge's own untranscribed `rpc.discover` reads (`engine_call`'s timeout), so the transcript line, not the id, identifies a request. Unconnected, `editor_status` lists the editors running with automation (pid, project, renderer): `editor_attach {pid}` joins one.
- **No scene is open after a launch.** Opening a project opens none of its scenes, so scene and entity tools answer `InvalidState` ("no scene open") until you open one: `scene_open {path: "Assets/Scenes/Main.scene"}` (the project's `StartScene`, from `project_get_settings`), or `scene_new {path}` in a new project. An attached editor shows whatever scene its user has open, or none. `editor_status` (its `session.scene`) and the result of a launch or an attach report the open scene's `path` and `dirty` flag, or null.
- After `EditorCrashed {autosaveAvailable: true}`, `editor_launch {recover: true}` adopts the autosave as an unsaved scene; save it deliberately.
- **A stale tool list.** A Claude Code session keeps the tool list it started with, and a workflow's subagents use their parent's MCP connection and tool list. After `GenerateDocs.py` rewrote the bridge's `catalog.json` (a method's parameters or the method set changed), work from a fresh top-level session (or `/mcp`, Reconnect, in the parent): until then new tools are missing (`engine_methods` and `engine_call` reach every method), and a parameter the cached schema lacks reaches the bridge as a string, converted only where the current catalogue types it.

## 2. Project settings

`project_set_settings {patch}` applies an RFC 7386 merge patch to the `.eproj` as one undoable command; a member the settings lack is dropped and named in `warnings`. Objects merge key by key; **arrays replace whole** (restate the full `Layers`, `Collisions`, `BuildScenes`, `Suites` or `Replays` list each time).

```json
{"patch": {
	"Name": "Tetris", "StartScene": "Assets/Scenes/Main.scene",
	"Window": {"Title": "Tetris", "Width": 720, "Height": 900},
	"Simulation": {"FixedHz": 60, "Seed": 42},
	"Input": {"Actions": {
		"MoveLeft": {"Type": "Button", "Bindings": ["Key.Left", "Gamepad.DPadLeft"]},
		"MoveX": {"Type": "Axis", "Positive": ["Key.D"], "Negative": ["Key.A"], "Gamepad": "Gamepad.LeftX"}}},
	"Export": {"BuildScenes": ["Assets/Scenes/Main.scene"]},
	"Testing": {
		"Suites": [{"Script": "Assets/Tests/Board.test.luau"},
			{"Script": "Assets/Tests/Tetris.test.luau", "Scene": "Assets/Scenes/Main.scene", "Isolation": "Case"},
			{"Script": "Assets/Tests/Record/Opening.test.luau", "Scene": "Assets/Scenes/Main.scene", "Modes": ["Editor"]}],
		"Replays": ["Assets/Tests/Replays/*.replay"]}}}
```

- `project_get_settings` returns the whole document; `docs_get {topic: "reference/Schemas/Project"}` lists every field with its type, range and default.
- **Build settings.** Set `StartScene` and list it in `Export.BuildScenes` (the scenes the export loads strictly beside it): the games suite fails a game whose `StartScene` is empty or whose `BuildScenes` is empty or does not list `StartScene` as written, and reports these first among each editor half's failures (its other checks still run).
- **Folders.** A new project has `Assets/{Scenes, Scripts, Prefabs, Materials, Models, Textures, Audio, Fonts, Tests}` (`asset_list` lists assets, never folders). `asset_create` creates missing parent folders, so a `Folder` op is needed only for an empty folder; one whose path is already a folder is a no-op (no command, `created: false`), and a file there stays `AlreadyExists`.
- Physics layers: `Physics.Layers` holds 1 to 16 names with `Default` first, and `Physics.Collisions` lists the pairs that collide; unlisted pairs do not.
- **Validation codes come from `project_validate {}`.** `_meta.diagnostics` only counts what was logged since your previous call (`newErrors`, `newWarnings`, `newScriptErrors`, the first three entries in `firstNew`) and never lists a validation code. `BUILD_START_SCENE_MISSING` and `BUILD_SCENE_MISSING` are expected until the start scene exists, and `TEST_SUITE_INVALID` until each suite's script exists.

### `Testing.Suites`

Each entry is `{Script, Scene?, Parameters?, Isolation?, Clock?, Overrides?, ExpectQuit?, Modes?}` (§11.10; `reference/Schemas/Project` describes each): `Script` the `*.test.luau` file; `Scene` the scene it runs in (omitted: an empty scene, right for pure-logic suites); `Parameters` the `Scene.Load` parameters (`Scene.GetLoadParameters()`), such as a timer carried into level 2; `Isolation` `"Suite"` (cases share one scene, in order, so a board carries from case to case) or `"Case"` (the scene restarts before each case, each from the same seed); `Clock` frame deltas that replace the lockstep clock (frame-timing tests); `Overrides` `{CallbackBudgetMs, MemoryLimitMB, PauseOnError}` for this suite, applied exactly; `ExpectQuit` the exit code the suite must end with through `Application.Quit` (-1: it must not quit); `Modes` the run modes it runs in, `["Editor", "Release", "Dist"]` by default, `["Editor"]` for recording suites (§8).

`Testing.Replays` holds globs of `.replay` files; every run verifies each one. `CaseTimeoutTicks` and `SuiteTickLimit` bound cases and suites. Leave `CoverageGates` false: only `Projects/FeatureTest` evaluates the engine's coverage gates.

## 3. Scenes, assets and prefabs

- `scene_new {path: "Assets/Scenes/Main.scene"}` creates and opens a scene; `scene_save` writes it; `scene_open {path, save | discardChanges}` switches.
- **Batches.** Build content with one atomic `edit_batch {label, ops: [{method, params}]}` per logical step: if op *k* fails, ops 0..k−1 are undone and the error names `failedOp`. Create the assets in a first batch and name them by path afterwards (`"Materials": ["Assets/Materials/Wall.material"]`, also inside component data). To name an entity that an earlier op of the same batch created, use its path (`"parent": "/Game"`, in an entity param or an `Entity` value), or give that op a `name` (`{"name": "board", "method": ...}`) and write `{"$ref": "board.entity.id"}`: unlike a positional `{"$ref": "3.entity.id"}`, neither shifts when you insert an op. Run `dryRun: true` first and check each op's `entity.path` in `results`.
- `entity_create {name, parent?, components: {Type: {Field: value}}}` and `entity_update` take component values by registry name; `component_schema {name}` lists fields, ranges, defaults and enum values. Write enum values in their canonical spelling, as the schemas list them (`"Orthographic"`, `"Game"`, `"Play"`). Entity params take an id, a unique id prefix or a path (`/Game/Board`). An **`Entity` value inside component data** (a script's `Field.Entity()`, any entity field of a component) takes the same forms, resolved in the scene the call targets. Assets are referenced by handle, `Assets/...` path or `engine://...` path. The built-ins (`engine://Meshes/Cube`, `engine://Environments/Studio`, ...) are listed by `asset_list {dir: "engine://"}` (or a folder below it, `"engine://Environments"`) and in `reference/BuiltinAssets`; an unknown engine path's NotFound suggests the closest.
- `asset_create {type: Material | SoundEffect | Scene | Prefab | Folder, path, values}` writes native assets; `asset_import {source, destDir}` imports external files (glTF, PNG, HDR, audio, fonts). `asset_delete {asset}` moves an asset with its `.meta` to `Library/Trash/` as one undoable command; it removes a folder below `Assets/` that holds no files (only empty folders, as a trashed recording leaves), also undoably, and refuses one that holds files (`Validation`, naming them: delete its assets first).
- Prefabs: build an entity, `prefab_create {entity, path, replaceWithInstance?}`, then `prefab_instantiate {prefab, parent?, index?, transform?, name?, components?}`; `prefab_apply` writes an instance's overrides into the prefab and `prefab.revert` (through `engine_call`) drops them. `prefab_create` returns the replacing instance as `instance`, `prefab_instantiate` returns the new root as `entity` (`{"$ref": "2.entity.id"}` in a batch). A member of an instance (an entity below its root that the prefab made) cannot be deleted in the edit scene, since the instance's next update would bring it back: `entity_destroy` (and `prefab_create {replaceWithInstance: true}`) refuses it with `InvalidState`, so deactivate it (`entity_update {active: false}`), or `prefab.unpack` the instance first.
- **Per-instance values.** `prefab_instantiate`'s `components` sets instance overrides in the same command, as the inspector would: `{<Component>: {<Field>: value}}`, script fields through `Script: {Fields: {...}}`. It works inside `edit_batch` and with `dryRun`, so a grid of variants is one op per cell, with no `entity_update` after each:

```json
{"label": "Brick grid", "ops": [
	{"method": "prefab.instantiate", "params": {"prefab": "Assets/Prefabs/Brick.prefab", "parent": "/Bricks", "name": "Brick_1_01",
		"transform": {"Translation": [-7.2, 5.5, 0]},
		"components": {"MeshRenderer": {"Materials": ["Assets/Materials/BrickRed.material"]}, "Script": {"Fields": {"Points": 5}}}}},
	{"method": "prefab.instantiate", "params": {"prefab": "Assets/Prefabs/Brick.prefab", "parent": "/Bricks", "name": "Brick_1_02",
		"transform": {"Translation": [-5.6, 5.5, 0]},
		"components": {"MeshRenderer": {"Materials": ["Assets/Materials/BrickRed.material"]}, "Script": {"Fields": {"Points": 5}}}}}]}
```

- **Tracks and levels.** Give each level a root entity with a `Static` `RigidBody` and instantiate every track piece under it: the pieces join one static compound body, so a rolling ball crosses seams without bumps. Separate static bodies that touch are reported as `PHYSICS_ADJACENT_STATIC_BODIES`, and `project_validate {fix: ["PHYSICS_ADJACENT_STATIC_BODIES"]}` adds that root body for you. Lay out a level as one `edit_batch` of `prefab.instantiate` ops under the root (`"parent": "/Level"`), plus ordered waypoint entities along the main route for the autopilot.
- **Entities that report their own collisions** (bricks, targets, pickups) keep their own bodies instead, since a collision callback names the body's owner and colliders merged into a compound body all report its root: give each brick its own `Static` `RigidBody` (in its prefab), under a root without a body, with a 0.1 m gap between neighbours so they never touch and `PHYSICS_ADJACENT_STATIC_BODIES` stays quiet. Walls the ball only bounces off can share one compound body under a root. The body settings of a constant-speed ball and of a player-driven paddle are idioms of `luau-gameplay`.
- Look at the result: `scene_tree {format: "Text"}` for the outline, `entity_bounds` for layout and gaps, and `viewport_screenshot {view: "Game", width: <Window.Width>, height: <Window.Height>, annotate: {labels: "all"}}` (needs `renderer: "vulkan"`). Without `width` and `height` it renders 640 × 360 whatever the window (`game-debugging` item 7). The image comes back as image content; its PNG in `Library/Automation/Out/` lasts until the next editor session prunes it, so pass `keep: true` for one you must hand over (`Library/Automation/Kept/`, never pruned).

### Look

- **Defaults.** `PostProcess` has GTAO (`SsaoEnabled`), bloom (`BloomEnabled`, `BloomIntensity` 0.04) and FXAA on, with AgX tonemapping; a scene without one renders with these defaults. Exposure changes only through a `PostProcess`: without one, tune light and `Environment` intensities and material colours. A `DirectionalLight` casts PCSS soft shadows (`CastShadows`), whose penumbra radius is (receiver depth − blocker depth) × tan(`LightAngle` / 2), clamped: the default `LightAngle` 1 gives near-hard edges, about 10 looks soft. Its up to four cascades spread over `ShadowDistance` (default 100 m); about twice the camera's distance to the board keeps them sharp.
- **Receivers.** Shadows and GTAO show only on surfaces the camera sees: a board viewed straight on needs a backboard behind it to receive them. A `Blend` material casts no shadow and takes no GTAO.
- **Glow.** Bloom has no threshold: it blends `BloomIntensity` of a blurred copy into the image, so at the default 0.04 the halo is barely visible, and emission alone pales the colours towards white before it glows. Tetris's tested pair, under ACES at `ExposureEV` -0.8: `Emissive` the piece colour with `EmissiveStrength` 4 (6 for an accent line) and `BloomIntensity` 0.3; a high intensity also lifts the shadows. `BloomIntensity` is a scene component, hashed (set it before recording replays); `EmissiveStrength` is a material value, not hashed. Prove the glow with two screenshots in play at one tick, `BloomEnabled` true then false (`entity_update {target: "Play"}`).
- **Background.** An orthographic camera's skybox is one flat colour: set `Camera.Clear` to `"Color"` with a dark `ClearColor` and keep the environment for lighting.
- **Screen text.** A `Screen` `Text` sits at `Anchor` (viewport-normalized: (0, 0) top-left, Y down), its block's `Pivot` on that point, moved by `Offset`; `Size` and `Offset` are pixels at the 1080p reference, scaled by viewport height / 1080 (× 0.83 at 900 px). The default font's digits are proportional, so a number centred on its anchor jitters as it changes: pin its left or right edge (`Pivot` x 0 or 1). A `World` text's em is `Size` / 100 metres before the entity's scale.
- **GTAO.** An occluder further than `SsaoRadius` in front of a surface casts little occlusion on it: set it above the depth gap between the pieces and the surface behind them. GTAO darkens the environment's image-based light only, never direct lights, so it shows mostly in `debugView: "AO"` and where ambient light dominates.
- **Framing.** Iterate the camera on game-view screenshots at the window's size (`width` and `height`), taken in play (`target: "Play"`) once the runtime entities exist, and with `debugView: "AO"` or `"ShadowCascades"`, which colours each surface by its cascade (`game-debugging` item 7): one colour over an orthographic board means it lies in one cascade, which `CascadeCount` 1 suits.
- **Iterate in play, then record.** Try values with `entity_update {target: "Play"}` in the lockstep session, which leaves the scene file and the replays alone, then write the chosen ones to the scene. `asset_get_properties {asset}` reads a material's or sound effect's values; lockstep sessions defer asset reloads, so after an `asset_set_properties` stop and restart play to see it. Finish the look before recording replays: every look component is hashed (§5), so changing one in the scene later changes every replay's checkpoints and final hash, and each must be re-recorded (§9).

## 4. Scripts

- `script_create {path, template: "Behaviour" | "Module" | "Test"}`, then `script_write {path, source}`. Each result carries compile, type and lint diagnostics with full ranges; iterate until `script_check {}` returns an empty `diagnostics` array. Its `passed` counts only errors, but the games suite fails a game on any diagnostic, and Luau's lint warnings (severity `Warning`, such as an unused local or two statements on one line) count. Set `Scripting.BlockPlayOnTypeErrors` to keep type errors out of play: play, reloads and test runs then refuse them (test runs always do).
- The Behaviour and Module templates (`templates/Scripts/<Template>` in `docs_get`) name their table `Script_<File>` (a Behaviour also its exported alias and its `Script.Define` name), a unique valid identifier: rename it in the first `script_write`. The Test template has no type and names its suite after the file stem without `.test`: `Assets/Tests/Board.test.luau` gives `Test.Suite("Board", ...)`.
- `script_write` replaces the whole file. Keep scripts small modules (rules in a Module, the behaviour that drives them in another) so each write stays short.
- Attach a behaviour with `entity_update {entity, components: {Script: {Script: "Assets/Scripts/Game.luau", Fields: {...}}}}`. The call refuses an override that names no declared field or has the wrong type or range (InvalidParams at `/components/Script/Fields/<Name>`), so success means every override matched; `project_validate` reports such overrides already in files (`SCRIPT_UNKNOWN_FIELD_OVERRIDE`, `SCRIPT_FIELD_TYPE_MISMATCH`).
- Keep pure logic (boards, scoring, kick tables, and the spawn rules: bag, hold, top-out, levels) in Modules without engine calls, so the empty-scene suites test it. The behaviour reads input, calls them and mirrors their state into components (cells' active flags and materials, HUD `Text`), which the state hash and the replays see.
- **A native C++ module** (Windows, only while the user's "Allow native code" preference is on, kept in `user://Editor.json` for every editor that user starts; no tool sets it): `native_write` its `.cpp` and `.h` files below `Native/` (one includes the engine's `NativeApi.h`, the topic `native/NativeApi.h`, as `native.write`'s example in `rpc.discover` spells it, and names `ENGINE_NATIVE_MODULE`; own headers as `#include "Native/<File>.h"`), `native_build` (until no `NATIVE_FORMAT_WARNING` is left), `native_load`, then `native_set_components {entity, components: {"Native.<Name>": {...}}}`. A game kept free of `PostProcess` and physics starts from `Empty`, or deletes `Basic3D`'s `/Post Process` and Ground's `RigidBody` and `BoxCollider`. `game-debugging` ("Native module") has the rules.

## 5. Verify deterministically

- `scene_save`, then `play_start {lockstep: true}`. Without `seed` the session runs with the session seed (the project's `Simulation.Seed` XOR the scene's `Seed`), as every suite and every recording does, so it shows their piece order and spawns, which another `seed` can change. `play_start` plays the open scene with its unsaved edits, while recordings and test runs play the saved file. Only `play_step {ticks, input?, render?}` advances it; each result carries `tick` and `stateHash`.
- Input events are tick offsets from the step's start: `{tick: 0, type: "Action", name: "MoveLeft", state: "Tap"}` (down this tick, up the next). Analog actions take `value`, which holds on every later tick until another value replaces it: send `value: 0` to let go. A `Down` button likewise stays down until an `Up`.
- `script_eval {context: "Play", entity: "/Game", code: "return self.Board:ToAscii()"}` reads state; `play_wait_for {until: "<luau returning a boolean>", timeoutTicks}` steps until a predicate holds.
- Repeated runs with the same seed and input must give the same `stateHash`. A difference is a determinism bug in the game: `^` with a computed exponent, `pairs` over entity keys and gameplay that reads the host (`Application.IsEditor`, `Application.IsFocused`, `Time.GetRealTime`) are the usual causes, and split the editor's hashes from the export's (`luau-gameplay`, "Determinism pitfalls").
- **What the state hash covers.** Every entity with its id, name, parent, active flag, tags and every serialized component, the look included (`PostProcess`, `Environment`, lights, `Camera`, `Text`; a `Script` component's authored `Fields`, never its Luau instance state), the tick, the session's `Random` state, the id draws and every body's position, rotation, velocities and sleep flag. So which entities draw, with which material handles, and every `Text` string are covered. It never covers material or sound asset contents (a component stores the handle), script tables (`self.State`, module locals), a `Random.New` generator's state, audio voices, input state or rendered output (frames, interpolated positions): a score that lives only in a script table is invisible to the hash until a Text or another component shows it. Observe script state with `Expect` (replays) and `Test.Expect*` (suites).
- `play_stop` returns to the edit scene unchanged.

## 6. Test suites

- One suite per area: pure-logic suites in the empty scene (`Board.test.luau`) and integration suites bound to a scene (`Tetris.test.luau`) that drive play with `Test.InjectAction`, `Test.WaitTicks` and `Test.WaitUntil` and read the game through `GetScript()` and component values. `Test.GetStateHash` hashes the tick too, so two reads at different ticks always differ and no suite can compare two runs: compare runs with `input_replay` (§7).
- **Tick budgets.** A case has 600 ticks by default (`Testing.CaseTimeoutTicks`, or `{ TimeoutTicks = N }` on the case) and a suite 36,000 in all (`SuiteTickLimit`). Drive cases with hard drops rather than gravity, and give a gravity-paced case its own `TimeoutTicks`. `Test.WaitUntil(predicate, timeoutTicks)` checks now and after every tick, its predicate must return a boolean, and a timeout fails the case.
- `test_run {}` runs every suite and verifies every replay; `test_run {filter: "Tetris/hard drop"}` selects by a case-insensitive substring of `<suite>/<case>` (a replay by its path), so `"Breakout/"` also selects `Autopilot.Breakout/...`: name the longer suite or a case when one suite's name ends another's (a `record` filter must select exactly one suite). The result has `passed`, `counts` (rows by status: `total`, `passed`, `failed`, `error`, `timeout`, `skipped`, `quit`), `failedCases` (up to 20 `"<suite>/<case>"` names), each case with its outcome and failures with file and line, and the `jsonPath` and `junitPath` reports. The `coverage` object's `counters` stay empty unless you pass `coverage: true` (the JSON report always holds them). A green run has no failed, errored, timed-out or skipped rows.
- **Test runs play saved scene files.** `test_run` refuses with `InvalidState` (hint `scene.save first; test runs play the saved scene file`) while the open scene has unsaved changes and a selected suite is bound to it or a selected replay plays it: `scene_save` first.
- Write a feature's tests first: stub the new function, write its cases and run them red, then implement it and run them green. `edit_undo` and `edit_redo` also take a `script_write` back and forth, so a test can be shown failing without the feature through automation.
- The same suites run headless with `Editor --headless --project Projects/<Game> --run-tests [--filter F]` and, in exported testing builds, with `Runtime --feature-test`.

## 7. Replays

A replay records the input applied per tick from tick 0, the state hash of every 60th tick (its **checkpoints**) and the final state hash (§6.7, §13.6). The checkpoints make a replay prove the trajectory of its run, not only where it ends.

- **Record every replay from a recording suite** (§8): re-recording is then one `test_run {record}`, and the input plan stays readable through `script_read`. `input_read_replay {path}` returns a replay's events in `play_step`'s input form, a page at a time, so a replay made with `input_record` can be re-recorded from its own events.
- `input_record` suits a quick check of planned input, written to a scratch replay (it plays the saved scene, "Pitfalls"). In Edit mode, `input_record {action: "Start", scene?, parameters?, seed?}` starts a lockstep session at tick 0 (default seed: the session seed) and records. Drive it with `play_step` input, then `input_record {action: "Stop", path: "Assets/Tests/Replays/Check.replay", expect: [{tick: 600, luau: "return (Scene.FindByName('Game') :: Entity):GetScript().Lines >= 1"}]}`: an expectation that only the input satisfies, at a tick no later than the last. Expectations are compiled, never type-checked: run the exact expression with `script_eval {context: "Play"}` before `stop`. Once you have checked it, `asset_delete {asset: "Assets/Tests/Replays/Check.replay"}`: every replay left below `Assets/` counts as committed (the games suite fails one that `Testing.Replays` leaves out), and a committed replay comes from a recording suite.
- **`stop` verifies with the input.** Every recording is first replayed with its input (`verify`, `strictHash`, its `expect`). Unless that playback reproduces every checkpoint, the final hash and every expectation, without stopping early or raising a script error (at teardown, in `OnDestroy`, too), `stop` refuses with `Validation` ("replayed with its input, the recording does not reproduce itself: <reason>", the first failing checkpoint, expectation, final hash, stop or script error, with its tick), writes nothing and ends the recording; error data `verification` holds the playback's outcome.
- **Evaluate only reads while recording** (`luau-gameplay`, "Recording", lists the mutating APIs). A `script_eval` or `play_wait_for` that calls a mutating engine API invalidates the recording at once; one that writes script state (a `self` field, a board table) is neither detected nor recorded, so `stop` refuses the recording once that write shows. A hot reload or a play-scene edit during the recording invalidates it too: `stop` then fails, writes nothing and names the reason.
- **The input check.** A recording with input events is then replayed without them before it is written. When that run reproduces every checkpoint, the final hash and every `Expect` (whatever script errors it raises), the outcome does not depend on the input: `stop` (and `test_run {record}`) refuse it with `Validation` ("does not depend on its input") and write nothing. That happens only when the input never shows in the world at a checkpoint, at the end or in an `Expect` (`game-debugging` has the cases): a recording under 60 ticks that ends idle, input that changes only script state or that the game ignores, or play after the last checkpoint that a restart undoes. So give the first input well inside the first 60 ticks, end every recording while the played state is still in the scene (pieces placed, score shown, a life lost), and keep an `Expect` for what only the input causes. A check that differed only at checkpoints but reached the recorded final hash writes the recording with a warning (`warnings`): only its checkpoints prove the play. After `stop` the session is the check's, paused at the replay's final tick (or where the check stopped); `inputCheckTick` names the first checkpoint that differed. Inspect the recorded run before `stop`, or replay the written file.
- Verify with `input_replay {path, verify: true, strictHash: true}`: every `Expect` must hold, every checkpoint must match when playback reaches its tick (the first that differs stops it there, `checkpointFailed`, naming the tick and both hashes) and the final hash must match. `checkpointsChecked` counts the checkpoints compared, the one that failed included, so a passing replay compared all of them. A failure's `changes` name what changed since the recording (entities, components, directly referenced assets), the first one ending its message. `Testing.Replays` makes every test run verify them; each replay's entry in the run's `suites` reports the same count as `checkpointsChecked` and the tick of a checkpoint that differed as `failedCheckpointTick`.
- **Replay twice.** Verify each new replay twice that way: the two `stateHash` values must be equal (a demo's acceptance names it, and the transcript keeps both).
- `input_replay {path, verify: true, strictHash: true, withoutInput: true}` plays the replay with none of its input events. It must fail for a replay with events, as an error like every failed verification (-32003 `Validation`; `game-debugging` reads its data). When it passes, re-record the replay (the games suite checks this for every committed replay).
- After `input_replay` the session stays paused where playback ended: inspect it (`script_eval {context: "Play"}`, `entity_get`), then `play_stop`.

## 8. Recording suites

A replay is recorded by a test-only **recording suite** that plays like a player: an **autopilot** where hand-written input is impractical (steering a physics ball), or a single case that injects a **planned input list** at fixed ticks (a Tetris opening). Record its run, then verify the replay without it:

1. Add it to `Testing.Suites`, bound to the scene, with `Modes: ["Editor"]`, so exported builds never run it.
2. Its single case reads the scene and injects input with `Test.InjectAction`: an autopilot follows the level's waypoint entities with a PD controller every tick until the goal is reached; a planned case taps each action at its tick. It must only read the scene and inject input: never move entities, write components or draw from the session's `Random` stream, so the run equals a player pressing the same inputs. End it with `Test.Expect` on what only the input causes, while the played state is in the scene, with no restart at its end (cover restarts in another suite).
3. **Name it so that no replay path contains its name** (`Record.Opening`, not `Opening`, whose filter would also select `Assets/Tests/Replays/Opening.replay`), and record with exactly that filter: `test_run {filter: "Record.Opening", record: "Assets/Tests/Replays/Opening.replay"}`. The filter must select exactly one suite, and every selected row must pass: a refused recording names the selected rows that did not pass (a `replay:<path>/...` row is a committed replay the filter also selected). The editor verifies the candidate in fresh ordinary gameplay without the test driver, every checkpoint and the final hash included, then runs the input check (§7), before it writes the file. The result's `recording` block describes the replay written, its `inputCheck.divergedAtTick` saying where the run without input first differed, with `expectations` and the input check's `warnings`.
4. The replay is then verified **without** the suite by `input_replay {verify: true, strictHash: true}` and by every test run through `Testing.Replays`, which proves that plain input reproduces the play. Level 2 and 3 suites set `Parameters` (such as the carried timer), which the replay header stores. A recording made by `test_run` carries an `Expect` only when you pass `expect: [{tick, luau}]` with `record`, which it verifies with and without the input; its checkpoints and the input check make it prove its gameplay anyway, and the suite's own `Test.Expect` asserts it at record time.

`luau-gameplay` ("Recording") has a planned-input suite (`Record.Opening`) and an autopilot suite for a rolling-ball level.

## 9. Re-recording replays

When an engine change legitimately alters simulation results (a physics fix, a new serialized field, a changed default), or the scene (the look included: a `PostProcess`, light or `Camera` value) or the game's native module changes after recording, replay hashes change and their verification fails, its hint saying that the world differs from the recording:
- Re-run each recording suite with `test_run {filter, record}` through automation, so provenance and the transcript record the new replay; verify it twice and run the input check again (§7).
- After a gameplay change, re-record a replay when it must cover the new behaviour: a matching hash only means the worlds matched at each checkpoint and at the end, and script state that never reached the world is not compared.
- The review of the change states why the hashes changed. A verifier's hash never replaces a recorded one by hand.
- A replay of format version 1 (no `Checkpoints`, so verified by its final hash only) or 2 still verifies; `project_upgrade` rewrites it as version 3 with no start fingerprint (and, from version 1, no checkpoints), and re-recording it adds them.
- An engine change that alters the canonical form of project files also runs `project.upgrade` on every affected game (`project_upgrade {dryRun: true}` first, then `project_upgrade {}` through the bridge; `changes` gives each rewritten file with its reason, such as `"format version 1 to 2"` or `"canonical form"`; its refusals are in `game-debugging`; or `Editor --headless --project <Game> --upgrade`, which appends its own `cli` transcript lines: `project.refreshAssets` for its deferred asset scan, then `project.upgrade`), so the audit and the byte-identical re-save test stay green; the same change regenerates FeatureTest and re-records the affected replays.

## 10. Validate and export

- `project_validate {}` must report nothing. `fix: true` applies every safe fix as one undoable command; `fix: ["<id or CODE>"]` only the selected ones. `reference/Validation` explains each code and its fix.
- `project_export {config: "Dist", smokeTest: true}` writes `Build/<Platform>-Dist/<Game>/` and runs the exported executable with `--headless --frames 300 --expect-no-errors`; it must exit 0. Check the result: `smokeTestRan: true` and `smokeTestExitCode: 0`. A Dist Runtime needs a graphics device, so from a `renderer: "none"` editor the export succeeds with `smokeTestRan: false` and a warning, which proves nothing: relaunch with `renderer: "vulkan"`. The Dist smoke test keeps the game's log in the user's real data folder (`%LOCALAPPDATA%\<Game>` on Windows), as a shipped game does. What an export refuses is in `game-debugging` ("An export is refused"). On Windows the executable carries the icon, version and company (`resourcesPatched`); every package holds `THIRD_PARTY_NOTICES.txt`, and a macOS export is `<Game>.app`. The result's `phaseTimings` show where the time went.
- `project_export {config: "Dist", testing: true}` is a testing export (`Build/<Platform>-Dist-Testing/<Game>/`): it packages `Assets/Tests/**`, every `Testing.Suites` script and scene and every `Testing.Replays` match whatever `Export.Exclude` says, refuses invalid suites and replays whose expectations do not compile (issues at `/Testing/Suites/<i>` and `/Testing/Replays/<i>`), and its `Game.json` says `"Testing": true`, so `<Game> --headless --feature-test` runs the suites and replays in the shipping binary and writes `bin/TestResults/FeatureTest-<Mode>.{json,xml}` below its working directory, its user data in `<package>/bin/TestUserData/<Game>`. The result counts `testSuiteCount` and `replayCount`. With `featureTest: true` the export runs the package's `--feature-test` itself, reports its rows by status in `featureTest.counts` and every replay's `stateHash` in `featureTest.replays`: before handing over, compare them with your editor's `input_replay` hashes (the games suite's Dist half compares the same).
- With `Export.PruneUnreferenced: true` (opt-in) an export ships only what `StartScene`, `Export.BuildScenes` and a testing export's test content reach through references and literal `Assets.Load("...")` paths; the result's `reachability` says why each asset ships and lists what it left out, and `project_validate` warns about each computed path (`SCRIPT_COMPUTED_ASSET_LOAD`), which it cannot follow.
- Outside an editor session, `Editor --headless --project <P> --export <dir> --config Dist [--testing] [--smoke-test] [--export-report <file>]` (or `python Scripts/Export.py`) exports once and exits 0 exported, 1 failed, 3 the project does not open or a build output is missing.

## Definition of done

A game is done when all of these hold:
1. `project_validate {}` reports no diagnostics and `script_check {}` none, lint warnings included; `native_build` no `NATIVE_FORMAT_WARNING`.
2. `test_run {}` is green: every suite in every mode it lists, and every replay verified with its committed hash. `Testing.Replays` matches at least one committed replay recorded from tick 0 with input events, and every replay with input events fails its verification without them (§7).
3. Every replay comes from a recording suite (every level a physics ball plays has an autopilot whose replay reaches the goal without it), and each was verified twice with `input_replay {verify: true, strictHash: true}` with equal `stateHash` values.
4. `StartScene` is set and `Export.BuildScenes` lists it.
5. `project_export {config: "Dist", smokeTest: true}` succeeds from a rendering editor, with `smokeTestRan: true` and `smokeTestExitCode: 0`.
6. **Soak-ready.** The milestone gate soaks every scene below `Assets/Scenes/` of a game in `Projects/<Game>` (not one in `Tests/Projects/<Game>`) for 10,000 rendered lockstep ticks without input, from the session seed, rendering each scene's game view too (a sample whose game view did not render fails), and fails a scene whose entity, body, voice or device-allocation counts are higher in its last twentieth than in ticks 5,000 to 5,500, whose memory or script heap grows, or that raises a new script error (in `OnStart` too). So pool entities (no `Scene.Instantiate` per lock), give pooled entities no `RigidBody` or collider, let game over wait for `Restart` with a short sound and no looping audio, keep live data bounded (no move history), and write HUD text on change. Check it: from the saved scene `play_start {lockstep: true}`, `play_step` to tick 10,000, `script_errors {}` (before any `script_eval`, whose failures it lists too), and `engine_call {method: "stats.get"}` past ticks 5,000 and 9,500 (`entities`, `bodies` and `voices` must not grow between them).
7. `python Scripts/AuditProvenance.py --project <Game>` passes on the staged project (index mode, the acceptance mode: it audits the staged files as a fresh clone holds them): every engine-consumed file has a provenance entry with its current XXH64, written by an automation method whose request at the entry's transcript line in `BuildLog.jsonl` has the same id, method and client (or by `project.upgrade`); no entry names a file that no longer exists unless the transcript records an `asset.delete` or `asset.move` of that file (deleting its folder never excuses it); no two staged paths differ only in letter case.
8. `python Scripts/Test.py --suite games --config Debug,Release,Dist --require-gpu` passes with the game staged: the audit; the build settings (4), `script.check`, `project.validate` and the `project.upgrade` dry run clean; every suite and replay at its committed hash in the Debug and Release editors and in a testing Dist export; at least one committed replay with input events, and every one failing its verification without them (§7); and the plain Dist export's smoke test run and exiting 0.
9. `<Game>/AGENTS.md` describes the scenes, input actions, scripts, suites and replays, and its `luau` fences follow "Documentation is exempt" (Ground rules): a failing fence fails every later commit.

A demo milestone adds its Roadmap acceptance. **Tetris (M17):** `Board.test.luau` covers kicks at both walls and the floor, clears of 1–4 lines and their scores, the 7-bag yielding each piece once per bag, top-out ending the game and hold swapping once per piece; `Tetris.test.luau`, bound to `Main.scene`, has integration cases driven by `Test.InjectAction`; `Opening.replay` (several pieces placed with moves, rotations, a hold, a soft drop and hard drops, ending with them in the well) and `LineClear.replay` (a planned placement of the known pieces that clears at least one line, the HUD showing it) each come from a recording suite; and the look screenshots, from a `renderer: "vulkan"` editor in a lockstep session with a stack of cells, are `viewport_screenshot {view: "Game", target: "Play", width: 720, height: 900}` plus the same with `debugView: "AO"` and with `"ShadowCascades"`, their paths reported.

## Pitfalls

- **Arrays replace.** A settings patch with `"Suites": [one entry]` drops every other suite.
- **Unsaved scene.** Recording, replay verification, test runs (every suite bound to a scene and every replay) and export use the saved files, while `play_start` plays the open scene with its unsaved edits: `scene_save` first.
- **Renderer none.** The bridge's default editor cannot take screenshots (`Unsupported`), and a `Test.Screenshot` call errors its case there; relaunch with `renderer: "vulkan"`.
- **Lockstep ownership.** Only the client that started lockstep may step it; a disconnect releases it.
- **Large results** over 48 KB come back as `{path, truncated: true, summary}`: read the file, or a test run's `jsonPath` and `junitPath` reports, with the bridge's `result_read` (`game-debugging`), never another file tool.
- **Hot reload pauses for determinism.** Lockstep, recording, replay and test sessions defer script and asset reloads until the session ends (`game-debugging`).
