## Context

Each fact below was read in the code at `bb51e110`.

- **The session pause stops every tick.** `PlaySession::SetPaused` and the host loop's `AdvanceLoopStep` and `AdvanceLoopFrame` run nothing while the session is paused (`PlaySession.cpp`); `play.pause` and `play.state`'s run state `Paused` (`PlayRunState`) are that pause. `Time.SetTimeScale(0)` also stops every fixed step, and with it the UI, whose `UiInput`, `UiEvents` and `UiLayout` phases run in the fixed step (`PlaySessionPhase`; `Docs/Backlog.md` §6's "A time scale of 0 stops the UI").
- **The fixed step's phases** (`PlaySession::FixedStep`): InterpolationSnapshot, ApplyInput, TextLatch, UiInput, StartFlush, UiEvents, FixedUpdate and Tasks (Play only), NativeStep (Play with a native module), SpriteAnimation, AnimationSystem, PreStepTransformUpdate, PhysicsPreStep, PhysicsStep, PhysicsPostStep, Physics2DPreStep, Physics2DStep, Physics2DPostStep, DestroyFlush, PostStepTransformUpdate and UiLayout; the frame phase (`RunFramePhase`) LatchFrame, Update, LateUpdate, FrameDestroyFlush, FrameTransformUpdate, FrameUiLayout, AudioUpdate (Play only), Particles and RenderExtraction. The world's systems take `SimStep::FromTick(tick, FixedDelta)`; none of them reads absolute time for simulation (physics and 2D physics step by `FixedDelta`, the animation systems advance by it, `ParticleSystem::Step(scene, tick)` steps each emitter from its `LastTick` to `tick`); their ticks label events and diagnostics, and the native module reads its step's tick (`NativeWorld`'s `GetTick`).
- **Scripts' clock.** `Time.GetTick` and `Time.GetTime` read `ScriptFrameState::Tick` (`Bindings/Time.cpp`); every task and wait counts it: `TaskScheduler::Spawn` and `Delay` (`frame.Tick` plus the delay), `ResumeDue` (`task.Due <= frame.Tick`), and the threads' waits (`ScriptEngineAccess::ArmTaskWait`, `CreateThread`'s `Due`, `ScriptEngine::State::PrepareWait` and `Resume` in `ScriptThreads.cpp`). A task's owner is `ScriptTaskOwner{Entity, Case, Slot}`: an instance's for lifecycle callbacks and their tasks, a case's for a test case body, none for neither.
- **The callbacks' dispatch.** `ScriptEngine::FixedUpdate`, `Update` and `LateUpdate` call `ScriptEngine::State::Phase`, which invokes the callback on every started instance in (ExecutionOrder, canonical entity, slot) order (`ScriptInstances.cpp`). A behaviour's class is the table `Script.Define(name, class)` authenticates (`Bindings/Script.cpp`), whose registration record holds its name, fields and location; `InspectScriptRegistration` reads it back at instance creation and at hot reload.
- **Audio.** `AudioSystem::SetPaused` pauses every voice (sources and one-shots), new voices start paused, and a source's own `Pause` survives a resume (`AudioSystem.cpp`); a voice's group is `AudioVoiceSettings::Group` (Music, Sfx, Ui), which `AudioEngine::GetVoiceInfo` reports.
- **The state hash** (`PlaySession::ComputeStateHash`): the scene, the tick, `Random`, the id draws, then the physics, native, physics2d and ui blocks. Phase 5's ledger puts M28's save-data block after ui and M35's world-pause block after save-data, whatever the landing order; both are empty in every existing run.
- **`play.state`** returns `PlayStateResult` (`PlayMethods.h`); `play.setTimeScale` is the model of a play method that changes run state without being a command (`Mutates` false, `AvailableInRuntime`, no dry run, refused for another client of a lockstep session by `Utils::CheckLockstepOwner`). During an `input.replay`, a `play.step` or a `play.waitFor` the session is stepping (`PlaySession::IsStepping`); during `input.record` its recorder is recording.
- **The unflushed disable.** `Entity:SetActive` synchronizes the instances at once (`Bindings/Entity.cpp`). `ScriptEngine::SynchronizeInstances` records an instance whose entity it sees inactive in `DisabledHistory` and runs its `OnDisable`; while the key stays there, the instance is skipped (`found->second.DestroyPrepared || m_State->DisabledHistory.contains(key)`), even after its entity is enabled again; the next destroy flush (`PrepareDestroyFlush`) runs its `OnDestroy`, cancels its tasks and erases it, and the next synchronization creates a new instance with `OnCreate` and `OnEnable`, whose `OnStart` runs at the next start flush (`ScriptEngine.cpp`). So the instance `GetScript` returned between the switch-on and the flush, and every field written on it, is discarded, though Architecture §11 recreates instances only "when an entity is enabled after its disable was flushed".
- **The prefab rebuild.** `PrefabInstantiator::UpdateInstance` applies an instance's overrides through `OverrideApplier::Apply`, one at a time: `SetField` canonicalizes (validates) the component after each field, so of `UiRect`'s `AnchorMin` and `AnchorMax`, overridden together to `[0, 0]` against the prefab's `[0.5, 0.5]`, `AnchorMax` (sorted first) is invalid alone and dropped as `PREFAB_STALE_OVERRIDE`, and `AnchorMin` then applies (`PrefabInstantiator.cpp`). `EditorContext`'s rebuild (`RebuildPrefabInstances`) only logs its `LoadReport`; `scene.open`'s `diagnostics` hold the scene file's load diagnostics alone (`SceneMethods.cpp`).

## Decisions

### 1. The world pause: its names, its state and when it applies (W35.1)

- **Names.** The *world pause* is distinct from the run state's pause (`play.pause`, `play.state`'s `Paused`, `PlaySession::SetPaused`), which stops every tick; a paused world's session runs on. Scripts: `Time.PauseWorld(sounds: WorldPauseSounds?)`, `Time.ResumeWorld()`, `Time.IsWorldPaused() -> boolean`. Automation: `play.setWorldPaused {paused, sounds?}` and `play.state`'s `worldPaused`, `worldSounds` and `worldTick` (decision 5). Session: `PlaySession::RequestWorldPause(paused, sounds)`, `IsWorldPaused`, `GetWorldPauseSounds`, `GetWorldTick`. The enum `WorldPauseSounds` (Pause, Finish) is in `Scripting/ScriptHost.h`, registered for scripts by `RegisterTime` and for automation by `RegisterPlayMethodTypes` (`ScriptApiRegistry::Freeze` takes identical names and values as one enum).
- **When it applies.** A request (a script's, automation's) is recorded and takes effect at the start of the next fixed step, after the step's replay checkpoint and before anything of it runs, so a tick runs wholly paused or wholly not. A later request before that step replaces the pending one, and one that asks for what is already in force cancels it (a pause and a resume in one tick change nothing). `IsWorldPaused` and `GetWorldPauseSounds` report the state the next fixed step runs with: the pending request's, else the one in force. A frame phase runs with the pause the last fixed step applied.
- **Where it may be called.** Time.PauseWorld and ResumeWorld are host mutations (`ScriptCall::PrepareHostMutation`): refused in a read-only evaluation, and an evaluation's call invalidates an input recording as every evaluation's host write does. They work from any phase; a pause a replay must reproduce in every frame grouping is requested from the fixed step (`OnFixedUpdate`, a UI callback, a task), as every simulated write is (§11.3). The edit evaluation's host has no world: `IScriptHost::RequestWorldPause` defaults to `Unsupported` and `IsWorldPaused` to false, so the members follow ADR 0042's host rule and the other hosts need no change. The script test fixture (`Tests/Source/Support/ScriptTestFixture.h`, shared test support) gains an opt-in world for the `TimeBindings` cases, which call every new member: with its `WorldPaused` set it records `Time.PauseWorld`'s and `Time.ResumeWorld`'s requests there (and the sounds choice in `WorldSounds`); by default it keeps the refusal of a host without a world (the review's finding 8).
- **Session state.** The pause in force, its sounds choice, the pending request and the world's clock are session state, like the tick and the time scale: `Scene.Load` and `Scene.Reload` keep them, as the established engines keep theirs (the lead's decision 3). So a pause menu that loads or restarts a scene must call `Time.ResumeWorld` first: otherwise the new scene starts with its world paused and only its `RunsWhileWorldPaused` behaviours running, which soft-locks a scene without a menu of its own. `Time.PauseWorld`'s description (so `Engine.d.luau` and the references), the luau-gameplay skill's `world-pause` page and Architecture §5.6 say so. It works in Play and Simulate (Simulate has no scripts; automation pauses its world).
- **The time scale is unchanged** and independent of the world pause; `Docs/Backlog.md` §6's row on a time scale of 0 now points at the world pause as the way to freeze the world while the UI runs.

### 2. What holds and what runs: the phases, the world's clock, the opt-in and tasks (W35.1)

- **The classification** (ADR 0042's execution-order list made exact). While the world is paused, the world's phases do not run, and the observer is not told of them: NativeStep, SpriteAnimation, AnimationSystem, PhysicsPreStep, PhysicsStep, PhysicsPostStep, Physics2DPreStep, Physics2DStep and Physics2DPostStep in the fixed step, Particles in the frame phase. FixedUpdate, Tasks, Update and LateUpdate run, for the behaviours that run while the world is paused (below). Every other phase is the UI's and runs as always: InterpolationSnapshot, ApplyInput, TextLatch, UiInput, StartFlush (every instance's `OnStart`, so a menu creates its own entities, and `SynchronizePhysicsBodies`, which creates a new entity's body without moving any; and the events held for an instance that starts then, delivered after the round), UiEvents (every behaviour's `OnUi*` callbacks), PreStepTransformUpdate, DestroyFlush (bodies of destroyed entities removed, and the pairs of the entities destroyed or switched off meanwhile closed with their synthesized `OnCollisionExit` and `OnTriggerExit`), PostStepTransformUpdate, UiLayout, LatchFrame, FrameDestroyFlush, FrameTransformUpdate, FrameUiLayout, AudioUpdate and RenderExtraction. Bodies keep their velocities, since no physics step runs; a paused world draws as it stands, its interpolation held because its snapshots stop changing. No new contact or animation event arises, but the exits of the destroy flushes and the start flush's held events reach every behaviour, one that holds while the world is paused too: gating them would leave an exit without its enter (the review's finding 4, which found the earlier wording, that no physics callback arises, wrong; "PlaySession: while the world is paused the destroy flush's exits and the start flush's held events reach every behaviour" pins it). A phase a sibling adds is classified at the later lander's merge (ADR 0042's risk).
- **The world's clock.** `PlaySession::GetWorldTick` counts the fixed steps the world ran; it advances at the end of every step that was not paused and holds otherwise, while `GetTick` counts every step. The world's systems step on it: NativeStep, SpriteAnimation, AnimationSystem and the physics phases take `SimStep::FromTick(GetWorldTick(), FixedDelta)`, and Particles steps to it (`ParticleSystem::Step(scene, worldTick)`), so the ticks the world ran before the pause took effect step at the first Particles phase after it resumes and none is lost or doubled. In every session that never paused the world's clock is the session's, so nothing a world system or a script reads changes there.
- **Scripts' clocks.** `ScriptFrameState` gains `WorldPaused` (the pause of the phase that runs) and `WorldHeldTicks` (`Tick` less the world's tick), appended with defaults (false, 0), so the edit evaluation and the test fixture keep a world clock equal to the session's. `Time.GetTick` and `Time.GetTime` read the world's clock, which holds while the world is paused (gameplay timers stop behind a menu); new `Time.GetSessionTick` and `Time.GetSessionTime` read the session's, which counts every step (a menu's own animation). Error ticks, replay ticks and `play.state`'s `tick` stay the session's, a native fault's too: `NativeWorld`'s `StopSession` takes the session's tick (`PlaySession::GetTick`), while the systems step on the world's (`INativeStepContext::GetTick`, documented as the world's tick; the review's finding 2). `physics.contacts`' and `physics2d.bodyInfo`'s `sinceTick` is the world's tick of the step that reported the enter (`play.state`'s `worldTick`), and `script.errors`' `tick` the session's, as `Time.GetSessionTick` reads it (findings 3 and 11).
- **The opt-in.** A behaviour class sets `RunsWhileWorldPaused = true` (a boolean or nil; anything else fails `Script.Define`, and so the import): its `OnFixedUpdate`, `OnUpdate`, `OnLateUpdate` and tasks run while the world is paused. It is a key of the class table beside `Fields`, read by `Script.Define` (so a class sets it before the call; one set later is not seen) into the class's registration record, which instance creation and a hot reload read into the instance (`ScriptEngine::State::Instance::RunsWhileWorldPaused`), never a Script component field (one written with its default would re-hash every scene with a script). Every other behaviour holds: `Phase` skips it while `WorldPaused`. A visual-scripting graph behaviour cannot opt in, since its transpiled class sets only `Fields`; that is an accepted limit (`Docs/Backlog.md` §6, the lead's decision on the review's follow-ups): a pause menu is a Luau behaviour.
- **Tasks.** Each task and thread has a clock, chosen when it is created from its owner (`ScriptEngine::State::UsesWorldClock`): the world's for an instance that does not run while the world is paused (or no longer exists), the session's for one that does, a test case's and one without an instance owner; its due tick is on that clock (`ScriptEngine::State::GetClockTick`; `TaskScheduler::State::Task::WorldClock`, `Reference::WorldClock`). While the world is paused, `ResumeDue` skips every world-clock task whatever its due tick, and the world's clock holds, so a world behaviour's `Task.Wait` and `Task.Delay` hold for exactly the paused ticks (a half-second delay begun before a 20-tick pause ends 20 ticks later), while a menu's and a test case's count on, so `Test.WaitTicks` steps a suite through a pause. `ResumeDue` still orders the due tasks by their due tick, then their creation sequence; in a session that never paused both clocks agree, so the order is as before. Once the world has held ticks, a world-clock task's due tick is below a session-clock task's due in the same tick, so a world behaviour's due tasks resume before a menu's or a case's, whatever their creation order: deterministic, since both clocks are state, and stated in Architecture §11.3 (a follow-up of the review).

### 3. Audio (W35.1)

The world pause's `sounds` choice: `Pause` (the default) holds every voice outside the `Ui` group (Music and Sfx sources and one-shots) until the world resumes, and voices of those groups started meanwhile start held; `Finish` lets them play on to their end (a looping one keeps looping). The `Ui` group's voices play on either way, so a menu still sounds. `AudioSystem::SetWorldPaused` (beside `SetPaused`, in other functions than M28's mix) pauses a voice while either pause or its source's own `Pause` holds it; a source's group is the `Group` field as last applied (a source moved into or out of `Ui` while the world is paused follows at the next update), a one-shot's the engine's record of the voice. The session applies it when a pause takes effect and to the new `AudioSystem` of a scene transition. Audio stays outside the state hash.

### 4. Determinism: the world-pause block (W35.1)

- **The block** follows M28's save-data block (the ledger), and is written from the session's first request to pause on (`WorldPauseUsed`, set by `RequestWorldPause(true)`; a resume alone sets nothing), as five little-endian 64-bit values: the pause in force (0 or 1), its sounds choice (0 Pause, 1 Finish), the pending request (0 none, 1 pause, 2 resume), the pending request's sounds choice (0 when none) and the world's clock. A session that never asked to pause writes nothing, so every committed hash stays; a pending request is part of the state the next tick starts from, so a checkpoint taken between a request and the step that applies it differs from one without.
- **Replays.** Every world pause comes from the session's scripts or its automation, and automation's is refused while a recording records or a replay plays (decision 5), so a replay reproduces its pauses from its scripts and its input, and verifies in Debug, Release and Dist like any other. `play.step` and test cases step through a pause (the UI advancing, the world not).

### 5. Automation parity (W35.1)

- **`play.setWorldPaused {paused, sounds?}`** joins the play methods (`PlayMethods`, after `play.setTimeScale`; no new registration function): `paused` required, `sounds` a `WorldPauseSounds` (default Pause, ignored by a resume). It returns the session's state (`PlayStateResult`). Flags as `play.setTimeScale`'s: `AvailableInRuntime`, not `Mutates`, no dry run (Unsupported, as every play method), not `AllowedInBatch`, not a tool (not in `PROXIED_TOOLS`; agents reach it through `engine_call`), scene relation None. Errors: InvalidState "not playing"; InvalidState naming the owner for another client of a lockstep session; InvalidState while an input recording is active and while a `play.step`, `play.waitFor`, `input.replay` or `input.record` verification advances the session (`IsStepping`); InvalidParams for a missing `paused` or an unknown `sounds`.
- **`play.state`** (and every result that returns `PlayStateResult`) gains, appended after `input`: `worldPaused` (the pause the next tick runs with), `worldSounds` (its choice) and `worldTick` (the world's clock, `ToAutomationCounter`). Architecture §13.5's count goes from 120 to 121 methods.

### 8. An unflushed disable keeps the instances (W35.2)

`ScriptEngine::SynchronizeInstances` treats an instance whose disable was observed but not yet flushed (its key in `DisabledHistory`, not `DestroyPrepared`) and whose entity is active again, with its slot still holding the instance's script, as re-enabled: its key leaves `DisabledHistory`, it becomes active, and it receives `OnEnable`, the pair of the `OnDisable` its disable ran. It keeps its table, its fields, its `Started` state and its tasks (a destroy flush cancels the tasks only of what it tears down), so the instance `GetScript` returned is the one that starts (an unstarted one at the next start flush, the brief's case) or goes on (a started one, with no second `OnStart`). Only the outermost synchronization does it (`ScriptEngine::State::SynchronizationDepth`): one nested in another's callbacks (an `OnDisable` that switches entities back on) leaves it to the next outermost one, so no instance gets `OnEnable` before the `OnDisable` the outer one observed, and a switch back on inside a destroy flush's own synchronization still completes that flush's teardown (the existing case "ScriptInstanceLifecycle: re-enabling a subtree in OnDisable still tears down every observed instance" keeps its expectation). An instance whose slot's script changed meanwhile keeps the old path (torn down at the flush, recreated after). A disable that was flushed recreates the instances as before (Architecture §11.3's rule, which the code now follows). Tests: "ScriptInstances: an entity instantiated, switched off and on and given a state in one tick starts with that state" (the brief's sequence in a play session; before the fix its trace was create, disable, destroy, create, enable, start:Inactive), "ScriptInstanceLifecycle: disable then enable before flushing keeps the instance, its state and its tasks" (the case that pinned the old rule as "disable then enable before flushing still replaces the old instance", rewritten to the new one) and "ScriptInstanceLifecycle: a disable whose script changed before the enable is still torn down and replaced". Run alone on a build with the fix reverted (2026-11-16, `ScriptEngine.cpp` as at `986d23b0`), the first failed with the trace create, disable, destroy, create, enable, start:Inactive against the expected create, disable, enable, start:Dropping, and the second with create, start, disable (no enable) and a destroy flush that tore the instance down; both pass with the fix.

### 9. A prefab instance's overrides apply together (W35.2)

A rebuild (`OverrideApplier::ApplyFields`) applies an entity's Field overrides of one component (the same `Path` and `Component`) as one write, as `entity.update` with the same fields would. Each override's own target is checked first (the entity, its removal, the component, a component overrides may change, the component on the entity; then, as it is written, a serialized field or the script slot), an override whose target is gone being stale on its own. The remaining overrides' values are written into the component in their sorted order and the combined component is validated once (`Canonicalize`). Valid, all of them apply. Invalid, the overrides whose fields the error locates (its JSON pointer or an issue's inside the override's field; a slot member's override also for its slot as a whole) are dropped, each reported with the error, and the rest are written again, until the write is valid or none is left; an error that locates none of them (a rule of the component that blames a field no override writes, as `UiRect`'s blames `AnchorMin`) sends the rest one at a time, in their sorted order, over the component as written so far (`OverrideApplier::ApplyEach`), each validated after its write, and only those invalid there are dropped. As first built, such an error dropped all of them, so an `AnchorMax` made invalid by the prefab's new `AnchorMin` took a valid `Size` with it (the review's finding 1, major; the lead's decision: the fallback above). So an invalid value never takes a valid sibling with it (the existing case "PrefabInstantiator: overrides that no longer match the prefab are dropped with a warning" keeps its five drops and its kept Scale), and the brief's pair (`AnchorMin` and `AnchorMax` at `[0, 0]` over the prefab's `[0.5, 0.5]`) applies together. RemoveEntity, RemoveComponent, AddComponent and EntityKey overrides keep their checks. Test: "PrefabInstantiator: an entity's overrides of one component apply together, and a write's error drops only the overrides it locates", whose fourth scenario (the review's: `AnchorMax` `[0.2, 0.2]` and `Size` `[300, 50]` below the prefab's `AnchorMin` `[0.5, 0.5]`) keeps `Size` and drops `AnchorMax`. Run alone on a build with the fix reverted (2026-11-16, `PrefabInstantiator.cpp` as at `986d23b0`), it failed: the pair's rebuild dropped one override as stale and left AnchorMax at the prefab's (0.5, 0.5); it passes with the fix. Run alone again with only the fallback reverted (2026-11-16, an error that locates none dropping all of them), it failed at the fourth scenario: two drops, `Size` among them, against one; it passes with the fallback.

### 10. Every dropped override is reported where an agent sees it (W35.2)

Each override a rebuild drops is a `PREFAB_STALE_OVERRIDE` warning located at the instance root's `/Components/Prefab/Overrides/<i>` and naming the instance root, logged as before and reported in the result of the method that rebuilt:
- **`scene.open`**: its `diagnostics` (`SceneLoadIssue`), after the scene file's own, from `EditorContext::UpdatePrefabInstances`' new `rebuild` out-parameter.
- **`prefab.apply`, `prefab.revert`, `asset.import` (a replace of a prefab), `asset.reimport` and `asset.setImportSettings`**: a new `rebuildDiagnostics` member, a list of the new registry struct `PrefabRebuildDiagnostic` `{scene, severity, code, message, pointer, entity}` (the open scene's project path, the instance root's 16 hex digits), appended at the end of each result. It holds the rebuilds of every open scene the call rebuilt, the addressed one's and those of the other open scenes that follow it (`PropagatePrefabUpdate`), gathered by `EditorContext`'s new scoped `PrefabRebuildCollector`, which every rebuild of the then addressed scene (`UpdatePrefabInstances`, through `CreatePrefabUpdateCommand`) reaches while one lives; `prefab.revert` reports its own rebuild's report.
- **`edit.undo` and `edit.redo`** (the lead's addition from the review's follow-ups; main's `60b1833a`): undoing or redoing a prefab write makes the other open scenes' instances follow it (`PrefabPropagationCommand::Follow`, `EditorContext::PropagatePrefabUpdate`), so their results gain the same `rebuildDiagnostics`, gathered by a `PrefabRebuildCollector` around the history's undo or redo. `PrefabRebuildDiagnostic` is registered by `RegisterEditMethodTypes`, the first of the domains whose results report it (the registry wants a struct before its use, and `RegisterEditorMethodTypes` registers the edit methods' types before the asset and prefab methods'); it stays declared in `AssetMethods.h`.

A `RefreshOverrides` failure inside a rebuild ("The overrides of the prefab instance ... were kept as recorded", `EditorContext.cpp`) stays a log line, not a rebuild diagnostic: the review suggested reporting it, and the lead withdrew that, since a rebuild remaps every prefab-local ID through the instance map (`MakeInstanceMap` covers the whole document), so no rebuilt member holds the ambiguous reference that alone fails the refresh, and the warning stays a defensive log.

Tests: "PrefabMethods: a rebuild keeps overrides valid only together and reports each it drops in prefab.apply's and scene.open's results", "PrefabMethods: prefab.revert, asset.reimport and asset.import with replace report the overrides their rebuilds drop", "PrefabMethods: edit.undo and edit.redo of a prefab write report the overrides the other open scenes' rebuilds drop" and `AssetMethodsTests.cpp`'s "AssetMethods: asset.setImportSettings reports the overrides its rebuild of the asset's instances drops" (C++; the review's finding 6), and `test_prefab.py`'s `test_rebuild_keeps_overrides_valid_together_and_reports_what_it_drops` (Python).

### 11. A script-field patch at instantiation names the instance's own members (W35.2; brief 13's third item)

`prefab.instantiate {components}`'s request preparation completes a Script slot entry that gives `Fields` without a `Script` from the prefab root's slot (`EditorMethodContext::CompletePrefabScriptOwner`), whose values are in prefab space. After the instantiation the handler maps them (`MapScriptPatchToInstance` in `PrefabMethods.cpp`): every value of an entry for a slot whose script the instance's slot holds that still equals the prefab root's slot value takes the instance's value, the same value with its references mapped to the instance's own members, so the patch merges into the slot as the instantiation mapped it. Then, when the call gives components, the instance's overrides are computed (`PrefabInstantiator::ComputeOverrides`): a reference they cannot record (an entity outside the instance named by a prefab-local ID) refuses the call with that error, located at `/components`, creating nothing, where before the commit kept the old record behind a warning ("PrefabMethods: prefab.instantiate refuses a patch whose reference the instance's overrides cannot record, creating nothing", the review's finding 7). The handler loads the prefab once for both, when the call gives components (finding 14). Added to W35.2 by the lead's ledger amendment of 2026-11-15 (`77d42dd0`). Tests: "PrefabMethods: a script-field patch at instantiation keeps the slot's other references on the instance's own members" (the brief's case: a patch of `Warden` alone leaves `Menus` naming the instance's own Menus, and the response's `_meta` holds no diagnostic) and the same check in `test_rebuild_keeps_overrides_valid_together_and_reports_what_it_drops`. Run alone on a build with the fix reverted (2026-11-16, the handler writing the completed patch unmapped and computing no overrides before the commit), it failed: `Menus` named the source entity's ID, not the instance's member, and the commit logged one warning; it passes with the fix.
