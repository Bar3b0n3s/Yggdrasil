# 0039 — Script callback budgets count the script thread's CPU time

- **Status:** accepted
- **Date:** 2026-10-29
- **Decided by:** the lead, as a fix straight to main outside the phase-2 milestones (ADRs 0032 to 0038 are reserved for M21 to M27 by ADR 0028's ledgers).
- **Context:** The runtime Luau watchdog measured a callback's budget (`Scripting.CallbackBudgetMs`, 1,000 ms by default; FeatureTest's Errors suite and `Tests/Data/Project/AllSettings.eproj` use 50 ms) in wall time, `lua_clock` (Architecture §11.1). On a loaded machine a legitimate callback was descheduled past its deadline and interrupted as `script exceeded 1000 ms in Game.OnStart (possible infinite loop)`, so the game state, and with it test outcomes and replay hashes, depended on machine load. The lead reproduced it: PreCommit's games suite failed Tetris's `LineClear` replay with a different `FinalStateHash`; a stress loop (fresh Debug editors with `--renderer vulkan` running `test.run` on a staged copy of Tetris beside 8 CPU burners) failed 5 of 15 runs, each time with `Game.OnStart` timing out; and the unit case "ProjectSettings: every AllSettings.eproj value is observed by its consumer" timed its 50 ms suite out the same way. The load-time VMs already measure the import thread's CPU time (ADR 0022 "Integration" item 5), but sampling it (`GetThreadTimes`, a system call) at every interrupt of a runtime VM, which Luau calls at every loop back-edge and call, costs too much. In the same PreCommit run the Debug automation suite, which takes 1,562 s on an unloaded machine, reached Test.py's 1,800 s bound beside its siblings' load.

## Decisions

1. **The budget counts the script thread's CPU time.** A callback times out once the CPU time its thread spent on it, since the outermost protected entry and less the credited host time, reaches the budget. The wall clock stays the fast path of every interrupt: `lua_clock` is compared with a wall deadline, the budget after the outermost entry, and since the thread's CPU time never advances faster than the wall clock, the budget cannot be spent before that deadline. Only when it passes does the watchdog sample the thread's CPU time (`ThreadClock::GetCpuSeconds`): with budget left, the wall deadline moves to now plus what is left and the callback continues; otherwise the timeout latches as before. The CPU clock is also sampled at each outermost entry and at a host period's boundaries, and never on a `gc >= 0` interrupt.
2. **What stays.** Nested callbacks inherit the outer deadline and budget; task and test-case resumes start fresh; host periods (`ScriptEngine::RunHostOperation`, ADR 0022 "Integration") exclude host work, now its CPU time too, and a period that begins past the wall deadline with budget left moves the deadline first; backwards or non-finite samples of either clock fail closed; the timeout message, its `ScriptError` kind and Dist's 5,000 ms minimum outside test runs (`ScriptWatchdog::ResolveCallbackBudget`) are unchanged.
3. **Injectable clocks.** `SandboxSpecification::CpuClockSeconds` (forwarded by `ScriptEngineSpecification` and the tests' `ScriptTestFixtureSpecification`) and `ScriptWatchdog::SetCpuClock` inject the CPU clock as `ClockSeconds` injects the wall clock, so unit tests drive both by hand. Empty, a VM uses `lua_clock` and `ThreadClock::GetCpuSeconds`. A supplied `ClockSeconds` without a `CpuClockSeconds` stays the budget's only clock, so the existing single-clock tests keep their exact samples.
4. **The load-time VMs stay as they are.** `ScriptImporter` passes the import thread's CPU time as `LoadTimeVmSpecification::ClockSeconds`, their only clock, sampled at every interrupt as before (an import runs only module tops). A load-time VM created without a clock, which only tests do, takes the runtime VMs' pair.
5. **The Debug automation suite's bound.** Without `--timeout`, Test.py bounds the Debug automation run with 3,600 s (`DEBUG_AUTOMATION_TIMEOUT_SECONDS`), more than twice its unloaded time; every other run keeps 1,800 s. The bound only catches a hang.

## Consequences

- A loaded machine no longer times a legitimate callback out, so test outcomes and replay hashes no longer depend on machine load through the watchdog, while a runaway loop, which spends its own thread's CPU time, still times out.
- A player's hitch is still bounded on an unloaded machine, where CPU time equals wall time. On a loaded one a callback may take longer than its budget in wall time, by the time the machine gave to other work.
- Windows accounts a thread's CPU time per clock tick (`GetThreadTimes`, about 15.6 ms), so a runaway loop can run up to one tick past its budget, and a callback within a tick of its budget can be charged that tick; `Docs/Backlog.md` lists this as an accepted limit. Linux and macOS keep their existing `ThreadClock` backends (`CLOCK_THREAD_CPUTIME_ID`).
- Every outermost protected entry (each callback, task resume and case resume) samples the CPU clock once, a system call; an interrupt stays one comparison until the wall deadline passes.
- ADR 0022 decision 6 names the Errors suite's watchdog faults as the coverage's only wall-clock influence; they are now CPU-time faults, which its pure-Luau spin loops still reach.
- Tests: "ScriptWatchdog: past the wall deadline a callback with CPU budget left continues and one without expires", "ScriptWatchdog: host work's CPU time is excluded from the budget", "ScriptWatchdog: a nested entry cannot extend the outer CPU budget", "ScriptWatchdog: a gc interrupt samples no clock and invalid CPU samples fail closed", "Watchdog: a callback whose wall time passes its budget while its CPU time stays below it finishes" (the regression test), "Watchdog: a callback that waits for another thread's work is not timed out by the wait", "Watchdog: a runaway loop whose CPU time passes its budget still times out" and "Watchdog: a GC interrupt samples neither clock"; `Tests/Automation/test_test_script.py` checks the automation suite's bounds.
