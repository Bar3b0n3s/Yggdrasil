### 2. The six components (R-UI-CORE, R-UI-RENDER, R-UI-TEXT, R-UI-LAYOUT)

A category of their own, **Ui**, after Scripting (ADR 0028's phase-2 ledger: phase 2's categories go after Scripting in landing order; M21's go before or after by landing), registered by `RegisterUiComponents` in `Scene/Registration/UiRegistration.cpp`, each at version 1 with the default flags (serializable, script-visible, editor-visible, removable), in this order:

| Component (registry name) | Fields (defaults, ranges) | Relations |
|---|---|---|
| `UiCanvasComponent` (`UiCanvas`) | `int32 SortOrder{0}`; `UiScaleMode ScaleMode{ConstantPixelSize}` (ConstantPixelSize, MatchHeight); `float ScaleFactor{1}` (0.01 to 100); `float ReferenceHeight{1080}` (1 to 100,000); `bool PixelSnap{true}` | excludes UiRect (declared by both, as RigidBody and CharacterController are) |
| `UiRectComponent` (`UiRect`) | `vec2 AnchorMin{0.5}`, `vec2 AnchorMax{0.5}` (0 to 1; AnchorMin at most AnchorMax per axis, a Validate hook with its Generate hook); `vec2 Pivot{0.5}` (0 to 1); `vec2 Position{0}`, `vec2 Size{100}` (±1,000,000 canvas units); `bool ClipChildren{false}` | excludes UiCanvas |
| `UiImageComponent` (`UiImage`) | `AssetRef<SpriteSheet> Sheet` (null: a plain rectangle of Color); `uint32 Frame{0}` (0 to 65,535); `color4 Color{1}`; `UiImageType Type{Simple}` (Simple, Sliced); `float BorderScale{1}` (0.01 to 1000); `UiImageFilter Filter{Point}` (Point, Linear) | requires UiRect |
| `UiTextComponent` (`UiText`) | `std::string Text`; `AssetRef<Font> Font` (null: the default font); `float Size{32}` (1 to 100,000 canvas units per em); `color4 Color{1}`; `TextAlignment Alignment{Left}` (the Text component's registry enum); `UiTextVerticalAlignment VerticalAlignment{Top}` (Top, Middle, Bottom); `bool Wrap{true}`; `float LineSpacing{1}` (0.1 to 10) | requires UiRect |
| `UiLayoutComponent` (`UiLayout`) | `UiLayoutKind Kind{Stack}` (Stack, Grid, Flex); `UiLayoutDirection Direction{Vertical}` (Horizontal, Vertical); `UiPadding Padding` (registry struct `UiPadding {Left, Top, Right, Bottom}`, each 0 to 1,000,000); `vec2 Spacing{0}` (0 to 1,000,000); `UiMainAlignment MainAlignment{Start}` (Start, Center, End); `UiCrossAlignment CrossAlignment{Start}` (Start, Center, End, Stretch); `uint32 Columns{0}` (0 to 1024); `vec2 CellSize{100}` (0 to 1,000,000); `bool Wrap{false}` | requires UiRect |
| `UiLayoutElementComponent` (`UiLayoutElement`) | `bool IgnoreLayout{false}`; `float Grow{0}`, `float Shrink{1}` (0 to 1000); `vec2 MinSize{0}` (0 to 1,000,000) | requires UiRect |

- **Why these six.** The plan's W22.1 names a canvas and rectangles (R-UI-CORE), images with 9-slice and clipping (R-UI-RENDER), text (R-UI-TEXT) and stack, grid and flex containers (R-UI-LAYOUT): a container component holds the three kinds (one component, so a container switches kind without losing its padding and alignment), and its children's flex weights and opt-out need a per-child component (UiLayoutElement). Clipping is a rectangle's flag (`ClipChildren`), so W22.2's ScrollView clips with it and needs no component of its own.
- **Elements.** A UI element is an entity with a UiRect below a canvas; its parent element is its nearest ancestor with a UiRect below that canvas, or the canvas (an entity without a UiRect in between is transparent to the layout). A UiLayout container places the elements whose parent element it is, in canonical order, so a grouping entity's elements are placed as the container's own (`UiLayoutComponent.h`, `UiRectComponent.h`, `UiLayout.h` and `UiContainerLayout.h` state the same rule). A UiCanvas below another canvas's element starts a canvas of its own, laid out over the whole scene image. A canvas has no rectangle of its own (it excludes UiRect), so a full-screen background is a child with stretched anchors. An entity may hold a UiImage and a UiText together (a button's background and label): the image draws first.
- **Left for later waves, with a stated reason:** a canvas's render mode (C22.3 adds `RenderMode` with World and Screen; a one-value enum now could not be covered by FeatureTest's gate 1, which needs a non-default value of every field); interaction (`RaycastTarget`, widgets, focus) and the canvas's theme font (C22.2). Fields are added while the components are unlanded, so no version changes within M22.
- **The demos' hashes.** No audited project holds a UI component (fact 8), so the components change no hash and need no canonical upgrade.

### 3. The UiLayout and FrameUiLayout phases, and the session's UI (R-UI-CORE; stream A)

- **Positions** (ADR 0028's phase-2 execution order; `PlaySessionPhase` in `Session/PlaySession.h`): **UiLayout** ends the fixed step, after PostStepTransformUpdate, so the layout matches the state the step left; **FrameUiLayout** follows FrameTransformUpdate and precedes AudioUpdate and RenderExtraction, so UI written in `OnUpdate` or `OnLateUpdate` is laid out as the frame draws it. The contract adds both enumerators and their names; stream A runs them (`EnterPhase`), in Play and Simulate, with or without a canvas, and adds them to "PlaySession: step order matches the documented sequence" and "PlaySession: Simulate mode skips the script and audio phases", which change with it (extended, not weakened). C22.2 and C22.3 insert TextLatch and UiInput after ApplyInput and UiEvents after StartFlush, and M21 and M23 their own phases, at the ledger's positions.
- **`UiSystem`** (`Scene/UiSystem.h`), owned by the session (`PlaySession::GetUi`): `LayoutStep` and `LayoutFrame` compute `ComputeUiLayout(scene, sceneSize)` into the step's and the frame's table; `GetLayout` is the later of the two (the frame's when a FrameUiLayout ran after the last UiLayout, the step's when none did), which W22.2's UiInput hit-tests and `ui.tree` reads, so a hit test depends only on the state, never on how many frames ran between two ticks (the ledger).
- **The scene resolution.** Both phases lay out at the session's scene resolution: in W22.1 the session's view size (`GetViewSize`: the game view in live play, the project's window size, `GetDeterministicViewSize`, in every deterministic session), the scene resolution of the default `RenderOutputSettings`. The later lander of M21 and M22 makes it the scene resolution M21's PixelPerfectCamera sets (the combined test, plan §3.5), in the session and in extraction alike.
- **Not simulated state.** Layouts are derived from the scene and the scene resolution; they never reach the state hash. W22.2's ui hash block (after physics2d, empty without a canvas) holds interaction state only.
- **The current scene's layout, always.** Outside the phase list (no observer reports it), `PlaySession::Activate` runs `LayoutStep` of the session's scene both before the scene's startup callbacks (`OnCreate`, `OnStart`) and after them, and so does a `Scene.Load` or `Scene.Reload`'s replacement of the scene at the end of a frame (`ConsumeRequests`: right after `ResetInteraction`, before the new scene's scripts start, and again after its startup): `GetLayout` is empty only before `Activate` and never describes a replaced scene, so the W22.2 Ui module reads the scene's own layout from its startup callbacks (a menu's `OnStart` can `Ui.SetFocus` its first button and `Ui.GetRect` its elements), `ui.tree {target: play}` right after `play.start` lists the UI, and the first UiInput after a load hit-tests the loaded scene (`UiSystem.h`, `PlaySession.h`; "PlaySession: the current UI layout is the scene's from the start and the loaded scene's right after a Scene.Load", and "Ui: a scene's startup callbacks read its own layout and take focus, at the session's start and after a Scene.Reload"). The layout before the startup callbacks was added by the review of W22.2 (its major, the lead's decision 1): until then the module read an empty table at `Activate` and the replaced scene's after a load or reload.

### 4. Layout (`Scene/UiLayout.h`; R-UI-CORE; stream A)

- **Space.** Scene pixels: x right, y down, origin at the scene image's top-left corner (ADR 0029 decision 8). A canvas covers the scene image; its scale is `ScaleFactor` (ConstantPixelSize) or `sceneHeight / ReferenceHeight` (MatchHeight); its size in canvas units is the scene resolution over its scale.
- **A rectangle in its parent's** (`UiRectComponent.h`): anchor rectangle `A = [P.Min + AnchorMin * P.Size, P.Min + AnchorMax * P.Size]`; size `(A.Max - A.Min) + Size`, each component at least 0; pivot point `A.Min + Pivot * (A.Max - A.Min) + Position`; rectangle `[pivot point - Pivot * size, + size]`; in canvas units, then times the scale from the canvas's origin. A UiLayout parent places its children instead (decision 5), unless a child's UiLayoutElement ignores the layout.
- **PixelSnap** rounds each corner to `floor(v + 0.5)` scene pixels after the scale and before the children are placed in it, so images and clips land on pixel corners.
- **Clip:** the intersection of `ComputeUiClipRect` of every ancestor element with ClipChildren; the element's own flag clips only its descendants. A rectangle covers the pixels whose centres it holds (`min <= x + 0.5 < max`), so `ComputeUiClipRect` is `ceil(v - 0.5)` at both ends (`UiClipRect`, `Renderer/UiDrawList.h`), each clamped to ±2^30 (`UiClipCoordinateLimit`; a NaN to -2^30) before it converts to int32. The registry's ranges do not keep rectangles inside int32 (a MatchHeight canvas scales a unit to up to the scene's height in pixels, and lengths add down a hierarchy), nor inside float's exact integers (2^24): such values are inexact but deterministic, and the clamp keeps the conversion defined.
- **Visible:** the rectangle, intersected with its clip and with the scene image, covers a pixel.
- **The table** (`UiLayoutTable`): the scene resolution; every effectively enabled canvas in draw order (ascending SortOrder, ties in canonical order) with its scale, size and node range; every effectively enabled element of each canvas in canonical order (a parent before its children, siblings in order: painter's order), with its canvas, parent, depth, rectangle, clip and visibility. An effectively disabled element and its subtree are left out and take no space in a container; a UiRect without a canvas ancestor is not laid out (project.validate's `UI_ELEMENT_WITHOUT_CANVAS`, decision 13).
- **Deterministic:** only IEEE-exact float operations (+, -, *, /, comparisons, floor and ceil) on the components' values, in canonical order; no asset access (decision 6). The acceptance "UI layout tables are byte-identical across configurations" is checked by the layout cases' exact expected values in the Debug and Release unit runs, and by the UI replays of W22.2 in the four runs.

### 5. Containers (`Scene/UiContainerLayout.h`; R-UI-LAYOUT; stream D)

`LayoutUiContainer(layout, containerSize, children)` places a container's children (the elements whose parent element it is, decision 2) in canvas units; the header states every rule. In short: the inner rectangle is the container's less Padding; a child's preferred size is its UiRect Size (its UiLayoutElement adds MinSize, Grow and Shrink); **Stack** puts the children one after another along Direction with Spacing, the run placed by MainAlignment (an overflowing run starts at the inner start); **Flex** shares the line's free space by Grow or takes the overflow back by Shrink times size (never below MinSize, without redistribution; a line whose total of Shrink times size is 0 does not shrink and overflows), with Wrap starting new lines, each line as tall as its tallest child; **Grid** gives each child a cell of CellSize, Columns per row (Horizontal) or column (Vertical), or with Columns 0 as many as fit, clamped to 1 to 1024 (1024 when the main axis's cell plus spacing is 0); CrossAlignment places each child across its line (Stretch fills it, a Stack's or Flex's child never below its MinSize; such a child larger than its line follows the same formula, so Center overflows both sides equally and End overflows the start, accepted at W22.1's integration). No rule divides by 0, and every placed size is at least 0. A container's own size never follows its children (decision 6). A pure function, called by stream A's `ComputeUiLayout`; the header is public so the unit tests reach it (a Scene `Private/` header is Scene's alone, Lint's `include-private`).

### 6. Text measurement and character ranges (R-UI-TEXT, R-UI-L10N's ranges; stream B)

- **Beside the frozen `TextLayout.h`** (ADR 0013 decision 11), which keeps laying out TextComponent unchanged: `Renderer/TextMeasurement.h`, `MeasureText(fonts, text, options)` and `MeasureTextSize`, from a font chain's metrics to positioned glyphs in pixels, lines (their byte ranges, left, width, top and baseline) and a block size, with word wrapping (`TextWrap::Word` breaks at spaces, a word wider than `MaxWidth` between glyphs), line feeds, `LineSpacing` and alignment within `MaxWidth` (or the widest line). The header states the contract's rules, and `TextMeasurement.cpp`'s file comment and Architecture §8.10 the finer wrapping rules stream B implemented beside them (W22.1's integration: which space of a run a line breaks at, that a line never wraps empty, where skipped bytes and carriage returns belong, one skipped codepoint per ill-formed byte, the 2^32 - 1 byte bound); the output is identical for equal inputs in every configuration.
- **Shaping and bidi are reserved for W22.3** behind these signatures: `TextDirection` (Auto, LeftToRight, RightToLeft; every value lays out left to right in W22.1), `TextMeasuredGlyph::ByteOffset` (a cluster's first byte once HarfBuzz shapes clusters) and the **font chain** (a codepoint takes the first font of the chain with a glyph for it; W22.1's callers pass one font, W22.3's fallback chain more). C22.3 pins HarfBuzz and SheenBidi and puts them inside `MeasureText`.
- **Scene does not include it.** ADR 0028's ledger adds the measurement header to SnapshotHeaders "if Scene's layout includes it"; it does not: render extraction reads no asset (fact 3), so Scene's layout needs no font, and a rectangle never follows its content (a label is not sized to its text, an image not to its frame, a container not to its children). Text wraps and aligns inside the rectangle it is given, which the renderer lays out with its fonts, as it lays out TextItems (decision 7). The header includes nothing beyond Core, Asset, glm and the standard library, so a later contract may list it if content sizing is ever wanted. Recorded as an accepted limit (Backlog §6).
- **Character ranges:** Latin-1 is already baked (fact 4). Per-font ranges are a new import setting, frozen here and landed by stream B with the registry change: `FontImportSettings.Ranges`, an array of the registry struct `FontCharacterRange {First, Last}` (UInt32 codepoints, `0x20 <= First <= Last <= 0x10FFFF`, at most 64 ranges and 65,536 codepoints in all, located Validation errors otherwise), baked with ASCII and Latin-1 (codepoints the font lacks left out, as today); **FontImporter version 4** (the ledger's "4 and up": every cached atlas is rebuilt once, byte-identical for a font without ranges). `FontData` stays at format 1 in W22.1 (the glyph list grows; C22.3 takes FontData 2 if shaping needs glyph indices). The default font takes no ranges, so its atlas, and the Text golden, do not change.

### 7. The draw list and the Ui pass (R-UI-RENDER; stream C)

- **`Renderer/UiDrawList.h`** (in SnapshotHeaders and Scene's Headers): `UiDrawList {Items, Annotations}` over a memory resource like the snapshot's containers (M18's R-ARENA); a `UiDrawItem` is an image or a text of one element in scene pixels with its entity, rectangle, colour and clip, and for an image its sheet handle, frame, type, border scale (scene pixels per texel) and filter, for a text its string, font handle, size in scene pixels per em, alignments, wrap and line spacing (the draw list's own enums, since the header cannot include Scene); a `UiAnnotation` is a capture's outline or label (decision 9). `RenderSnapshot::Ui` follows `Output` (ADR 0028's ledger).
- **Extraction** (`ExtractRenderSnapshot`, `Scene/UiExtraction.h`'s `AppendUiDrawItems`, stream C's code in `RenderExtraction.cpp` after M23's paths): for the Primary and Entity camera sources (the game view and a camera's view; a view without a primary camera draws its UI, as it draws its screen texts), every canvas laid out at the scene resolution of the snapshot's Output (the view's size by default) and each visible element's image, then its text when not empty, with the canvas's scale applied to the lengths. The editor's scene view (Explicit) draws no game UI; W22.2's authoring overlay decides what the editor shows there. Extraction lays out afresh: the layout is a pure function, so the game view's draw list equals the session's frame layout at the same scene resolution, and a screenshot at another size lays out at its own (fact 3: every host gets UI without a change).

### 8. `ui.tree` (R-UI-AUTO; stream E)

- **`ui.tree {canvas?, depth?, format?, width?, height?, target?}`** (`Engine/Automation/Methods/UiMethods.h`), shared by the editor and the Runtime: the target scene's UI laid out in scene pixels. The play scene reads the session's current layout (`UiSystem::GetLayout`) at its scene resolution unless `width` and `height` ask for another; the edit scene is laid out at `width` x `height`, by default the project's window size (`GetDeterministicViewSize`, the view of every deterministic session). `canvas` (an EntityRef) narrows it to one canvas; `depth` limits the levels below each canvas (0: unlimited); `format` is `SceneTreeFormat`'s Text or Json.
- **The result:** `{scene, width, height, text | elements}`; an element (`UiTreeEntry`) is `{id, name, path, canvas, parent, depth, components, rect, sortOrder, scale, clipped, clip, visible, text}` (`sortOrder` and `scale`, the scene pixels per canvas unit at the resolution laid out at, are a canvas's, 0 for an element, as the text outline prints them) (rectangles as `UiPixelRect {x, y, width, height}`; the text cut to 256 bytes at a UTF-8 boundary) plus the **interaction fields reserved for W22.2**, reported as their defaults until then: `interactable`, `focused`, `hovered`, `pressed` and `widget` (the widget kind W22.2 names; W22.3's `TextInput`). The text outline: a header line `<file name>  rev <n>  <width>x<height> scene pixels  <count> elements`, then per canvas `<name> <8 hex> UiCanvas(sort <n>, scale <s>)` and per element a box-drawn line with its name, 8 hex digits, short component forms (`UiImage(<sheet path>#<frame>)`, `UiText("<text>")`, `UiLayout(<kind> <direction>)`), its rectangle `(x,y wxh)` and `clipped` or `hidden`.
- **Flags:** a tool (`ui_tree`; §13.8: 66 proxied tools), `AvailableInRuntime`, `AllowedInBatch`, `SupportsSceneTarget` (the scene-target inventory's Target: it reads the addressed scene, ADR 0031 decision 16), not mutating, no dry run (a read). Errors: the target's and `canvas`'s (ResolveEntity at `/canvas`); InvalidArgument at `/canvas` for an entity without a UiCanvas, and for one of `width` and `height` alone.
- **Parity:** the UI the editor shows (its game view, decision 7) is read by `ui.tree` and captured by `viewport.screenshot`; the method has its C++ round trip ("UiMethods: ...") and its Python tests (`Tests/Automation/test_ui.py`, the Runtime's included), and gate 5.

### 10. String tables (R-UI-L10N; stream L)

- **The type:** `AssetType::StringTable`, 12 on M22's branch (ADR 0028's phase-2 ledger: the first of M21 and M22 to land takes 12, the other 13, renumbering its own at its merge and rebuilding its checkouts' cooked caches), spelled `StringTable` in `.meta` files, the script API (`Field.Asset("StringTable")`) and automation. No placeholder table.
- **The file:** `.stringtable`, format `StringTable` version 1, canonical JSON written in full (§6), an authored extension (load and save byte-identical; `ModuleRules.json`'s `Json` list). The data (`Asset/StringTableData.h`): the registry structs `StringTable` (`StringTableData`: `Locales`, `Entries`) and `StringTableEntry` (`Key`, `Values` a Map from locale to string); the header's conventions are the rules: locales are 1 to 35-byte tags of ASCII letters, digits and '-' starting with a letter, unique ignoring ASCII case, the first the fallback; keys 1 to 256 bytes of UTF-8 without control characters, unique; values at most 16,384 bytes of UTF-8 (line feeds and tabs allowed); every entry has the fallback's value; at most 64 locales and 65,536 entries; `ValidateStringTable` reports one located issue per violation in document order.
- **Lookups** (`ResolveStringTableLocale`, `FindStringTableEntry`, `FindLocalizedString`): the table's locale equal to the requested one ignoring ASCII case, else the one equal to its language (before the first '-'), else the fallback; the entry's value for it, or the fallback's. Byte-wise, no locale database, deterministic.
- **The cooked format:** a binary payload, FormatVersion 1, little-endian (the header documents it byte for byte): the locales, then the entries **sorted by key** (so a loaded table binary-searches), each with a presence byte and string per locale. The reader checks every count against its limit and the bytes left, refuses a presence byte other than 0 or 1, entries out of order and trailing bytes, then validates. Its fuzz target, `StringTableData` (`Tests/Data/Fuzz/Targets.json`, added by the contract), mutates the document and the cooked form: the plan placed it in W22.3's stream E, but the reader lands in W22.1, and ADR 0028 decision 12 has a wave that adds a reader of external input run its fuzz case in its targeted unit run, so it moves to stream L (accepted by the lead, 2026-10-29).
- **The importer** (`AssetPipeline/Importers/StringTableImporter.h`): id `StringTable`, version 1, `.stringtable`, no settings, strict (an unknown member fails the import), one artifact, `Import.Dependencies` set explicitly to `GetStringTableDependencies` (none: a table references no asset; ADR 0028's ledger). Registered with its source format (`Asset/SourceFormats.cpp`, gate 9) and its loader (`RegisterBuiltinLoaders`); `ReadCookedArtifact` accepts the type. No validation code (a bad table fails its import).
- **Authoring:** `asset.create {type: StringTable, path, values?}` (`AssetCreateType::StringTable`, appended), `asset.getProperties` and `asset.setProperties` as for a sprite sheet (refusals located under `/values`); the content browser's Create popup gains "String table" after "Sprite sheet" (ADR 0028's ledger: the create list in landing order), which submits `asset.create` without values (a table with the locale "en" and no entries); tables show `EditorIcon::StringTable` (implemented by the contract). The reference generator documents the format (`FileFormats.md`, `Schemas/StringTable.schema.json`).
- **Export:** the exporter cooks every registered asset; M19's pruning follows `Import.Dependencies` and the literal `Assets.Load` scan, so a table a script loads by literal path is kept.

### 11. `Loc` and the locale setting (R-UI-L10N; stream L)

### 12. W-CLOCK: the same-frame input preview (stream K)

- **Acceptance** (Roadmap M22): "A frame that runs no step sees new input while the step view is unchanged."
- **`PlayInput`** (`Session/PlayInput.h`): `SetFramePreview(bool)` and `IsFramePreviewEnabled()` (off at creation). With the preview on, `LatchFrame` latches the frame view from the devices' state with the **device events** queued for `GetNextTick()` (`QueueDeviceEvent`'s, in queue order, as `ApplyTick` will apply them) applied on a preview copy; the step view, the applied state, the queue and the next `ApplyTick` are unchanged, and a previewed edge is reported once by the frame view (the frame after the tick that applies it sees no second press). Injected events (`Queue`: automation, replays, `Test.Inject*`) are never previewed: they belong to the tick that applies them.
- **The session's policy** (`PlaySession`'s LatchFrame phase): the preview is on only while the session is neither in lockstep nor recording, so lockstep, recording, replaying and test sessions latch exactly as before and every replay keeps its hash (a recording replays with the frame views its ticks gave). The policy, not the hosts, keeps the preview out of deterministic runs: a lockstep or recording session can still receive device input (the Runtime's window queues it in lockstep, the editor's Game view while recording), and the policy switches the preview off for both; replay and test sessions receive no device input (their hosts queue none while a replay or FeatureTest owns input). So the preview never touches a deterministic run. (Corrected by W22.1's review: this bullet first said that deterministic sessions receive no device input at all.)
- **The ledger:** LatchFrame changes in place (no PlaySessionPhase). Stream K amends Architecture §4.3 and §5.7's frame step 1, and W22.1's integration closes Backlog §5's row.

### 21. The widget components and the members C22.2 adds (R-UI-WIDGETS, R-UI-SCROLL, R-UI-THEME)

Appended to the Ui category after UiLayoutElement (decision 2; ADR 0028's ledger: no existing category gains a component), each at version 1 with the default flags, each requiring UiRect and excluding the other three (declared by both sides, as the C22.1 review's m1 requires), in this order:

| Component (registry name) | Fields (defaults, ranges) |
|---|---|
| `UiButtonComponent` (`UiButton`) | `bool Interactable{true}`; `bool Focusable{true}` |
| `UiToggleComponent` (`UiToggle`) | `Interactable`, `Focusable` as UiButton's; `bool IsOn{false}`; `EntityRef Graphic` (null: none) |
| `UiSliderComponent` (`UiSlider`) | `Interactable`, `Focusable`; `float Value{0}`, `Min{0}`, `Max{1}` (each ±1,000,000; a Validate hook requires Min < Max, with its Generate hook); `bool WholeNumbers{false}`; `float Step{0}` (0 to 1,000,000; 0: a tenth of the range; with WholeNumbers rounded to a whole number of at least 1, whatever Step says); `UiLayoutDirection Direction{Horizontal}` (the registry enum of decision 2); `EntityRef Fill`, `EntityRef Handle` |
| `UiScrollViewComponent` (`UiScrollView`) | `bool Interactable{true}`; `bool Focusable{false}`; `EntityRef Content`; `bool Horizontal{false}`; `bool Vertical{true}`; `vec2 ScrollPosition{0}` (0 to 1,000,000 canvas units); `float ScrollStep{40}` (0 to 1,000,000) |

- **Why one component per widget, each with Interactable and Focusable.** An element is one widget (ui.tree's `widget`, the exclusions), every widget needs both flags, and a field-less marker component cannot be registered (`IsReflectableComponent`: a built-in component is non-empty). A shared selectable component would make an element's widget two components and leave a Button with nothing of its own.
- **Value as read.** A slider's Value is not validated against its range, so a script that moves the range and then the value never fails between the writes; readers clamp it (`ReadUiSliderValue`), with WholeNumbers then round it (`floor(v + 0.5)`) and keep it to the range's whole numbers (`[ceil(Min), floor(Max)]`, or Min when the range holds none), so the value as read never leaves `[Min, Max]` nor its position `[0, 1]`; interaction writes the value as read. A scroll view's ScrollPosition is read clamped to the content's overflow the same way (`ClampUiScrollPosition`).
- **Parts by EntityRef.** Graphic, Fill, Handle and Content name elements below the widget; prefab instantiation and duplication remap them as every EntityRef field (§5.5). A part that is null or not an element below its widget in the same canvas is ignored (decision 26) and reported (decision 35).
- **The members added to W22.1's components** (unlanded components, so no version changes, decision 2), frozen in the headers and registered by their streams (decision 20): `UiCanvasComponent::Font` (`AssetRef<Font>`, null), `Theme` (`UiTheme`, decision 25) and `DefaultFocus` (`EntityRef`, null: where navigation starts, decision 23; remapped by prefab instantiation and duplication as every EntityRef field), registered after PixelSnap in that order by stream C with the registry struct `UiTheme`; `UiImageComponent::RaycastTarget` (after Filter) and `UiTextComponent::RaycastTarget` (after LineSpacing), `bool{true}`, registered by stream A.
- **The demos' hashes.** No audited project holds a UI component (decision 2), so none of this changes a hash.

### 22. Pointer targets and the hit test (R-UI-INPUT; stream A)

`Scene/UiInteraction.h`'s file comment is the rule: a pointer target is a Visible element holding a widget, or a UiImage or UiText whose RaycastTarget is set; a point is over it when it lies in its rectangle (Min <= p < Max) and, when it is Clipped, in its clip; the topmost target is the last in the table's draw order; its widget is the nearest element at or above it, within its canvas, holding a widget. A target without a widget blocks the pointer (it is over the UI, `Ui.IsPointerOverUi`, and reaches nothing), so a panel's background keeps a click from the buttons of a lower canvas, while an image with RaycastTarget off lets it through. Empty grouping rectangles are no targets. `HitTestUi` returns the target and its widget.

### 23. Focus and navigation (R-UI-INPUT; stream A, the reveal stream C)

- **Focusable:** in the layout table, not Hidden, with a rectangle of positive width and height, holding a widget whose Interactable and Focusable are set. Clipping and the scene image do not matter, so a list item scrolled out of its scroll view stays focusable and focusing it scrolls it into view.
- **Directions** (`FindUiNavigationTarget`): from the focused element's centre, the focusable element ahead (a positive along-distance a) with the smallest a + 2 × b (b the across-distance), the first in draw order on a tie; nothing ahead keeps the focus (no wrap-around); with nothing focused, the default focus (below) or nothing. Every canvas's elements take part.
- **Next and Previous** (`FindNextUiFocus`): draw order from the focused element, wrapping; Previous is Next pressed with a Shift key down; with nothing focused, the default focus either way, or nothing.
- **Where navigation starts** (the lead's decision on the review of C22.2, replacing "with nothing focused, the first focusable element in draw order"): the navigation commands (the four directions, the stick's directions, Next and Previous) move focus only from a widget that has focus. With nothing focused, a command focuses the layout's default focus, the `DefaultFocus` of the last canvas in draw order whose `DefaultFocus` is focusable (a pause menu's canvas over the HUD's wins), whatever its direction, and does nothing when no canvas names one. Submit acts only on the focused widget. Focus otherwise comes from a pointer press on a focusable widget, never one whose Focusable is off, and from `Ui.SetFocus`. So a game whose play uses the arrows and Space (Tetris among them) keeps them while nothing has focus: its HUD buttons, not Focusable, are clicked without taking keyboard focus, and its menus opt in through their canvas's `DefaultFocus` or `Ui.SetFocus`. The reading of Roadmap M22's "every widget works by keyboard and gamepad": it holds for a UI whose canvas names its `DefaultFocus` (or whose script sets focus), which is how the keyboard-and-gamepad case and the Ui replay start; neither the Roadmap's M22 section nor the plan's R-UI-INPUT row ("Focus and navigation") asks for navigation without a starting focus, so nothing stays out and the Backlog gains no line.
- **The stick:** the left stick of the connected gamepad whose stick has the largest magnitude gives a direction when its larger axis is at least 0.5 (`GetUiStickDirection`); each new direction is one press, kept in the interaction state (`UiInteractionState::Stick`).
- **The pointer and focus:** a press on a focusable widget focuses it; a press elsewhere, a widget whose Focusable is off included, leaves focus as it is.
- **Reveal:** focus moved by navigation or `Ui.SetFocus` into a scroll view's content scrolls every scroll view holding it the least that shows it (`RevealInUiScrollViews`), against a layout of the scene as it is at the move (`ComputeUiLayout` at the current layout's scene size, never stored), so a scroll position changed since the current layout was made (by this UiInput's wheel, drag, step or earlier reveal, or by a script) is the one the reveal starts from (the review of W22.2, the lead's decision 2; layout is a pure function of the scene, so this stays deterministic).
- **Consumed directions:** a focused slider takes the two directions along its Direction, and a focused Focusable scroll view the directions of its scrolling axes; the other directions navigate.
- **What the plan's risk 8 asks:** focus and navigation run only in the UiInput phase, from the tick's latched step view, against the current layout (decision 3's rule: the later of the step's and the frame's), so they depend only on the state.

### 24. The UiInput phase and the interaction state (R-UI-INPUT, R-UI-WIDGETS; stream A, the widgets' behaviours streams B and C)

- **Position** (ADR 0028's phase-2 execution order): UiInput after ApplyInput, before StartFlush; C22.3's TextLatch goes between ApplyInput and UiInput. Play and Simulate, with or without a canvas: interaction writes components (simulation), so Simulate runs it and drops the events (no scripts). Without a canvas it reads no input (below).
- **Input** (`UiInputFrame`, built by the session from the step view): the mouse's position mapped from view coordinates to scene pixels through the session's output mapping (the identity of the default `RenderOutputSettings` in W22.2; the later lander of M21 and M22 makes it PixelPerfectCamera's, with the scene resolution, decision 3), Mouse.Left's state and edges, the step's scroll delta, the Ui settings' commands pressed (decision 30) and the left stick. The pointer is the mouse only (an accepted limit, Backlog §6).
- **The state machine** (`UiSystem::ProcessInput`; `UiSystem.h` states it step by step): stale state cleared; hover; press (focus, a slider's value, a scroll view's drag); drag; release (a button's click or a toggle's flip over the pressed widget, never elsewhere); the wheel (the innermost interactable scroll view at or above the hit target); the stick's edges; navigation in the order Next, Previous, Up, Down, Left, Right; Submit (activation of the focused widget, nothing without one); Cancel (at the focused element, else the last canvas). Submit acts on its press edge and shows no Pressed state.
- **Without a canvas** (the review of C22.2's major): when the current layout holds no canvas, the stale-state step clears the state's ids (raising Focus or Hover false at an entity the scene still holds), the rest of the state returns to its default and the phase ends, reading no pointer, wheel, stick or binding. So the interaction state of a scene without a canvas is always empty, and its hash never holds a ui block (decision 29); before this rule, a held stick set `UiInteractionState::Stick` in every scene.
- **Drags:** a slider's press sets DragOrigin to the pointer and DragStart to zero; a scroll view's sets DragOrigin to the pointer and DragStart to its ScrollPosition as read; whenever Dragged is cleared (the release, or the stale-state step), DragOrigin and DragStart return to zero, so a drag leaves nothing in the state once released.
- **The widgets' behaviours** (`Scene/UiWidgets.h`): `ActivateUiWidget`, the slider's `SetUiSliderFromPointer` and `StepUiSlider` (stream B), and the scroll view's `ScrollUiScrollView`, `DragUiScrollView`, `StepUiScrollView`, `RevealInUiScrollViews` and `FindUiScrollView` (stream C). Each writes its widget's component in the scene (so the scene's serialization, and so the state hash, holds what interaction changes) and raises its event only when a value changed.
- **The interaction state** (`UiInteractionState`: Focused, Hovered, Pressed, Dragged, DragOrigin, DragStart, Stick, PointerOverUi) lives in the session's `UiSystem`, outside the scene; a scene replacement resets it with the layouts (`ResetInteraction`).
- **Determinism:** IEEE-exact float operations in canonical order (decision 4's rule), from latched input only.
- **Two rules stream A chose, accepted at W22.2's integration** (`UiSystem.cpp` states both): no Focus or Hover event (false) is ever raised at an entity the scene no longer holds, in the stale-state step as in the hover step and a focus move (step 1's rule applied throughout; dispatch would drop such an event anyway, decision 27); and a press of the step that the pointer still holds is not released by a release edge of the same step, since the step view's edges carry no order and the pointer being down says the press came last.

### 25. Theme: state tints and the canvas font default (R-UI-THEME; stream C)

- **`UiTheme`** (registry struct, `UiCanvasComponent.h`): `color4 Normal{1}`, `Hovered{0.85, 0.85, 0.85, 1}`, `Pressed{0.6, 0.6, 0.6, 1}`, `Focused{0.75, 0.85, 1, 1}` (a visible focus for gamepad play), `Disabled{0.5, 0.5, 0.5, 0.5}`, each component 0 to 1, linear with straight alpha. A canvas's `Theme` tints its widgets: no per-widget override (an accepted limit; another canvas or a script colour gives another look).
- **The tint** multiplies, component by component, the colour of a widget element's own UiImage at extraction (`AppendUiDrawItems`); its texts and its children's images keep theirs (an accepted limit, Backlog §6). The state, first match: Disabled (Interactable false), Pressed, Focused, Hovered, Normal. The state comes from `RenderExtractionRequest::UiInteraction`, the session's state, which the session sets for its game view and `ExtractView` (so `viewport.screenshot` of the play scene shows it without a change to `ScreenshotMethods`); every other view (the edit scene, its screenshots, the UI preview) draws Normal, or Disabled when not interactable.
- **The canvas font default:** a UiText whose Font is null takes the Font of the canvas it belongs to (the nearest canvas above it), and a null canvas Font is the default font, as before. Extraction writes the resolved handle to the draw item; the Ui pass is unchanged.
- **No GPU object:** tints are the draw items' colours through M18's QuadBatcher; W22.2 creates no GPU object, so no recreation hook or loss test is added (plan §7 item 3).

### 26. The widgets' layout rules (R-UI-WIDGETS, R-UI-SCROLL; streams B and C)

`Scene/UiLayout.h`'s file comment states them; each applies only to a part that is an element below its widget in the same canvas:

- **UiSlider** (stream B): its Fill's and Handle's anchors along its Direction follow the value's normalized position t, in place of their own, before they are placed in their parent element (Horizontal: Fill's AnchorMin.x 0 and AnchorMax.x t, Handle's both x anchors t; Vertical: Fill's AnchorMin.y 1 - t and AnchorMax.y 1, Handle's both y anchors 1 - t). Every other UiRect field is the part's own. The slide rectangle a pointer sets the value along is the Handle's parent element's, else the Fill's parent's, else the slider's own.
- **UiToggle** (stream B): while IsOn is false, its Graphic and that element's subtree are Hidden (`UiLayoutNode::Hidden`, new) and so not Visible: laid out, never drawn, hit or focusable.
- **UiScrollView** (stream C): it clips its descendants as ClipChildren does, whatever ClipChildren says; Content is laid out as usual, then moved with its subtree by -offset canvas units (times the canvas's scale), offset being ScrollPosition clamped per axis to [0, max(0, content size - view size)], 0 on an axis that does not scroll; with PixelSnap the moved corners snap again.

The layout stays a pure function of the scene and the scene resolution (decision 4); rectangles still never follow their content (decision 6), so a list's content element is given its height.

### 27. UI events, the UiEvents phase and bubbling (R-UI-EVENTS; stream B)

- **The events** (`UiEventKind`, raised by UiInput and `Ui.SetFocus`, queued in `UiSystem` in the order raised): Click (a button activated), ValueChanged (a toggle's IsOn or a slider's Value changed by interaction), Focus (gained or lost), Hover (the pointer entered or left an interactable widget), Cancel, Scroll (a scroll view's position changed by interaction). Writes by scripts or automation raise none.
- **The UiEvents phase** (ADR 0028's position: after StartFlush, so a new instance runs `OnStart` before its first UI callback, and before FixedUpdate, which sees the interaction): the session takes the queue and `ScriptEngine::DispatchUiEvents` delivers it; Play only.
- **The callbacks** (frozen here, registered by stream B in `Bindings/Script.cpp` after `OnHotReload`, with their names appended to `ScriptData.cpp`'s reserved field names, both in landing order by the ledger; all modes, Runtime and Test):

  | Callback | Signature | Description |
  |---|---|---|
  | `OnUiClick` | `(self: ScriptInstance, element: Entity) -> boolean?` | "Called when a UI button is clicked or submitted, at its entity, then bubbling to its ancestors; return true to stop it." |
  | `OnUiValueChanged` | `(self: ScriptInstance, element: Entity, value: boolean \| number) -> boolean?` | "Called when interaction changes a UI toggle's IsOn (a boolean) or a UI slider's Value (a number); bubbles like OnUiClick." |
  | `OnUiFocus` | `(self: ScriptInstance, element: Entity, focused: boolean) -> boolean?` | "Called when a UI element gains (true) or loses (false) keyboard and gamepad focus; bubbles like OnUiClick." |
  | `OnUiHover` | `(self: ScriptInstance, element: Entity, hovered: boolean) -> boolean?` | "Called when the pointer enters (true) or leaves (false) an interactable UI widget; bubbles like OnUiClick." |
  | `OnUiCancel` | `(self: ScriptInstance, element: Entity) -> boolean?` | "Called when Cancel is pressed, at the focused UI element (or the last canvas when none is focused); bubbles like OnUiClick." |
  | `OnUiScroll` | `(self: ScriptInstance, element: Entity, position: vector) -> boolean?` | "Called when interaction scrolls a UI scroll view, with its new ScrollPosition (x, y, 0); bubbles like OnUiClick." |

- **Bubbling** (ADR 0031 decision 18, on M20's slots): every UI event bubbles, from its element (the callbacks' `element`) through each ancestor; at each entity every started, enabled instance whose behaviour defines the callback receives it in slot order; after an entity where any of those returned true the event goes no further, that entity's other slots included. An event whose element the scene no longer holds, or holds pending destruction, when its turn comes is dropped (as the stale-state step raises Focus or Hover false only at an entity not pending destruction); during an event's walk, an ancestor that a callback of that event destroyed, so pending destruction when the walk reaches it, is passed over and the walk goes on to its parent (a pending entity's subtree is pending with it, so a live element's ancestors are live when its walk starts). A callback's fault disables only its instance (§11.7) and the event goes on. `ScriptEngine::DispatchUiEvents`'s comment states it.
- **Two rules stream B chose, accepted at W22.2's integration** (`ScriptEngine.cpp`, `ScriptInstances.cpp`, Architecture §11.3, and `DispatchUiEvents`'s comment, amended by the lead): an event walks the ancestors its element had when its walk started (a snapshot, so a callback that reparents an entity neither lengthens nor loops the walk, as a live re-read could); and only the boolean `true` stops it, any other value, truthy or not, letting it bubble on.
- **Coverage:** stream B adds a `RunUiBindingsCoverage` scenario to "ScriptApi: every registered function ... has a test" and the six callbacks to `RunBehaviourCallbacksCoverage`, in the same change that registers them (fact 6), and FeatureTest's suites call them in every mode (gate 3, decision 36).

### 28. The Ui script module (R-UI-EVENTS; stream B)

Frozen here and registered by stream B after `Loc` in `RegisterBindings.cpp` (decision 20), Runtime and Test environments, all modes:

| Member | Signature | Description |
|---|---|---|
| alias `UiElementRect` | `{Min: vector, Max: vector}` | "A UI element's laid-out rectangle in scene pixels: its top-left (Min) and bottom-right (Max) corners as (x, y, 0), x right and y down." |
| module `Ui` | | "The game UI's interaction state in the running scene: keyboard and gamepad focus, the widget under the pointer and the one it presses, and where elements were laid out. UI events reach behaviours through the OnUi callbacks, which bubble from the element to its ancestors." |
| `GetFocus` | `() -> Entity?` (read) | "Returns the UI element that has keyboard and gamepad focus, or nil." |
| `SetFocus` | `(element: Entity?) -> ()` (mutates) | "Moves focus to element, a laid-out, interactable and focusable UI widget, or clears it with nil; OnUiFocus follows in the next UiEvents phase. Any other element raises a located error saying why." |
| `GetHovered` | `() -> Entity?` (read) | "Returns the interactable UI widget under the pointer, or nil." |
| `GetPressed` | `() -> Entity?` (read) | "Returns the UI widget the held pointer pressed, or nil." |
| `IsPointerOverUi` | `() -> boolean` (read) | "Returns whether the pointer was over a UI image, text or widget that catches it at this tick, so gameplay can ignore clicks meant for the UI." |
| `GetRect` | `(element: Entity) -> UiElementRect?` (read) | "Returns element's rectangle in the current UI layout, in scene pixels (which are view coordinates unless the output is upscaled), or nil when it is not laid out." |

The module reaches the session's `UiSystem` through `IScriptHost::GetUi` (implemented by the contract, null by default; the play session's host returns `PlaySession::GetUi`, stream B). Without one (an edit evaluation) the reads report nothing and `SetFocus` raises. `Ui.SetFocus` changes focus at once (`UiSystem::SetFocus`) and its Focus events are dispatched at the next UiEvents phase, behind those already queued. Stream B's rules, accepted at W22.2's integration: `GetFocus`, `GetHovered` and `GetPressed` return nil for an entity the scene holds pending destruction (as for one it no longer holds), and `SetFocus` with the current focus, or with an element it refuses, reports no external mutation.

**Amended by the review of W22.2** (the lead's decision 2, a contract change): `UiSystem::SetFocus` checks and reveals against a layout of the scene as it is at the call (`ComputeUiLayout` at the current layout's scene size, never stored), not the current layout, which UiInput's hit test and `Ui.GetRect` keep reading (what was drawn). So a menu that a callback shows (`SetActive(true)`), creates or moves takes focus in that same callback, and a scroll position written since the last layout is the one the reveal moves from (decision 23). `UiSystem::CheckFocus` (new, const) answers the same check without a change: whether `SetFocus` would change focus, or its refusal; the Ui module asks it first, so the rule above (no mutation reported for the current focus or a refused element) holds without a second check of its own. The refusal names why at the call ("not laid out", hidden, no widget, not interactable, not focusable, or no area), which is now true at the moment it is raised; before the amendment an element enabled earlier in the same tick was refused as not laid out below an enabled canvas, which it was. The registered description is unchanged ("a laid-out, interactable and focusable UI widget" is laid out at the call).

### 29. The ui state-hash block (R-UI-DET; stream A)

- **Position** (ADR 0028's ledger): after the native block now, after M21's physics2d block once a merge inserts it before the ui block; the order is fixed whichever lands first.
- **Content** (`UiSystem::AppendStateHash`): nothing while the interaction state is empty (`UiInteractionState::IsEmpty`: nothing focused, hovered, pressed or dragged, the stick at rest, the pointer over no target) and the event queue is empty; otherwise the 8 ASCII bytes "UiState1", Focused, Hovered, Pressed and Dragged (their UUID values), DragOrigin.x, DragOrigin.y, DragStart.x and DragStart.y (each float's bit pattern, zero-extended), Stick and PointerOverUi, then the queue: its event count, then each event's Kind, Target (its UUID value), Flag, HasNumber, Number, Vector.x and Vector.y (the floats' bit patterns), in the order queued, each value with `UpdateU64`. The queue is in the block because it crosses a tick boundary whenever a script calls `Ui.SetFocus` after the tick's UiEvents phase (from `OnFixedUpdate`, a task, `OnUpdate`, `OnLateUpdate` or an `OnUi*` callback): its events reach their callbacks at the next UiEvents phase, so two runs whose queues differ there must hash differently (the review of C22.2). What interaction writes is in the scene's serialization.
- **Scenes without UI keep their hash** (Roadmap M22): UiInput keeps the interaction state empty while the scene has no canvas (decision 24), and nothing can queue an event there (`Ui.SetFocus` needs a laid-out widget), so a scene without a canvas appends nothing, whatever its input; every committed replay keeps its hash. A scene with UI appends the block from the first tick its state or queue is not empty, which may come without input: the pointer rests at (0, 0) until the mouse moves, over whatever target lies there.

### 32. `ui.createWidget` and the Create UI menu (R-UI-EDITOR; stream D)

- **`ui.createWidget {kind, parent?, index?, name?, text?, scene?}`** (`EditorCore/Automation/UiAuthoringMethods.h`, a file of M22's own, ADR 0028's ledger: new methods take M20's scene target from their own files): builds a widget's entities and components from its template in the addressed edit scene as one undoable command, below `parent` (last, or at `index`) or, without `parent`, as a root canvas (kind Canvas) or below a new root canvas named "Canvas" created in the same command. A kind other than Canvas needs a UiCanvas at or above its parent: below a parent without one (the hierarchy's "Create UI child" on a mesh entity), the widget goes below a new canvas named "Canvas" created below `parent` (last, or at `index`) in the same command, so the menu never builds UI outside a canvas (`UI_ELEMENT_WITHOUT_CANVAS`). Without `parent`, `index` is the created root's position among the scene's roots (the Canvas kind's, or the new canvas's); past them it is refused at `/index`. The kinds (registry enum `UiWidgetKind`: Canvas, Panel, Image, Text, Button, Toggle, Slider, ScrollView) and their templates are the header's table, plain colours only (no texture, so nothing for M23's `Compression: None`), the labels in the canvas's font. The result: `{entity, entities, undoIndex}`, `entities` every created id in creation order, a new canvas first.
- **Flags:** a tool (`ui_create_widget`; 67 proxied tools), mutating, with a dry run, AllowedInBatch, `SupportsSceneTarget` (the inventory's Target); editor only (the play scene takes `entity.create`). Errors: NotFound for an unknown parent; InvalidArgument at `/name` (empty), `/text` (a kind without a label: Canvas, Panel, Image, Slider, ScrollView) and `/index`; InvalidState as `entity.create`'s.
- **The Create UI menu** (`Editor/Source/Editor/Ui/UiCreateMenu.{h,cpp}`): the hierarchy's entity context menu gains "Create UI child" and its background context menu "Create UI", each listing the eight kinds, which submit `ui.createWidget` through `EditorActions` (the parent: the clicked entity, or none), so the menu needs no parity exemption; `SceneHierarchyPanel.cpp` only calls it. Both are popups, so no editor-UI golden changes.

### 34. Minimal authoring and the §5.4 drawer exception (R-UI-EDITOR; stream D)

- **The overlay** (`Editor/Source/Editor/Ui/UiAuthoringOverlay.{h,cpp}`, drawn over the UI preview only): every laid-out element's outline (from a layout of the edit scene at the frame size, `ComputeUiLayout`), the selected element's rectangle with its eight handles; a click selects the topmost element at the point (`PickUiElement`, drawn or not, Hidden elements left out) with `edit.select`; dragging a handle or the body (`FindUiRectHandle`, `DragUiRect`, the pixel delta turned into canvas units by the canvas's scale) submits one `entity.update` of the UiRect at the release, one undo step per drag.
- **Anchor presets** (`Editor/Source/Editor/Drawers/UiRectDrawer.{h,cpp}`): a 4 × 4 grid above UiRect's reflected fields (horizontal Left, Center, Right, Stretch by vertical Top, Middle, Bottom, Stretch; `ApplyUiAnchorPreset`, the current one highlighted by `FindUiAnchorPreset`); a click keeps the element's rectangle, Shift also sets the pivot and Alt also moves it to the anchors (`UiAnchorPresetOptions`: Position 0, and Size 0 on an axis the preset stretches, while an axis it does not stretch takes the element's laid-out size before the change, so a stretched header moved to the centre keeps its width instead of collapsing to its negative inset); the result is submitted as `entity.update`. `InspectorPanel.cpp` only calls the drawer (ADR 0028's ledger: M21 owns the panel in phase 2).
- **The §5.4 drawer exception:** Architecture §5.4 allows custom inspector drawers only for Script fields and Prefab overrides; UiRect's anchor presets are a third, above the reflected fields, which still draw as every component's. §5.4 says so (amended by this contract).
- **Limits** (Backlog §6, added by this contract): no snapping, no guides, no multi-element alignment, no rotation or scale of UI elements.
- **Parity:** every action is an existing method (`edit.select`, `entity.update`); `ui.tree` gives an agent the rectangles the overlay shows, and the preset rule is pure and tested, so the tools need no parity exemption.

## Risks

1. **The draw list is laid out twice.** Extraction lays the UI out for each view and the session for its phases; both are the same pure function, so they agree at one scene resolution, and the hit test (W22.2) reads the session's. A view at another size (a screenshot) shows its own layout, which `ui.tree {width, height}` reproduces.
2. **Text without content sizing.** A label is not sized to its text (decision 6's limit): builders give text rectangles room; `ui.tree` reports each rectangle so an agent sees overflow, and W22.3's measurement layer can feed a later content-size rule without a signature change.
3. **Glyph runs and image runs interleave.** Painter's order splits the pass into a run per change of kind, so a UI that alternates panels and labels records one draw per element; UI element counts are small, and a run never reorders draws.
4. **The scene resolution with M21.** In W22.1 it is the view's size; the later lander of M21 and M22 wires PixelPerfectCamera's into the session's phases and extraction in one place (decision 3), checked by the combined test.
5. **AssetType values.** StringTable is 12 on M22's branch; if M21 lands first, M22 renumbers to 13 at its merge and rebuilds its checkouts' cooked caches (the values live only in cooked headers).
6. **The registered surface ahead of its implementation.** The contract registers components, `ui.tree` and `Loc` so the streams share stable references; until W22.1's integration the coverage gates name them uncovered, which no contract checkpoint runs.
7. **The edit VM's locale** rests on decision 17's amendment, granted on main (2026-10-29); stream L adds the initializer, and until it lands the edit evaluation reads each table's fallback, a difference only `script.eval {context: edit}` sees.
8. **UI determinism (plan risk 8).** Focus and navigation must run only from latched step input: UiInput reads the step view alone, against the current layout, which in every deterministic session is the frame's of the tick (one frame per tick), and the ui block covers every member scripts read; the Ui replay in the four runs is the proof (decision 36).
9. **The surface registered by the streams** (decision 20). Until A, B and C land, the new members of W22.1's components, the Ui settings section, the Ui module and the callbacks exist in the headers and this record only: nothing reads or writes them, the references do not show them, and the wave's integration regenerates the references and FeatureTest once with all of them.
10. **M21's editor files.** The UI preview and its overlay hook into the scene viewport and the editor host, which M21 changes for its 2D editor mode: the calls are single lines into M22's own files, and the later of M21 and M22 adapts them after merging main (ADR 0028's ledger). `viewport.setOptions` may gain an option from each.
11. **The combined 2D/UI test.** A button pressed through PixelPerfectCamera at scale 3 needs the session's pointer mapping and scene resolution to be the camera's; UiInput maps the pointer through the session's output mapping (decision 24), the one place the later lander changes with decision 3's scene resolution.
