## Decisions

### 2. Recast and Detour: the pin, the projects and the process-level hooks

- **The pin.** recastnavigation `v1.6.0` (annotated tag object `b4554541`, commit `6dc1667f580357e8a2154c28b7867bea7e8ad3a7`), from the release archive (`archive/refs/tags/v1.6.0.tar.gz`, 1,280,501 bytes, SHA-256 `d48ca012…0074`), every kept file's git blob hash equal to the tag's; zlib licence (`License.txt`, kept in both directories). `Vendor/Recast/` and `Vendor/Detour/` keep upstream's `Include/` and `Source/` unmodified; each `VENDOR.md` lists every file's SHA-256, the audit and the notices row (Recast `Shipped: no`, Detour `Shipped: yes`).
- **Two projects**, C++17, precise floating point without contraction, no defines: `Recast` (`UseRecast()`: EditorCore, Editor and Tests, never the Runtime's projects) and `Detour` (`UseDetour()`: Engine, EditorCore, Editor, Tests and `UseRuntimeDependencies()`). `CheckBuildConfig.py` gains the `RC_` and `DT_` families (both empty everywhere) and both projects in `PRECISE_VENDOR_PROJECTS`, with the fixtures `Tests/Data/BuildConfig/FastMathRecast` and `FastMathDetour`; `Lint.py`'s `ABI_MACRO_PATTERN` bans `RC_*` and `DT_*` definitions in first-party source; the vendor cache links both (twenty libraries).
- **Process-level hooks** (Architecture §3 rule 5). A new ProcessContext step, `Navigation`, after TextureCodecs: `InitializeNavigationRuntime` (`Navigation/NavigationRuntime.h`) sets Detour's allocator and, outside Dist, its assert hook; then it calls `ProcessContextSpecification::NavMeshBuildHooks.Install` when set, which the editor (through `ApplicationSpecification::NavMeshBuildHooks`, like `RegisterTypes`) and the Tests main set to EditorCore's `InstallNavMeshBuildHooks` (Recast's allocator and assert hooks), so the Runtime, which passes none, never links Recast. Teardown removes Recast's hooks, then Detour's. Recast does not join the Dist map check's forbidden families (`Scripts/Lib/runtime_map.py`, the ledger's "if"): the Runtime's projects do not link the `Recast` library at all, so a reference from Runtime code fails its link before any map exists.
  - **The allocators** go to the C runtime's heap, as both libraries' defaults do, through a counting hook, and each teardown asserts (`ENGINE_CORE_ASSERT`, as `ShutdownScriptingRuntime`'s live-VM check does) that no allocation is live: a navigation mesh, query or bake that leaks is caught at the exit of every Debug and Release process, a leak check that the program's unhardened gates keep without AddressSanitizer (ADR 0042's answer 9). Not a VERIFY: a leaked block corrupts nothing (a later free goes to the same heap through the library's default), so a shipped game never ends on one.
  - **The asserts** go to the engine's assert handler (`Detail::ReportAssertFailure`), as Jolt's do, naming the library's file and line.
- **The audit** (ADR 0042 decision 3). The bake never calls `rcMarkWalkableTriangles` or `rcClearUnwalkableTriangles`: the walkable slope is marked first-party with `DetMath::Cos` (decision 7). The engine never calls Detour's `findRandomPoint` or `findRandomPointAroundCircle`: a random point is picked first-party from a seeded generator (decision 10). Every other C runtime function both libraries call (`sqrtf`, `floorf`, `ceilf`, `fabsf`, Detour's `roundf` between tiles, which one tile never reaches, and `isfinite`) is exactly rounded or exact.

### 3. The Navigation module and the module rules

- **`Engine/Source/Engine/Navigation/`**, layer 3, includes Core and Asset, Detour private to it (`ModuleRules.json`: the module, the `Recast` and `Detour` third-party entries), and in `SimulationPathModules`, since its queries run in the fixed step. ECS-agnostic like Physics and Animation: Scripting (layer 4) and Session (layer 5) reach it; it includes no other layer-3 module. - **Recast is EditorCore's**, restricted to `Editor/Source/EditorCore/Navigation/NavMeshBuilder.cpp` (EditorCore's `RestrictedThirdParty`), the one translation unit of the bake that calls it: the editor runs the bake, as it runs `lighting.bake`, and EditorCore never reaches the Runtime.

### 4. The NavMesh asset (`AssetType::NavMesh` = 19, format version 1)

- **The payload** (`Asset/NavMeshData.h`): the bake input's hash, the area costs, and one `NavMeshAgent` per agent type: its name and settings at bake time, its cells and bounds, and Recast's polygon mesh and detail mesh as plain arrays (`Vertices` as uint16 cell coordinates, `Polygons` as 2 × `VerticesPerPolygon` uint16 per polygon, `Areas`, `DetailMeshes`, `DetailVertices`, `DetailTriangles`). Little-endian, no padding: equal meshes give equal bytes.
- **Validation** (`ValidateNavMeshData`) checks everything `dtCreateNavMeshData` and Detour's queries read: 1 to 4 agents with unique names of 1 to 64 bytes; at most 62 area costs in [1, 10,000]; each agent's settings, cells and bounds in range and finite; array sizes that agree; at most 0xfffe vertices and 0x7fff polygons (Detour stores a neighbour as its index + 1 and reads `DT_EXT_LINK`, 0x8000, as a link to another tile, so every neighbour index stays below 0x7fff, which `NavigationRuntime.cpp` static_asserts); every polygon's first three vertex indices in range, its used slots contiguous, its neighbours `0xffff` or a polygon index (no portal flags: one tile without a border), its area 63 (walkable) or a listed cost; every detail mesh's ranges inside its arrays, at least the polygon's vertices and at most 255 more, at most 255 triangles, each triangle's indices below its vertex count, and all polygons' extra detail vertices at most 0xffff. So no payload that passes makes Detour read outside an array, and Detour's data is always built from it at load, never trusted as bytes. An agent type without polygons (a bake over nothing walkable) is valid.
- **The source file** `.navmesh`: "ENAV", the uint32 version 1, the payload (binary, so not one of `ModuleRules.json`'s JSON extensions). `NavMeshImporter` (id `NavMesh`, version 1, no settings, no sub-assets, no dependencies: a stale bake is `NAV_MESH_STALE`'s to report) cooks it unchanged; `SourceFormats.cpp` gains `{NavMesh, .navmesh, NavMesh, importable}`; `AutomationTypes.cpp` the `NavMesh` asset type entry; the Editor's icons `EditorIcon::NavMesh` (two polygons crossed by a path).
- **Fuzz target** `NavMeshData` ("NavMeshData: 10,000 seeded mutations of a payload never crash", seed 0x4E4D), sorted into `Targets.json` and `FuzzTests.cpp`'s required readers: 51 targets on this branch (53 once M28's two land). An accepted payload must validate and reserialize to its own bytes. No 1,000,000-iteration fuzz step runs in the program (ADR 0042's answer 9).

### 5. The components (category Navigation, after Terrain)

- **`NavAgentType`** (a registered struct): `Name` (string, default "Default", unique, 1 to 64 bytes), `Radius` (0.4 m, [0.05, 10]), `Height` (1.8 m, [0.1, 20]), `MaxSlope` (45°, [0, 85]), `MaxStep` (0.4 m, [0, 10]).
- **`Navigation`** (version 1, unique per scene): `NavMesh` (`TypedAssetHandle<NavMesh>`, null), `AgentTypes` (1 to 4 `NavAgentType`, default one "Default"), `Layers` (physics layer names, empty: every layer), `CellSize` (0.2 m, [0.01, 10]), `CellHeight` (0.1 m, [0.01, 10]), `MinRegionArea` (1 m², [0, 10,000]). Its `Validate` refuses no or more than four agent types, empty, long or duplicate names and empty or duplicate layer names.
- **`NavModifier`** (version 1, requires Transform): `Kind` (`NavModifierKind`: `NotWalkable`, the default, or `Cost`), `Cost` (4, [1, 10,000]), `HalfExtents` (0.5 m each, [0.01, 10,000]). The box is centred on the entity, scaled by its world scale's magnitude and turned by its world rotation's yaw only.
- **Not script-visible** (`RemoveFlags(ScriptVisible)`), both: their fields are the editor's bake's input, and a play session reads only the baked mesh (no run-time rebakes, decision 1), so a script that changed them would change nothing. **This settles the ledger's name clash:** with no `Navigation` component type in the script API, the `Navigation` namespace (decision 10) is the only `Navigation` there, and no reader or tool has to tell a type from a value of one name. The components keep their brief's names in scenes, automation and the inspector.
- **FeatureTest coverage** (decision 13): gates 1 and 1b; gate 4 has nothing to cover.

### 6. The bake input (`Scene/NavigationBakeInput.h`)

A pure Scene function, `CollectNavigationBakeInput(scene, layers, assets)`, used by the bake and by `project.validate`:
- the first Navigation component, in canonical order, on an effectively enabled entity (NotFound without one), its settings checked against the component's ranges and its layer names against the project's (Validation);
- the bodies `ComposePhysicsBodies` plans, in its order, that are creatable, Static, not sensors and on a named layer (every layer when `Layers` is empty), each described by `DescribePhysicsBodyShape` (no mesh shape cache) and triangulated first-party in its collider order, placed at the owner's world translation and rotation: a box's 12 triangles; spheres and capsules as UV spheres of 16 longitudes and 8 latitude bands (a capsule's hemispheres joined by its cylinder), vertices on the surface through `DetMath::SinCos`; a mesh collider's mesh triangles, convex or not (its hull's points are the mesh's vertices in order, so the mesh's indices triangulate it); a height field's cells split as `TerrainGeometry.h` splits them. Triangles face outward (a floor's normal up); a mirrored placement turns its winding back. A body whose shape cannot be described (`PHYSICS_INVALID_SHAPE`, never created in play) adds nothing and is listed in `SkippedBodies`;
- every effectively enabled NavModifier, in canonical order: its four XZ corners and its vertical extent, from square roots only;
- `HashNavigationBakeInput`: XXH64 of a little-endian serialization of `NavigationBakeInputVersion` (1), the settings without `NavMesh`, the vertices, the indices and the modifiers. `PhysicsShape.h` and `PhysicsComposition` are unchanged (the ledger's "none" row).

### 7. The bake (`EditorCore/Navigation/NavMeshBuilder.h`)

`BuildNavMesh(input)`, per agent type, with Recast's steps:
1. **Walkable triangles, first-party:** walkable when the normal's Y (cross(b − a, c − a), normalized) is at least `DetMath::Cos(MaxSlope)`, so a slope of exactly `MaxSlope` is walkable and an agent type of `MaxSlope` 0 walks flat ground.
2. **Voxels:** a heightfield of `CellSize` × `CellHeight` cells over the input's bounds, at most 4,096 cells along X and Z and 8,191 (Recast's `RC_SPAN_MAX_HEIGHT`) from bottom to top (Validation otherwise, naming a larger `CellSize` or `CellHeight`), measured in double before Recast converts any of it to int; the triangles rasterized with the agent's step as the merge threshold; Recast's three span filters; the compact heightfield. In voxels: walkable height ⌈Height / CellHeight⌉, climb ⌊MaxStep / CellHeight⌋, radius ⌈Radius / CellSize⌉.
3. **Modifiers:** each `NotWalkable` box cut with the null area before the erosion by the agent's radius, so an agent keeps its radius from a hole as from a wall; each `Cost` box after it, in ascending cost (canonical order among equal costs), so the highest cost wins where boxes overlap, as area 1 + i of the sorted distinct costs (at most 62, Validation otherwise).
4. **Mesh:** the distance field and watershed regions (no border; `MinRegionArea` / `CellSize`² cells as the smallest region, 400 cells below which regions merge), contours (1.3 cells of error, edges at most 12 m), polygons of at most 6 vertices, the detail mesh (samples 6 cells apart, 1 cell of height error).
The mesh passes `ValidateNavMeshData` or the bake fails naming the limit and a larger `CellSize`. An input without triangles bakes agents without polygons. Before Recast reads anything, a vertex or a modifier that is not finite and a modifier more than 2^30 cells from the grid's minimum (Recast converts its corners to int cells unchecked) are Validation errors, the modifier's naming its entity. Recast's objects are freed by RAII guards on every path; its failures are Validation errors quoting Recast's own message, except its allocation failures, which are OutOfMemory: a null object, a failed `rcCreateHeightfield` (which fails only allocating its columns) and a step whose logged error says it ran out of memory. Equal inputs build byte-identical meshes (precise floating point, canonical order).

### 8. `navigation.bake` and the Bake Navigation action

- **`navigation.bake {}`** (`EditorCore/Automation/NavigationMethods.h`, `NoParams` and the reserved scene target; Mutates, `SupportsSceneTarget`, an MCP tool `navigation_bake` with a 600 s timeout, not a batch op, no dry run, not in the Runtime). Result: `entity` (the Navigation entity), `path`, `asset`, `changed`, `inputHash` (16 hex digits), `agents` (`name`, `polygons`, `vertices` each) and `skippedBodies`. It calls `BakeNavigation` (`EditorCore/Navigation/NavigationBake.h`): InvalidState without a project, for the play scene and for a scene never saved; NotFound for an unknown scene and a scene without a Navigation component; the input's and builder's Validation before anything is written. The file is `Assets/Navigation/<the scene's path below Assets/ without its extension>.navmesh` (`Assets/Scenes/Arena.scene` → `Assets/Navigation/Scenes/Arena.navmesh`), written only where its bytes changed, with a `.meta` for a new source, reimported when either changed, then the component's `NavMesh` set in one `SceneEdit` "Bake Navigation", cancelled when nothing changes. CPU only: it works with `--renderer none`. The method count becomes 121 and the proxied tools 83 (appended after M28's in landing order, ADR 0042's ledger); the scene-target inventory lists it as `Target`.
- **The Tools menu's "Bake navigation"** (`Editor/Panels/NavigationBakeAction`, which `EditorLayer.cpp` only calls), between Reload shaders and Bake lighting, so the existing cases that click the menu's first and last items keep their items; enabled when a writable project's active scene is saved and neither a play session nor a test run is active (no renderer needed); it queues `navigation.bake` without params.

### 9. The validation codes

### 10. The queries and the `Navigation` script namespace (W30.2; planned, amended when W30.2 lands)

`Navigation.FindPath(from, to, agent?)` (the path's corners, or nil when either end is not on the mesh, with whether it reaches `to`: an unreachable goal gives the partial path to the closest reachable point), `Navigation.ClosestPoint(position, maxDistance?, agent?)`, `Navigation.Raycast(from, to, agent?)` along the surface and `Navigation.RandomPoint(center?, radius?, agent?, generator?)` from the session's `Random` stream or a script's `RandomGenerator`, picked first-party (area-weighted polygon, then a point in it) since Detour's `frand` callback has no user data. Usable in every callback, the fixed step's included; deterministic (they read only the baked mesh and their arguments; queries keep no state). The corner cap goes in `ScriptLimits.h` after M28's limits; `RegisterNavigation` follows M28's `RegisterSaveData` in `RegisterBindings.cpp`.

### 15. Accepted limits (`Docs/Backlog.md` §6)

- One tile per agent type: a bake voxelizes at most 4,096 × 4,096 cells (819 m at the default 0.2 m cells), and every rebake rebuilds the whole scene's mesh.
- A convex `MeshCollider` over a non-convex mesh is baked as its mesh's surface, not its hull: the bake does not fill the hollows the physics hull fills.
- Spheres and capsules are baked as 16 × 8 UV tessellations whose vertices lie on the surface, so their flat faces lie up to about 4 % of the radius inside it (3.7 % at the middle of a quad's diagonal).

## Risks

- **Determinism of the vendored float code** across configurations (ADR 0042's risks): both libraries build with the precise model (`CheckBuildConfig.py`, its fixtures). What the gates check: `Scaffold.py --check` rebakes FeatureTest's mesh in a Release editor and compares it byte for byte with the committed one, and the unit suite's builder cases, which run in Debug and Release, check that two bakes of one input are byte-identical within each configuration. No gate compares a Debug bake with a Release one: the bake runs only in the editor, whose Debug and Release builds share the precise model, and W30.2's replay, verified in Debug, Release and Dist, is the first cross-configuration check of the meshes the queries read.
- **Detour trusting its data:** every payload is validated first-party before `dtCreateNavMeshData` reads it, and the fuzz case's accepted payloads are checked to validate.
- **The hooks' leak check** ends a Debug or Release process that leaks a Detour or Recast allocation (an ASSERT at the Navigation step's teardown); a test that leaks fails its whole Tests run at exit, which names the step. A Dist game that leaks exits normally.
- **Merging after M28** (`ScriptHost.h`, `PlaySession.*`, `RegisterBindings.cpp`, `RegisterMethods.cpp`, the validation codes after M34's, `Application.h`'s `ApplicationSpecification`, which W28.1 also changes): M30 lands last and adapts at its merge, as the ledger says.
