### 2. Graphs are Script assets, not an AssetType of their own

ADR 0028's ledger leaves the choice to this contract: a `Graph` AssetType (value 16) or graphs kept as Script assets. **Graphs are Script assets**: a `.graph` source imported by `GraphImporter` (importer id `"Graph"`) into a `ScriptData`, exactly the artifact a `.luau` gives (fact 2's pattern). The reasons:

- **A graph is one behaviour** (ADR 0028 decision 6), and its cooked output is a behaviour's bytecode, field schema and source map. As a Script asset it fills a script slot as any behaviour does, so the Script component stays at version 2 with no member added (the ledger: a member would move every demo's hash), slots keep their `TypedAssetHandle<AssetType::Script>`, and the script engine, hot reload, script errors, `script.fields`, the export's paks and Dist take its cooked script as they take a `.luau` one's. Two changes make that so: the scripting stack accepts a graph's origin through decision 9's script source rule (`IsScriptSourcePath`; fact 11), and the export scans a graph's transpiled text (decision 24). A `Graph` type would need the slots to accept two types (a component change) or a second artifact pointing at the first.
- **No AssetType value:** nothing for M26 to renumber. The ledger's `Graph` 16 is released: M26's `IrradianceVolume`, `ReflectionProbe`, `Lut` and `Heightfield` take 16 on, as the ledger already provides ("from 16 without `Graph`"). No loader, no cooked-range change, no AssetType icon.
- **What tells a graph from a Luau script** is its importer (`AssetMetadata::Importer == GraphImporter::Id`) and its extension (`.graph`). `asset.list {type: "Script"}` lists both; `asset.info` names the importer. `script.read` and `script.write` refuse a graph with `InvalidArgument` at `/path`, the hint naming `graph.read` and the graph edits (stream G-C); `script.create` makes Luau only; `script.check` checks `.luau` sources as before, and a graph's findings are `graph.read`'s and `project.validate`'s (decisions 5, 8 and 13).
- **A graph is self-contained:** it requires no module, and no Luau script requires it (a require request names a `.luau` module only, which decision 9's rule leaves unchanged); a script reaches a graph's instance by its behaviour name, `Entity:GetScript("Door")`, as any slot's (decision 23's kept limit).

### 3. No VisualScripting module

The ledger's default holds: the graph document, the node library and the transpiler live in **AssetPipeline**, in `Engine/Source/Engine/AssetPipeline/Graph/`, and the importer in `AssetPipeline/Importers/GraphImporter`. The reasons (fact 6): AssetPipeline is layer 5 with `MaxLayer` 4, so the node library reads Scripting's `ScriptApiRegistry` without a new edge; it is editor-only, the Runtime project denies it, and Dist runs a graph's compiled bytecode with no transpiler; and the Dist map check's AssetPipeline family already holds every type and free function declared under `AssetPipeline/**.h`, so the graph code is checked out of the Dist Runtime with no family of its own. A `VisualScripting` module would add a `ModuleRules.json` module and `Layer5Edges` entry and a `CheckRuntimeMap.py` family for no layering gain. `Scripts/ModuleRules.json` changes only by the `.graph` lint extension (decision 22); `CheckRuntimeMap.py` and `runtime_map.py` do not change. EditorCore and the Editor include the graph headers as they include the importers'.

### 4. The graph format, version 1

`Engine/Source/Engine/AssetPipeline/Graph/GraphDocument.h` (stream G-A) freezes the document and its rules; its file comment is the rule text. In short:

- **The file:** `"Format": "Graph"`, `"Version": 1`, then the registry struct `"Graph"`'s fields in member order, every field written (§6): `Name` (the behaviour's `Script.Define` name), `Fields`, `Variables`, `Nodes`, `Links` (the example under "Data formats").
- **Members:** a field (a behaviour field, serialized and set per script slot) or a variable (instance state, created at `OnCreate`) has a `Kind` (`GraphValueKind`, one per Luau `Field` constructor: Number, Integer, Bool, String, Vector, Color, Quat, Entity, Asset, Enum, Array), a `Default` in that kind's JSON spelling, an `Element` (an Array's element kind; Number otherwise), an `AssetType` (an Asset's; empty otherwise), `EnumValues` (an Enum's; empty otherwise); a field also has `Options`, the Luau `FieldOptions` (`Min`, `Max`, `Step`, `Tooltip`). Names are Luau identifiers of at most 64 bytes, not starting with `__`, not a reserved script field name (`IsReservedScriptFieldName`: `Entity`, `Fields`, the callbacks), unique across both lists.
- **Nodes:** `Id` (1 to 2^31 - 1, unique, stable for the node's life; `graph.addNode` gives one more than the highest), `Kind` (a library kind, decision 6), `Position` (layout only; the transpiler never reads it), `Values` (literals of the node's input pins by pin name: null, a boolean, a finite number, a string, or an array of 3 or 4 numbers). A literal whose pin is also linked is kept, and the link wins.
- **Links:** `{From: {Node, Pin}, To: {Node, Pin}}`, an output pin to an input pin, both nodes existing and different, each pair once.
- **Canonical form:** Fields and Variables sorted by Name, Nodes by Id, Links by (From.Node, From.Pin, To.Node, To.Pin), byte-wise, so every write of one graph is byte-identical and an edit's diff is small (`CanonicalizeGraph`). A number is one `JsonWriter` writes back as itself (W24.1's review, the lead's decision): an integer, or a fractional number that is the float it rounds to (the writer writes every fractional number as that float, -0 as 0); `0.30000001` or `1e-50`, which a re-save would write as `0.3` or `0`, is a structural issue at its pointer whose message names the float to write, as a list out of its order is one, so a file and its canonical re-save hold the same numbers and transpile to the same text (decision 7).
- **Limits:** 4,096 nodes, 16,384 links, 128 fields, 128 variables, 64 values a node, 64 enum values, 64-byte names, 256-byte kinds, 4,096-byte strings, 256-byte tooltips, positions within 10^6, so a hostile file cannot exhaust memory.
- **Reading:** strictly through the registry (`GraphFromJson`, `GraphFromText`), then `ValidateGraphStructure`; unknown members warn (or fail strictly); a newer version is `UnsupportedVersion`. The registry types are registered by `RegisterGraphTypes`, which `RegisterAssetPipelineTypes` calls (G-A), so graphs read and write wherever the importers' types are (the editor, the tests' built-in registry), never in the Runtime.

### 5. Validation: the structure, the library, and the codes

- **`ValidateGraphStructure`** (G-A) checks every rule of decision 4 that needs no library: names, ids, kinds' spelling, positions, values' shapes, links' nodes, members' defaults, elements, asset types, enum values, options, the canonical order and the limits, one located issue per violation.
- **`ValidateGraph`** (G-B, `GraphNodeLibrary.h`) checks the graph against the library: every kind resolves; every literal names a data input of its node and fits its type (an Entity or Object input takes none, and a Quat literal is no zero quaternion, which `Quat.New` refuses: W24.1's review); every link joins an output to an input of compatible pins (`AreGraphPinsCompatible`: exec to exec; equal data types, Enum and Object also by name; Any with any data; an Enum into a String); a data input and an exec output take at most one link (an exec input any number); no data cycle and no exec cycle; a member node names a member; and, once every other issue is Incomplete, no flow nests deeper than decision 7's depth allows and the transpiled text stays within decision 7's size (W24.1's integration and review). Four issues are **Incomplete**, which the edit methods accept on the way to a finished graph and the import refuses: a required input that has no `Default` and is neither linked nor set, reported at `/Nodes/<i>/Values/<pin>`; a data link from a statement's output to a node that statement does not dominate in its event's flow; a data link from `Flow.IfNotNil`'s `Result` to a node that its `True` flow alone does not lead to (W24.1's review: the `True` link must be the only exec link into its target, which must dominate the node), where the `Result` may be nil; and a data link from a loop's (`Flow.ForRange`'s, `Flow.ForEach`'s) `Index` or `Element` into an input that needs a value (neither optional nor Any) of a node that its `Body` flow alone does not lead to (the milestone review: on the `Completed` flow and after it they are nil when the loop ran zero times, so they are optional there, read by the same rule as `Flow.IfNotNil`'s `Result`). Several event nodes of one callback are valid and run in id order.
- **The validation codes** (Architecture §13.7), appended after `ANIMATION_SKELETON_MISMATCH` in both of `ProjectValidator.cpp`'s tables, kept in step, each with its `Tests/Data/Validation/<CODE>/` fixture (`MakeValidationFixtures.py`) and its row in the game-debugging skill's `validation-codes` page (stream G-D):
  - `GRAPH_INVALID` (Error, not fixable): one per `ValidateGraph` or `ValidateGraphStructure` issue of a graph source, located at its JSON pointer and naming its node, from the validator's own read of every Graph-imported source (as it reads tilemaps and prefabs). The graph does not import; its import failure is this code's, reported once: never a second `ASSET_IMPORT_FAILED` for the same cause, nor again from the import's script check, which carries the same findings for `graph.read` and the hosts (decision 9).
  - `GRAPH_UNREACHABLE_NODE` (Warning, not fixable): a statement node that no event's flow reaches, so it never runs (`FindUnreachableGraphNodes`).
- **The validator's script checks** (stream G-D; fact 5): `CheckScriptSources`' Scene scope takes a script slot's source through decision 9's script source rule, sending a `.luau` source to `EditorScriptService::Check` as before and a `.graph` source to these graph checks, never to the Luau check, so `project.validate {scope: "Scene"}` reports on a scene holding a graph slot; and `SCRIPT_COMPUTED_ASSET_LOAD` (ADR 0030 decision 21) covers a graph's computed loads, `CheckComputedAssetLoads` scanning a Graph-imported source's transpiled text as the exporter does (decision 24).

### 6. The node library, and the node set W24.1 ships

`Engine/Source/Engine/AssetPipeline/Graph/GraphNodeLibrary.h` (stream G-B) freezes the library; its file comment states the kinds, the eligibility rule, the pin names and purity. The library **grows from the script API**: `GraphNodeLibrary::Create(const ScriptApiRegistry&)` derives a node kind from every eligible member of the frozen registry and adds the hand-written built-ins, so a binding added later (an M26 component's proxy fields included) adds its nodes with no change here.

- **Pin types** (`GraphPinType`): Exec, Any, Bool, Number, String, Vector, Color, Quat, Entity, Asset (`AssetRef`), Enum (a registered enum's string union, `TypeName` its name) and Object (any other named type: an extern type such as a component proxy, `TaskHandle` or `RandomGenerator`, or a record alias such as `CollisionContact`, `TypeName` its name). A Luau `T?` input is optional (unlinked and unset, it passes nil). An unlinked, unset required input of type Bool, Number, String, Vector, Color, Quat or Enum takes its `Default` (false, 0, "", the zero vector, white, identity, the first choice). A union of types other than an enum's strings and nil (`OnUiValueChanged`'s `boolean | number`) is an Any pin.
- **Optional values** (the lead's decision on the contract's review): a `T?` output (a result, a property, a constant or a callback parameter: `Assets.Load`'s `Result`, an Entity's component proxies, `Scene.FindByName`'s `Result`) is optional too (`GraphPinDescription::Optional`): it may give nil, so it feeds only an optional input or an Any input, and the built-in `Flow.IfNotNil` turns it into a value every data input takes, on its `True` flow. `AreGraphPinsCompatible`, the contract's live rule, refuses an optional output into a required input, so a link whose transpiled text the strict checker would refuse ("value of type T? could be nil") is refused when it is made (`graph.connect`'s hint names `Flow.IfNotNil`), never found at the import. It is the smallest model that keeps every generated text strict-clean: no type follows a link, and the one new node is a branch. A member's own value (`Self.Get`) is typed by its kind and never optional: the text reads it through `self: any`, and an unset Entity or Asset field reads nil, a located runtime error where a required input gets it, as in Luau.
- **Generated kinds:** `Event.<Callback>` from the `Behaviour` type's callbacks (outputs: `Then` and the callback's parameters, by name; the event's function returns nothing, so a graph's UI event never consumes the event, decision 23's kept limit); `Call.<Group>.<Member>` from functions, methods and constructors (a method's object is the input `self`); `Get.<Group>.<Member>` and `Set.<Group>.<Member>` from readable and writable properties and component proxy fields, and `Get` from a record alias's fields; `Const.<Group>.<Member>` from constants. Results are `Result`, or `Result1`, `Result2`, ...; a property's value is `Value`.
- **Eligibility:** a member available in every run mode (`RunModes::All`: a graph runs alike in the editor, Release and Dist) and at run time (`ScriptApiEnvironment::Runtime`), whose signature is one function type (no generic, no overload intersection) of parameters and results the pin types model; a trailing variadic (`...any`, as `Log.Info`'s) becomes one optional input `Values`, passed as its one argument. Every other member has no node: `OnHotReload` (EditorOnly), `Test.*` (Test only), `Script.Define` (generic), `Task.Spawn` and `Task.Delay` (function parameters; `Flow.Delay` covers the delay). Two members that would give one kind fail `Create` (Validation), so a collision is found by the library's test, never at run time.
- **Purity:** a member registered with `Mutates` false that returns a value, a getter, a constant and an operator is **pure** (no exec pins, evaluated where each statement needs its outputs); every other node, a member that returns nothing included (`Log.Info`), is a **statement** (`In` and `Then`).

The vector operators use Luau's `vector` library, whose operations are IEEE-exact or `sqrt`, so they keep §9.1's determinism; numeric operators are Luau's own. ### 7. The transpiler's output contract

`Engine/Source/Engine/AssetPipeline/Graph/GraphTranspiler.h` (stream G-B) freezes it; its file comment is the rule text. One graph gives **one behaviour's Luau text**:

- **Byte-identical in every configuration:** a pure function of the document, the library and the path, with no pointer, unordered iteration or locale; numbers in the shortest form that reads back to the same double; strings in double quotes with Luau escapes; LF lines and a final newline. Only the editors transpile, so "every configuration" is the Debug and Release editors (their imports give identical cooked bytes); exported Release and Dist games run the cooked bytecode.
- **The layout,** in order: `--!strict`; the comment `-- Generated from <path> by the graph transpiler: edit the graph, not this text.`; `local Graph = {}`; `Graph.Fields = {...}` with one `<Name> = Field.<Kind>(<default>, <options>),` line per field in name order; `function Graph.OnCreate(self: any)`, always, which first sets `self.__GraphLive = {}` (decision 14), then each variable to its default in name order, then runs the `Event.OnCreate` nodes' flows; then one `function Graph.<Callback>(self: any, <parameters>)` per other callback the graph has an event node of, in byte-wise callback order, running its event nodes' flows in id order; last `return Script.Define("<Name>", Graph)`. Nothing else is global: no require, no upvalue across functions.
- **Stable names:** a statement's outputs are the locals `n<Id>_<Pin>`, declared with their types at the top of each event function that runs the statement (an Any one annotated `any`); a pure node's value computed for one statement is `v<Id>_<Pin>` inside that statement's own `do ... end` block, so a function's active locals stay below Luau's 200, and a value computed again for a statement nested in that block assigns the enclosing block's local instead of declaring one that would shadow it (Luau's `LocalShadow` lint); a flow that several exec links enter is the local function `flow<Id>`; each node's code starts with the comment line `-- <Id>: <Kind>`. So a name changes only when its node does, and a human reading a Dist log's line finds the node (W24.1's integration aligned this text with the transpiler as built; `Tests/Data/Graphs/Door.luau` is the illustration below byte for byte).
- **Semantics:** a statement runs when its `In` is reached and continues at `Then` (Flow's outputs per decision 6); a pure node is evaluated again for every statement input it feeds, in pin order, depth first, so a value is always current; `Flow.Delay` continues at `Then` at once and at `Later` from `Task.Delay(<Seconds>, function() ... end)`; `Flow.IfNotNil` continues at `True` when its `Value` is not nil (its `Result` the `Value`) and at `False` otherwise; a statement's output read later in its flow is the value of its last run. Several event nodes of one callback run in id order, and an event's function returns nothing.
- **Values and types:** a literal is written in Luau's spelling of its pin's type (a vector `vector.create(x, y, z)`, a Color `Color.New(r, g, b, a)`, a Quat `Quat.New(x, y, z, w)`, an Enum's choice its string); an Asset literal, an `AssetHandle`, is `(Assets.Load("<16 hex digits>") :: AssetRef)`, the `AssetRef` a required Asset input takes, nil at run time only for an asset that no longer exists (a located runtime error where it is passed on); an Any pin's value is typed `any` (an Any output's local annotated `: any`), so an Any input takes any value, nil included, and an Any output feeds every data input. Where the strict checker needs it, a typed value is cast to `any`: an Any input of a generated member (whose Luau type is a table or a non-enum union, both Any pins), `Flow.ForEach`'s array, `Flow.IfNotNil`'s value, one operand of `==` or `~=` between two typed operands, and a statement's single Any result; the script API's operators (`__eq`, `__mul`) give no node.
- **Depth** (W24.1's integration, the lead's decision): a statement's code starts at most 64 blocks deep (`MaxGraphTextDepth` in `AssetPipeline/Private/GraphTextLimits.h`, which W24.1's review renamed from `GraphTextDepth.h`, a constant the transpiler and `ValidateGraph` share), each branch, loop body, `Flow.Delay` later flow, `Flow.IfNotNil` flow, merge's flow function and statement block (of pure values, or binding a cast object) nesting one level. Luau's parser recurses once per block, and a 1,200-deep text overflowed the Debug test thread's stack before the parser's own 1,000 limit. `ValidateGraph` reports a flow that would nest deeper as a `GRAPH_INVALID` issue (not Incomplete) at the statement that first passes the limit, measured by laying the text out as `TranspileGraph` does (`Utils::FindGraphTextLimitIssues`) whenever every other issue is Incomplete, so a graph transpiles exactly when it validates (the fuzz case's invariant) and the edit that nests a flow too deep is refused while the graph is built.
- **Size** (W24.1's review, the lead's decision): the text holds at most 8 MiB (`MaxGraphTextBytes`, the second constant of `GraphTextLimits.h`). Each statement evaluates again the pure values it reads, so the text grows with statements times values, which the document's limits bound only at hundreds of megabytes (2,000 statements reading a chain of 2,000 values: about 0.5 GB, laid out at every validation). `ValidateGraph` reports a text that would pass the limit as a `GRAPH_INVALID` issue (not Incomplete) at the statement whose code passes it, measured by the same layout, which stops there, so every layout costs at most the limit, a graph transpiles exactly when it validates and the edit that grows the text too large is refused. The limit is chosen far above any real graph: FeatureTest's four graphs transpile to 1.6 KB to 3.6 KB (Steering 1,649 bytes, Flows 2,641, Vectors 3,313, Arithmetic 3,572) and the fixture graphs to 0.8 KB to 5.0 KB (Door 754 bytes, Mover 4,954), the tests' graphs at `MaxGraphNodes`' scale to 162 KB (4,095 chained statements) and 449 KB (one statement reading 4,093 values), and a graph's fields, variables and layout lines alone give at most about 4.4 MB, so the text passes the limit only inside a statement's code. A kept limit (decision 23, `Docs/Backlog.md` §6).
- **Clean:** the text of every graph that validates type-checks without an error in the engine's strict checker (decision 6's optional rule keeps a nil out of every required input); a graph with any `ValidateGraph` issue, Incomplete ones included, has no text (`TranspileGraph` returns Validation carrying every issue).

### 8. Source mapping

- **The line map:** `GraphTranspileResult::LineNodes` names the node whose code each line of the text is (0 for the layout's own lines); `FindGraphNodeAtLine` reads it.
- **The import's source map** (decision 9) describes the transpiled text under the `.graph` path: `ChunkName` `"@<path>"`, `Path` the `.graph` path, the line offsets the text's. A compile, type or runtime error therefore names `<path>:<line>` of the text, and the editor, which has the transpiler, maps that line to its node by transpiling the graph's current source (decision 13's `graph.read` diagnostics, decision 14's live errors). In an exported game the log names the line, and `graph.read {luau: true}` shows the text with each line's node; every node's code also starts with its `-- <Id>: <Kind>` comment.
- **The import's findings** carry the node: a type or compile finding of the text keeps `SCRIPT_TYPE_ERROR` or `SCRIPT_COMPILE_ERROR` at its line, its message prefixed `node <Id> (<Kind>): ` where the line map names one; a graph's own issue is a `GRAPH_INVALID` finding at line and column 0, located by the JSON pointer and node its message names, which `IScriptDiagnosticsProvider.h`'s `ScriptDiagnostic` documents with the contract.

### 9. The importer

`Engine/Source/Engine/AssetPipeline/Importers/GraphImporter.h` (stream G-B) freezes it: id `"Graph"`, version 1, main type Script, extension `.graph`, no settings, no sub-assets, not main-thread. In order: read the document strictly and validate it against a library built from the import context's shared pure script API (`ImportContext::GetLoadTimeScriptApi`, the editor's one `PureScriptApi`, ADR 0041 decision 3; a `PureScriptApi` built for the import when the context has none; amended at the landing, section "Landing": first a `ScriptApiRegistry` of its own, `RegisterBindings` over the context's frozen type registry, as each load-time VM then built one, fact 3); transpile; extract the text through `LoadTimeVm::Extract` under the `.graph` path, its VM binding the same API (a Behaviour named the graph's Name, or Validation); and publish the script check before anything can fail, as `ScriptImporter` publishes it: `SourceHash` the XXH64 of the `.graph` bytes, `EnvironmentHash` the provider's, and the findings of decisions 5 and 8: `GRAPH_INVALID` at line 0 and the text's type and compile findings, never `GRAPH_UNREACHABLE_NODE`, which `graph.read` and `project.validate` compute themselves (`FindUnreachableGraphNodes`), so an unreachable node never enters the check the export's script-error refusal reads. Because the check's environment hash is the declarations' hash (fact 4), **every graph is imported again whenever the script API's declarations change**, which is also when the library can change: the cache follows the library with no version of its own. `Import.Dependencies` (ADR 0028's phase-3 ledger) hold every non-null Asset literal of the graph's inputs (`FindGraphAssetLiterals`), sorted and unique, as a component's asset references are listed: a pruned export keeps them and `CheckReferences` checks them. The import is a pure function of its inputs: identical cooked bytes in every run and configuration. - **The script source rule** (fact 11; the lead's decision on the contract's review): `IsScriptSourcePath(const VfsPath&)` (`Asset/ScriptData.h`, frozen; stream G-B) holds for a `project://` path below `Assets/` whose extension is `.luau` or `.graph`. A require request still names a `.luau` module only: the path `Resolve` resolves a request to keeps the `.luau` rule, which today shares `ValidateModulePath` with the importer's and `EnterModule`'s check, so G-B splits the two (`RequireResolver.h`'s comment states both), and no script requires a graph (decision 23). A trial implementation of the rule at these sites, reverted, passed both cases below and the existing `RequireResolver`, `LoadTimeVm`, `Sandbox` and `HotReload` cases, and the require check of the second case failed when the resolved request took the rule too. G-D's validator takes a script slot's source through the same rule (decision 5). The cases: "ScriptData: a script source path is a project Assets path of a Luau source or a graph" and "HotReload: a behaviour under a .graph origin extracts, instantiates and hot-reloads as a .luau one, and no script requires it" (skipped, G-B), with "GraphTranspiler: the text of every fixture graph type-checks without an error" for the checker.

### 14. Live values (W24.2, stream B)

- **What a node shows:** during play, the last value of each of its data outputs, and, in the canvas's members panel and the inspector's graph slot, the instance's fields and variables; a node whose code raised a retained script error shows the error. The inspector names a graph slot by the graph's current `Name` (`ReadGraphBehaviourName`, through the editor's `GraphLiveCache`), as the method matches it, so a rename during a session that defers reimports keeps its values, and in a simulation, which runs no behaviours, it says it has none (the milestone review).
- **How the values get there:** the transpiled text writes every value it computes (a pure node's and a statement's data outputs) also to `self.__GraphLive["<Id>.<Pin>"]` (`ScriptLiveValuesKey`; `GetGraphProbeKey`; `GraphTranspileResult::Probes`), a table the generated `OnCreate` makes first. The writes are in every configuration's bytes, so the text stays one; they change no state the state hash covers, since instance tables are outside it as every script's are (ADR 0028's phase-3 ledger), and their cost is one table store per computed value, bounded by the graph's node count.
- **How the editor reads them:** `ScriptEngine::ReadInstanceValues(entity, slot)` (`Scripting/ScriptEngine.h`) reads the instance's own string-keyed members and its live-value table's entries between phases, **running no Luau and allocating nothing in the VM**: raw reads only, no metamethod, iterating the tables as they are, no new string, table or userdata pushed. Neither the VM's heap nor its collector's debt changes, so every later result of the session is what it would have been without the read, and the state hash is unchanged. Values come back in reflection's JSON spelling with their type names (`ScriptInstanceValue`), byte-wise by key, at most `MaxScriptInstanceValues` a list.
- **`graph.liveValues {entity, script?}`** reads the play scene's instance of a graph slot (the slot's behaviour name, matched against the graph's current name, its document's `Name` read on each call, the first of two slots of one name; or the entity's first graph slot): its nodes' values (`ParseGraphProbeKey`), its members, and the instance's retained script errors raised by the graph's own code (their script is the graph's path) mapped to nodes through the graph's current text, with the session's tick. Read-only, `AllowedInBatch`, a tool; not scene-targeted (it reads the play session, as `play.*` does); among the reads a test run admits; not in the Runtime. Its errors as built (W24.2's review): `InvalidState` without a play session or in a simulation; `NotFound` at `/entity` for an entity the play scene does not hold (`InvalidArgument` for an ambiguous or malformed reference); `NotFound` at `/script` for an entity with no graph slot or none of that behaviour (a graph source that does not read names none); without `script`, the first graph slot's read errors (`ImportFailed` for a source that does not read). (W24.2's integration amends the error and name rules and the test-run admission.)
- **The graph's read is kept between calls** (W24.2's review, the lead's decision (d)): the method reads a graph strictly, and while an error is retained transpiles it to map the error's line, on every call, which the canvas and the inspector make once a frame. The editor keeps each graph's document and its text's line map (`EditorCore/Graph/GraphLiveCache`, owned by `EditorContext::GetGraphLiveCache`, no global), keyed by the graph's handle, its source's project path, the XXH64 of its source's bytes and its asset version, so every change of the graph (an edit, an undo, an outside write, a move, a reimport that publishes a new version) reads it again; the source's bytes are read on every call, since an edit during a lockstep or test session writes the file and defers its reimport. At most `MaxGraphLiveCacheEntries` (8) graphs, the least recently used going first; `CloseProject` empties it. Results are unchanged.
- **The canvas** polls it once a frame while a play session runs and its graph is open, between frames (the ledger: the editor reads live values between frames; no `PlaySessionPhase`), a test run's session included (W24.2's integration): `graph.read` and `graph.nodes` join `graph.liveValues` among the reads a test run admits (W24.2's review, the lead's decision (e)), so a graph opened during a test run shows itself and its live values. It shows a read only while the read's graph is the graph it shows (W24.2's review, the lead's decision (b)): when an earlier slot of the entity holds another graph of the same behaviour name, which the method reads instead, it draws no value under its nodes or beside its members and says why, naming the slot and the graph read, as the inspector says "Shown in slot N" on the second of two slots.
- **Kept limits** (`Docs/Backlog.md` §6; W24.2's integration and review): of two graph slots of one behaviour name on an entity, only the first can be read live, by the method, the canvas or the inspector; and the errors are mapped through the graph's current text, so after an edit during a session that defers reloads (§7.5 race rule 4) and runs the old code, an error names the node its line has in the edited text. A `slot` (or `graph`) param on `graph.liveValues` would lift the first, mapping through the line map of the text the session's script was compiled from the second; no work is planned.
- **The acceptance:** "ScriptEngine: reading an instance's values between phases runs no Luau and allocates nothing in the VM" and Python `test_live_values_are_read_in_play_without_changing_the_state_hash`, which compares the state hash of a lockstep play that reads live values with one that does not.

### 18. Platform windows: the design (stream V)

- **The platform side** is the vendored `imgui_impl_glfw`'s viewport support (its `Platform_*` callbacks create GLFW windows for viewports); **the renderer side** is `Engine/Source/Engine/ImGui/ImGuiPlatformWindows.h`: the `Renderer_*` callbacks and `ImGuiBackendFlags_RendererHasViewports`, one target per platform window (a swapchain on its GLFW window by default, `CreateSwapchainPlatformWindowTarget` over the new `Swapchain::CreateForNativeWindow`), each window's draw data recorded through the application's `ImGuiRenderer` on its own command list, submitted with its target's semaphores and presented.
- **`ImGuiLayer`** (`ImGuiLayerSpecification::PlatformWindows`) sets the flag and creates the `ImGuiPlatformWindows` only when asked, on the GLFW backend, and when `CheckPlatformWindowSupport` allows; `GetPlatformWindowSupport` says why not otherwise. `EndFrame` also calls `ImGui::UpdatePlatformWindows`; `RenderPlatformWindows(frameSlot)` draws them.
- **The Application** (`ApplicationSpecification::ImGuiPlatformWindows`) passes the request to the layer and calls `RenderPlatformWindows` after the main window's submission and present and before the frame's `FramePacer::EndFrame`, on every frame that rendered the UI while the main window is not minimized (the milestone review: a UI frame forced while it is draws none); a recording's failure to create what it records with, which `Render` returns as OutOfMemory, is treated as the main UI's Gpu error, and a platform window's swapchain or target failure, which it returns as Gpu, as the main window's swapchain failure (`FatalError(Gpu)`), each fatal on a healthy device and the loss's on a lost one (§8.14 item 6; the milestone review), and a platform window's target that runs out of GPU memory is no error there (decision 19's rule fails only that window). So the pacer's wait covers the platform windows' submissions, and each window waits only for its own image (its own acquire and present semaphores): clean under synchronization validation.
- **The editor** sets it from the user's `PlatformWindows` preference (`user://Editor.json`, on by default, read at startup so a change takes effect at the next start), toggled by the Window menu's "Platform windows" checkbox, before Reset layout (the editor has no View menu, and adding one would change every editor-UI golden's menu bar; W24.1's integration); the Runtime never asks. Windowed editors on Windows get platform windows; headless editors never do.
- **Screen coordinates:** with viewports on, Dear ImGui's coordinates are desktop coordinates, so V audits the editor's code that assumes the main window's origin (the viewport panels' picking and ImGuizmo's rectangle, `EditorHostViewports`, `SceneViewportPanel`, `GizmoOverlay`, the stats overlay, `ImGuiScreenshot`), all files M24 owns or that only it changes.

### 19. Platform windows and the recreation protocol (stream V)

`ImGuiPlatformWindows::Create` registers the window set as one owner, **"ImGuiPlatformWindows"**, after the "ImGuiRenderer" it draws with, so a loss releases it first and recreates it after (ADR 0029 decision 26's order): Release drops every window's target (a swapchain releasing its swapchain and surface before the old `VkInstance` is destroyed) and command list, tolerating a half-recorded frame; Recreate creates a target again for every platform window that still exists, at its size, on the recreated device. A target never registers itself.

**Out of GPU memory** (M18's rule after startup, ADR 0029 decisions 42 and 44; the lead's decision on the contract's review): a platform window's target is created after startup (when a panel is undocked) and again at its resize, so each creation is a request like the frame's resize: an out-of-memory creation is trimmed and retried once (`RetryAfterTrim`; the default target with the swapchain's own out-of-memory classification, as `Swapchain::AcquireNextImage`'s recreation passes it), and a second one leaves that window without a target, logged at Warn and never fatal: it draws nothing, the other windows and the frame go on, `GetWindowCount` leaves it out, and its creation is tried again at its next size change. A target creation that fails otherwise leaves that window without a target until its next size change too, and is `Render`'s error once a size (a swapchain's as Gpu, decision 18; the milestone review: never a creation every frame), and in a recovery's Recreate an out-of-memory creation is a second startup's, which fails the recovery, as every owner's. The case "ImGuiPlatformWindows: an out-of-memory target is trimmed and retried once, and otherwise only its window draws nothing until its next resize" (GPU, skipped, V) proves it with the injected `oom-rendertarget` faults on the headless device's offscreen targets.

Two loss tests, reconciling the plan's "a loss test through the shared helper" with ADR 0029 decision 32's rule for presenting owners:

- **Through the shared helper** (`Test::RunDeviceLossTest`), on the headless device with a test factory whose targets are offscreen: "ImGuiPlatformWindows: a device loss recreates every platform window's target and draws the same image" (owners `ImGuiRenderer` and `ImGuiPlatformWindows`; a fake platform side without OS windows, which gives the main viewport a platform handle as a backend's initialization does), so the registration, the release, the recreation and the live counts are proven like every owner's.
- **In a windowed child**, for the presenting half the headless device cannot reach (swapchains on real windows, `Recover(window)`): "ImGuiPlatformWindows: platform windows recover their swapchains after an injected loss and present without a GPU message" runs the child target "ImGuiPlatformWindows: a windowed application with a platform window loses its device and presents both windows again" (`ExpectNoGpuErrors`, validation and synchronization validation on).

### 23. Kept limits

Added to `Docs/Backlog.md` §6 with this contract:

- **A graph is one self-contained behaviour:** it requires no module and no Luau script requires it; a script reaches its instance by its behaviour name (`Entity:GetScript("Door")`) and types it as `any`.
- **The node library models one function signature a member:** a generic, overloaded or function-typed member (`Script.Define`, `Task.Spawn`, `Task.Delay`) has no node; `Flow.Delay` gives a graph its delayed flow, and the rest is Luau's.
- **A graph's transpiled text is bounded** (W24.1's integration and review): a statement's code starts at most 64 blocks deep and the text holds at most 8 MiB (decision 7's depth and size), each a `GRAPH_INVALID` issue at the statement that passes it and refused by every edit; a graph within both whose text exceeds another of Luau's limits (a function's 200 locals: one statement reading more than about 200 values) validates, is accepted by the edits and fails its import with `SCRIPT_COMPILE_ERROR` at the line of the node that exceeds it, which `graph.read` maps to that node (risk 1).
- **A graph's UI event never consumes the event:** an event's function returns nothing, so a graph's `OnUiClick` and the other `OnUi*` callbacks always let the event bubble on to the parent's behaviours (M22's bubbling), as a Luau callback that returns nil does; a behaviour that must stop the bubbling is written in Luau. The reason: consuming needs a result from a flow, which several event nodes of one callback (run in id order in one function) and `Flow.Delay`'s later flows (run after the callback has returned) cannot give one meaning; a `Consume` input on the event node would be the later design, and no M24 acceptance needs it (the lead's decision on the contract's review: a kept limit rather than support).
- **Platform windows are drawn on the frames the main window renders while it is not minimized** (while the main window is minimized its frames are skipped, a UI frame forced for `editor.screenshot` renders the main window's UI alone, and the platform windows keep their last image; the milestone review); `editor.screenshot` captures the main window's UI alone; the `PlatformWindows` preference takes effect at the next editor start.
- **A Game view undocked into a platform window gets no game input** (W24.1's integration, stream V's coordinate audit): the engine `Window`'s callbacks see only the main GLFW window (`imgui_impl_glfw` chains user callbacks for the main window only, and `Platform/Window.cpp` owns them), so while the Game view's own OS window has the focus or the cursor, no native key, mouse or gamepad event reaches the play session; the Game view docked in the main window gets its input with platform windows on (`EditorHostViewports::ToGameEvent` offsets native cursor positions by the main viewport's desktop position). Play with the Game view docked.

### 24. The export's scan of graph sources (granted: ADR 0028's ledger amendment)

Fact 5: the exporter runs the Luau literal-load scan over every packaged Script asset's source, which would fail an export of a project holding a graph (a `.graph` source is JSON). Skipping the scan would be unsafe: a graph computes a load's reference whenever `Call.Assets.Load`'s `reference` is linked (from `Text.Concat`, a String field's `Self.Get` or any String or Enum output), and only the scan finds computed loads. The lead granted `Exporter.cpp` to stream G-B (ADR 0028's ledger amendment on main) with this design: **the exporter scans a graph's transpiled Luau text exactly as it scans a `.luau` source.**

- **What is scanned:** for an included Script asset whose importer is Graph (`AssetMetadata::Importer == GraphImporter::Id`), `FindScriptAssetLoads(<text>, <path>)` runs over the graph's transpiled text instead of its source, with the graph's plain project path as its chunk name exactly as a `.luau` source's (W24.1's integration aligned the text; the import's source map keeps `"@<path>"`, decision 8); nothing changes for any other Script asset. The export's refusal of script errors reads the import's check, which holds no unreachable-node warning (decision 9). A graph's literal and computed loads then take the paths a Luau script's take (ADR 0030 decisions 19 to 21): a literal load resolves as `Assets.Load` resolves it (a project path with an optional sub-asset key, an `engine://` path or a 16-hex handle), its target reached with reason `LiteralLoad` in a pruned export and a missing or `Export.Exclude`d target adding nothing; a built-in target joins `Engine.pak`; a computed load keeps every File and Generated built-in in `Engine.pak` and enters `ExportReport::Reachability::ComputedLoads` at the text's line; and `project.validate`'s `SCRIPT_COMPUTED_ASSET_LOAD` names it, G-D's `CheckComputedAssetLoads` scanning a Graph-imported source's text the same way (decision 5). An Asset literal, written `(Assets.Load("<16 hex digits>") :: AssetRef)` (decision 7), is found as a literal load too, besides being a dependency (decision 9).
- **Where the text comes from:** the exporter reads the `.graph` source through the project file system, as it reads a `.luau` one, reads it strictly (`GraphFromText` with the editor's type registry) and transpiles it (`TranspileGraph` with its project-relative path) against one library per export, built from the engine's frozen script API registry (`GraphNodeLibrary::Create`), which is the same library (equal fingerprint) as the one the importer builds from the editor's load-time pure script API, both registries made by the same bindings (`RegisterBindings`; ADR 0041 decision 3, decision 13 and the landing's redo; worded so by the milestone review). A graph that does not read or transpile fails the export, located at its source, as a `.luau` source the Luau parser rejects does; such a graph has failed its import too (`GRAPH_INVALID`).
- **Why it stays safe:** the text is a pure function of the document, the library and the path (decision 7), and the library of the registry, so the scanned text is byte for byte the text the import compiled into the bytecode the game runs; a cooked import is current only while its check's environment hash, the declarations' hash, equals the provider's (fact 4, decision 9), which is also when the library is the importer's. The scan therefore sees every `Assets.Load` the game can call, literal or computed, exactly as it sees a Luau script's, so computed and literal loads, built-ins and sub-assets behave as for `.luau`, and an unresolvable computed load warns the same way. No cooked format changes and no importer version moves.
- **The test** (G-B, `Tests/Source/EditorCore/Export/ExporterTests.cpp`): a project holding a graph with a literal load of a project asset, a literal load of a built-in and a computed load exports with `Export.PruneUnreferenced` on: `Game.pak` holds the project asset (reason `LiteralLoad`), `Engine.pak` keeps every File and Generated built-in for the computed load, and the report's `ComputedLoads` names the graph's path and line.

- **Its transpiled text,** the layout of decision 7 (an illustration; G-B's committed fixture texts, `Tests/Data/Graphs/<Name>.luau`, freeze the bytes):

  ```lua
  --!strict
  -- Generated from Assets/Scripts/Door.graph by the graph transpiler: edit the graph, not this text.
  local Graph = {}

  Graph.Fields = {
  	Player = Field.Entity(),
  	Speed = Field.Number(2, { Max = 10, Min = 0 }),
  }

  function Graph.OnCreate(self: any)
  	self.__GraphLive = {}
  	self.Opened = false
  end

  function Graph.OnTriggerEnter(self: any, other: Entity)
  	-- 4: Flow.Branch
  	do
  		-- 3: Self.Get.Player
  		local v3_Value = self.Player
  		self.__GraphLive["3.Value"] = v3_Value
  		-- 2: Compare.Equal
  		local v2_Result = other == v3_Value
  		self.__GraphLive["2.Result"] = v2_Result
  		if v2_Result then
  			-- 5: Self.Set.Opened
  			self.Opened = true
  			-- 6: Call.Log.Info
  			Log.Info("Door opened")
  		end
  	end
  end

  return Script.Define("Door", Graph)
  ```

- **A live-value key:** `"<Id>.<Pin>"` (`"2.Result"`), the key of `self.__GraphLive` and of `graph.liveValues`' values.
- **No other format changes:** `ScriptData` and `ScriptImporter::Version` stay at 1, Script version 2, the replay, pak, manifest, scene document and `.eproj` unchanged (ADR 0028's ledger).

## Risks

1. **The transpiler meets Luau's limits** (200 locals, 255 upvalues, the register file) on large flows: the `do ... end` blocks bound a statement's locals, and G-B's tests include a graph at `MaxGraphNodes`' scale; a flow nested deeper than the text may nest, or a text larger than it may be, is `GRAPH_INVALID` at its node (decision 7's depth and size), and a graph that still exceeds a limit fails its import located at its node, never at run time (decision 23's kept limit).
2. **The library follows the script API.** A binding's change changes its node and re-imports every graph (decision 9); a removed or renamed binding makes its graphs `GRAPH_INVALID`, as it gives a Luau script a type error. No demo holds a graph, and FeatureTest's graphs are rebuilt by `Scaffold.py` through the methods, so a later lander (M26's components add `Get` and `Set` kinds) changes no graph of the repository.
3. **The export of a project with a graph** scans the graph's transpiled text (decision 24): a scan of a text other than the one the import compiled would miss a load the game makes, which the environment hash rules out (a cooked import is current only while the declarations, and so the library, are the importer's), and G-B's exporter case proves the literal, built-in and computed loads.
4. **A live-value read must allocate nothing:** Luau's `lua_tolstring` converts a number in place and would corrupt `lua_next`'s iteration, and pushing a key string may intern a new one; B reads by type without conversion, and the test compares the VM's used bytes before and after.
5. **Platform windows' coordinates:** with viewports on, Dear ImGui's positions are desktop coordinates; code that assumes the main window's origin (picking, ImGuizmo, the stats overlay, `ImGuiScreenshot`) is audited by V (decision 18); monitors with different scales follow `imgui_impl_glfw`'s per-viewport framebuffer scale.
6. **The graph editor is the largest new editor surface** (plan §8 risk 15): its data actions are the tested methods, and only its presentation is exempt.
7. **Optional values cost a node:** an optional output that must reach a required input goes through `Flow.IfNotNil` (decision 6), where Luau needs only an `if`; `graph.connect`'s refusal names the node, so an agent learns it from the error, and the strict check stays the guarantee.

**Correctness and robustness**

Major:

1. **`editor.screenshot` of a minimized windowed editor failed with platform windows on** (`ImGuiLayer.cpp`). Checked in Dear ImGui: with `ImGuiConfigFlags_ViewportsEnable` the main viewport, a platform window from the context's creation (`PlatformWindowCreated`), asks the GLFW backend whether it is minimized (`UpdateViewportsNewFrame`), and a minimized viewport's draw data gets an empty display (`SetupViewportDrawData`), which `BeginFrame`'s retained `io.DisplaySize` does not reach; the forced frame drew nothing and `CaptureImGuiScreenshot` refused it ("no area to capture"). Fixed by decision 1:
   - `ImGuiLayer::EndFrame`, on a frame whose `BeginFrame` retained the display size with platform windows on, gives the main viewport's draw data the main viewport's size, which Dear ImGui keeps while the window is minimized (the private `m_RetainedDisplaySize`), so the forced frame renders and the capture takes the UI at the size it was laid out at.
