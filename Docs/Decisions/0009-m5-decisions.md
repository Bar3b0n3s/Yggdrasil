# 0009 — M5 contract decisions

- **Status:** accepted with revisions by the M5 integration task (decisions 20 to 32), and completed by the M4/M5 merge (decision 33). The contract task proposed decisions 1 to 19 and the streams implemented against them. The amendments listed at the end are either applied by integration or the merge, where marked, or left for the docs owner.
- **Date:** 2026-10-06
- **Context:** The M5 contract task (Roadmap rule 3) froze the public headers of every M5 deliverable: `Engine/Source/Engine/Graphics/`, `Engine/Source/Engine/ImGui/`, `Engine/Source/Engine/Renderer/{TrianglePass,ViewportCapture}.h`, `Engine/Source/Engine/Testing/ImageCompare.h`, the M5 parts of `App/` and `Platform/`, the shared shader headers and the GPU and golden test support. M4 (EditorCore, automation core) runs in parallel, so its `MethodRegistry` is not available. Writing complete headers exposed places where the Architecture and Roadmap are silent or cannot be followed literally. `AGENTS.md` ("Deviations") requires a record of each. Two reviews of the contract revised it before the contract commit; the decisions below are the result.

## Decisions

### 1. The Vulkan loader is a process step with a policy

§4.1 loads the loader at process level "if rendering"; §4.6 item 1 puts the catch of `vk::detail::DynamicLoader`'s `std::runtime_error` into `GraphicsDevice.cpp`, but §8.1 moves the loader to the process level, into `Graphics/VulkanDispatch.cpp`.

- **Step:** `ProcessContextStep::VulkanLoader` runs between `CrashHandler` and `Glfw` (where §4.1 puts it; Luau and Jolt join before it later) and calls `VulkanDispatch::Initialize`. GLFW receives `VulkanDispatch::GetInstanceProcAddr()` (null without a loader).
- **Policy:** `ProcessContextSpecification::VulkanLoader` is `None` (no step), `Required` (a missing loader fails `Create` with Unsupported and `NoVulkanLoaderMessage`, "No Vulkan loader found; install a GPU driver with Vulkan 1.3 support"), or `IfAvailable` (a warning, and the step completes without a loader). `RunApplication` passes `Required` for `RendererMode::Vulkan` and `None` for `RendererMode::None`; the Tests main passes `IfAvailable` for every Tests process, so a machine without a GPU still runs the unit suite and the GPU tests skip (decision 14). `ProcessContext::IsVulkanLoaderAvailable()` reports the outcome.
- **Allowlist:** `Graphics/VulkanDispatch.cpp` joins `Banned.TryCatchFiles` for that one catch. It also holds `VULKAN_HPP_DEFAULT_DISPATCH_LOADER_DYNAMIC_STORAGE`, at the end of the file (the regex naming checker of the macOS job reads the macro as a namespace name when a namespace follows it).
- **Test hook:** `ENGINE_VULKAN_LOADER=missing` makes `Initialize` fail exactly as without a loader library; any other non-empty value is InvalidArgument, so a misspelled hook never passes silently. Dist ignores the variable (`GpuTestHooksEnabled`).

### 2. Platform additions

- **`Platform/Environment.h`:** `ReadEnvironmentVariable(name)`, with `Windows/EnvironmentWindows.cpp` (`GetEnvironmentVariableW`, UTF-8 out) and `Posix/EnvironmentPosix.cpp` (`getenv`). The MSVC runtime deprecates `getenv` (C4996) and `getenv_s` does not exist on POSIX, so no other file reads the environment. The name avoids `<windows.h>`'s `GetEnvironmentVariable` macro. Users: `ENGINE_VULKAN_LOADER` and `ENGINE_GPU`.
- **`Platform/ErrorDialog.h`:** `ShowErrorDialog(title, message)`, the "message box when windowed" of §4.6, §8.1 and §14.3 (a Dist Runtime has no console): `MessageBoxW` on Windows, `CFUserNotificationDisplayAlert` on macOS, none on Linux (X11 has no standard dialog; the message stays in the log and on stderr). The name avoids the `MessageBox` macro. It is step 4 of ProcessContext's fatal-error handler (ADR 0005 decision 9 reserved the place) and reports initialization failures in `RunApplication` and `Application::Run`, only when `ProcessContextSpecification::ShowErrorDialogs` is set, which `RunApplication` does for windowed applications and tests never do: a dialog blocks until a user dismisses it. Process tests that expect an initialization failure or a fatal error therefore run headless. The dialog itself is not unit-tested (it is modal); review covers it.
- **`Window::SetSize`** joins the frozen `Window.h` (implemented by the contract: one `glfwSetWindowSize`, tested on the null platform): the swapchain resize test needs a programmatic resize.

### 3. Renderer mode, graphics options and the editor's CI runs

- `Graphics/GraphicsSpecification.h` holds `RendererMode`, `VulkanApiVersion`, `GpuFault` and `GraphicsSpecification` (§4.1 "validation, GPU override, frames in flight, API cap", plus VSync, synchronization validation and the injected fault), with their command-line spellings, implemented header-only by the contract.
- `ApplicationSpecification` gains `Renderer` (default `Vulkan`, §4.1), `Graphics`, `ExpectNoGpuErrors`, `EnableImGui` and `ImGuiIniPath`. The engine options gain `--renderer vulkan|none` (§12.1, §13.9), `--gpu-validation[=sync]`, `--expect-no-gpu-errors`, `--vulkan-api 1.3|1.4`, `--gpu <index|name>` and `--gpu-inject-fault device-lost|oom-texture|hang`, all absent from Dist (§13.9 lists what Dist honours). `ENGINE_GPU` is read by `GraphicsDevice::Create` when `--gpu` is not given.
- **GPU processes started by tests validate and fail like the fixture.** §15.3 and the Roadmap run the GPU acceptance tests (the `ImGuiDemo` golden included, which runs a whole editor) with synchronization validation on, and any hazard fails. `--gpu-validation=sync` turns on validation plus synchronization validation; `--expect-no-gpu-errors` makes a run whose device reported an error or a warning in its whole life return `ExitCode::Failed` (1) instead of Success. The counts are read after the device's own teardown (`EngineContext::DestroyGraphics`, decision 32), so leaks and the validation layer's reports at `vkDestroyDevice` count too. `Test::GetGpuApplicationArguments` passes both to every Editor and Runtime process a GPU test starts. Architecture §13.9's later `--expect-no-errors` (M7, any logged error) is broader; the GPU-only option exists now because M5's process tests need it.
- **Overlap with M4:** M4's deliverables include `Editor --headless --renderer none`. Whichever milestone merges second keeps one definition of `--renderer` and of `RendererMode`; the lead resolves the conflict at the M4/M5 merge.
- **CI has no GPU.** With the Vulkan renderer as the default, the existing Editor and Runtime process tests of the unit suite pass `--renderer none` (they test windowing, the frame loop and the log, not rendering), and the in-process `Application` tests set `Renderer = None`. Rendering processes are tested in the GPU suite (decision 14). `EditorApp: the --renderer none editor needs no Vulkan loader` proves that logic-only runs never touch the loader.

### 4. The engine context's Graphics step and `shaders://`

- `EngineContextStep::Graphics` follows `Window` (§4.1) when `EngineContextSpecification::Graphics` is set: in development builds the read-only mount of the compiled shaders, then `GraphicsDevice::Create` (presenting to the context's window only in a windowed process), then the context's `ShaderLibrary` and `PipelineFactory`. They are destroyed before the window.
- **`shaders://` instead of `engine://Shaders`.** §2.2 and §8.12 mount `engine://Shaders` at `bin/<OutputDir>/Shaders` while `engine://` points at `Resources/`, but the VFS mounts whole schemes (ADR 0003). Development builds therefore mount the shader output as `shaders://` (`ShaderScheme`), from the new define `ENGINE_SHADER_DIRECTORY` (non-Dist, `ApplyFirstPartySettings`). The path is defined once, as the workspace global `ShaderOutputDirectory` in `premake5.lua`, which the Shaders project's output and the define both use. `ShaderLibrary` takes its root as a `VfsPath`, so M6/M7 can keep `shaders://` or mount the pak's shaders elsewhere without touching it.
- **Dist has no shader mount yet.** Exported games read their shaders from `Engine.pak`, which M7 mounts in this step (the context grows with every milestone by design, §4.1). Until then a Dist context's `ShaderLibrary` finds no variant (NotFound), which the M5 runtime never asks for: its frames are cleared and presented without shaders, and it has no ImGui in Dist. A review proposed an `EngineContextSpecification::ShaderRoot` field now, with the Graphics step failing in Dist without it; it was not adopted, because no caller could mount anything under the root before `Create` builds the context's VFS, and failing would break the M5 Dist runtime, which has no `--renderer none`.
- **One device per process at a time.** vulkan.hpp's default dispatcher, which NVRHI calls through, is process-level state that `GraphicsDevice::Create` initializes with its instance and device. A second live device is InvalidState; GPU tests create devices one after another.

### 5. The frame

- **The frame-boundary catch covers the whole frame** (§4.2 step 7, §4.6 item 2). `FrameLoop::RunFrame` runs the private `RunFrameSteps` (events, main-thread queue, steps, update, render, frame count and pacing) inside the one allowlisted `catch (const vk::SystemError&)`, because NVRHI work happens outside the render step too: asset swaps drained in step 2 upload textures (M6), the automation pump of step 3 runs `viewport.screenshot` (M4), and the editor's `--viewport-screenshot` reads back during its update. The catch maps the result with `GetFatalErrorKind(VkResult)`; device loss goes through `GraphicsDevice::RaiseDeviceLost` when the context has a device. The crash report's `FramePhase` breadcrumb names the step that threw. `IFrameLoopClient::OnFrameRender(frame)` is step 5 (frame phase `Render`). M4's `Dispatcher` catches `std::exception` for its JSON-RPC `Internal` error (§4.6 item 5), which would swallow a GPU error thrown inside a handler and let the editor run on a lost device; the lead is asked to make it rethrow `std::system_error`, from which `vk::SystemError` derives, so the frame boundary still sees it.
- `Application` gains the §4.1 hooks `OnRender(RenderContext&)` and `OnImGuiRender()`, the protected `GetImGuiLayer()`, and the private `InitializeRendering`/`ShutdownRendering`, which own the swapchain or offscreen target, the `FramePacer`, the `GpuProfiler` (decision 19) and the `ImGuiLayer`. `Graphics/RenderContext.h` is the per-frame data `OnRender` receives, with the frame's `GpuProfiler`, and defines `FrameClearColor`, the colour every frame's target is cleared to (the editor screenshot clears to it too). The frame order is documented in `Application.h`.
- **Rendering objects that fail at startup.** §8.14 item 7 makes render-target and pipeline creation failures `FatalError(OutOfMemory)`. `InitializeRendering` therefore turns a Gpu error creating a render target, framebuffer or pipeline into `FatalError(OutOfMemory)` (exit 4); other failures, such as Unsupported for a surface without an acceptable format, stay `ExitCode::InitFailed` (3). The editor's `ViewportCapture` (decision 16) follows the same rule.
- **Skipped frames and the UI clock.** A frame the swapchain skips (minimized, just recreated, or an acquire that timed out, decision 6) records nothing, calls neither `OnRender` nor `OnImGuiRender`, and passes `GraphicsDevice::GetLastSubmissionID` to `FramePacer::EndFrame`. `Application` accumulates the frame clock's delta until the next UI frame and passes the sum to `ImGuiLayer::BeginFrame`, which accepts 0 (a `SystemClock`'s first delta) and clamps to `ImGuiLayer::MinimumDeltaSeconds` (1 µs), because Dear ImGui asserts a positive `DeltaTime`.
- `imgui.ini` (§8.11) is `ApplicationSpecification::ImGuiIniPath` relative to the user-data folder, resolved under `ProcessContext`'s user-data root: the editor's `Editor/imgui.ini`, i.e. `user://Editor/imgui.ini` on disk.

### 6. Bounded GPU waits

- `RunBoundedGpuWait(slice, maxSlices)` is the pure state machine of §8.1: the budget is a count of slices (100 slices of 100 ms), so the "GpuHang after 10 s" rule is unit-tested without a GPU or a clock. `WaitForSubmission(device, submissionID, context)` applies it to `vkWaitSemaphores` on the graphics queue's timeline semaphore through the dispatcher's C entry point; `Readback` and screenshots use it, `FramePacer::BeginFrame` after `pollEventQuery`.
- **Swapchain acquisition is bounded but never fatal by itself.** `vkAcquireNextImageKHR` with an infinite timeout would be an unbounded wait, so each acquire waits at most one slice (`GpuWaitSliceNanoseconds`). A timed-out acquire (`VK_TIMEOUT`, `VK_NOT_READY`) means the presentation engine is holding its images back, as compositors do for a window that is hidden or occluded without being minimized (Wayland's FIFO, macOS occlusion), not that the GPU stopped. The frame is skipped (`SwapchainAcquireStatus::Skipped`, logged at Warn on the first of consecutive timeouts) and the next frame tries again. A GPU that really stopped is caught by `FramePacer`'s timeline waits: the skipped frame records the device's last submission for its slot, and the next frame of that slot waits for it, ending in `FatalError(GpuHang)` after the budget. §8.1 bounds only the timeline waits, so this is consistent with it.
- `GraphicsDevice::WaitForIdle` calls `vkDeviceWaitIdle` through the dispatcher's C entry point, as §8.1 allows for shutdown and resize, and maps its result: device loss to `RaiseDeviceLost`, anything else to `FatalError(GetFatalErrorKind(result))`. NVRHI's `waitForIdle` is the same call through vulkan.hpp's throwing wrapper, which catches only device loss, so out-of-memory results would have thrown outside the frame boundary (the swapchain's destructor, application shutdown) and terminated the process from a destructor (decision 32).
- **Swapchain results are tested through the real paths.** "Swapchain: resize, minimize and out-of-date recover" requires out-of-date to be handled as a `VkResult`, but no compositor produces `VK_ERROR_OUT_OF_DATE_KHR`, `VK_SUBOPTIMAL_KHR` or `VK_ERROR_SURFACE_LOST_KHR` on demand. `Swapchain::InjectAcquireResultForTesting` and `InjectPresentResultForTesting` make the next real call act on a given result through the same classification switch: a suboptimal acquire replaces the success of a call that acquired an image, out-of-date and surface-lost acquires replace the call (they acquire no image), and a present result replaces the return value of a real `vkQueuePresentKHR`. The windowed child drives every result through them; production code never calls them.

### 7. Device-fault details travel in the fatal-error message

§8.14 item 6 asks for `VK_EXT_device_fault` details in the crash report. `GraphicsDevice::RaiseDeviceLost(context)` appends `DescribeDeviceFault()` to the `FatalError(DeviceLost)` message, which becomes the report's Reason line, so `CrashHandler.h` stays unchanged (ADR 0005 decision 14 deferred this text to M5).

`GpuDiagnostics` implements `nvrhi::IMessageCallback`; its `message` override is defined in the class and delegates to `ReportNvrhiMessage`, because the regex naming checker accepts the third-party name only on an in-class `override` (ADR 0003 decision 26).

### 8. Fault injection semantics

§8.14 item 8 names the three faults; the contract fixes what each does.

- **device-lost:** the device-lost flag is set after the first submission, so the check that follows every submission ends the process through `RaiseDeviceLost`.
- **oom-texture:** every creation of a sampled-only texture (neither render target nor UAV) fails as if out of device memory, through `GraphicsDevice::CreateTexture` and both upload paths, while render targets, the swapchain and storage images keep working, so the application runs on and the failure path is observable. The ImGui font atlas is such a texture: `ImGuiRenderer` logs the failure once, keeps the invalid `ImTextureID` and skips draws that use it. The asset placeholder of the same path arrives with `GpuResourceCache` (M6), which reacts to the error with the placeholder and an `AssetDiagnostic` (§8.14 item 7); M5's test checks the logged diagnostic and that nothing crashes.
- **hang:** "a timeline wait that always reports `VK_TIMEOUT`". On a fast GPU the documented early-outs (`pollEventQuery` in `FramePacer::BeginFrame`, the completed-submission check of `WaitForSubmission`) would return before any slice runs, so the fault would never fire. Under the hang fault, `BeginFrame` skips `pollEventQuery` once its slot has a recorded submission, `WaitForSubmission` skips its early return, and every slice reports Timeout without calling `vkWaitSemaphores`. The first such wait (the third frame of a run with two frames in flight) therefore ends the process with `FatalError(GpuHang)` after the budget's 100 slices, without the 10 s of wall time: the budget's length is `RunBoundedGpuWait`'s unit-tested slice count, so the fault test does not need to wait it out.
- **The editor's autosave:** there is nothing to autosave before a project can be open (M4) and before `EditorCore/Autosave` (M10). `EditorApp` installs its fatal-error hook now, in the place the autosave will take, and the hook logs `Editor fatal-error hook (<kind>): no project is open, nothing to autosave`. The fault tests check that line in the crash report's last log lines, which proves the hook runs before the report; M10 replaces the line with the autosave check.

### 9. `GpuResourceTracker` holds a reference and sweeps after NVRHI

NVRHI destroys its objects itself and offers no destruction hook. The tracker keeps one reference to every object the creation wrappers made and, in `Sweep`, releases those it is the last owner of and counts them as destroyed. Host-copied images, which NVRHI does not own, are counted with `RecordCreated`/`RecordDestroyed`. In Dist every member except `HasOtherReferences` is a no-op (§8.14 item 5: "non-Dist").

- **Order.** NVRHI's submitted command lists hold a reference to every object they used until `runGarbageCollection` retires them, so `GraphicsDevice::RunGarbageCollection` runs NVRHI's `runGarbageCollection` first, then `Sweep`, then `HostImageUpload::CollectGarbage`; objects whose last other reference was a retired submission are released in the same frame. The device's destructor runs `vkDeviceWaitIdle`, `runGarbageCollection`, the `HostImageUpload`'s teardown, a final `Sweep`, the leak report (a `GpuDiagnostics` error, so it counts), then `ReleaseAll`. `GraphicsDevice::Destroy` runs the same teardown and returns the counts afterwards (decision 32).
- **Sweep repeats until a pass releases nothing.** Objects reference each other (a framebuffer its textures, a binding set its resources, a pipeline its shaders and layouts), and releasing one can make the tracker the last owner of another, so one `Sweep` after a garbage collection on an idle device leaves exactly the objects someone still holds; a test dropping an `OffscreenTarget` with depth sees its live counts return to baseline after one `RunGarbageCollection`.
- **Owners ask `HasOtherReferences`.** The tracker's reference would make "is the pool's reference the only one?" false forever in Debug and Release (and true in Dist), so `RenderTargetPool` would never reuse a target and `HostImageUpload` would never release an image. `GpuResourceTracker::HasOtherReferences(resource, callerReferences)` discounts the tracker's own reference and answers the same in every configuration; pools and caches (`RenderTargetPool`, `HostImageUpload`, M6's `GpuResourceCache`) use it and never read the reference count themselves.
- **Native-texture wrappers are not tracked.** `GraphicsDevice::CreateHandleForNativeTexture` does not track its wrapper: the tracker's reference would keep a host image's wrapper, and the image views NVRHI creates for it, alive past the moment `HostImageUpload` destroys the `VkImage`. The host image is counted as `HostImage` instead, and the swapchain's images live exactly as long as the swapchain.

### 10. Host image upload

`HostImageUpload::CreateTexture(desc, subresources, preferredPath)` returns `TextureUpload {Texture, Path}`, so the test can tell which path ran. Host-copied images are released like NVRHI's own objects: `CollectGarbage` (from `RunGarbageCollection`, after NVRHI's garbage collection) finds each image whose handle nobody besides the upload references (`HasOtherReferences(texture, 1)`; the untracked wrapper of decision 9), drops the handle, which destroys the wrapper, queues the `VkImage` with the last submission ID and destroys it once the timeline passed that ID (§8.1 path 1). The upload rejects render targets, UAVs and incomplete subresource lists with InvalidArgument.

### 11. The PNG codec and the stb implementation live in Graphics

§3 gives `stb_image_write` to Testing and §2.2 puts the stb implementation into `Asset/ThirdParty/StbImplementation.cpp`. But PNG encoding is needed by every user of screenshots: Testing (ImageCompare, golden outputs), `Automation/Methods` (`viewport.screenshot` in the runtime subset, which may not include Testing), App (`Runtime --screenshot-at`), the Editor and EditorCore (thumbnails); and golden tests must decode committed PNGs. All of them sit above Graphics, which already owns `Image` (`Readback::ReadTexture`'s result, §8.1).

- `Graphics/Image.h` holds `Image` and the codec (`EncodePng`, `DecodePng`, `WritePng`, `ReadPng`, `ConvertToRgba8`, `DownscaleImage`). `Graphics/ThirdParty/StbImageImplementation.cpp` defines `STB_IMAGE_IMPLEMENTATION` and `STB_IMAGE_WRITE_IMPLEMENTATION`, compiled without the PCH. `ModuleRules.json` gives Graphics `stb`, restricted to those two files, and Testing no longer has its `stb_image_write` grant.
- M6's `Asset/ThirdParty/StbImplementation.cpp` must not define those two macros again; its importers call stb_image through this implementation. It keeps `stb_image_resize2` (and cgltf its own file).

### 12. Shared shader vocabulary

- **`Shared/ShaderTypes.h`** gives both languages PascalCase names: Slang typedefs of its built-in types (`Float2`, `Float3`, `Float4`, `Float4x4`, `UInt2`, `UInt4`) and C++ aliases of the glm types (glm is global third party, so shared headers may use it). Lower-case `float4x4` aliases in C++ would break the naming rules, and two definitions per struct would defeat the shared header.
- **Layout rule:** glm types are 4-byte aligned and packed, and Slang's constant-buffer layout aligns `float3` to 16 bytes; each shared struct orders its members so both layouts agree (a `Float3` followed by a 4-byte scalar, `Float2` pairs on 8-byte boundaries). The C++ side `static_assert`s the size and key offsets, and "Shaders: SharedStructsMatchReflection" checks every member.
- **`Shared/ViewConstants.h`:** View, Projection, ViewProjection, InverseProjection, InverseViewProjection, CameraPosition, ProjectionKind (`ProjectionKindPerspective`/`ProjectionKindOrthographic`), OrthoHalfExtents, Near, Far, ViewportSize, InverseViewportSize, TanHalfFovY, AspectRatio, Exposure: 384 bytes, everything §8.3's reconstructions need.
- **`Common/Color.slang`** is a Slang module (`import Common.Color;`) with the sRGB OETF and its inverse (§8.9). `Passes/Triangle.slang` and `Passes/ImGui.slang` (with `Shared/ImGuiConstants.h`, the push constants of §8.11) join `Shaders.json`; `Smoke` stays.
- **The matrix convention is checked on the GPU** (§8.4). `Passes/MatrixConvention.slang`, a compute program no pass uses (like `Smoke`), transforms a buffer of known vectors by `ViewConstants::ViewProjection`; "Shaders: matrix convention transforms known vectors" compares the results with glm's `M * v` for a matrix with sixteen distinct entries, which tells the product from the transposed one. Its layout lives in `Tests/Source/Support/MatrixConventionProgram.h`.

### 13. Shader reflection and pipeline layouts

- `Graphics/ShaderReflection.h` (beyond the Roadmap's file list) parses the parts of slangc's `-reflection-json` the checks need, without a GPU: binding kind, set, shifted binding number, array size, constant-buffer and push-constant sizes, image formats, and struct member offsets.
- `PipelineLayoutDescription` describes a pipeline without a device (program, entries, permutation, binding layouts, the formats the pass creates for its storage images, and since decision 32 the byte size it binds to each constant buffer); `ValidatePipelineLayout` is §8.12's check. Each pass provides one through a static function, and "Shaders: LayoutsMatchReflection" checks every engine pipeline and that every `Shaders.json` program has one. The Smoke and MatrixConvention programs, which no pass uses, have their layouts in `Tests/Source/Support/`; Smoke drives the §15.3 "compute arithmetic" GPU test.
- The pipeline specifications carry `Specializations` (Vulkan specialization constants, applied to every stage through `GraphicsDevice::CreateShaderSpecialization`), which §8.5's debug-view toggles need, so M8 does not change the frozen header.
- **"spirv-val clean":** `CompileShaders.py` already runs `spirv-val` on every output and writes the stamp only after a complete run validated, so a build with shaders is spirv-val clean by construction. "Shaders: every Shaders.json variant was compiled and passed spirv-val" checks the stamp and the outputs from C++.
- The shader checks run in doctest's `Static` suite (§15.1 T0), which the unit stage includes.

### 14. GPU and golden tests

- GPU test cases carry `doctest::test_suite(Test::GpuSuite)`; golden ones live in `TEST_SUITE(Test::GoldenSuite)` ("Golden"). The unit stage excludes both (`--test-suite-exclude=GPU,Golden`).
- `HeadlessGpuFixture` creates the device (validation and synchronization validation on, the API cap of `--vulkan-api`), mounts `shaders://` and checks zero validation errors and zero live objects at destruction. doctest has no runtime skip, so `ENGINE_REQUIRE_GPU` passes a case after printing "GPU test skipped: <reason>" without a device, and fails it under `--require-gpu`, which CI.py passes on this machine (§15.2).
- New Tests options: `--require-gpu`, `--vulkan-api=<1.3|1.4>`, `--update-golden`. Test.py's gpu suite runs the GPU tests once without and once with `--vulkan-api=1.3` (§8.1, §15.3). `GetGpuApplicationArguments` passes `--gpu-validation=sync`, `--expect-no-gpu-errors` and the API cap to Editor and Runtime processes (decision 3), and `GetGpuTestsChildArguments` the cap and `--require-gpu` to Tests child processes.
- **Skipped GPU and golden tests:** Test.py's listing check (ADR 0004 section 3) lists the unit selection only. Lint's `test-skip` rule catches a skip in GPU and golden cases too, and Test.py's gpu and golden suites must run the same listing check over their own selection (stream E).
- **Device class:** `GetDeviceClass(vendorID, driverVersion, driverID)` decodes the driver major with the encoding of the driver that reported it, chosen by `VkPhysicalDeviceDriverProperties::driverID` (NVIDIA's proprietary driver bits 31-22, Intel's Windows driver bits 31-14, every other driver `VK_API_VERSION_MAJOR`), never by the OS it runs on, so the function is pure and its unit test gives the same answers on Windows, Linux and macOS. It replaces the last digit of a major with two or more digits by `x` ("nvidia-58x", §15.4) and keeps a one-digit major ("amd-2").
- **Goldens:** `Test.py --update-golden` writes candidates directly into `Tests/Golden/<DeviceClass>/`, reviewed through the diff before commit (skill `golden-images`). The smoke mode of a device class without goldens requires a valid image with at least two colours and a mean luminance in [0.01, 0.99], and warns "goldens missing".

### 15. The ImGui GLFW glue and NoPCH files

- `ImGui/ImGuiGlfwImplementation.cpp` includes the vendored `backends/imgui_impl_glfw.cpp`, as `Vendor/imgui/VENDOR.md` prescribes. The include step rejects `.cpp` includes (CodeStyle §4.4 rule 6), so `ModuleRules.json` gains `SourceIncludes`, which grants that one file that one vendored source, and `Lint.py` honours it.
- **The glue includes `<vulkan/vulkan.h>` first.** Without `VULKAN_H_` the backend declares its own one-enumerator `enum VkResult` and handle stand-ins, a second, different definition of `::VkResult` in the Engine library next to `vulkan_core.h`'s: a one-definition-rule violation that Dist's link-time optimization may diagnose (`-Wodr`, `-Wlto-type-mismatch`) or miscompile once Runtime links the glue through `Application`'s `ImGuiLayer`. `ModuleRules.json` grants the ImGui module the Vulkan headers, restricted to the glue.
- The ImGui module may include `ShaderShared`: `ImGuiRenderer`'s push constants are `Shared/ImGuiConstants.h`.
- premake 5.0.0 has no `NoPCH` flag; `Engine/premake5.lua` sets `enablepch "Off"` for `Engine/*/ThirdParty/**.cpp` and the GLFW glue.
- `ImGuiLayer::BeginFrame(deltaSeconds, frameSlot)` overwrites the backend's wall-clock delta with the frame clock's time since the last UI frame (decision 5), so a headless editor on a `ManualClock` renders identical UI frames (the `ImGuiDemo` golden).

### 16. Screenshots live in Engine, before `MethodRegistry`

The Roadmap's `viewport.screenshot` (clear/triangle scene) and `editor.screenshot` (ImGui demo window) need M4's `MethodRegistry`, which is built in parallel. M5 delivers the capability, and the lead registers the two methods, with their Python tests and parity coverage, after the M4/M5 merge. The capability lives where its callers can reach it under §3: `viewport.screenshot` belongs to `Automation/Methods` (shared by Editor and Runtime, §3, §13.5), `Runtime --screenshot-at` to the runtime, and `editor.screenshot` to `EditorCore`, which may include neither the Editor executable nor ImGui.

- **`Renderer/ViewportCapture.h`:** a `ViewportCapture` created once at startup (§8.12: every engine pipeline is created at startup) that owns its pipeline (`Renderer/TrianglePass` in M5, the scene renderer from M7) and renders any requested size into a new `OffscreenTarget`, read back with `Readback` (`Capture(ViewportScreenshotRequest)`: 640×360 by default, `MaxDimension`). `Automation/Methods`, App and the Runtime may include Renderer. ### 19. GPU timings on the profiler timeline

NVRHI's timer queries measure durations, not timestamps, so `GpuTimingSample::StartMilliseconds` is laid out back to back: a scope starts where its previous sibling ended, or where its parent started, relative to the frame's first scope; the gaps between scopes are not measured. ### 20. Frozen-header changes accepted at integration

No public declaration of a frozen M5 header changed, except the test-support additions in decision 30. The streams added private members, nested types and helpers, as decision 17 allows:

- `VulkanDispatch.h`: private `RegisterDevice`, `UnregisterDevice` and `HasDevice`, plus `friend class GraphicsDevice`. These enforce one device per process (decision 4).
- `GraphicsDevice.h`, `GpuResourceTracker.h`, `HostImageUpload.h`, `Swapchain.h`, `FramePacer.h` (which now includes `<nvrhi/nvrhi.h>` and `<vector>`), `GpuProfiler.h`, `Application.h` (`FrameRendering`, `m_Rendering`), `ImGuiLayer.h`, `ImGuiRenderer.h`, `OffscreenTarget.h`, `Readback.h`, `RenderTargetPool.h`, `ViewportCapture.h` and `HeadlessGpuFixture.h`.

These documentation comments were corrected to describe the behaviour the implementations and their tests established:

- **`GraphicsDevice::DescribeDeviceFault`:** `vkGetDeviceFaultInfoEXT` is valid only on a device that is really lost, and the validation layer rejects it otherwise. A healthy device, and one whose loss is only the injected device-lost fault, report "no fault information" without querying.
- **`HostImageUpload`:** both paths create `keepInitialState` textures whose initial state is `ShaderResource`, never `setPermanentTextureState`. NVRHI refuses `copyTexture` out of a permanent-state texture, which would break `Readback` and "Texture upload: host-copy and staging paths read back identically". Decision 10 and Architecture §8.1 path 1 and §8.2 follow.
- **`Swapchain`:** an iconified window counts as minimized, and the swapchain is released while minimized. Recreations are coalesced into one per acquire (decision 22). `Application` no longer calls `RequestRecreate` on a `WindowResizeEvent`: the several events of one restore cost an extra recreation and an extra skipped frame, and the size check alone covers resizes. `Create` documents its InvalidState and Unsupported errors.
- **`FramePacer`:** submission 0 returns at once, and failed waits map through `GetFatalErrorKind` (out of memory becomes OutOfMemory).
- **`PipelineFactory::ValidatePipelineLayout`:** the comment now lists every check the implementation makes:
  - the resource shape;
  - stage visibility of each used binding;
  - the layout's `bindingOffsets`;
  - push constants matched by kind and capped at 128 bytes;
  - agreement between entry points;
  - leftover `StorageImages` entries, storage images without `[vk::image_format]`, unbounded arrays, and duplicate sets and bindings.

  A `BindingLayoutDesc` carries no byte size, so decision 32 adds `PipelineLayoutDescription::ConstantBuffers` for the constant-buffer size check §8.12 names. `ParseShaderReflection` skips specialization constants and rejects ParameterBlocks.
- **`TrianglePass.h`, the `PipelineFactory.h` `RenderState` comment, `Shared/ViewConstants.h` and `Passes/Triangle.slang`:** clip space has +Y up and nothing flips Y (decision 23).
- **`ImGuiLayer.h` and `ImGuiRenderer.h`:**
  - the null-platform backend (decision 24);
  - `Create` fails with InvalidState while any Dear ImGui context exists, which the contract's own test expects;
  - pipelines are created per target format on first use (decision 25), binding sets are cached per texture and per pipeline, and the error lists are completed.
- **`Readback::ReadTexture`:** a 3D texture is InvalidArgument (NVRHI would assert on a depth-slice copy).
- **`HeadlessGpuFixture.h`:**
  - `ReportGpuUnavailable` also writes the Warn line that Test.py counts.
  - The destruction checks include the warning count (decision 26).
  - `ENGINE_CHECK_GOLDEN` in `GoldenImage.h` prints a doctest `MESSAGE` for the SmokePassed and Updated outcomes. Its `WARN_MESSAGE` printed nothing when the check passed. The macro's name, parameters and pass/fail meaning are unchanged.
- **The skeleton test "HeadlessGpuFixture: GPU process arguments follow the run's options":** it looks for `--gpu-validation=sync`. `--gpu-validation` is an optional-value option, and the frozen comment already gave that spelling.
- **The child test of "Swapchain: resize, minimize and out-of-date recover":** it is renamed "Swapchain: a native window's swapchain survives resizing and minimizing". doctest's `--test-case` filter splits on commas, so the contract's name selected no test. The acceptance name of the parent is unchanged.

### 21. Uploaded and immutable textures keep their initial state

Uploaded textures, and later every immutable texture, are `keepInitialState` textures in `ShaderResource` (decision 20). Every command list starts and ends with them in that state, and copying out of them stays legal. The host-copy path declares the layout to NVRHI with one submitted `beginTrackingTextureState` command list.

M8 should follow the same rule for the IBL cubes and the DFG LUT that §8.6 calls "state permanent", because the §15.3 references read them back.

### 22. The swapchain coalesces recreations

Every resize event and every suboptimal or out-of-date result is coalesced into one recreation at the next acquire, which skips that frame. Recreation waits for idle, drops the image handles and runs garbage collection, so the image views go before the swapchain that owns the images. §8.1's "debounced for 2 frames" applies to viewport render targets (the editor viewport, M10), not to the swapchain.

### 23. Clip space has +Y up; nothing flips Y

NVRHI's Vulkan backend gives every viewport a negative height (`VKViewportWithDXCoords` in `Vendor/NVRHI/src/vulkan/vulkan-graphics.cpp`), so clip space is D3D-like with +Y up. With §8.3's Y-flipped projection, the GPU showed that back-face culling removed the counter-clockwise triangle and the image came out upside down.

- Projections never flip Y. The perspective term `m[1][1]` is `+f`. `TrianglePass::MakeViewConstants` follows, its CPU test is "TrianglePass: the fixed camera is orthographic and reverse-Z with clip-space +Y up", and "Rasterizer: CCW triangle survives back-face culling" also checks that the image is upright and that front-face culling removes it.
- ImGui's projection uses the same convention: Scale `(2/w, -2/h)`, Translate `(-1 - 2·x0/w, 1 + 2·y0/h)`.
- `SV_VertexID` and `SV_InstanceID` compile to SPIR-V's DrawParameters capability, which needs `VkPhysicalDeviceVulkan11Features::shaderDrawParameters`, and the validation layer rejects such a shader without it. `Triangle.slang` uses `SV_VulkanVertexID` instead. No M5 shader needs the feature, so the device does not enable it yet. The first pass that uses `SV_InstanceID` (M7 or later) enables it in `GraphicsDevice::Create` when the device supports it, which nearly every Vulkan 1.3 device does, together with that pass's GPU test; until then shaders use `SV_VulkanVertexID` and `SV_VulkanInstanceID`.

### 24. ImGui's GLFW backend runs on native platforms only

The vendored `imgui_impl_glfw` needs a native window handle. On GLFW's null platform, `glfwGetWin32Window` raises `GLFW_PLATFORM_UNAVAILABLE`, after which `IM_ASSERT(bd->PrevWndProc != nullptr)` aborts the process on Windows, and `glfwGetCocoaWindow` logs a GLFW error on macOS. In headless mode `ImGuiLayer` is therefore the platform side itself:

- display size and framebuffer scale come from the `Window` every frame;
- the delta comes from the frame clock, as on native platforms;
- the clipboard is GLFW's in-memory one, so a headless run never touches the user's clipboard;
- there is no input, because the null platform delivers none.

The vendored backend runs on Win32, Cocoa and X11, and the GPU suite covers it with a windowed child. This revises §8.11 and `Vendor/imgui/VENDOR.md`, both amended here.

### 25. ImGui pipelines are created per target format on first use

The frozen `ImGuiRenderer` creates its pipeline for a framebuffer format the first time it renders into one: the swapchain's format (BGRA8 on most desktops) on the first UI frame, and RGBA8 for the first screenshot. That departs from §8.12's "every engine pipeline is created at startup", which stays true for the passes. A pipeline failure on that frame returns a Gpu error from `Render`, and the failure rule of §8.14 item 7 still applies: `Application` turns any Gpu error from `ImGuiLayer::Render` (a pipeline, geometry buffer or binding set that could not be created) into `FatalError(OutOfMemory)`, as `InitializeRendering` does at startup (decision 5). Texture failures never come back through `Render`: the renderer logs them and skips their draws (decision 8). Other `Render` errors are logged once per run of failing frames.

### 26. Zero validation messages; the loader's notes do not count

- The GPU fixture fails a test on any `GpuDiagnostics` error or warning, which covers validation, synchronization validation and NVRHI, and reads the counts after the device's teardown (`GraphicsDevice::Destroy`). Editor and Runtime processes started by GPU tests fail the same way through `--expect-no-gpu-errors` (decision 3), and the windowed children check the same counts. "GraphicsDevice: create and destroy with zero validation messages" therefore holds for every GPU test. "GraphicsDevice: validation and synchronization-validation messages reach GpuDiagnostics and count" provokes a real write-after-write hazard and a real validation error to prove the wiring.
- The debug messenger's general messages named "Loader Message" describe the machine's installation, not the application's use of Vulkan. Examples: a third-party implicit layer built for an older API version, such as OBS's `VK_LAYER_OBS_HOOK` on the developer machine, or no driver at all on a hosted runner. They are logged as `Vulkan loader (<severity>): ...` warnings and never counted. The rule is the public `IsLoaderInstallationMessage`, applied by `GpuDiagnostics::ReportDebugUtilsMessage` and unit-tested on the CPU. A machine without a driver then fails `GraphicsDevice::Create` with an error value that the GPU tests report as their skip reason, instead of failing the test through an undeclared Error log. The loader's validation of API calls carries the validation type and still counts.
- Disabling implicit layers in GPU runs (`VK_LOADER_LAYERS_DISABLE=~implicit~`) was rejected. It also disables vendor layers such as `VK_LAYER_NV_optimus`, which change device enumeration on hybrid laptops, and the loader warns about each disabled layer.

### 27. NVRHI's timer-query pool

`GraphicsDevice` raises `DeviceDesc::maxTimerQueries` to at least `GpuProfiler::MaxScopesPerFrame × FramesInFlight × 2`. That covers an application profiler and a capture's. With NVRHI's default of 256, a third frame in flight or a second profiler would make `createTimerQuery` report an NVRHI error. "GpuProfiler: two profilers time MaxScopesPerFrame scopes in every one of three frames in flight" is the regression test: it fails on the default pool through the fixture's error check.

### 28. GPU tests gate every commit; the hosted runners run them too

- **Commit gate:** `PreCommit.py` runs the unit, gpu, golden and feature suites in Debug, the gpu and golden suites with `--require-gpu` (§15.1: T2 gates every commit on this machine's GPU). The golden images run in Debug there and must match the Release goldens, which the matrix allows (§15.8); the committed goldens match bit for bit in both configurations. `--gpu-optional` drops `--require-gpu` on a machine without a Vulkan device.
- **`CI.py`:** the gpu and golden stages pass `--require-gpu` unless `--gpu-optional` is given.
- **GitHub Actions** (revises decision 18's "the file needs no change"):
  - **Linux** (GCC 14 and Clang 19) runs the gpu stage in Debug and Release and the golden stage in Release on Lavapipe (`mesa-vulkan-drivers`), with `--require-gpu`. The SDK's `VK_LAYER_KHRONOS_validation` comes through `VK_LAYER_PATH`, `VK_DRIVER_FILES` selects Lavapipe's ICD alone, and the stages run inside the unit stage's Xvfb display with openbox, so the windowed swapchain and application children present to X11. The workflow fails early if the layer or the ICD manifest is missing, and logs `vulkaninfo --summary`.
  - **Lavapipe's features:** Every Mesa release Ubuntu 24.04 ships (24.0 and later) exposes Lavapipe as a Vulkan 1.3 device, and it meets §8.1's feature set: dynamic rendering, synchronization2, timeline semaphores, `samplerAnisotropy`, `imageCubeArray`, `shaderStorageImageExtendedFormats`, storage support for the six required formats, and a graphics and compute queue. `--require-gpu` is therefore correct there, and a regression in the image would fail with the selection's per-candidate rejection reasons instead of skipping silently. Mesa releases that report Vulkan 1.4 with `hostImageCopy` also run the host-copy path. No other machine has run this configuration yet: the first Linux CI run is the evidence.
  - **Lavapipe goldens:** the golden stage runs in smoke mode on Lavapipe. §15.4 commits no software-rasterizer goldens, and this machine cannot run Lavapipe to render candidates for review, so none are committed.
  - **Windows and macOS** run the gpu and golden stages with `--gpu-optional`. The Windows image has no Vulkan driver, and MoltenVK's loader is not on the macOS library path (`copy_only=1`). Every GPU test case therefore names the reason, passes without running, and the step ends as a warning.

### 31. Known limits carried forward

- **NVRHI does not reference cleared textures.** `clearTextureFloat` and `clearDepthStencilTexture` record no command-buffer reference to the texture, so a texture used only by a clear and dropped before its submission completes can be destroyed while the GPU uses it. Owners keep targets alive until their frame retires, or wait for idle before garbage collection, as the fixture does. `Application` keeps each frame slot's headless target until the slot's next frame has waited for it, and `RenderTargetPool` releases a free target only once the submission of the last frame that used it has completed (decision 32). The tracker cannot do it for every owner: in Dist it holds no reference, so a dropped object dies with its last handle.
- **Readback assumes coherent staging memory.** It assumes NVRHI's `HostVisible | HostCached` staging memory is host-coherent, as it is on NVIDIA, AMD and Mesa drivers. NVRHI offers no hook to invalidate a mapped range.
- **`imgui.ini` holds a date.** Dear ImGui 1.92.9 writes `LastUsed=<date>` into it. Rendering and goldens do not depend on the date: they use a fresh user-data folder.
- **A rare hang at exit was not reproduced.** Stream B saw one hang after the crash report of an injected device-lost fault in about 30 runs. The likely cause is `std::_Exit` reaching `ExitProcess`, which runs the driver's and the validation layer's DLL detach while GPU work is in flight. Integration ran 30 runtime and 40 editor fault runs (device-lost and hang), and every one exited 4 within a second. The Core owner is asked to consider `TerminateProcess` after the logs are flushed on Windows (`Core/FatalError.cpp` is M1's).

### 32. Review findings applied at integration

The review of the integrated milestone found the following; the fixes are part of the milestone commit, each with a test that fails without it where the failure can be provoked.

- **Frame targets outlive the frames that cleared them** (decision 31). Destroying a headless frame target that a frame still in flight had cleared was a use-after-free: with the frame held back on the GPU (`Test::GpuSubmissionGate`, below), the validation layer reported `vkDestroyImage` of an image in use, and the GPU then faulted on freed memory. "Application: a headless frame target replaced by a resize outlives the frames that cleared it" and "RenderTargetPool: a free target is released only after the submissions that used it completed" are the regression tests. A fix in `GpuResourceTracker::Sweep` was rejected: it covers only Debug and Release, because the Dist tracker holds no reference.
- **The whole life of a device is checked.** `GraphicsDevice::Destroy(Scope<GraphicsDevice>) -> GpuMessageCounts` and `EngineContext::DestroyGraphics()` return the device's counts after its teardown; the tracker's leak report is a `GpuDiagnostics` error. `HeadlessGpuFixture`, `--expect-no-gpu-errors` (which counts warnings too) and the windowed swapchain child read them. Process tests also check that the process printed no GPU message line (`Test::FindGpuMessageLines`), and clean runs no error line either (`Test::FindProblemLogLines`).
- **The debug messenger's routing is testable.** `GpuDiagnostics::ReportDebugUtilsMessage` holds the callback's logic and prefixes the message ID ("[SYNC-HAZARD-WRITE-AFTER-WRITE] ...") when the text lacks it; `IsLoaderInstallationMessage` is decision 26's rule. One `VkResultToString(VkResult)` ("ErrorDeviceLost (-4)") in `GpuDiagnostics.h` replaces four local versions.
- **`WaitForIdle` never throws** (decision 6).
- **Host image upload.** `ValidateUpload` checks every pitch product for overflow and the host copy's 32-bit row lengths, compares the subresource count before sizing anything from the desc, and rejects 1D textures taller than 1. `HostImageUpload::SupportsHostImageCopy(const nvrhi::TextureDesc&)` asks `vkGetPhysicalDeviceImageFormatProperties2` for the image the host copy would create (type, cube flag, usage) and checks the desc against its limits; `CreateTexture` takes the host-copy path only then. The per-format overload keeps only the cached format features.
- **An empty `Image` is invalid.** The new tests of the golden harness found that a size mismatch wrote a bogus `<Name>-diff.png` (a PNG with a 0×0 header), because a default-constructed `Image` counted as valid. `Image::IsValid` now requires a size above zero, as `CreateImage` does, so `EncodePng` refuses an empty image and a comparison of two sizes writes no difference image.
- **Constant-buffer sizes are checked** (§8.12): `ConstantBufferSize` and `PipelineLayoutDescription::ConstantBuffers`, filled by `TrianglePass` and the test programs.
- **ImGui pipeline failures are fatal** (decision 25).
- **Test support.** `Test::MountCompiledShaders`, `Test::GpuSubmissionGate` (a timeline semaphore the next submission waits for until the test signals it, so a submission stays in flight deterministically), `Test::FindGpuMessageLines` and `Test::FindProblemLogLines` join `HeadlessGpuFixture.h`; `Test::GoldenSettings`, `GetRepositoryGoldenSettings` and a `CheckGoldenImage` overload with explicit settings join `GoldenImage.h`, so the comparison paths are tested on the CPU in a temporary directory. Host-copy skips are logged with a stable prefix, which `Test.py` reports (a warning under the 1.4 cap).
- **Frozen headers changed** (integration acting as contract owner): `GpuDiagnostics.h`, `GraphicsDevice.h`, `EngineContext.h`, `HostImageUpload.h`, `PipelineFactory.h` and `RenderTargetPool.h` (public additions and documentation), `Swapchain.h` (the private `Image` is now `SwapchainImage`, which no longer hides `Engine::Image`), `Image.h` (`IsValid`), `ImGuiRenderer.h` and `OffscreenTarget.h` (documentation), and the test support above.
- **Not testable in process:** an out-of-memory result of `vkDeviceWaitIdle` and a Gpu error from `ImGuiLayer::Render`. Neither can be provoked: NVRHI asserts on every failed Vulkan creation in Debug and Release, and no injected fault reaches those paths.

## The M4/M5 merge

### 33. Merging M5 with M4, and the screenshot methods

The lead merged `milestone/m5` into the branch that already holds M4 (`Docs/Decisions/0008-m4-decisions.md`). Both milestones' behaviour is kept. Where they met, this is what the merge decided.

**One definition of each shared thing.**

- **`--renderer`** (decision 3, "Overlap with M4"). The engine option of `GetEngineCommandLineOptions` (`RendererMode`, `RendererModeFromCommandLine`) is the only definition. The Runtime takes the option too, so it cannot live in EditorCore. M4's `EditorRenderer`, `EditorLaunchOptions::Renderer` and the `--renderer` entry of `GetEditorCommandLineOptions` are gone. The spelling rule is M5's: exactly `vulkan` or `none`, as "GraphicsSpecification: command-line spellings round-trip and reject anything else" tests. M4 had accepted any ASCII case, so its test "EditorCommandLine: every option parses into the launch options" now passes `none` instead of `NONE`, and its `--renderer metal` case moved out of the EditorCore list. The engine's own test rejects `opengl`, and "EditorApp: inconsistent editor options are usage errors" still rejects `metal` for the whole process. `GraphicsSpecification.h` gains `RendererModeToCommandLine`, the inverse used for `session.info`'s `renderer` (`AutomationServerSpecification::RendererName`). The merge acts as contract owner for this addition to a frozen header.
- **`EngineContextSpecification`** holds `RegisterTypes` (M4) and `Graphics` (M5), in that order. `Application` passes both. `ApplicationSpecification` holds `RegisterTypes`, `Renderer`, `Graphics`, `ExpectNoGpuErrors`, `EnableImGui` and `ImGuiIniPath`.
- **The frame.** In order, a frame runs the events, the queue drain, the safe point (`OnFrameSafePoint`, M4), the steps, the update and the render (`OnFrameRender`, M5), all inside the frame-boundary catch. `IFrameLoopClient` has both hooks, and `Application` forwards them to `OnSafePoint`, `OnRender` and `OnImGuiRender`. In "FrameLoop: the safe point runs once per frame after the queue drain and before the steps", the recording client now records the render too, so the test also checks that rendering follows the update.
- **`EditorApp`** is M4's host with M5's rendering.
  - The factory parses the engine's, EditorCore's and the executable's own screenshot options. It sets `RegisterTypes`, `EnableImGui` and `ImGuiIniPath`, and turns the headless throttle off for `--batch` and `--upgrade`.
  - `OnInitialize` installs the fatal-error hook, creates the `ViewportCapture` when there is a device (a Gpu error there is `FatalError(OutOfMemory)`), and then builds the EditorCore state. The automation server receives the captures and the system-error handler (below).
  - `OnShutdown` releases the server and the editor first, then the capture, then the hook. A failed `OnInitialize` runs `OnShutdown` itself before it returns the error, because `Application::Run` does not call `OnShutdown` after a failed `OnInitialize` and destroys the engine context and its device next. Otherwise a rendering editor whose EditorCore initialization failed (an invalid or locked project, a missing batch file, a server that cannot start) freed the capture's GPU objects after the device and crashed with exit code 4 instead of returning 3. "EditorApp: a rendering editor whose EditorCore initialization fails exits 3 without GPU errors" and "EditorApp: a rendering editor on a locked project exits 3 without GPU errors" (GPU suite) cover it.
  - The UI is still Dear ImGui's demo window (`OnImGuiRender`).
  - Headless editors listen for automation unless the run is one-shot (ADR 0008 decision 14). This holds for rendering editors as well, including the GPU tests' editors.
- **The fatal-error hook** logs "Editor fatal-error hook (<kind>): nothing is autosaved before EditorCore/Autosave (M10)". M5's "no project is open" was true before M4, and it is false once a project can be open. The hook may run on any thread, so it reads no editor state. The fault-injection tests check the new line.
- **The Dispatcher and GPU errors** (decision 5 asked the lead to make the Dispatcher rethrow `std::system_error`). Lint bans every rethrow (`banned-throw`), so the Dispatcher instead hands a `std::system_error` escaping a handler, a `Poll` or a `Cancel` to the host's `DispatcherSpecification::SystemErrors`, before the usual exception handling. The editor passes a handler through `AutomationServerSpecification::SystemErrors`. When its device exists, the handler maps an error of `vk::errorCategory()` with `RaiseVulkanError` (new in `GraphicsDevice.h`), the function the frame-boundary catch in `FrameLoop.cpp` now calls too: device loss goes through `RaiseDeviceLost`, everything else through `FatalError(GetFatalErrorKind(result))`. A GPU error inside `viewport.screenshot` therefore ends the process like the same error in a frame, instead of becoming an Internal response on a lost device. When a handler returns, the error is handled like any other exception: it asserts in Debug and becomes Internal otherwise. Tests:
  - "Dispatcher: a std::system_error escaping a handler goes to the host's SystemErrorHandler first" (a death test);
  - "Dispatcher: after a SystemErrorHandler that returns, a system error is handled like any other exception";
  - the protocol test method `test.systemError`.
- **Scripts.** Every suite, stage and flag of both sides is kept, as follows.
  - `Test.py` runs the unit, gpu, golden and automation suites. `run_suite` dispatches between the doctest runs (`plan_runs`, one per API cap for gpu) and the Python run, and `junit_path` takes a report stem.
  - `PreCommit.py` runs `unit,gpu,golden,feature,automation` in Debug with `--require-gpu`, unless it gets `--gpu-optional`.
  - `CI.py` runs the gpu, golden and automation stages through `device_suite`, so `--gpu-optional` reaches all three.
  - `Lint.py` keeps M4's Python contract scopes and M5's `SourceIncludes`.
  - `.github/workflows/ci.yml` runs the automation stage on every job:
    - Windows and macOS with `--gpu-optional`;
    - Linux in the Release step, inside the Xvfb display, on Lavapipe with `--require-gpu`.

  It keeps M4's setup of the virtual environment and pip cache, and M5's Lavapipe steps.

**`viewport.screenshot` and `editor.screenshot`** (decision 16; Roadmap M5 deliverables):

- **Where.** `EditorCore/Automation/ScreenshotMethods.h|.cpp`, one file for the screenshot theme as `ObserveMethods` is for observation. `viewport.screenshot` is `AvailableInRuntime`, and its declarations move to `Engine/Automation/Methods` with the Runtime subset in M7 (ADR 0008 decision 26).
- **The captures.** They are injected, because EditorCore may not include ImGui. `AutomationServerSpecification::Screenshots` (`ScreenshotCaptures`) carries `Viewport(width, height)` and `EditorUi()`. The editor fills them from `EditorApp::CaptureViewport` (`ViewportCapture::Capture`) and `EditorApp::CaptureEditorUi` (`CaptureImGuiScreenshot`). The `--viewport-screenshot` and `--editor-screenshot` options call the same two functions. Without a device (`--renderer none`) the server gets no captures, and both methods answer Unsupported with the hint to start the editor without `--renderer none`. The handlers downscale with `DownscaleImage`, encode with `EncodePng` and write the file. The C++ tests can therefore inject CPU captures.
- **Params** (§13.5).
  - `viewport.screenshot {view, width?, height?, camera?, debugView?, annotate?, maxDimension?, inline?}`: `view` is required (`ViewportView`, case-insensitive, echoed as `Scene`). `width` and `height` default to the golden size of 640×360, and `maxDimension` to 1024 (§13.4); each is 1 to `MaxViewportScreenshotDimension` (8192). `inline: true` adds the PNG as base64 `data` when the PNG is at most 30 KB (`MaxInlineScreenshotPngBytes`); a larger PNG is only written, and the result reports `inlineOmitted: true`. The result therefore stays below the 48 KB offload threshold: an offloaded result would carry neither the PNG's `path` nor its `mimeType` (the offload summary describes strings by length), and the MCP bridge could return no image. Inline images suit a small `maxDimension`.
  - Nothing is accepted and ignored. Four members need later milestones, and whenever one is present the call fails with Unsupported, located at its pointer and naming the milestone:
    - `view: "game"`: play sessions and the scene renderer, M7;
    - `camera`: camera entities, M7;
    - `debugView`: §8.5's debug views, M8;
    - `annotate`: the overlay pass, M9.

    Those milestones turn each refusal into behaviour.
  - `editor.screenshot {maxDimension?}`: the editor UI's last frame, re-rendered at its framebuffer size, 1600×900 for a headless editor. It re-records the draw data of the last UI frame the editor rendered. A request answered at a later safe point than another one shows that request's effects, because a UI frame renders in between. A request handled earlier in the same `AutomationServer::Pump` (pipelined, or another client's) does not show yet, and while a windowed editor is minimized no UI frame renders, so the screenshot shows the UI from before. The M5 UI shows no editor state. Waiting for a UI frame rendered after the request, as a pending operation that keeps the wire contract, comes with the editor panels (M10).
- **Results.** The PNG's absolute native `path`, `mimeType` "image/png", and `width` and `height` after the downscale. `viewport.screenshot` adds `view`, `data` and `inlineOmitted`.
- **Files.** `AutomationServer::WriteOutputFile` writes `<serverTag>-<sequence>.png` into the directory of offloaded results: `project://Library/Automation/Out/`, or `user://Automation/Out/` without a writable project. Unlike offloaded results, a server's output files outlive it, so the screenshots of a `--batch` run can be read after the run exits. The first write of a later server to the directory removes them, together with the other leftovers of servers that are gone, so the directory stays bounded.
- **Flags.**
  - Both are tools, because §13.8 lists `viewport_screenshot` and `editor_screenshot`.
  - Neither `Mutates` nor `SupportsDryRun`: they change nothing.
  - Not `AvailableInLauncher`.
  - Not `AllowedInBatch`: they write a file outside a command.
- **MCP.** `catalog.json` is regenerated (27 tools). For a result with an image `mimeType`, the bridge adds an image content block: the inline `data`, or the file at `path`, since it runs on the editor's machine. The text summary names the file instead of repeating the base64, and the structuredContent leaves `data` out, so the base64 is sent once.
- **Tests.**
  - C++ (`ScreenshotMethodsTests.cpp`, with CPU captures): the rendered size, the PNG's pixels, the downscale, base64, inline data left out of a PNG over the budget (the result not offloaded), Unsupported at each pointer, InvalidArgument ranges, the `--renderer none` answer, capture errors with their context, and the launcher state.
  - C++: "AutomationServer: output files share the offload directory and naming, and outlive their server", plus the method lists of `RegisterMethodsTests.cpp`.
  - Python (`Tests/Automation/test_screenshot.py`):
    - the parameter checks and the `--renderer none` answers, without a GPU;
    - rendering editors writing real PNGs of the documented sizes, with inline data equal to the file, followed by a clean `session.shutdown` under `--gpu-validation=sync --expect-no-gpu-errors`.
  - MCP: `test_screenshot_results_return_image_content_and_name_the_file` (with `tool_content`, which leaves the inline `data` out of the structuredContent) and the conformance test's inline screenshot. Method coverage stays complete.
- **Python tests that need a GPU** follow decision 14. `Tests/Automation/harness.py`'s `require_gpu()` probes once per run whether `Editor --headless --frames 1` can create its device with the GPU options. Without a device, the test prints the GPU suite's line "GPU test without a device (passes without running): <test>: <reason>" and returns. `Test.py` counts those lines, as it does for gpu runs, and ends the automation run as a warning. With `--require-gpu` (`ENGINE_AUTOMATION_REQUIRE_GPU=1`) the test fails instead. This is not a skip marker: ADR 0008 decision 16's lint rule and the runner's skip count are unchanged, and a run that passes without rendering is never reported as passed.
- **The golden `ImGuiDemo`** now comes from `editor.screenshot`, as the Roadmap's acceptance names it. A `--batch` run creates a project, because the method is not available in the launcher state, and calls `editor.screenshot {maxDimension: 8192}`. The golden test reads the PNG the run left behind. It matches the committed `nvidia-61x/ImGuiDemo.png` with zero differing pixels. The golden `Triangle` still renders through `ViewportCapture`, the capture behind `viewport.screenshot`.
