### 2. Replay v3: the start fingerprint (A-FPRINT, stream B)

A replay records what its session held at tick 0, so a playback whose state hash differs names what changed since the recording instead of only listing the causes (ADR 0027 friction F13).
- **The format** (`ReplayData.h`): version 3 (`ReplayFingerprintFormatVersion`, reserved by the ledger: `ReplayFormatVersion` 3, `ReplayImporter::Version` 3, cooked `ReplayData::FormatVersion` 3) adds `Fingerprint` after `Config`: `{"Entities": [{"Id", "Path", "Hash", "Components": {<name>: <hash>, ...}}, ...], "Assets": [{"Handle", "Path", "Type", "Hash"}, ...]}` or `null`. Entities are every entity of the scene at tick 0, sorted by id; `Hash` is the entity's own members (id, name, parent, active flag, tags) and each component's hash its value, both taken from the scene's minified canonical serialization, the document the state hash covers, so the fingerprint and the state hash agree on what a component holds. Assets are every asset an `AssetRef` value of those components names, once, sorted by handle: a Script component's script and the values of its asset fields among them, which only the session's script field schemas tell from entity fields (both are 16-hex strings in `Fields`), so the fingerprint reads them with `PlaySession::GetScriptSchemas` (a field its schema types `AssetRef`, or an `Array` of them; none without schemas); each with `AssetManager::GetCookedHash` (not const: the editor's override cooks on a cache miss): the XXH64 of its cooked artifact, which the editor's cache entry and an exported pak's entry share, so the Runtime compares them too. Every hash is XXH64 (seed 0) as 16 lowercase hex digits; paths are readable and never compared. Validation: ids and handles valid and strictly increasing, component names unique and in registry order, hashes canonical. The cooked payload appends the fingerprint after the final state hash (`CookReplay`'s comment).
- **Who writes it:** every recording. `ReplayRecorder::Begin` takes `ComputeReplayFingerprint(session.GetScene(), session.GetScriptSchemas(), session.GetAssets())` (`Session/ReplayFingerprint.h`), whose errors fail `Begin`, so `input.record`'s `start` and `test.run {record}` refuse a scene that references an asset whose cooked hash cannot be taken (an import that failed), naming the asset, rather than write a recording without it; `Finish` writes it; `test.run`'s concatenated recording keeps its first segment's. A version 1 or 2 file migrates to version 3 with a null fingerprint (nothing recorded, so nothing can be named), which `project.upgrade` writes byte for byte as `Tests/Data/Formats/Replay/v2.upgraded.replay` (the v2 fixture is `Tests/Data/Formats/Replay/v2.replay`); in versions 1 and 2 a `Fingerprint` member is unknown. Stream B regenerates `Tests/Data/Formats/Replay/v1.upgraded.replay` the same way (version 3, no checkpoints, `"Fingerprint": null`), since readers always return the current version.
- **Live tests stream B changes, keeping what they check:** "ReplayData: a version 1 replay migrates to version 2 with no checkpoints" (`ReplayDataTests.cpp`) and "ProjectMethods: project.upgrade migrates a version 1 replay to version 2 and records it" (`ProjectMethodsTests.cpp`), which compare with `v1.upgraded.replay`'s bytes and whose names then say version 3; and `test_replay.ReplayTests.test_record_refuses_a_recording_whose_outcome_does_not_depend_on_its_input`, whose written replay's `Version` becomes 3 (stream A's file, so stream B lists the change in its result for the integration).
- **The generated references** (stream B, the owner of `Editor/Source/EditorCore/Reference/ReferenceGenerator.cpp` and `Tests/Source/EditorCore/Reference/ReferenceGeneratorTests.cpp` in W19.1): the hand-written Replay schema (`ReplaySchema`) gains `Fingerprint` after `Config`, an object of `Entities` and `Assets` as above or null, among its required members, and its example (`ReplayExample`) becomes version 3 with a fingerprint; `GenerateDocs.py` regenerates `Docs/Reference/Schemas/Replay.schema.json`. The contract already changed the schema's `EngineVersion` description, which no longer says the recording build's version (decision 13). Stream D's manifest change of the same file is decision 18's.
- **Who compares it:** `ReplayPlayer::Begin` takes the playback's own fingerprint for a replay that has one, in a playback with its input. It only explains a hash that differs, so an error taking it does not fail `Begin` (the review of W19.1): the playback plays to its verdict, and a hash that differs names that error as its one change, `not known, because the playback's start fingerprint could not be taken: <error>`. When the failed checkpoint's or the final hash differs, `ReplayPlaybackResult::Changes` holds `DescribeReplayFingerprintChanges(recorded, observed)`: one line per difference, entities added, removed or changed, then components, then assets, at most `MaxReplayFingerprintChanges` (16) with "... and <n> more" last. `input.replay`'s result carries them as `changes` and its error's message ends with `; changed since the recording: <the first change>`; a checkpoint's stop reason and `test.run`'s `Checkpoint@<tick>` and `FinalStateHash` rows name the first too. A playback `WithoutInput` names none (failing is its expected outcome), nor does `input.record` Stop's verification (nothing changed since a recording made moments before).
- **What it cannot name** (a kept limit, Backlog §6): only direct references are fingerprinted, so an asset that only another asset references (a module that only a script requires, a material's texture) changes nothing in it, and a replay migrated from version 1 or 2 names no change until it is recorded again. Its failure then lists the causes as before.
- **Demo replays.** The integration's recorded `Editor --upgrade` of Tetris and Breakout migrates their replays to version 3 with null fingerprints and their hashes unchanged (plan §3.4, "Integration"); M20's re-record gives them fingerprints. FeatureTest's replays get theirs from `Scaffold.py`, which re-records them.

### 3. The continue-past-checkpoint flag and the final-hash warning (A-F29; stream B for the player, stream A for the guards)

- **`ReplayPlaybackOptions::ContinuePastCheckpoint`** (requires `StrictHash`; InvalidArgument from `Begin` otherwise): a checkpoint whose hash differs no longer ends the playback. `ReplayPlaybackResult::CheckpointsFailed` counts them, `FirstCheckpointFailure` holds the first's tick and both hashes, the playback goes on to `FinalTick` and compares the final hash (`HashMatched`), and it has failed whenever a checkpoint differed (`Passed` false, `CheckpointFailed` true). `input.replay {continuePastCheckpoint}` exposes it (requires `strictHash`; result `checkpointsFailed`, `firstFailedCheckpointTick`).
- **The guards keep their one rule** (Architecture §13.6): `input.record` Stop's and `test.run {record}`'s input checks play `WithoutInput` with `ContinuePastCheckpoint`, and refuse exactly when that run passes verification, as now. `inputCheckTick` and `divergedAtTick` stay the first differing checkpoint's tick, else where the run ended.
- **The warning:** when the check failed only at checkpoints, every expectation satisfied and the recorded final hash reproduced, the recording is written with one warning, `MakeFinalHashIndependentWarning` (`ReplayPlayer.h`), exactly: `'<replay>': its final state hash does not depend on its input: without its input events the run first differed from the recording at checkpoint tick <t>, then reached the recorded final state hash <hash>, so only its checkpoints prove the play; end the recording while the played state is still in the scene`. `input.record`'s result reports it in `warnings`, `test.run`'s recording block in `warnings`; the games and determinism suites' input checks pass `continuePastCheckpoint` and print the same line, which `games.input_check_warning` builds, as a warning that never fails a step.
- **After the check** the play session is the input check's, paused at the replay's final tick (it no longer stops at the first differing checkpoint).

### 4. `input.record` verifies an event-free recording (AL-EVFREE, stream A)

Every Stop verifies its candidate with its input (ADR 0027 decision 3, A1's playback; an event-free one has none), so an event-free recording's expectations and any nondeterminism are checked before anything is written, as `test.run {record}` already does. Only a recording with input events then gets the input check; an event-free one is written after its verification (`inputCheckTick` 0), and the play session is the verification's, no longer the recorded one. The accepted limit of ADR 0027 decision 12 ("`input.record`'s `stop` writes a recording without input events as recorded") closes when stream A lands. ### 5. Teardown errors in `input.record`'s verification (AL-TEARDOWN, stream A)

Once the verification's playback has reached its final tick with nothing else failed, Stop stops the session's scripts (`ScriptEngine::Stop`, as `test.run` does before it reads a replay's errors) and counts the errors their `OnDestroy` raises. The first refuses the recording like any other script error, its reason `the playback raised <n> script error(s); the first: <script>:<line>: <message> (at teardown)`. The play session is then the verification's, paused at its final tick with its scripts stopped: `script.eval` in the play context is refused, `scene.query` and `entity.get` read its final state, and `play.stop` ends it. The accepted limit of ADR 0027 decision 12 closes when stream A lands.

### 7. Entity paths in component data: `IEntityReferenceResolver` (A-EREF, stream C)

- **The interface** (`Automation/Protocol/MethodContext.h`): `IEntityReferenceResolver::ResolveEntityReference(reference, pointer) -> Result<UUID>`, returned by `MethodContext::GetEntityReferenceResolver()` (null by default). `MethodRegistry::Invoke` rewrites every `EntityRef` value in component data that is not a 16-hex id to the id it returns, in the pass that reaches it, before strict validation, as convention 13 rewrites asset references; its NotFound joins the asset references' NotFound rule, its InvalidArgument is an issue, any other code is returned unchanged. - **The host side** (`Automation/Methods/SharedMethodSupport.h`): `Utils::SceneEntityReferenceResolver`, constructed over a scene, resolves by `Utils::ResolveEntityReference`'s rule (an id prefix of 6 to 15 hex digits or an entity path), so component data and entity params resolve alike. The editor's context returns one; the Runtime has no component writes and returns none.
- **The scene a path or `$ref` resolves in** (the phase 1 ledger's "Entity paths and scenes", shared with M20): an entity path is the `/`-separated names from a scene root and continues through a prefab instance's members, nested instances included, as the scene holds them (`Scene::FindEntityByPath`'s grammar); a path or `$ref` resolves in the request's (an op's: its batch's) target scene, the active scene when it names none. ### 13. The build id (B-BVER, stream D)

- **The record** (`Core/BuildId.h`): `BuildId {Version, Commit, Dirty}`: `Version` is `EngineVersionString` (moved there from `JsonRpc.h`), `Commit` the build's commit as exactly 12 lowercase hex digits (empty without git), `Dirty` true when tracked files differed from it or when a file git neither tracks nor ignores lies below `Engine/`, `Editor/`, `Runtime/` or `Resources/` (premake compiles every source there, added or not, and the build copies the resources), so a source not yet added never passes for the commit. `GetBuildId()` returns the binary's own; `FormatBuildId` writes semantic-versioning build metadata, `<Version>`, `<Version>+<Commit>` or `<Version>+<Commit>.dirty` (`0.2.0+3f2a9c1d4e5b.dirty`), which `ParseBuildId` reads back strictly.

### 14. `input.readReplay` (A-RREAD, stream B)

`input.readReplay {path, cursor?, limit?}` (an immediate, read-only tool `input_read_replay`, editor only, neither a batch nor a dry-run op) reads the project's source `.replay` through `AutomationMethodContext::ReadReplayDocument`, strictly and migrated to the current version, and returns its canonical `path`, the file's own `formatVersion`, the `header` as the file writes it (PascalCase, the 64-bit seed exact), `finalTick`, `finalStateHash`, `eventCount`, one page of `events` (convention 9: `limit` 1 to 1000, default 100, and `nextCursor`), its `expect` as `input.record`'s and `test.run`'s `expect` take them, its `checkpoints` and `hasFingerprint`. ### 17. Pak version 2: per-entry compression (B-PAKZ, stream G)

- **The format** (`PakFormat.h`; `PakCompressionFormatVersion`, reserved by the ledger): the header keeps its layout and both versions become 2. Every TOC entry gains, after `"XXH64"`, `"Compression"` (`"None"` or `"Deflate"`, `PakCompression`) and `"StoredSize"` (the bytes it takes at `Offset`). `Size` and `XXH64` keep meaning the entry's own bytes, the ones `ReadEntry` returns (a cooked artifact, whose XXH64 `AssetManager::GetCookedHash` shares with the editor's cache, decision 2), so a deflated entry is verified after it is inflated; the byte-range rules apply to `[Offset, Offset + StoredSize)`. A `None` entry has `StoredSize == Size`; a `Deflate` entry holds a zlib stream with `0 < StoredSize < Size` and `8 × (Size − StoredSize) ≥ Size` (`IsValidPakDeflateSize`, which the writer's policy and `ParsePakToc` share); anything else is Validation. Readers read exactly the current version: paks are build outputs, never committed, and an export's paks and Runtime always come from one build, so there is no migration.
- **The codec** (`Asset/PakCompression.h`): zlib streams (RFC 1950) through stb's `stbi_zlib_compress` at the fixed `PakDeflateQuality` 8 (stb's own default) and `stbi_zlib_decode_buffer` into exactly the expected size; lengths up to `MaxPakCompressedEntrySize` (stb's lengths are `int`), and a deflated input of at most 1 GiB, since stb's deflate grows its output buffer with `int` arithmetic that overflows once its output passes 1,610,612,735 bytes (stream G's finding; `DeflatePakEntry` refuses a larger input with InvalidArgument). `PakCompression.cpp` declares `stbi_zlib_compress` itself, as `stb_image_write.h` defines it (`extern "C"`), so no vendored file changes; `ModuleRules.json` lets that one file include the stb headers (the contract). stb checks no Adler-32, so a damaged stream that still inflates to the right size is caught by the XXH64. Running out of memory is fatal, as for every engine allocation.
- **The writer's policy** (`PakWriter.h`): `Build` deflates each entry whose `Compress` is set and whose size is at most 1 GiB (the codec's deflate limit), and keeps the stream only when it saves at least an eighth; an empty entry, a larger one and one with `Compress` false are stored. The exporter sets `Compress` false for nothing today; M23 sets it for BC textures and Opus clips (plan §6 "M19", "Export"). The policy depends only on the bytes, so paks stay byte-identical for equal inputs, from the Debug and the Release editors alike (stb's deflate is integer code, and one compiler's configurations agree: ADR 0028's encoder rule).
- **The reader** (`PakReader.h`): `ReadEntry` inflates a `Deflate` entry on every read and verifies the inflated bytes on the first; a stream that does not inflate is the entry's Validation error. `PakMount` and `RuntimeAssetManager` read through `ReadEntry`, so a mounted file reads, streams and reports its size as its inflated bytes, with no change of theirs.
- **Fuzzing:** the inflater reads bytes from a pak the Runtime did not write, so it gets the fuzz target `PakInflate` in `Tests/Data/Fuzz/Targets.json` (sorted by reader) with the case "PakCompression: 10,000 seeded mutations of a deflate stream never crash and always return Result", and the `PakReader` case's seed pak gains a deflated entry so its mutations reach the inflater through `ReadEntry`; M20's hardened gate runs both at 1,000,000 mutations (ADR 0024 decision 14; T-FUZZMODEL sizes the shards).
- **Byte identity across configurations:** the skipped case "PakWriter: a pak with deflated entries built from fixed entries has its pinned bytes in every configuration" (`PakWriterTests.cpp`) builds a pak from fixed entries of fixed bytes, a deflated one among them, and compares its XXH64 with a constant that stream G records from its first run when it lifts the skip (the contract cannot compute it before the version 2 TOC and the codec exist); the Debug and the Release unit runs both check it, and that pinned hash is the proof of Roadmap M19's acceptance "compressed paks are byte-identical from the Debug and Release editors". Two exports cannot prove it: `Game.json` and `Engine.pak`'s metadata carry the exporting build's id (decision 13), which differs between two editors built at different moments.
- **Live tests stream G changes, keeping what they check:** "PakFormat: the 64-byte header round-trips" (its newer version becomes `CurrentVersion + 1`), "PakFormat: the TOC text has the documented members and spellings", "PakFormat: the reader rejects what the writer never produces" and the `MakeTocText` helper (the version 2 members), "Pak: flipped byte is detected" (the flipped byte lies inside the stored bytes) and "PakWriter: the layout is the documented one" (the padding follows `StoredSize`).
- **Docs** with the behaviour: Architecture §14.1's pak layout, TOC members and "Compression" bullet, §7.6's determinism sentence, and Appendix C's and Backlog §2's "Pak compression and reachability pruning" rows, which close once stream R lands too. Accepted limit (Backlog §6): an entry above 1 GiB is stored uncompressed.

### 19. The literal `Assets.Load` scan (stream D)

- **The function** (`Scripting/ScriptAssetLoads.h`): `FindScriptAssetLoads(source, chunkName)` returns every use of the global `Assets.Load` in source order. A call with one string literal (a plain or long string, or an interpolated string without expressions, possibly in parentheses or under a type assertion) is a literal load carrying the literal's text; every other use is a computed load: another argument or none, a method call, the function read as a value, `Assets["Load"]` or `Assets[<expression>]`, and the global `Assets` used other than by a field name, since the scan cannot follow where such a value goes. The sandbox keeps the globals table `_G`, so `_G.Assets` and `_G["Assets"]` are the global `Assets` (their literal loads are found), and `_G` used other than by a constant field name (`_G[<expression>]`, `local g = _G`, `rawget(_G, "Assets")`) is a computed load; another field of `_G` is no use (the review of W19.1). A local or field named `Assets` is not the global, and type annotations are not read. Locations are 1-based; a source that does not parse is `CompileFailed` at its first syntax error, as `ScriptCompiler` reports it. It parses with Luau's parser only (`Luau/Parser.h` and its AST visitor, which Dist keeps anyway, decision 22): no compiler, no VM and no type checker, so it is pure and thread-safe.
- **A literal's target** resolves as `Assets.Load` resolves it at run time (`AssetManager::Resolve`: a project path with an optional sub-asset key, an `engine://` path or a 16-hex handle). A literal that resolves to nothing, or to an asset `Export.Exclude` leaves out, adds nothing and is no error, since `Assets.Load` returns nil for it, in the editor too (FeatureTest's Assets suite loads a missing path on purpose).
- **Its users:** the exporter, for every packaged Script asset (decisions 20 and 21), and `project.validate` (decision 21). The exporter reads each script's source through the project file system, as the importer does; no cooked format changes, so no importer version moves.

### 26. The native module and its interface (C-NATIVE-STATIC; the engine's side is stream N-B's)

- **Layout.** One module per game: the `.cpp` and `.h` files below `<Game>/Native/`, at any depth. A game "has a native module" when it has a `Native/` directory (`HasNativeModuleDirectory`), whatever it holds; a `Native/` without a source is a module that does not build. One source names the module's registration function with `ENGINE_NATIVE_MODULE(<function>)`. Builds go below `<Game>/Library/Native/` (gitignored with `Library/`), never into `Native/`.
- **The interface** is `Engine/Source/Engine/Native/NativeApi.h`, the one engine header a module includes (decision 35's include rule). It is header-only and includes only the standard library and glm, so a module links no engine library and the editor's shared library of it holds no second copy of the process-level state of §3 rule 5 (the logger, the assert handler, Jolt's factory); everything the module reaches in the engine goes through two abstract classes the engine implements, `INativeRegistrar` while it registers and `INativeStepContext` while a system runs, whose standard-library views (`std::string_view`, `std::span`) cross the boundary soundly because the module is compiled by the same toolchain with the same settings as the engine (decision 30), and the engine copies every view it keeps. Its parts, frozen whole:
  - `NativeApiVersion` (1): a module of another version is refused with `UnsupportedVersion` naming both; a change to anything a module compiles against takes the next value, and the source hash covers the header anyway (decision 30);
  - types: trivially copyable, standard-layout structs with a default constructor, every member default-initialized, named by `static constexpr std::string_view NativeTypeName`; their reflected members are of the kinds of `NativeFieldKind` (bool, int32, uint32, float, glm vectors and quaternions, linear colours through `ColorField`, `NativeEntity`, an enum class over int32 through `EnumField`), each with a description and optional `NativeFieldOptions` (`Min`, `Max`, `Unit`, `RenamedFrom`); members that are not registered are neither saved nor hashed. A type's defaults (`NativeTypeDescriptor::Defaults`, the bytes every new value starts from) hold each registered field as a `T{}` holds it and zero everywhere else, the padding and the unregistered members included: a `T{}` is aggregate-initialized, whose padding is indeterminate (whatever the stack held), and those bytes would otherwise differ between two registrations of one module; the layout hash reads the defaults through their canonical JSON, never their bytes (`NativeModuleTypes::GetLayoutHash`);
  - `NativeComponent<T>` (data on entities, "Native.<Name>" in files and automation, decision 27) and `NativeResource<T>` (one value per play session, decision 28), registered with `INativeRegistrar::Add`, and systems (`NativeSystemDescriptor`: a name, a description and a `void(INativeStepContext&)` function), registered with `AddSystem` and run in registration order (decision 28);
  - `ENGINE_NATIVE_MODULE`: in the shared-library build (`ENGINE_NATIVE_SHARED_LIBRARY`, which `Scripts/BuildNative.py --kind module` defines) it exports `extern "C"` `EngineNativeModuleApiVersion` and `EngineNativeModuleRegister`, which the editor resolves after loading the library; in the Runtime build it defines `Engine::GetLinkedNativeModule()`, which only the Runtime calls (decision 30).
- **The engine's side** is the `Native` module (layer 4 beside Scripting, ≤3; it includes Scene for native components in scenes): `BuildNativeModuleTypes(entry, keepalive)` runs the registration and validates it by `NativeModule.h`'s rules (PascalCase ASCII names of at most 64 bytes unique within their kind; descriptions; sizes, alignments and field layouts; bounds; enum entries; defaults a field accepts; the limits on types, fields and systems; at least one type or system), the first broken rule refusing the whole module with Validation naming the type, field or system, and copies everything into an immutable `NativeModuleTypes`. The registration is the module's own code, so it runs inside a try/catch: `Native/NativeModule.cpp` joins Lint's `TryCatchFiles` and Architecture §4.6's boundary list with this contract, and an exception that escapes the registration refuses the module with Validation naming the exception's message, nothing it registered kept, so `native.load` fails with the previous module still loaded and an exported Runtime's startup fails with an error instead of terminating (a crash is not caught, decision 28). The result is shared by `Ref` and thread-safe to read, which keeps the module's code loaded (`keepalive`, the editor's `SharedLibrary`) while anything holds it, so a system never outlives its library.
- **Why its own registry.** Native types are not registered in the `TypeRegistry`: it is frozen at startup, its pointers live as long as it does and every consumer holds them, while a module comes and goes with hot reload and with the user's preference. The cost, accepted (Backlog §6): native components are not registry components, so they have no script proxy (a script's lookup of a `Native.<Name>`, through an `Entity` method or `Scene.FindAllWithComponent`, fails with a hint naming `native.getComponents` instead of did-you-mean names; W19.3, friction NT-05), no inspector drawer and no `component.schema` (`native.status` gives each type's JSON Schema), and `project.validate` does not check them (their findings are load diagnostics, decision 27).

### 27. Native components in scenes (stream N-B)

- **Names and files.** A native component is written under its entity's `"Components"` as `"Native.<Name>"` (`NativeComponentPrefix`, `IsNativeComponentName`), after the built-ins, with the `"ComponentVersions"` entry `NativeComponentVersion` (1). The prefix keeps native names apart from every built-in name, present and future, since built-in names hold no dot.
- **Storage.** A native component lives as its JSON in the entity's preserved components (`UnknownComponentsComponent`), with or without a module loaded, so the serializer, the play copy, undo snapshots, prefabs and every other JSON path carry it unchanged, and an editor without the module (the preference off, Linux and macOS) loses no data. The serializer keeps every `Native.` component as written and never reports it as unknown: no `SCENE_UNKNOWN_COMPONENT`, so no error under `--strict` either; whether the loaded module registers it is the native layer's check. That is one condition in `SceneSerializer.cpp`'s unknown-component branch, and `SceneSerializer.cpp` is M20's in phase 1 (ADR 0028's ledger), whose decision 17 needs a deviation amended on main. The amendment is therefore a precondition of W19.1: the lead lands it on main, a documentation-only change, before the W19.1 streams start (`milestone/m19` then merges main), and records its commit here; without it this storage design does not hold, the native test game cannot open in the games suite's strict editors and stream N-B's case cannot be lifted. Its text, for the ledger's single-owner row of `SceneSerializer`: "M20; M19 adds one condition to `SceneSerializer.cpp`'s unknown-component branch, so that a `Native.` component (`IsNativeComponentName`) is kept as written and never reported as `SCENE_UNKNOWN_COMPONENT`, with the case "SceneSerializer: a native component is kept as written and never reported as unknown, also under --strict" (`SceneSerializerTests.cpp`; ADR 0030 decision 27); M20 merges it at its landing". Amendment commit: `45f3358` (the lead's, on main, landed after W19.1; W19.2's stream N-S wrote the condition and lifted the case). The contract does not touch the file.
- **The canonical form** (`CanonicalizeNativeComponents`, with a module loaded): every component the module registers is an object holding every field in registration order in its kind's form (`NativeValueToJson`; floats as float, an entity as 16 lowercase hex digits or null, an enum by name), and an entity's native components are sorted by registry name (byte order) ahead of its unknown ones; a scene saved with its module loaded is canonical, and load then save is byte-identical (§6). Without a module nothing is rewritten or reordered.
- **Migration by field name** (`NativeValueFromJson`, decision 31's reloads included): a member named like a field, or like a field's `RenamedFrom` while the field's own name is absent, sets that field; a member of another kind's form that converts exactly is converted; one that does not is reset to the field's default with `NATIVE_FIELD_RESET`; a member no field is named after is dropped with `NATIVE_FIELD_DROPPED`; both are warnings, errors with `--strict`. A value of the field's form that the field rejects (out of bounds, non-finite, an entity that is not 16 hex digits, an unknown enum name, a quaternion not of unit length) is `NATIVE_COMPONENT_INVALID`: an error, the component kept as written, and a play session of its scene does not start. A component the loaded module does not register, every one while no module is loaded, is kept as written with `NATIVE_COMPONENT_UNREGISTERED` (a warning; an error with `--strict`). A native type has no version and no migration function (an accepted limit: renames go through `RenamedFrom`).
- **Who canonicalizes:** the editor when a scene opens with a module loaded and when a module loads or reloads (decision 31); `native.setComponents` (`PatchNativeComponents`); a play session's start (`PlaySession::Prepare` with `PlaySessionSpecification::Native`, its errors failing the start like a strict load's); the Runtime's sessions (its linked module). A scene `Scene.Load` loads and a prefab instantiated during play are not canonicalized when they arrive: NativeStep reads their components by decision 28's rule. A `--strict` editor runs it with `strictUnknowns` over every scene and prefab when a project opens (`EditorContext`'s strict document check, stream N-C), so a `Native.` component that the loaded module does not register refuses the project, naming it; the games suite therefore builds the module before it starts a strict editor (decision 35).
- **Automation's scene reads** (W19.3, friction NT-07): `scene.tree` lists an entity's `Native.<Name>` components after its built-ins, `entity.get` (`all`, the default) and `scene.query`'s `select: ["all"]` carry their JSON as the entity's preserved components hold it, and a `Native.<Name>` names one in `entity.get`'s `components` and in `scene.query`'s `where.component` and `select`; a name is not checked against the loaded module, which the shared Engine handlers cannot see (`native.getComponents` reads through it). Since `entity.get`'s components may be sent back, automation's writes of registry components refuse a `Native.<Name>` with a hint naming `native.setComponents` (`MakeNativeComponentWriteError`, `Automation/Protocol/MethodRegistry.h`): a component value of `entity.create`, `entity.update` and `prefab.instantiate` (convention 10's `ResolveComponentValue`) and `entity.update`'s `removeComponents` (EditorCore's `FindWritableComponent`), `InvalidArgument` instead of did-you-mean names of built-in components (W19.3's review).
- **The replay fingerprint** (decision 2) lists an entity's components in the order its scene document writes them: the built-ins in registry order, then the native components, then the unknown ones; its reader checks the order of the registered names only. Stream B follows this.
- **Prefabs** keep their members' native components as written. A prefab file is never canonicalized or migrated on disk: only `prefab.create` rewrites one, from entities whose native components are canonical while the module is loaded. An instance's members get the prefab's components as the file holds them, made canonical by the next canonicalization of their scene (its opening, a module load, a play session's start); an instance created during play is read by NativeStep's rule (decision 28). No prefab override records a native component, so `native.setComponents` refuses a member of a prefab instance (an entity with a `PrefabLink`) in the edit scene with `InvalidState` (`NativeMethods.h`), since the next rebuild of the instance from its prefab (a prefab change, `scene.open`) would restore the prefab's components and lose the edit silently: a prefab's native components are set on the entity before `prefab.create`, or on an unpacked instance. On the play scene, which no prefab rebuilds, the method changes them for the session. An Entity value inside a prefab is not remapped when the prefab is instantiated, unlike an `EntityRef` field. These are accepted limits (Backlog §6).
- **Fuzzing:** a native component's JSON comes from scene files, so `CanonicalizeNativeValue` gets the fuzz target `NativeComponent` with the case "NativeModule: 10,000 seeded mutations of the JSON of a native component never crash and always return Result" (no apostrophe: `Support/Fuzz.cpp` refuses one in a fuzz case's name); M20's hardened gate runs it at 1,000,000 mutations (ADR 0024 decision 14).

### 28. The NativeStep phase, the step context and the native block (stream N-B)

- **The phase** is the ledger's `PlaySessionPhase::NativeStep`, after `Tasks` and before `PreStepTransformUpdate` (§5.7's step 4a), entered only in Play mode with a module (`PlaySessionSpecification::Native`); Simulate (Play without gameplay code, §5.6) has no native world, and a session without a module no NativeStep, so §5.7's sequence and every existing step-order test are unchanged. Before `PreStepTransformUpdate` so the Transforms native systems write reach physics in the same tick, as scripts' writes in `OnFixedUpdate` do.
- **The native world** (`NativeWorld`, owned by the session for its whole life, `Scene.Load` included) runs the systems in registration order, each with an `INativeStepContext` whose rules `NativeApi.h` and `NativeWorld.h` freeze: `Query` lists the effectively active entities that hold a component in canonical order (§5.1); a component's data is read from its JSON in the scene the first time a system asks for it in the step and stays at the same address until the system returns; when the phase ends every component whose bytes a system changed is written back as canonical JSON and every component a system added or removed is added to or removed from the entity's preserved components, so the scene holds the native data for `scene.get`, `native.getComponents`, the fingerprint and the state hash, and automation writes between ticks reach the next step. Entities: `CreateEntity` as a script's `Scene.CreateEntity` (§5.7's creation semantics and `Simulation.MaxEntities`), `DestroyEntity` deferred to the destroy flush, `SetTransform` as a script's Transform write in `OnFixedUpdate` (interpolated; physics teleports a body whose pose it changed, as for a script). Input: the latched step view of the project's actions as scripts read it in `OnFixedUpdate`; an action the project does not define reads as up and 0 and logs one error per session and name (devices are not exposed: an accepted limit, games bind them to actions). Randomness: the session's stream, shared with scripts in step order. Mathematics: DetMath through the context (`Sin` to `Pow`, `AngleAxis`). The log: `Write`, attributed `native:<System>`.
- **Stored values the step reads.** A component's data is read with `NativeValueFromJson`'s migration by field name, because only the starting scene is canonicalized (`PlaySession::Prepare`): a scene `Scene.Load` loads and a prefab instantiated during play reach the step as their files hold them, in the editor and in every Runtime alike. A value its type rejects (`NATIVE_COMPONENT_INVALID`) stops the session fatally, as an escaped exception does: `PlaySession::GetFatalError` names the entity (its path and id), the component and the first issue, and no later system, phase or tick runs. A value read with notes (`NATIVE_FIELD_DROPPED`, `NATIVE_FIELD_RESET`) is used migrated and written back canonical when the phase ends, like a changed one, and each note is logged as a warning once per session, component and field; notes never fail a step (`NativeWorld.h`).
- **The §4.6 boundary.** `NativeWorld` calls each system inside a try/catch (`Session/NativeWorld.cpp` joins Lint's `TryCatchFiles` with this contract): an exception that escapes a system stops the session fatally (`PlaySession::GetFatalError`, naming the system and the exception's message), and no later system, phase or tick runs. A crash in native code is not caught; it ends the process like an engine crash (an accepted limit, which the user-only preference bounds, decision 29).
- **The native block** is the ledger's state-hash block after the physics block: `NativeWorld::AppendStateHash` appends, for each resource in registration order, its name and its canonical JSON minified (`AppendNativeValueHash`), never raw bytes, so padding never reaches it. It is empty without a module and for a module without resources, so every existing replay keeps its hash. Native components need no block: they are in the scene's serialization, which the end of every NativeStep keeps current. Resources start at their defaults when the session starts and keep their values across `Scene.Load`, like the Random stream; `native.status` reports them in play.
- **Determinism** (§1.3, §4.12). Native code is simulation code: it is compiled with the configuration's first-party settings (precise floating point, decision 30) in every build that runs it (the editor's Debug and Release libraries, the exported Release and Dist Runtimes), checked by the determinism lint (decision 35), and reads time only as ticks, randomness only from the session's stream and input only from the latched step view; the hash reads canonical JSON. A module keeps no mutable state of its own: every variable of static or thread storage duration is const or constexpr (`NativeApi.h`; decision 35's lint), because the editor keeps a module's library loaded across play sessions, so a counter a system keeps would start the verification of a recording made in the same editor where the recording left it, while each exported Runtime starts fresh; a session's state lives in its resources and components, which the session starts and the hash covers. So "a native component hashes identically in Debug, Release and Dist" (Roadmap M19's acceptance) holds as it does for the engine's own simulation code (§2.2), which the native test game's replays prove in the games suite's three halves (decision 35).
- **Cost:** a native component's data round-trips through its JSON once per step that touches it (an accepted limit, Backlog §6; typed scene storage would need the serializer to know native types, which the frozen registry rules out, decision 26).

### 29. The "Allow native code" preference (stream N-C)

- **The user's preference**, `"AllowNativeCode"` in `user://Editor.json` (`EditorPreferences::AllowNativeCode`, off by default), kept like the "Allow AI automation" preference (Architecture §12.2 and §13.2, `EditorHostPreferences`, ADR 0021): the Native panel's checkbox (`Editor/Panels/NativePanel`, a new panel closed by default and opened from the Window menu, so no editor-UI golden changes; its enumerator `EditorPanel::Native` goes immediately before `ProjectLauncher`, named "Native" by `EditorPanelToString`, so `editor.state`'s `openPanels`, docking ids and saved layouts name it, and the editor's loops bounded by `ProjectLauncher` include it; saved layouts store panel names, so the insertion moves no saved value) queues the change (`NativeModuleHost::QueuePreferenceChange`, no I/O), and the host applies it at the next frame boundary (`Update`: `WriteEditorPreferences`, keeping every other member of the file). The host reads it when the editor starts and when a project opens (`ReadPreference`).
- **Automation cannot set it.** No method takes it as a param or writes `user://Editor.json`: `native.status` only reports it as `allowed`, `project.setSettings` writes the `.eproj`, which has no such key, and every other writer is confined to `project://` or `Library/`. The MCP bridge writes no preference and passes the user-data root its operator configured. A test proves that no method's params name it and that a settings patch cannot reach it (decision 37). Test harnesses that need it write the file into the user-data directories they create for their own editors (the games suite, `Tests/Automation/test_native.py`): the operator's tooling, never the automation API.
- **While it is off**, `NativeModuleHost::StartBuild`, `StartRuntimeBuild` and `Load` refuse with `PermissionDenied` and the hint "the user turns on Allow native code in the editor's Native panel; no automation method can", so `native.build` and `native.load` do; a project's opening loads no module; an export of a game with `Native/` is refused at its step 1 (decision 33); and turning it off unloads a loaded module at the next frame boundary without a play session, its components staying in the scene as written.
- **Parity** (Roadmap rule 5): the preference is exempt by design, a permission automation must not be able to give itself (plan §6 "M19", risk 14); every other action of the Native panel has its method (Build: `native.build`; Load: `native.load`; the selected entity's native components, shown read-only: `native.getComponents`). Editing native components in the inspector is not built (`InspectorPanel` is M20's in phase 1; an accepted limit: `native.setComponents` edits them).

### 30. The native build (stream N-A)

- **`Scripts/BuildNative.py`** (new; Windows only, exit code 3 elsewhere naming the platform): `python Scripts/BuildNative.py --project <root> --kind module|runtime --config Debug|Release|Dist --out <dir> [--json] [--jobs N] [--timeout S] [--lock-timeout S | --no-wait]`, holding the machine-wide build lock (a capped slot) like `Build.py`. It first runs decision 35's checks on the sources (their findings are `NATIVE_LINT_ERROR` diagnostics) and its format check (`NATIVE_FORMAT_WARNING`, which fails nothing; W19.3), then generates a workspace below `<out>` with premake from a native-module script that applies the engine's own `ApplyFirstPartySettings()` and `Use<Lib>()` functions (precise floating point, warnings as errors, the first-party defines), so the module is compiled exactly like engine code, and builds it with MSBuild (vswhere, the vendor cache as `Build.py` links it):
  - `module`: a shared library of the editor's configuration (Debug or Release; Dist has no editor), with `ENGINE_NATIVE_SHARED_LIBRARY` defined and no engine library linked;
  - `runtime`: the game's Runtime executable of the configuration, the module linked in. The Runtime project splits into a static library, `RuntimeCore`, and the prebuilt executable, which compiles `RuntimeMain.cpp` and `NoNativeModule.cpp`, so the entry point always comes from an object file; the game's link compiles `RuntimeMain.cpp` and the module's sources instead and links `RuntimeCore`, so the module's `ENGINE_NATIVE_MODULE` defines `GetLinkedNativeModule` there, with the prebuilt Runtime's other settings (Dist's LTO and map, the subsystem, the manifest).
  - The record `<out>/NativeBuild.json` (`NativeBuildRecord`, `ParseNativeBuildRecord`; written canonically, read strictly like a `.meta` file and fuzzed, case "NativeBuild: 1,000 seeded mutations of a build record never crash", target `NativeBuildRecord`): `Format`, `Version` 1, `Kind`, `Configuration`, `SourceHash`, `Sources`, `Succeeded`, `Output` (the file name of the library or executable, empty when the build failed), `Log` (the file name of the build's whole output, beside the record) and `Diagnostics` (`Severity`, `Code`, `File`, `Line`, `Column`, `Message`); with `--json` the same document on standard output. Exit codes: 0 built, 1 a lint, compile or link failure (the record says which), 2 usage, 3 no `Native/` or no source, not Windows, or the build outputs it links missing (`bin/<OutputDir>/...`), 5 the lock's timeout.
- **The source hash** (`ComputeNativeSourceHash` in C++, `native_build.source_hash` in Python, pinned equal by stream N-A's test): XXH64 (seed 0), 16 lowercase hex digits, over "EngineNativeSources 1\n<Configuration>\n", then for `NativeApi.h` and for each source in `ListNativeSources`' order (byte order of the project-relative paths): its path (`Engine/Native/NativeApi.h` for the header), "\n", its size as 8 little-endian bytes and its bytes. A build is current when its record's `SourceHash` equals the hash now; a changed source, a changed `NativeApi.h` or another configuration makes it stale.
- **The editor's backend** (`CreateNativeBuildBackend`, Windows): one process, by fixed paths with fixed arguments: the interpreter `Scripts/Generate.py` ran under (`ENGINE_PYTHON_EXECUTABLE`, which premake defines from `--python` beside `ENGINE_REPO_ROOT` in the non-Dist first-party projects; an empty one is `InvalidState` naming `python Scripts/Generate.py`) running `<ENGINE_REPO_ROOT>/Scripts/BuildNative.py --project <the open project's root> --kind module|runtime --config <the editor's configuration | the export's> --out <a new Library/Native/Builds/<sequence>/ | the export's directory beside its staging directory> --json`, never an argument a request supplies; polled once per frame, killed on cancel, its record read when it exits. Linux and macOS: `Unsupported` (decision 34).
- An export of a game with `Native/` therefore needs the Windows toolchain at export time (plan §6; an accepted limit).
- **Cancellation** (an accepted limit, `Docs/Backlog.md` §6; recorded by W19.1's integration): cancelling a native build (`native.build`'s disconnect or cancel, an export's cancelled NativeBuild step) kills `Scripts/BuildNative.py`, but the MSBuild it started runs to its end, writing only into that build's own output directory (`Library/Native/Builds/<sequence>/` or the export's), whose record is never read; a Windows job object would also end an `mspdbsrv` shared with builds in other worktrees.

### 31. The editor's load and hot reload (stream N-C)

- **`Platform/SharedLibrary`** (new; Windows backend in `Platform/Windows/SharedLibraryWindows.cpp`: `LoadLibraryExW` with `LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR | LOAD_LIBRARY_SEARCH_DEFAULT_DIRS`, so neither the working directory nor `PATH` is searched, `GetProcAddress`, `FreeLibrary`). `CreateNativeLibraryLoader` loads a build's library with it and resolves the two exported functions; the `SharedLibrary` is the types' keepalive.
- **`NativeModuleHost`** (owned by `EditorContext`): a build goes to a new numbered directory (`Library/Native/Builds/<sequence>/`, at least 8 digits), because Windows does not let a loaded library be replaced; a load takes the newest successful build of the editor's configuration whose source hash is current, loads its library, registers the module and only then replaces the loaded module, so a load that fails at any step leaves the previous module loaded and the scene unchanged. It then canonicalizes the open scene against the new types (decision 27's migration): a reload whose layout hash (`NativeModuleTypes::GetLayoutHash`) equals the replaced module's rewrites nothing, so the scene stays byte-identical, and a load whose layout changed (every first load, one after an unload included) migrates every native component, marks the scene modified when its canonical form changed and clears the undo history, whose entity snapshots hold the previous layout's values or, recorded without a module, the values as written, which undo would restore whole (`native.load`'s `undoCleared`; the review of W19.2). The lead accepts this behaviour as final (the review of W19.2's finding 1, recorded with the pre-bridge checkpoint, Integration of W19.2): every load whose layout changed clears the undo history while a scene is open, a first load included, even when its migration changed nothing, so the edits made before a module's first load can no longer be undone (Backlog §6). The previous types are released last, which unloads their library once nothing holds them. The host keeps the loaded build and the newest; older builds are removed when no longer loaded (a failure to remove one is logged).
- **Frame boundaries without a play session.** `native.load` runs at the automation pump, a frame boundary, and is refused with `InvalidState` while a play session (Play or Simulate) runs; a build may run during play, since it writes only below `Library/`. A project's opening loads the newest current build when the preference is on and the platform supported, and never builds: a project without a current build opens without its module (its native components kept as written), and `native.build` then `native.load` load it. Closing the project cancels a running build and unloads the module.
- **`EditorContext`'s hooks** (stream N-C): the host reads the preference when the context is created and when a project opens, `OnProjectOpened` and `OnProjectClosed` around the project's lifecycle, `Update` once per frame, and the strict document check's native canonicalization (decision 27). `EditorApp` is not touched: the preference flows through the host.

### 32. The native.* methods (stream N-D)

Seven editor-only methods, every one an MCP tool (`NativeMethods.h` freezes their params, results and rules):
- `native.status` (a read, batchable): the user's preference (`allowed`), the platform's support, the sources and their hash, the newest build and whether it is current, the last build's diagnostics, the loaded module's components and resources (each with its JSON Schema) and systems, whether it is current, and in a Play session running it the resources' values (`playResources`).
- `native.read {path}` and `native.write {path, source}`: a `.cpp` or `.h` file below `Native/`, resolved like `script.read`'s paths below `Assets/` (another folder, another extension or a path that escapes is `InvalidArgument` at `/path`); `native.write` creates missing folders, is one undoable edit (`AssetEditCommand`), records provenance (decision 35), supports dry runs and batches, and is refused while a build runs (`InvalidState`). It builds nothing.
- `native.build` (pending, 900 s, a disconnect cancels it): `NativeModuleHost::StartBuild` and `PollBuild`; a build that fails to compile resolves with `succeeded` false and its diagnostics, not an error; refused per decision 29 and in read-only editors.
- `native.load` (immediate, neither a batch op nor a dry run): `NativeModuleHost::Load`; its result names the module's types and systems, whether it was a reload, whether the layout changed, the migration's diagnostics and whether the scene changed and the undo history was cleared.
- `native.getComponents {entity, target?}` and `native.setComponents {entity, components, target?}`: an entity's `Native.` components (`ReadNativeComponents`) and a merge patch of them (`PatchNativeComponents`; null removes a component, a missing one starts from its type's defaults), one undoable edit on the edit scene (a `SceneEdit`), transient on the play scene, batchable and dry-runnable; `native.setComponents` needs a loaded module (`InvalidState`), refuses a member of a prefab instance in the edit scene (`InvalidState`, decision 27), and resolves an Entity value that is not a 16-hex id through the context's `IEntityReferenceResolver`, as decision 7 resolves `EntityRef` values in component data. The entity param resolves as `entity.get`'s.
- The MCP tool list gains `native_status`, `native_read`, `native_write`, `native_build`, `native_load`, `native_get_components` and `native_set_components`, so the next builder or re-record driver starts in a fresh top-level session (plan §4.3).

### 33. The export of a game with Native/, and the §13.2 and §14.2 amendments (stream N-A)

- **The exporter** (`Exporter.h` step 3a, wired by the contract through `NativeExport.h`): a project with a `Native/` directory is refused at step 1, before anything is cooked or written, on Linux and macOS (`Unsupported`), while the preference is off (`PermissionDenied`) and, stream N-A's addition (`CheckNativeExport`), when `Native/` holds no source (`NotFound`); step 3a (`ExportPhase::NativeBuild`, after `WritePaks`) builds the Runtime of the export's configuration with the module linked (`StartNativeRuntimeBuild`, through `NativeModuleHost::StartRuntimeBuild` and its backend) into a directory beside the staging directory; a build that does not succeed fails the export with `CompileFailed` and its diagnostics as issues (`MakeNativeBuildError`); step 4 copies that executable instead of the prebuilt one, and the rest of the export (resources, manifest, smoke and feature tests) is unchanged. `ExportReport::NativeModule` and `project.export`'s `nativeModule` say so, and `phaseTimings` lists `NativeBuild` only for a game with a native module. A game without `Native/` exports the prebuilt Runtime unchanged. The exported Runtime registers its linked module at startup and runs it in every session (§14.3), and never loads a library.
- **§13.2's sentence**, the final one with decision 10's feature test, which the W19.1 integration keeps when it merges streams F and N-A (each applies its half): "No method runs a process, a shell command or code that a request names: the only processes a method starts are `project.export`'s runs of the exported game, its smoke test (`smokeTest`) and its feature test (`featureTest`, a testing export's suites and replays), and, on macOS, `codesign` in its Sign phase (§14.2), each by a fixed path with fixed arguments. The one exception is a game's native module (Windows only): while the user's "Allow native code" preference is on, the open project's `Native/` sources, which `native.write` may author, are built by the fixed-path `Scripts/BuildNative.py`, run by the interpreter the workspace was generated with (`native.build`, and `project.export`'s NativeBuild step), and the build is loaded into the editor's process (`native.load` and the project's opening) and linked into the games the editor exports. That preference therefore grants every connected automation client code execution in the editor and in its exports: it is the user's alone, set in the editor's Native panel, and no method can change it (ADR 0030 decisions 29 to 33)."
- **§14.2 and §14.1**, applied by stream N-A with the behaviour: step 4's "the editor never spawns a build" becomes "the editor never builds the engine; for a game with `Native/` it builds the game's Runtime with its module (step 3a, ADR 0030 decision 33)", step 3a is added, §14.1's package row reads "the configuration's Runtime, or for a game with `Native/` a Runtime built with its native module", and §14.3 says the Runtime registers its linked module.

### 34. Linux and macOS (ADR 0028 decision 10, Windows backends only)
