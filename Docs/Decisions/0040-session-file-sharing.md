# 0040 — Session files are replaced and read with sharing that never conflicts

- **Status:** accepted
- **Date:** 2026-11-02
- **Decided by:** the lead, as a fix straight to main outside the phase-2 milestones (ADRs 0032 to 0038 are reserved for M21 to M27 by ADR 0028's ledgers; 0039 is taken).
- **Context:** M23's W23.1 integrator saw the GPU case "RuntimeApp: a game-view render that runs out of memory warns once, renders again after the trim, and runs without errors" fail once under API 1.4 while sibling worktrees loaded the machine: `PermissionDenied` opening the Runtime child's session file. The case waits until `<pid>.json` exists, then reads it. A server writes the file to `<pid>.json.tmp` and renames it over `<pid>.json` (`std::filesystem::rename`, `MoveFileExW` with `MOVEFILE_REPLACE_EXISTING` in the MSVC STL, ADR 0003); the reader opened it with `std::ifstream` (`FileSystem::ReadFile`), and the Python clients with `open()`.
  - **The cause.** On Windows a rename renames the file through a handle opened with DELETE access (`NtSetInformationFile` with `FileRenameInformation` needs one), and that handle stays open until the rename returns. For that moment the file has its new name, so the client's poll sees it, while a handle with DELETE access is still open on it. The C runtime's and Python's opens share only reading and writing (`_SH_DENYNO` is `FILE_SHARE_READ | FILE_SHARE_WRITE`), so they conflict with that handle: `ERROR_SHARING_VIOLATION`, which the C runtime reports as `EACCES`, `PermissionDenied`. A loaded machine stretches the moment by descheduling the writer between the rename and its return. Measured on the development machine: a writer process publishing 3,000 files with `MoveFileExW` while a reader spun until each existed and then opened it at once, the reader sharing reading and writing failed 536 opens with `ERROR_SHARING_VIOLATION` (32), and a reader that also shared deletion failed none. With the rename's handle held open on purpose, `FileSystem::ReadFile` fails every time with the reported message (`cannot open '<sessions>/4321.json': permission denied`).
  - **The writer's side.** `MoveFileExW` cannot replace a file that any reader has open, whatever its sharing (`ERROR_ACCESS_DENIED`): a client reading the editor's session file while the editor rewrites it (a project opened or closed) fails the rewrite, which the editor then tries again a second later (`SessionFileRetryInterval`) with a warning. Measured: 2,000 replaces with `MoveFileExW` beside a reader looping over the file failed 1,741 times (1,718 with a reader that shared deletion), and 1,698 times with a POSIX-semantics rename beside a reader that did not share deletion; a POSIX-semantics rename beside a reader that shared deletion failed none, and neither side failed.
  - **Not the cause.** The server holds no handle once its rename returns (the temporary's stream is closed and `std::filesystem::permissions` toggles only the read-only attribute), the Runtime writes its file once, and the case's reader opened only after the file existed. No antivirus scan is needed to explain it: the writer's own rename reproduces the failure deterministically, and a reader with full sharing conflicts only with a handle that denies reading, which neither the writer nor a scan's read holds.

## Decisions

1. **`Platform/PublishedFile.h`.** A new Platform unit for files one process publishes and others read while it runs. `PublishedFile::Read` reads the whole file through a handle that shares reading, writing and deletion (`FILE_SHARE_READ | FILE_SHARE_WRITE | FILE_SHARE_DELETE`), so a rename or removal in flight never fails it and it never fails them. `PublishedFile::Replace` renames a file over another in one step through `SetFileInformationByHandle(FileRenameInfoEx)` with `FILE_RENAME_FLAG_REPLACE_IF_EXISTS | FILE_RENAME_FLAG_POSIX_SEMANTICS`, which replaces a target that readers hold open with `FILE_SHARE_DELETE` (they keep reading what they opened; every later open finds the new file). A volume or Windows release without POSIX rename semantics refuses that call as an invalid or unsupported request (`ERROR_INVALID_PARAMETER`, `ERROR_NOT_SUPPORTED`, `ERROR_INVALID_FUNCTION`), and `Replace` then falls back to `MoveFileExW(MOVEFILE_REPLACE_EXISTING)`. On Linux and macOS no open conflicts with a rename or an unlink: `Platform/Posix/PublishedFilePosix.cpp` keeps the portable calls the session files used before (`FileSystem::ReadFile`, `std::filesystem::rename`). ADR 0028 decision 10's "Windows backends only" covers capabilities the program adds; session files are an existing capability on every host, so their POSIX behaviour stays as it was, and no POSIX OS call is written.
2. **The session file goes through it.** `SessionFile::Write` renames the restricted temporary over `<pid>.json` with `PublishedFile::Replace` (an error stays `Io`, now naming both paths), and `SessionFile::Read(directory, pid)` is the C++ clients' read (`PublishedFile::Read`, then `FromText`). The Runtime tests' automation connection (`RuntimeAutomationConnection::Open`, `Tests/Source/Runtime/RuntimeAppTests.cpp`) reads with it. Architecture §4.10's atomic writes are unchanged: `FileSystem` is Core, which includes no OS headers, and only the session files are read by other processes while they are replaced.
3. **The Python clients read the same way.** `Tools/Automation/engine_client.py`'s `read_shared_bytes(path)` opens with `CreateFileW` and full sharing on Windows (`path.read_bytes()` elsewhere), and `_parse_session` reads with it, so `list_sessions`, `find_session` and `launch_editor`'s wait, and through them the MCP bridge (`editor_launch`, `editor_attach`, `editor_status`), the automation harness and the scripts that start editors, never miss a live editor because its rename was in flight, and never fail its rewrite. `Tests/Automation/test_methods.py`'s read of a live editor's session file uses it too.
4. **No retry.** With full sharing, no transient state of a correctly published file fails a read, so the waits stay as they were: the C++ case's bounded `Test::WaitUntil` for the file to exist, and `launch_editor`'s poll. A read is not retried on any error; a file that a server is removing at exit (delete-pending on a volume without POSIX delete semantics) belongs to a session that is ending, for which an error is the right answer.
5. **The launch wait's bound** (the lead's addition, in the same area). `engine_client.LAUNCH_TIMEOUT_SECONDS`, how long `launch_editor` waits for a new editor's session file and `wait_for_lock_holder`'s default for an editor to take a project's lock, goes from 60 s to 300 s. It is only a hang bound: M21's stream measured a `--strict` Debug editor opening FeatureTest in 32 s unloaded, 43 s with M21's added content and 134 s while sibling worktrees loaded the machine, and the determinism suite failed twice on the 60 s bound. 300 s is more than twice the loaded measurement and well above the unloaded one, as ADR 0039 decision 5 sizes its bounds. The MCP bridge, `Tests/Automation/harness.py`, `Scripts/Test.py`'s export, determinism and games suites, `Scripts/Perf.py` and `Scripts/Hardening.py` start editors through `launch_editor` and have no session-file wait of their own, so they take the new bound; every failure message names it (`wrote no session file within 300 s`, `no process took the lock of <project> within 300 s`).

## Consequences

- A client never fails to read a session file because the server's rename is in flight, and the editor's rewrite never fails because one of the engine's clients is reading the file, on NTFS and every volume with POSIX rename semantics.
- Accepted limit (`Docs/Backlog.md` §6): a reader that opens a session file without `FILE_SHARE_DELETE` (a text editor, a script that is not one of the engine's clients) still fails the server's rewrite while it has the file open, and on a volume without POSIX rename semantics (FAT, exFAT, a network share holding the user-data folder) the fallback fails while any reader has it open; the editor tries the rewrite again every second and warns once per project, as before.
- `Docs/Architecture.md` §3 lists `PublishedFile` among Platform's units, and §13.2 says how the session file is replaced and read and how long clients wait for it.
- Tests: "SessionFile: a client reads the file while the rename that publishes it is still in flight" and "SessionFile: rewriting and removing the file succeed while a client is reading it" (the regression tests: on the code before this change the first failed with `PermissionDenied` and the second with `Access is denied`), "SessionFile: read returns the written content and reports a missing file", the four `PublishedFile` cases, the Windows probes `Test::RenameKeepingHandleOpen`, `Test::OpenForReadingSharingAll` and `Test::ReadRemaining`, and in `Tests/Automation/test_client.py` "test_a_session_file_is_listed_while_the_rename_that_publishes_it_is_in_flight" (it failed before this change: the live editor was not listed) and "test_the_launch_wait_is_a_hang_bound_with_headroom_over_a_loaded_start".
