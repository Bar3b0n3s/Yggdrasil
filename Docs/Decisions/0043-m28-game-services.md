## Context

M28 delivers World Tree's briefs 04 (display settings and a performance readout for scripts, with the game's additions: text that shows frame-paced values outside the state hash, and decisions on frame time recorded as input) and 03 (save data, with the game's addition: the session's audio mix kept across `Scene.Load`), in two waves (ADR 0042 decision 3): W28.1 display settings, the performance readout, presentation text and frame-time signals; W28.2 save data and the session's audio mix. The facts this record relies on, each checked in the code at `bb51e110`:

1. **`play.start` does not refresh.** `EditorMethodContext::StartRecordingSession` refreshes the project's assets (`Utils::RefreshAssets`) before `input.record` starts, but `StartPlay` calls `EditorPlayController::Start` directly, so a scene file written since the last refresh plays without its scene asset (`PrepareSession` finds no `AssetRecord` for its path): `Scene.GetCurrent` is nil and the play scene's summary falls back to the open scene's file (the F25 fix agent's open point 1). `EditorAssetManager::Refresh` is "the implicit refresh before every automation call that takes a path".
2. **The window.** `Platform/Window` is one GLFW class without OS backends; `WindowSpecification` has `Title`, `Width`, `Height`, `Resizable` and `Fullscreen` ("full screen on the primary monitor at its current video mode"); fullscreen exists only at `glfwCreateWindow` (`Window.cpp`), nothing calls `glfwSetWindowMonitor`, no monitor or video-mode query exists, and the window is visible from creation. `Window::GetNativeHandle` is the `GLFWwindow*`. `CheckPlatformWindowSupport` (`Platform/PlatformWindowSupport.h`, `Platform/Windows/PlatformWindowSupportWindows.cpp`, `Platform/Posix/PlatformWindowSupportPosix.cpp`) is the precedent of a Windows-only capability: Win32 GLFW platform only, a headless process refused, `Unsupported` on Linux and macOS.
3. **VSync.** `SwapchainSpecification::VSync` is set once at `Swapchain::Create`, kept in `m_Specification` and read by `ChoosePresentMode` at every `CreateSwapchain`; `Swapchain::RequestRecreate` recreates at the next acquire. There is no `SetVSync`. `Application::CreateFrameObjects` builds the window's swapchain with `device.GetSpecification().VSync`, also after a device loss, so a VSync changed on the swapchain alone would revert at the recovery.
4. **The project's window.** `WindowSettings` (`Project/ProjectSettings.h`: `Title`, `Width`, `Height`, `VSync`, `Fullscreen`, `Resizable`) becomes the `ApplicationSpecification`'s `WindowSettings` and `Graphics.VSync` through `ApplyGameSettings` (`App/ProjectSettingsApplication.cpp`); the Runtime's factory (`CreateRuntimeApp`) applies it from `Game.json` before `Application::Run` creates the window. `EngineContext::Create` mounts `user://` (`<UserData>/<Name>/`, atomic writes without a backup) before it creates the window. `ReadStartupPlatformWindowsPreference` (`EditorCore/EditorPreferences.cpp`) is the precedent for reading a `user://` file before the window exists, through a temporary read-only mount.
5. **The frame boundary.** `FrameLoop::RunFrame` runs events, the main-thread queue, `OnFrameSafePoint` (before the fixed steps), the steps, the update and the render; `Application::OnSafePoint` is the subclasses' hook, and the Runtime already consumes the session's quit request there.
6. **Scripts and hosts.** `IScriptHost` (`Scripting/ScriptHost.h`) holds `GetEnvironment()` (a `ScriptEnvironment`: `IsEditor`, `IsHeadless`, `IsFocused`, `Platform`, `Version`, `WindowSize`) and members with defaults (`GetPhysics2D`, `GetUi`, `GetText`), so `EditScriptHost` and the tests' `ScriptTestFixture` need no change for a new defaulted member. `PlaySession::State` implements it and forwards host questions to `IPlaySessionHost` (`GetScriptEnvironment`, the cursor), which `RuntimeApp::State` and the editor play controller's state implement. The `Application` module (`Scripting/Bindings/Application.cpp`) has `Quit`, `IsEditor`, `IsHeadless`, `IsFocused`, `GetPlatform`, `GetVersion` and `GetWindowSize`. Scripting is layer 4 (`Scripts/ModuleRules.json`, at most layer 3), so it includes neither Session nor App.
7. **The readout's sources.** `stats.get` (`Automation/Methods/StatsMethods.{h,cpp}`) builds `StatsGetResult` and `StatsViewSummary` from the host's `GetHostStatistics` (the Runtime's `ReadHostStatistics` lambda and the editor's, both outside Dist), `CountSessionBodies` and the script VM's `GetMemoryState`. Every type and function declared under `Automation/` is a forbidden Dist symbol family (`Scripts/Lib/runtime_map.py`), `CountSessionBodies` and the stats structs among them. `RenderStats` (`Renderer/RenderStats.h`) has per-pass CPU and GPU milliseconds, draw calls and triangles, the shadow counters and no light count; `SceneRenderStats` (`SceneRenderer.h`) counts `Lights` and `DroppedLights` in `RecordPrepareStage` without passing them on; `RecordDeformStage` marks each deformed mesh (`entry.Deformed`), which no counter counts. `ParticleSystem::GetStats().Particles` is the live particles after the step, which nothing reads; `PhysicsSystemStats` and `Physics2DSystemStats` have `BodyCount` and `ActiveBodyCount`. `FrameLoopStatistics` (`App/FrameLoop.h`) has `Fps`, `CpuMilliseconds` and `DroppedSeconds`.
8. **The frame-phase rule.** `ParticleEmitter:GetParticleCount` (`Scripting/Bindings/Particles.cpp`) raises an error when `call.Execution->Origin == ScriptExecutionOrigin::Gameplay` and the host's frame state is `InputPhase::Step`, so it is readable in `OnUpdate`, `OnLateUpdate`, test cases and evaluations.
9. **UI text.** `UiTextComponent` (v1) is drawn by `AppendUiDrawItems` (`Scene/UiExtraction.cpp`), which already substitutes a `UiTextInput`'s live text for its text element's `Text`; layout (`UiLayout.cpp`) and hit testing (`IsUiPointerTarget`) never read `Text`; `ui.tree` measures what extraction draws (`MeasureUiTreeTexts`). `UiSystem` keeps the interaction state, which its `AppendStateHash` hashes ("UiState1", empty while unused); the session reaches it through `IScriptHost::GetUi`. No UiText proxy type has methods.
10. **Input and replays.** `PlayInputEventType` has nine kinds (`Action` to `Text`); `PlayInput::ApplyTick` applies the queued events of a tick in the ApplyInput phase, after which the recorder captures them (`ReplayRecorder::CaptureAppliedInput`); `LatchFrame` latches the frame view. The hosts suppress live device input in test runs, replays and lockstep (`EditorPlayController::OnInputEvent`, `RuntimeApp`'s input), and recordings (`input.record`, lockstep sessions with a recorder) take it. The replay format is version 3 (`ReplayFormatVersion`, `ReplayData::FormatVersion`, `ReplayImporter::Version`); readers accept versions 1 to 3, version 2 added checkpoints and version 3 the fingerprint; `Tests/Data/Formats/Replay/` holds `v1.replay`, `v2.replay` and their `.upgraded.replay` files (no `v3.replay`). `input.inject` (`Automation/Methods/InputMethods.cpp`) and `Test.Inject*` (`Scripting/Bindings/Test.cpp`) queue events of the nine kinds.
11. **The audio mix.** `AudioSystem::InitializeMix` records the engine's Music, Sfx and Ui volumes and sets them to 1; `~AudioSystem` restores the recorded ones. `PlaySession::Activate` builds the scene's `AudioSystem` and initializes its mix, and `State::ConsumeRequests` resets it (restoring the volumes recorded before the session) and builds a new one that initializes the mix again at every `Scene.Load` and `Scene.Reload`, so a group volume a script set (`Audio.SetGroupVolume`, documented "for the rest of the session") is lost, in editor play, the Runtime and an export alike. `SessionScriptingTests.cpp`'s "startup audio gains survive callbacks and restore across scene replacement" pins today's reset. The editor also records the mix at a play start and restores it at the end (`EditorPlayController`'s `MixerBaseline`); the Runtime has no equivalent.
12. **Files.** `FileSystem::WriteFileAtomic` writes a temporary file, flushes the stream (no `FlushFileBuffers`), optionally keeps a backup and renames; `PublishedFile::Replace` renames with `FILE_RENAME_FLAG_POSIX_SEMANTICS` on Windows; nothing flushes durably (ADR 0003 decision 5: "it would come through a Platform hook if ever required"). `JsonWriter` writes 32-bit floats; nlohmann's `dump` writes the shortest round-trip double. `CheckJson` and `PushJson` (`Scripting/Private/BindingRegistration.h`) convert Luau values and JSON (nil, booleans, finite numbers, strings, arrays and string-keyed tables; cycles and mixed keys refused). `EditorPreferences` (`user://Editor.json`, `{"Format": "EditorPreferences", "Version": 1}`) is the user-data format precedent and a fuzz target.
13. **The state hash.** `PlaySession::ComputeStateHash` hashes the scene's canonical form, the tick, the `Random` state, the id draw count, then the physics, native, physics2d and ui blocks, each empty while unused.

### 2. `play.start` refreshes the project's assets (F25's open point 1)

`EditorMethodContext::StartPlay` refreshes the project's assets (`Utils::RefreshAssets`, `EditorAssetManager::Refresh`) before `EditorPlayController::Start`, as `StartRecordingSession` does, so a scene file written since the last refresh plays with its scene asset. A start refused because no project is open or a session or test run is active refreshes nothing; a start the controller refuses later (no open scene, assets in error) has refreshed first, which registers new files and may write their `.meta` files. The method's description and `AutomationMethodContext::StartPlay`'s documentation say so; the Runtime's `StartPlay` stays `Unsupported`. Tests: "EditorMethodContext: play.start refreshes the assets first, so a scene file written since the last refresh plays with its scene asset" (fails before the fix: no scene asset) and "EditorMethodContext: play.start refused while a session runs leaves the assets unrefreshed".

### 3. Display settings (W28.1)

- **Types** (`Platform/DisplayModes.h`, new): `enum class DisplayWindowMode { Windowed, Borderless, Exclusive }`; `struct DisplayVideoMode { uint32_t Width = 0; uint32_t Height = 0; uint32_t RefreshRate = 0; }`; `struct DisplaySettings { DisplayWindowMode WindowMode = Windowed; uint32_t Width = 0; uint32_t Height = 0; uint32_t RefreshRate = 0; bool VSync = true; }`. `Windowed` is a decorated window of `Width` x `Height` screen units; `Borderless` an undecorated window covering the window's monitor at its current video mode (`Width`, `Height` and `RefreshRate` are the monitor's, never changed); `Exclusive` GLFW's full-screen monitor mode at `Width` x `Height` and `RefreshRate`, which must be one of the monitor's modes (without `VK_EXT_full_screen_exclusive`, ADR 0042 decision 3).
- **Platform** (Windows backend only, ADR 0028 decision 10): `Result<std::vector<DisplayVideoMode>> QueryDisplayVideoModes(const Window&)`, the modes of the monitor the window is on (the one it is full screen on, else the one holding its centre, else the primary monitor), sorted by width, height and refresh rate, without duplicates; `Result<DisplayVideoMode> QueryCurrentVideoMode(const Window&)`, that monitor's current mode; `Status ApplyDisplaySettings(Window&, const DisplaySettings&)`, through `glfwSetWindowMonitor` and the decorated attribute (a Windowed window keeps its place, or is centred on its monitor when it leaves a full-screen mode). The platform-independent half (`Platform/DisplayModes.cpp`): the mode names and `Status ValidateDisplaySettings(const DisplaySettings&)`, the ranges every request and the file take in every mode (a known mode, `Width` and `Height` 1 to `MaxDisplayExtent` (16384), `RefreshRate` 0 to `MaxDisplayRefreshRate` (1000); `InvalidArgument` naming the member). `Platform/Windows/DisplayModesWindows.cpp` implements both for GLFW's Win32 platform and refuses a headless process (GLFW's null platform; `Unsupported`, "a headless process has no display"); `Platform/Posix/DisplayModesPosix.cpp` reports `Unsupported` ("only Windows has a backend"), as `PlatformWindowSupport` does. `WindowSpecification` gains `DisplayWindowMode DisplayMode` (default `Windowed`) and `uint32_t RefreshRate` (0: any), appended after `Fullscreen`; `Fullscreen` keeps its meaning (the project's setting: full screen at the monitor's current mode) and `Window::Create` applies `DisplayMode` when it is not `Windowed`, on the primary monitor (`Borderless` undecorated at the monitor's position and current mode; `Exclusive` GLFW's monitor window, which takes the mode closest to the size and refresh rate).
- **Swapchain:** `Swapchain::SetVSync(bool)` changes the specification's `VSync` and requests a recreate when it changed (the present mode is chosen again at the next acquire); `GetVSync()` reads it.
- **Application:** `Result<std::vector<DisplayVideoMode>> GetDisplayVideoModes() const`, `DisplaySettings GetDisplaySettings() const` (the settings in force: the mode, `Exclusive` for the project's `Fullscreen` at the start, the window's size, its monitor's current refresh rate in the full-screen modes, the VSync in force) and `Status RequestDisplaySettings(const DisplaySettings&)`, which validates at once (`Unsupported` headless, without a window or without a backend; `InvalidArgument` outside `ValidateDisplaySettings`' ranges or for an `Exclusive` mode not in the list) and applies the request at the next frame boundary (`Application`'s frame safe point, before the subclass's `OnSafePoint` and the fixed steps); the last request of a frame wins, and a failed apply is logged and changes nothing. `GetDisplaySettings` reports the window's last size that was not 0 x 0 while it is minimized (an Exclusive window is, at every focus loss), so a VSync-only request works then, and Windowed once the monitor let an Exclusive window go (`Window::IsFullScreen`, also when the monitor was disconnected). A request fills the members it leaves out from the settings in force, so a later request in the same frame replaces an earlier one. After an apply, the virtual `OnDisplaySettingsApplied(const DisplaySettings&)` receives what was applied (the request; a Windowed window's refresh rate 0, a Borderless window's size and refresh rate its monitor's current mode). `Application` keeps the chosen VSync and passes it to every swapchain it creates, so a device-loss recovery keeps it.
- **Persistence:** `user://Display.json`, `{"Format": "DisplaySettings", "Version": 1, "WindowMode": "<mode>", "Width": <n>, "Height": <n>, "RefreshRate": <n>, "VSync": <bool>}`, read and written by `App/DisplaySettingsFile.{h,cpp}` (`ParseDisplaySettingsFile`, `SerializeDisplaySettingsFile`, `WriteDisplaySettingsFile`, `ReadStartupDisplaySettings`, `ApplyStartupDisplaySettings` and `RestoreStartupDisplaySettings`, the factory's gate); a missing file keeps the project's `Window` settings; an unreadable one is ignored, and its problem (`StartupDisplaySettings::Problem`), read by the factory before logging exists, is logged by `RuntimeApp::OnInitialize`, so it reaches the Dist game's log. The Runtime's factory reads it before `Application::Run` (as the editor reads its platform-windows preference) and applies it to the specification's window and VSync (`ApplyStartupDisplaySettings`: the mode, the refresh rate, the size but in `Borderless`, the VSync, and the project's `Fullscreen` cleared), so the first window shows in the chosen mode; `RuntimeApp::OnDisplaySettingsApplied` writes it after each applied request (a failed write is logged). Headless, `--feature-test` and `--replay` runs neither read nor write it (`RestoreStartupDisplaySettings` reads only for a windowed run that is not a fixed-view one). The reader is a fuzz target (decision 12).
- **Script API** (`Application`, appended after `GetWindowSize`): `GetDisplayModes() -> {DisplayMode}`; `GetDisplaySettings() -> DisplaySettings`; `SetDisplaySettings(settings: DisplaySettingsRequest) -> (boolean, string?)`, with the aliases `DisplayMode = {Width: number, Height: number, RefreshRate: number}`, `DisplaySettings = {WindowMode: string, Width: number, Height: number, RefreshRate: number, VSync: boolean}` (`WindowMode` one of `Windowed`, `Borderless`, `Exclusive`) and `DisplaySettingsRequest`, the same members each optional (a member left out keeps its current value). `SetDisplaySettings` returns true when the request was accepted for the next frame boundary, and false with the reason where the calls do nothing. A malformed request is a script error wherever the call is made: an argument that is not a table, a member of the wrong type, a number that is not a whole number, an unknown mode, or settings outside `ValidateDisplaySettings`' ranges (checked by the binding before it asks the host, so a request that would raise in the Runtime raises in the editor and a test run too); in the Runtime an `Exclusive` mode the monitor does not list raises as well.
- **Where the calls do nothing:** the editor (its game view and every editor session), headless runs and every fixed-view session (suites, replays, recordings, lockstep: the sessions whose view is the project's window size). There `GetDisplayModes` returns an empty list, `GetDisplaySettings` returns `Windowed`, the session's view size, refresh rate 0 and the project's `Window.VSync`, and `SetDisplaySettings` returns false with its reason; nothing touches the project's `Window` settings or the state hash.
- **Hosts:** `IScriptHost` gains `GetDisplayModes`, `GetDisplaySettings` and `RequestDisplaySettings`, each defaulted to `Unsupported` (the binding then reports no modes, the host's view as a window and a refused request), and `IPlaySessionHost` the same three with the same defaults; `PlaySession` answers them itself where the calls do nothing (its environment's `IsEditor` or `IsHeadless`, a test run, lockstep or an active recording) and forwards the others to its host; `RuntimeApp::State` implements them over `Application`.
- **Tests:** `DisplaySettingsFileTests.cpp` (the round trip, the refusals at their members, the startup read of a missing, valid and truncated file, `ApplyStartupDisplaySettings` per mode, "DisplaySettingsFile: only a live windowed Runtime run restores Display.json, and an invalid one gives its problem", the writer's mount, and the fuzz case); "RuntimeApp: a windowed run restores Display.json, logs an invalid one in the game's log and saves an applied request" (the Runtime as a process, windowed without a renderer: a headless run never reads the file, an invalid one's problem reaches the game's log file from `OnInitialize`, a valid one's settings are what `Application.GetDisplaySettings` returns, and a request the frame boundary applied is written back); `Application`'s own cases: the gpu case "Application: a display request applies at the frame boundary and the recovered swapchain keeps the chosen VSync" (a windowed child: nothing applies at the call, the frame's last request wins, a refused one (an unlisted `Exclusive` mode, settings outside the ranges) queues nothing, `OnDisplaySettingsApplied` receives a Windowed window's size at refresh rate 0 and a Borderless window's monitor mode, and the swapchain the device-loss recovery creates keeps the chosen VSync; `Borderless` for one presented frame), "Application: a minimized window keeps its last size in the display settings" (a windowed child without a renderer: a VSync-only request while minimized) and "Application: a headless application reports the project's full screen as Exclusive and refuses display requests"; "Window: a native window created Borderless covers its monitor" (a windowed child: the restored mode at creation, closed at once); the binding without a display through `ScriptTestFixture` (`ApplicationTests.cpp`: no modes, the view, a refused request and every malformed request raising); "PlaySession: the display calls do nothing in a fixed-view session and reach the host in live play" (`PlaySessionDisplayTests.cpp`); "DisplayModes: a Borderless window covers its monitor and a Windowed one keeps its place or is centred" (`ComputeDisplayWindowRect`, the geometry `ApplyDisplaySettings` computes once the window has left an exclusive mode, whose desktop mode it reads only then); FeatureTest's GameServices suite in every run mode; and the gpu case "Swapchain: VSync and the Borderless display mode switch at run time", a windowed child that turns VSync off and on (one recreation each, FIFO again), checks the mode list and the refusals, then switches its window to `Borderless`, holds it for one presented frame once the window covers its monitor, and switches straight back to `Windowed`, presenting at each size (the lead's limits, 2026-11-16: as few borderless frames as the check needs, never `Exclusive`, never a change of the monitor's mode). `Exclusive` mode changes the desktop's video mode, a system setting of the shared machine, so no test switches to it (ADR 0042's risk "display modes on the one test machine"); it is covered by the Dist export check the game makes (Acceptance).

### 4. The performance readout (W28.1)

- **Struct:** `ScriptPerformanceStats` in `Scripting/ScriptPerformanceStats.h`, a header of M28's own that `ScriptHost.h` includes, so M29's and M32's readout rows join it at their merges without touching `ScriptHost.h`, which the ledger closes to them (the W28.1 review's finding 10; Dist-safe, outside `Automation/`): `bool RenderAvailable`, `bool GpuAvailable`, `double Fps`, `double CpuMilliseconds`, `double GpuMilliseconds`, `uint32_t VisibleLights`, `uint32_t DroppedLights`, `uint32_t ShadowedLights` (shadowed spot and point lights), `uint32_t DrawCalls`, `uint64_t Triangles`, `uint32_t Particles`, `uint32_t SkinnedMeshes`, `uint32_t Bodies`, `uint32_t ActiveBodies`, `uint32_t Entities`, `uint64_t ScriptHeapBytes`. The render counters are the game view's last rendered frame (GPU times from the frame the profiler last read back), zero with `RenderAvailable` false without a renderer.
- **Session:** `Session/SessionStatistics.{h,cpp}` (new): `struct SessionStatistics { uint32_t Entities; uint32_t Bodies; uint32_t ActiveBodies; uint32_t Particles; }`, `SessionStatistics ReadSessionStatistics(const PlaySession&)` and `CountSessionBodies`, moved here from `StatsMethods` (both worlds' bodies, as today). `IPlaySessionHost` gains `void ReadFrameStatistics(ScriptPerformanceStats&) const` (default: fills nothing, so `RenderAvailable` stays false), which the Runtime and the editor's play controller answer with their frame loop's `Fps` and CPU time and the game view's last `RenderStats` (`AddRenderStatistics`, `Session/SessionStatistics.h`); `IScriptHost::GetPerformanceStats()` (default `Unsupported`) is answered by `PlaySession` from the host's frame statistics, its own counters and its VM's heap.
- **Renderer:** `RenderStats` gains `VisibleLights`, `DroppedLights` and `SkinnedMeshes`, appended; `SceneRenderer::Render`'s stats block fills them from `SceneRenderStats::Lights` and `DroppedLights` and a new count of `RecordDeformStage`'s deformed meshes.
- **Script API:** `Application.GetStats() -> PerformanceStats` (alias of the struct's members, PascalCase), an error in a fixed-step gameplay callback (`GetParticleCount`'s rule and check), readable in `OnUpdate`, `OnLateUpdate`, test cases and evaluations; available in every configuration, Dist included.
- **`stats.get`:** `StatsGetResult` gains `activeBodies` and `particles`, `StatsViewSummary` `lights`, `droppedLights` and `skinnedMeshes`, appended (ADR 0042's `stats.get` row), filled from `SessionStatistics` and `RenderStats`; the editor's Stats panel shows them (the Runtime's F1 overlay, an ImGui view outside Dist, keeps its rows).

### 5. Presentation text (W28.1)

- **API:** `UiText:SetPresentationText(text: string?) -> ()` and `UiText:GetPresentationText() -> string?`, methods of a new `UiText` proxy type (`Scripting/Bindings/Ui.cpp`'s registration); nil clears. Both raise an error in a fixed-step gameplay callback (the readout's rule), and the text is at most `MaxScriptPresentationTextBytes` (4 KiB, `ScriptLimits.h`) of valid UTF-8.
- **Storage:** `UiSystem` keeps a map from entity id to presentation text beside its interaction state, never serialized, hashed (`AppendStateHash` leaves it out) or recorded; a scene replacement clears it, and an entry whose entity is gone or no longer holds a `UiText` is dropped at the next frame's UI layout.
- **Drawing:** `RenderExtractionRequest` gains a borrowed `UiPresentation` pointer (a `UiPresentationTexts`, `Scene/UiInteraction.h`), set where `UiInteraction` is, which `AppendUiDrawItems` reads to draw the presentation text in place of the element's `Text` (a text input's own text keeps precedence; an empty one draws no item); layout and hit testing keep the authored text and rect. `ui.tree`'s entries gain `presentationText` (appended after `active`): the play session's text, cut as `text` is, empty without one and in the edit scene; their `textBounds` measure what the element draws.

### 6. Frame-time signals (W28.1)

- **API:** `Input.PostSignal(name: string) -> boolean` posts a named signal for the next fixed step; it raises an error in a fixed-step gameplay callback (a fixed-step decision is deterministic and acts directly) and returns whether the session takes live signals. `Input.WasSignalled(name: string) -> boolean` reads, in the fixed step, the signals the tick latched and, in the frame phase, those latched by the ticks since the last frame (the frame view's rule). Names are 1 to `MaxScriptSignalNameBytes` (64) bytes of valid UTF-8; a name posted twice for one tick counts once, and a tick takes at most `MaxScriptSignalsPerTick` (64) distinct live signals, each later one a located error (both in `ScriptLimits.h`, which `PlayInput` reads).
- **Latch:** a signal is an input event of the new kind `PlayInputEventType::Signal` (`"Signal"`, member `name`), appended after `Text` (the registry enum `InputEventType` and the codec follow); `PlayInput::QueueSignal` queues a live one for the next tick as an injected event (never previewed by the frame view) and `ApplyTick` latches it in ApplyInput with the device input (no new phase), so `ReplayRecorder::CaptureAppliedInput` records it like any applied event; `PlayInput::WasSignalled(phase, name)` reads the step's or the frame's latch. `IScriptHost` gains `PostSignal` and `WasSignalled` (defaults: `Unsupported`, false), which `PlaySession` answers.
- **Which signals a session takes:** ordinary live play and recordings take live ones; replays, suites, FeatureTest runs and lockstep sessions without a recorder ignore them (`PostSignal` returns false) and take only those a replay plays back, a test injects (`Test.InjectSignal(name)`) or automation injects (`input.inject`'s event type `signal` with `name`).

### 7. The replay's version 4

- `ReplayFormatVersion`, `ReplayData::FormatVersion` and `ReplayImporter::Version` become 4; `ReplayFingerprintFormatVersion` stays 3. Version 4 adds the header member `SaveData` after `Config` (an object: the save-data store's contents at the recording's start, `{}` when empty; decision 8; its numbers the store's doubles, written exactly, the one member of an authored file whose numbers are doubles: `JsonWriter` gains `WriteDouble` and `JsonNumbers::Double`, which `ReplayToText` and `CookReplay` use for it, and the readers check its numbers as finite doubles; so a recording starts from the store as it is, the session canonicalizes the header's values as it seeds its store, and every playback seeds the same values; the lead's decision on the W28.1 review's departure 1, 2026-11-16) and the event type `Signal` (cooked tag 9, its `Name` a string of 1 to 64 bytes). Readers accept versions 1 to 4; a file of version 1 to 3 migrates with an empty `SaveData`, and a `Signal` event in a file below version 4 is refused as an unknown type.
- Fixtures: `Tests/Data/Formats/Replay/v3.replay` and `v3.upgraded.replay` (new), `v1.upgraded.replay` and `v2.upgraded.replay` written again at version 4; `Replay.schema.json`'s `Version` and event types and the reference generator's replay example follow. FeatureTest's 14 scaffold-recorded replays are recorded again by `Scaffold.py`; the demos' eight committed replays are rewritten by a recorded `Editor --headless --project <P> --upgrade` on this branch, which the lander repeats on the merged tree if main changed them (the ledger's demo row). No hash moves (decision 10).

### 8. Save data (W28.2)

- **Script API** (`SaveData`, `Scripting/Bindings/SaveData.cpp`, `RegisterSaveData` after `RegisterTerrain`): `Get(key: string) -> any` (nil when absent), `Set(key: string, value: any) -> ()` (nil deletes), `Delete(key: string) -> boolean` (whether it held the key), `GetKeys() -> {string}` (sorted by their bytes), `Commit() -> (boolean, string?)` and `GetLoadError() -> string?`; `Test.SetSaveData(values: {[string]: any}) -> ()` replaces a test run's store. Keys are 1 to `MaxSaveDataKeyBytes` (256) bytes of valid UTF-8; values are what `CheckJson` converts (nil, booleans, finite numbers, strings, arrays and string-keyed tables). Reads and writes work in every callback (`Set`, `Delete` and `Test.SetSaveData` are external mutations of an evaluation, `PrepareHostMutation`, since the store is hashed); the store's compact JSON is capped at `MaxSaveDataBytes` (1 MiB; both limits in `ScriptLimits.h`), a `Set` past it a located error naming both sizes. `Commit` returns `(false, reason)` for any failure of its host's write. The module reaches the store through `IScriptHost` members (`GetSaveValue`, `SetSaveValue`, `ReplaceSaveData`, `GetSaveKeys`, `CommitSaveData`, `GetSaveDataLoadError`; defaults `Unsupported`, which the module raises), since Scripting does not include Session.
- **Store:** `Session/SaveDataStore.{h,cpp}` (`SaveDataStore`, `SerializeSaveDataFile`, `ParseSaveDataFile`, `LoadSaveDataFile`, `WriteSaveDataFile`), owned by the session (`PlaySession::GetSaveData`) and kept across `Scene.Load` and `Scene.Reload`; its values in key order and canonical (object keys sorted at every depth, every number a double, so a file's integer and a script's number hash alike), serialized by a double-preserving writer (nlohmann's shortest round-trip doubles, tabs), never `JsonWriter`. The file: `{"Format": "SaveData", "Version": 1, "Values": {...}}`. `PlaySessionSpecification` gains `SaveData` (the object it starts with) and `SaveDataLoadError`, `PlayStartOptions` `SaveData` (a fixed-view session's seed: a replay's header, a recording's start), and `IPlaySessionHost` `CommitSaveData(values)` (default `Unsupported`).
- **Backends:** the Runtime's live session reads and commits `user://SaveData/Store.json` (published atomically and, on Windows, flushed durably through a new Platform hook, `PublishedFile::WriteDurably`: a temporary beside the store written, `FlushFileBuffers`, then `Replace`; `Unsupported` on Linux and macOS: the write then falls back to `FileSystem::WriteFileAtomic` without a backup and logs it at Info); a headless Runtime, the Dist smoke test among them, reads it and never writes it (`Commit` returns false with the reason). Editor play uses `<project>/Library/SaveData/Store.json` (`EditorPlayController::ReadPlaySaveData` and `WritePlaySaveData`), and a `--read-only` editor a private store in memory that lives as long as the editor (a project opened next starts with an empty one). Fixed-view sessions (suites, replays, recordings, lockstep, FeatureTest) use an in-memory store, empty by default: a suite seeds it through `Test.SetSaveData(values)`, a replay through its header, and a recording records the store it starts with (the editor's play store's contents, seeded by `savedata.set`), never the machine's real store; their `Commit` returns true and writes nothing. A Runtime recording (automation `input.record`) starts with an empty store: the Runtime has no `savedata.set`, and the machine's store is never recorded. Every replay starts with its header's store: the editor's `input.replay`, both hosts' FeatureTest runners and the Runtime's `--replay` and automation replays.
- **Corruption:** an unreadable or invalid file is logged, moved aside as `Store.corrupt-<n>.json` (the first free `n` from 1), reported by `SaveData.GetLoadError()`, and the session starts with an empty store.
- **Methods** (`EditorCore/Automation/SaveDataMethods.{h,cpp}`, named `savedata.*`, ADR 0042's `saveData.*` in the domain's lowercase that `MethodRegistry` requires, MCP tools `savedata_get`, `savedata_set` and `savedata_clear`; editor only, after M26's terrain methods, exposed as MCP tools, none `Mutates`: the store is no project content, so a read-only editor serves them on its private store): `savedata.get {target?: Editor|Play}` (`{values, count, bytes, loadError}`: the play store, or the running session's with `target: "Play"`), `savedata.set {values, merge?}` (seeds the play store: `values` replaces it, or merges with `merge: true`, null deleting a key) and `savedata.clear`; an editor panel "Save Data" (`Editor/Panels/SaveDataPanel`, `EditorPanel::SaveData` after `Native`, closed by default and docked with the bottom panels, registered by `EditorLayer.cpp`) lists, sets, deletes and clears the play store.

### 9. The session's audio mix (W28.2)

The mix belongs to the session: its first `AudioSystem` records the engine's Music, Sfx and Ui volumes and sets them to 1 once at the session's activation (`InitializeMix`), and the last restores them once at its end; a scene replacement hands the recorded volumes from the replaced scene's system to the new one (`AudioSystem::TakeMix`, which leaves the engine's volumes in place and makes the replaced system restore nothing, and `AdoptMix`, which records them without touching the engine's) instead of initializing the mix again, so the volumes a script set before `Scene.Load` or `Scene.Reload` hold after it, in editor play, the Runtime and an export alike (ADR 0042's `AudioSystem` row: the session-owned mix's handover). A replacement whose new scene's scripts fail to start stops the session after the handover, so the recorded volumes still come back at its end. Tests: "PlaySession: a group volume set before Scene.Load holds after it" (every group, `Scene.Load` then `Scene.Reload`; it failed before the fix, every volume back at 1), "PlaySession: a scene replacement whose scripts fail still restores the mix recorded before the session", "AudioSystem: a mix handed over is restored by the system that adopts it, not by the one that gave it" and the changed "PlaySession: startup audio gains survive callbacks and scene replacement, and restore when the session ends". `SessionScriptingTests.cpp`'s case that pinned the reset is changed to the documented behaviour; FeatureTest covers it in every run mode (the SaveData suite's cases "a seeded store and the group volumes set before Scene.Reload" and "after Scene.Reload the seeded store opens the gated branch and a group volume set before it holds", with W28.2's save-data checkpoint: the suite's cases share one play session, since a case that requests a scene replacement returns in the requesting tick and only a later case sees the new scene).

### 10. Determinism and the state hash

- The display calls never reach the hash (decision 3); the readout and presentation text are frame-phase reads and writes that the fixed step cannot make (errors), and presentation text is never serialized or hashed; signals are input, outside the hash as all input state is, recorded and played back.
- **The save-data block** follows the ui block in `ComputeStateHash`: nothing while the store is empty, else a marker ("SaveDat1") and each key and value in key order (the value's canonical text), so every committed hash stays. M35's world-pause block follows it whatever the landing order (the ledger).
- Every replay with a signal or a seeded store verifies in Debug, Release and Dist (decision 11's FeatureTest replays).

## Departures from ADR 0042's design defaults

- **The durable flush's fallback logs every time, at Info, not once** (decision 8): a once-per-process flag is mutable process-level state, which §3 rule 5 does not list; a commit is rare (a player's save), so the line costs nothing.
- **The Runtime's F1 stats overlay keeps its rows** (decision 4): ADR 0042's `RuntimeApp` row gives M28 "the readout and the stats overlay's counters"; the overlay is an ImGui view outside Dist, while the brief needs the counters in Dist, which the script readout (`Application.GetStats`) gives, so the overlay is left as it was.
- **The display calls return `(false, reason)` from `SetDisplaySettings` only** (decision 3): the getters return values where the calls do nothing (no modes, the view as a window), so an options menu populates in the editor too; a malformed request raises, as every binding's does.
