## 1. Planned milestones

Milestones run in phases: the milestones of a phase are developed in parallel, each on its own branch in its own worktree, and their milestone-end `CI.py` runs go one at a time on the one GPU. Phase end: once the phase's last milestone has landed, main is pushed to `origin` as an off-site backup, and the work pauses for the product owner's go-ahead (ADR 0028 decision 14).

## 4. Linux and macOS catch-up

The product owner chose "Drop the catch-up" (ADR 0028 decision 10, superseding ADR 0026 decision 1's deferral of 2026-10-14 and the first version of ADR 0028, which scheduled it as M21). Windows is the only verified platform. First-party code stays portable by rule (the `Platform/` layering, no Windows-only shortcuts, the local portability stage's premake generation and clang-cl builds), but Linux and macOS are never verified: the Linux/macOS catch-up was dropped by the product owner, because there is no Linux or macOS machine without GitHub. GitHub is only an off-site backup of the repository: GitHub Actions is not part of the process, and nothing reads or waits for its results.

- The GitHub Actions failures of the M15 milestone commit, and whatever the runs of later pushes report (ADR 0026 decision 1): dropped by the owner (ADR 0028): there is no Linux or macOS machine without GitHub.
- A macOS run of an exported bundle: its signature and loader lookup (ADR 0026 decision 1): dropped by the owner (ADR 0028): there is no Linux or macOS machine without GitHub.
- **ADR 0025 finding M29:** port the Runtime's automation connection to POSIX, so that "RuntimeApp: F1 toggles the stats overlay in a windowed run and the game still receives F1" runs on Linux and macOS (ADR 0025 decision 15): dropped by the owner (ADR 0028): there is no Linux or macOS machine without GitHub.

- GCC 14, Clang 19 with libstdc++ and Apple Clang build only in GitHub Actions, and their failures were to be fixed here (ADR 0013 decision 25's third limit): dropped by the owner (ADR 0028): there is no Linux or macOS machine without GitHub.

The designs for these (the bundle probe, the M29 port and the M30 ELF reader) stay in the gitignored `bin/Reviews/M16-Map.json` of the development machine (ADR 0026 decision 1).

The owner's answer to the plan's open points, "Windows backends only" (ADR 0028 decision 10), also drops the kept items' Linux and macOS backends. ## 6. Accepted limits

Limits accepted for v1. A limit that names a milestone is scheduled by ADR 0028 (or, from phase 8, by ADR 0060) and leaves this list, or is amended, when that milestone lands; the others have no work planned, and reopening one needs an ADR. Each milestone's ADR adds the kept limits it accepts.

- No render thread; two frames in flight (§4.11). Won't do (§8), kept by the product owner's answer 5 to ADR 0060.
- The GPU failures that M18 does not recover stay fatal: autosave in the editor, a crash report and exit code 4 (§8.14 item 6). M18 (ADR 0028 decision 5; ADR 0029 decisions 25 and 40 to 46) recovers a device loss in process at the frame boundary, a hang that the driver or the operating system resets during the bounded wait's reset wait (like a loss), and GPU out-of-memory after startup (trimmed and retried once, then only the request fails with `OutOfMemory`). What stays fatal, each with its reason: a hang with no loss report after the 10 s budget and the reset wait (`--gpu-reset-wait`, 15 s by default: Vulkan cannot cancel submitted work, a device with pending work cannot be destroyed, and a second device on the same GPU would queue behind it; `project.open {recover}` restores the editor's autosave); out-of-memory at startup (nothing has rendered) and in a recovery's recreation (a second startup); out-of-memory in the swapchain's acquire and present and in the application frame's UI draw (no request there can fail alone); a Vulkan out-of-memory error that vulkan.hpp throws out of NVRHI's internals on a healthy device, at the frame boundary or in an automation method (the throw unwinds the frame or the method in the middle of a recording, with no request boundary to trim and retry at; Architecture §4.6 item 2); a loss before the first frame, a recovery whose device creation fails again after its one retry, a second loss during the recovery, an owner whose recreation fails on the recreated device, and a GPU object still alive after every owner released. No work planned. A swapchain recreation that runs out of memory again after its trim leaves the window black until its size changes or it is minimized and restored, since Vulkan retires the old swapchain: a window whose size never changes (a fullscreen game whose alt-tab does not minimize it, a fixed-size window) stays black for the rest of the run while the game goes on (ADR 0029 decision 44). No work planned: a retry without a size change would have no presented frame to pace it.
- The shader reload (`shaders.reload`, the editor's Tools > Reload shaders, M18) reloads the scene renderer's pass list only: ImGui's per-format pipelines and the Runtime's blit keep the shaders the library cached for them before the reload, also for a pipeline created after it, so a change to them needs a restart; exported games never reload shaders (ADR 0029 decision 3). No work planned.
- A hand-edited `.spritesheet` whose frame extends past its texture (or a texture reimported smaller than its frames) is accepted by the importer, and the frame samples clamped edge texels: `asset.create` and `asset.setProperties` refuse such a frame, where the texture's size is at hand (ADR 0029 decision 14 and risk 6), and M21 decided it by reporting it: `project.validate` warns `SPRITE_FRAME_OUTSIDE_TEXTURE` on the sheet's frame and on each tilemap palette entry that names it, against the imported texture's width and height, while the renderer draws it as before (ADR 0032's milestone review). No work planned.
- Recovery from a really lost device is exercised only by injection: the injected losses and the injected reset hang leave the Vulkan device alive, so `Recover`'s release on a really lost device (NVRHI's in-flight command lists retired without querying the device, `vkDeviceWaitIdle` and the timeline query answering `VK_ERROR_DEVICE_LOST`, a `vk::SystemError` thrown out of the middle of a recording) and a real driver reset (a Windows TDR) have never run here; that code is written not to rely on the device answering, and the injected tests answer the timeline with `VK_ERROR_DEVICE_LOST` through the dispatcher where they can (ADR 0029 risk 8 and decisions 39 and 40). No work planned: no test suite provokes a real TDR.
- Golden images exist for the `nvidia-62x` device class only; every other device class runs them in smoke mode (§15.4; ADR 0013 decision 25). Kept: goldens for other classes won't do (§8). Goldens stay on the nvidia-62x device class only, and the NVIDIA driver's major version is held at 62x for the rest of the program: the goldens were `nvidia-61x`'s until the product owner took driver 621.14 on 2026-11-10 and they were renamed (ADR 0028 decision 9, amended 2026-11-10); since M18 (W18.2) a renamed class is reported: a device class without an image's golden next to a same-vendor class that has it fails the golden run instead of smoke-testing, and `Tests/Golden/README.md` holds the rename procedure (ADR 0029).

The program stays on Vulkan SDK 1.4.350.0 and slangc 2026.8 (`Scripts/Lib/Toolchain.json` unchanged); it is revisited only if an in-scope item needs a newer toolchain, as an approval request at a phase boundary (ADR 0013 decision 25; ADR 0025 decision 18; ADR 0028 decision 3).
- The machine-wide build, GPU and gate locks cover the scripts and the MCP bridge's launches, not processes started by hand: a Tests or Editor binary run directly takes no lock (the build-and-test skill routes GPU test cases through `Test.py --filter`), and an editor that the bridge leaves running with unsaved changes when its MCP client goes away renders without the GPU lock, whose hold ends with the bridge (Architecture §2.3; ADR 0028 decision 16). No work planned.
- The machine-wide locks' queue (first come, first served, phase 6's setup) knows a dead waiter by its ticket's free operating-system lock, not a live one that stopped polling: a waiter whose process lives but stops polling (suspended at a debugger's break, or a console process blocked writing while a QuickEdit selection holds its window) keeps its place, and at the head of a queue holds the lock back from everyone behind it, as a suspended holder keeps its lock; a stalled `CI.py` anywhere in the gate's queue does more, since any live gate ticket closes the gate: every build, GPU run, `Test.py` run and bridge launch outside a held run waits, machine-wide; `Locks.py` lists it with its pid and wait time, and stopping it frees its place (Architecture §2.3). No work planned.

- Nothing in the solver stands for a character (M34, ADR 0049 decisions 1 and 3; World Tree's brief 11; M48, ADR 0066 decisions 3 and 4): its inner body meets sensors only there, so it no longer pushes Dynamic bodies with infinite mass (which drove light debris through floors and launched the character standing on it), and what stops a Dynamic body moving into a character is the character's own update. - M45's sky (`Docs/Decisions/0063-m45-sky-and-time-of-day.md` decision 1; Skerries' brief S03), accepted at its landing:
  - Relit probes lack the light the sun and the sky bounce off surfaces: an irradiance volume relit by the sky keeps its baked local light (lamps, fires, emission) and takes the sky's light through its baked visibility of the sky, so a noon interior lit through a window reads darker and bluer than a static bake at noon would; fill lights make up for it (the look skill), and §2's keyframed bakes would carry the bounce.
  - The sky's image-based light is taken at sea level, whatever the camera's altitude; only the Sky pass and the driven lights' transmittance take the camera's altitude.
  - A reflection probe is relit only by the ratio of the relit volume around its centre (the luminance of the relit to the baked constant term at the volume's probe nearest its centre, clamped to [0, 4]), and outside every relit volume it keeps its bake (`PROBE_NOT_RELIGHTABLE` names it). A relightable volume the view culls is kept for the reflection probe whose centre it holds only while one of the view's 8 volume slots (`MaxViewIrradianceVolumes`) is free: in a view that already keeps 8 volumes in view, such a reflection shows its bake's brightness until the camera turns toward the volume (the W45.4 review's finding 3).
  - The image-based light follows the clouds' drift in steps of `SkyCloudLightingStep` (1 s of simulation time), so a drifting cloud layer regenerates it once a second.
  - The sun's and the moon's discs and the stars are not in the image-based light: the Sun and Moon lights carry the discs' light.
  - Beside a `Sky`, an Environment is unused (`SKY_ENVIRONMENT_IGNORED`).
  - The image-based light's cloud layer is taken over the world origin, not under the camera, so a camera kilometres from the origin sees clouds overhead that its ambient light and reflections do not (the W45.2 review's nit 7).
  - The atmosphere's ground below the horizon is lit by the Sun, the Moon light and the zenith's radiance alone and seen without the extinction between it and the camera, so it reads too bright from a high camera (the W45.2 review's nit 7).
  - M26's probe grid under a Sky (the W45.3 review's finding 1): an `IrradianceVolume`'s outer probes lie on its box's faces and only surfaces inside the box take its light, so a volume that lights a room's walls puts its outer probes in them, where a probe sees through the culled back faces of single-sided geometry and the sky leaks in, while a box inset from the walls leaves them to the Environment's or the open sky's light. The game-building skill's `look` recipe (a 0.6 m `DoubleSided` shell with the outer probe layer in its middle, as `Golden: SkyProbes` builds) keeps the sky out at the cost of walls that read a little dark. The engine-side fix, excluding or relocating the probes that see back faces, or rendering the captures double-sided (which changes every bake), is the item to decide; no milestone yet.
- A surface without a normal map is shaded with a normal tilted by about 0.3 degrees (found by M45's `SkyProbes` diagnostic, the W45.3 review's follow-up; present without a Sky, so it predates M45): the flat normal texture (`engine://Textures/FlatNormal`) holds 128/255, which decodes to 0.0039 rather than 0 in its X and Y. So a surface exactly parallel to a directional light, which should take none of its light, takes a little, and that light's cascade shadow at so grazing an angle bands it in rows of acne (3 to 5 levels of 255 on a dark wall under automatic exposure). A scene avoids putting a light exactly in a wall's plane (the game-building skill's `look` page). The engine-side fix, decoding an unbound normal map as the exact (0, 0, 1), is the item to decide, with no milestone yet; it moves every map-less surface's shading slightly, so it re-baselines the goldens.
- Only the cascade owner casts directional shadows (one directional light per view, Architecture §8.7): a second directional light above the horizon, a Sky's Moon light by day included, is unshadowed and lights interiors through their walls. A game keeps such a light dim, or below the horizon by day, or turns its `CastShadows` off. No work planned.
- M46's mesh levels and wind (`Docs/Decisions/0064-m46-mesh-lods-draw-distance-and-wind.md` decision 3 and its W46.2 record; the Skerries brief S04), accepted at their landing:
  - A view culls a wind-swept mesh by its rest bounds (each submesh's bounds over every level, undisplaced), so a vertex the wind moves beyond them can be culled with its submesh at the edge of a view or a shadow map.
  - A material's `Flutter` is in metres at its entity's scale 1: the flutter moves along the normal through the entity's transform, unnormalized (the displacement allows no division or square root, so every pipeline computes the same bits), so it scales with the entity, and a non-uniformly scaled entity flutters off its normal; the lean and the sway are in world metres (the W46.2 review, finding 3).

  - Mesh colliders, the navigation bake, `scene.raycast` and CPU picking (`viewport.pick`) use a mesh's level 0 without wind, whatever level a view draws and however the wind moves it.
  - Wind displaces positions only: normals and tangents keep their rest direction, so the shading does not follow the bend.
  - A spot or point shadow map that holds a wind caster renders again every frame (its M29 signature hashes the wind's phases), a cost where many swaying plants sit under cached lights.

- M47's water (`Docs/Decisions/0065-m47-water.md` decision 3; Skerries' brief S01), accepted at its landing:
  - Each collider floats on the plane under its world bounds' centre, so a collider longer than the swell does not follow it: give a hull several colliders to ride a short swell.
  - Jolt's drag uses the whole body's local bounds, whatever is submerged, so a boat with spread pontoons is damped as its whole box.

## 7. Non-goals for v1

Out of scope by design (§1.2), each open to an ADR. ADR 0028 schedules some, records others as won't do (§8), and leaves the rest out of scope:

- **Graphics:** backends other than NVRHI-Vulkan, ray tracing, bindless and GPU-driven rendering, render-graph aliasing (won't do, §8); clustered light culling and point-light shadows (built by M23, W23.1); TAA, histogram auto-exposure, colour-grading LUTs and SSR (built by M26: auto-exposure and LUTs in W26.1, TAA and SSR in W26.2); GI beyond IBL plus AO (baked irradiance and reflection probes built by M26, W26.1; dynamic GI won't do, §8).
- **Assets:** GPU texture compression (imported textures as BC7 and BC5 since M23, W23.1; environment cubes as BC6H since its W23.2), EXR import (built by M23, W23.2), Ogg Opus import and mesh instancing (built by M23, W23.1).
- **Features:** skeletal and morph animation (built by M23, W23.3, with script-driven blending; an animation state-machine graph stays a non-goal, §1.2), particles and terrain (built by M26: particles and terrain import, physics and queries in W26.1, terrain rendering and its sculpt and paint tools in W26.2); visual scripting (built by M24: graphs, their transpiler to Luau and their edit methods by W24.1, `Docs/Decisions/0035-m24-contract.md` decisions 2 to 13; the Graph Editor canvas, live values in play (`graph.liveValues`) and the graphs skill page by W24.2, decisions 14 and 15) and native gameplay modules (built by M19 on Windows, W19.1 to W19.3, ADR 0030 decisions 25 to 35; on Linux and macOS dropped by the owner, §4); networking (out of scope, stays here: "Networking can stay in the backlog for now").
- **Editor and scenes:** native file dialogs (on Windows since M18, W18.1: nativefiledialog-extended's `IFileDialog` backend behind the FileDialog API, ADR 0029 decisions 19 to 21; their Linux and macOS backends dropped by the owner, §4, so the ImGui picker serves there), ImGui multi-viewport OS windows (built by M24 on Windows, W24.1: platform windows on their own swapchains, registered with M18's recreation protocol, `Docs/Decisions/0035-m24-contract.md` decisions 17 to 21; on Linux and macOS dropped by the owner, §4), a UI framework beyond `TextComponent` (the static UI since M22's W22.1, ADR 0033 decisions 2 to 9, and its interaction since W22.2: focus and navigation, events, the four widgets, the theme, minimal authoring and the interaction state in the hash, decisions 21 to 36; and since W22.3 the text input, fallback fonts, shaping and bidirectional text, and world-space canvases, decisions 42 to 53).
- **Platforms:** mobile and web, native Wayland, cross-OS export, bit-exact cross-OS or cross-compiler determinism (out of scope, stay here: "We are not doing this right now"); consoles, identity code signing and notarization (won't do, §8).
