## 4. Linux and macOS catch-up

The product owner chose "Drop the catch-up" (ADR 0028 decision 10, superseding ADR 0026 decision 1's deferral of 2026-10-14 and the first version of ADR 0028, which scheduled it as M21). Windows is the only verified platform. First-party code stays portable by rule (the `Platform/` layering, no Windows-only shortcuts, the local portability stage's premake generation and clang-cl builds), but Linux and macOS are never verified: the Linux/macOS catch-up was dropped by the product owner, because there is no Linux or macOS machine without GitHub. GitHub is only an off-site backup of the repository: GitHub Actions is not part of the process, and nothing reads or waits for its results.

- The GitHub Actions failures of the M15 milestone commit, and whatever the runs of later pushes report (ADR 0026 decision 1): dropped by the owner (ADR 0028): there is no Linux or macOS machine without GitHub.

## 6. Accepted limits

Limits accepted for v1. A limit that names a milestone is scheduled by ADR 0028 and leaves this list when that milestone lands; the others have no work planned, and reopening one needs an ADR. Each milestone's ADR adds the kept limits it accepts.

- No render thread; two frames in flight (§4.11). Won't do (§8).
- The GPU failures that M18 does not recover stay fatal: autosave in the editor, a crash report and exit code 4 (§8.14 item 6). M18 (ADR 0028 decision 5; ADR 0029 decisions 25 and 40 to 46) recovers a device loss in process at the frame boundary, a hang that the driver or the operating system resets during the bounded wait's reset wait (like a loss), and GPU out-of-memory after startup (trimmed and retried once, then only the request fails with `OutOfMemory`). What stays fatal, each with its reason: a hang with no loss report after the 10 s budget and the reset wait (`--gpu-reset-wait`, 15 s by default: Vulkan cannot cancel submitted work, a device with pending work cannot be destroyed, and a second device on the same GPU would queue behind it; `project.open {recover}` restores the editor's autosave); out-of-memory at startup (nothing has rendered) and in a recovery's recreation (a second startup); out-of-memory in the swapchain's acquire and present and in the application frame's UI draw (no request there can fail alone); a Vulkan out-of-memory error that vulkan.hpp throws out of NVRHI's internals on a healthy device, at the frame boundary or in an automation method (the throw unwinds the frame or the method in the middle of a recording, with no request boundary to trim and retry at; Architecture §4.6 item 2); a loss before the first frame, a recovery whose device creation fails again after its one retry, a second loss during the recovery, an owner whose recreation fails on the recreated device, and a GPU object still alive after every owner released. No work planned. A swapchain recreation that runs out of memory again after its trim leaves the window black until its size changes or it is minimized and restored, since Vulkan retires the old swapchain: a window whose size never changes (a fullscreen game whose alt-tab does not minimize it, a fixed-size window) stays black for the rest of the run while the game goes on (ADR 0029 decision 44). No work planned: a retry without a size change would have no presented frame to pace it.
- The shader reload (`shaders.reload`, the editor's Tools > Reload shaders, M18) reloads the scene renderer's pass list only: ImGui's per-format pipelines and the Runtime's blit keep the shaders the library cached for them before the reload, also for a pipeline created after it, so a change to them needs a restart; exported games never reload shaders (ADR 0029 decision 3). No work planned.
- A hand-edited `.spritesheet` whose frame extends past its texture (or a texture reimported smaller than its frames) is accepted by the importer, and the frame samples clamped edge texels: `asset.create` and `asset.setProperties` refuse such a frame, where the texture's size is at hand (ADR 0029 decision 14 and risk 6), and M21 decided it by reporting it: `project.validate` warns `SPRITE_FRAME_OUTSIDE_TEXTURE` on the sheet's frame and on each tilemap palette entry that names it, against the imported texture's width and height, while the renderer draws it as before (ADR 0032's milestone review). No work planned.

- A glTF mesh on a joint node is reported with `ASSET_CONTENT_SKIPPED` and not placed (M23): joint nodes become Skeleton joints, never entities, so nothing holds the mesh; a model attaches it to a non-joint child node instead, which the importer places under the Animator at its rest transform (ADR 0034 decision 25). No work planned.
- A glTF animation's morph-weight channels play only on a node at or below a skin's Animator (M23): a glTF of morph targets without a skin imports its meshes' morph targets and its nodes' SkinnedMesh weights, but its animations' weights channels are skipped with `ASSET_CONTENT_SKIPPED`, since no Animator plays them (ADR 0034 decision 25). No work planned: the AnimationSystem poses only an Animator whose Skeleton loads, so a morph-only rig would need an Animator that poses without one.
- A deformed item that casts shadows (M23) is deformed once a frame whenever any shadow is planned, even when every cascade, spot tile and point face then culls it: the Prepare stage prepares the shadow casters, acquiring each deformed caster's deformation, before the per-face culling, so an off-screen skinned shadow caster costs its Skinning dispatch whether or not a shadow draws it (`Docs/Decisions/0034-m23-contract.md` decision 36, stream C's design the lead accepted). No work planned: culling the casters per face before acquiring their deformations changes the Prepare stage's order of the shadow passes, which no milestone of the program schedules.

Not fixed in phase 3: `ScreenshotMethods` belongs to M26 in phase 3's ledger (ADR 0028). No work planned.

Not fixed in phase 3: `ScreenshotMethods` and `ViewportMethods` belong to M26 in phase 3's ledger; M25's lead judges its Annotated capture on the HUD labels (ADR 0036 decision 4). No work planned.
- No automation method reads a captured image's pixel colours (ADR 0036, friction F05): a look check of exact colours (ADR 0036 decision 4's palette check L2) samples the kept PNG with a colour picker or a script outside the editor. Not fixed in phase 3: `ScreenshotMethods` and `ViewportMethods` belong to M26 in phase 3's ledger. No work planned.
- `editor.screenshot` captures the editor window as it is and cannot bring a dock's tab forward (ADR 0036, friction F07): with the Scene and Game views docked as tabs, a capture shows the Game view only when its tab is already in front, so a game-view capture is taken with `viewport.screenshot {view: "Game"}`. Not fixed in phase 3: `ScreenshotMethods` belongs to M26 in phase 3's ledger. No work planned.
- The editor's Scene view runs the 3D post chain (DepthPyramid, GTAO, Bloom, Tonemap, FXAA) for a scene of sprites alone (ADR 0036, friction F06): a pass with nothing to draw still runs, because the Scene view is never in the 2D colour path (only a PixelPerfectCamera's game view is). Skipping the passes a 2D-only scene leaves empty is a renderer change no milestone of the program schedules; the soak renders each scene's game view (ADR 0036 decision 7). No work planned.
- `docs.get` needs a connected editor (ADR 0036, friction F09): the MCP bridge serves the skills through the editor's `docs.get`, so a session launches the editor before reading them, which costs nothing in the transcript. No work planned.
- The soak's memory rule measures an editor subject's C runtime heap, not its private memory (ADR 0036, "Landing", "The soak": A-prime, the lead's refinement of the product owner's option A, 2026-11-13): the soak no longer fails on growth inside a graphics driver's own heaps or any other memory outside the process heap (an arena of its own, a private heap, memory mapped directly), and the heap's growth in bytes is bounded by 1 % of the subject's baseline private bytes, the private rule's absolute bound, not by 1 % of the heap. The private bytes' warnings still show such growth: a private growth of 1 % or more prints a `WARNING` line naming the subject and its windows and counts in the step's summary. The Runtime subject keeps the private memory rule, and on Linux and macOS, where the heap has no measure, every subject does. No work planned.
- `test.run` does not report how many expectations a case evaluated (ADR 0036, friction F15 of M25's builder session S4): its case rows and its JSON report give each case's outcome, but a passing case says nothing of the `Test.Expect` calls it made, so a builder that adds checks to a case cannot see from the run that they ran (S4 proved its new checks with `script_eval` at the end of a replay instead; nothing in the game works around it). A per-case count of the expectations evaluated and passed in `test.run`'s rows and report is not fixed in M25, by the lead's decision. No work planned.
- A visual-scripting graph (M24) is one self-contained behaviour: it requires no module, and no Luau script requires it (the require resolver reads `.luau` modules), so a script reaches a graph's instance by its behaviour name (`Entity:GetScript("Door")`) and types it as `any` (`Docs/Decisions/0035-m24-contract.md` decisions 2 and 23). No work planned.
- The graph node library (M24) models one function signature a member: a generic, overloaded or function-typed script API member (`Script.Define`, `Task.Spawn`, `Task.Delay`) has no node, so a graph delays its flow with `Flow.Delay` and leaves the rest to Luau; a member that gains a node later needs nothing but its binding, since the library grows from the script API (`Docs/Decisions/0035-m24-contract.md` decisions 6 and 23). No work planned.
- A visual-scripting graph's UI event (M24) never consumes the event: an event node's function returns nothing, so a graph's `OnUiClick` and the other `OnUi*` callbacks always let the event bubble on to the parent's behaviours, as a Luau callback that returns nil does, and a behaviour that must stop the bubbling is written in Luau (`Docs/Decisions/0035-m24-contract.md` decisions 6 and 23). No work planned: consuming needs a result from a flow, which several event nodes of one callback and `Flow.Delay`'s later flows cannot give one meaning; a `Consume` input on the event node would be the design.
- A visual-scripting graph's transpiled text (M24) is bounded: a statement's code starts at most 64 blocks deep, since Luau's parser recurses once per block, and the text holds at most 8 MiB, since every statement evaluates again the values it reads; a graph past either limit is `GRAPH_INVALID` at the statement that passes it, and every graph edit that would pass one is refused (flatten a deep flow with a `Flow.Sequence` or a merge, and let fewer statements read long chains of values). A graph within both whose text exceeds another of Luau's limits (a function's 200 locals, as one statement reading more than about 200 values) validates, is accepted by the edits and fails its import with `SCRIPT_COMPILE_ERROR` at the line of the node that exceeds it, which `graph.read` maps to that node (`Docs/Decisions/0035-m24-contract.md` decisions 7 and 23 and risk 1, W24.1's integration and review). No work planned: the limits sit far above any graph built by hand (FeatureTest's and the fixture graphs' texts are at most 5 KB).
- Live values of a visual-scripting graph (M24) are read by an entity and a behaviour name: `graph.liveValues` reads the first of the entity's graph slots whose graph has that name, so of two graph slots of one behaviour name only the first can be read live; the inspector says so on the second ("Shown in slot N"), and the Graph Editor, when the slot read holds another graph than the one it shows, shows none of its values and names that graph (`Docs/Decisions/0035-m24-contract.md` decision 14, W24.2's integration and review). Its errors are mapped to nodes through the graph's current text, so after an edit during a lockstep, recording, replay or test session, which runs the old code until it ends (§7.5 race rule 4), an error names the node its line has in the edited text. No work planned: a `slot` (or `graph`) param on `graph.liveValues` would lift the first, and mapping through the line map of the text the session's script was compiled from the second.
- The editor's platform windows (M24, Windows only) are drawn on the frames the main window renders while it is not minimized, so while it is minimized (a UI frame forced for `editor.screenshot` included, which renders the main window's UI alone) they keep their last image; `editor.screenshot` captures the main window's UI alone, leaving out a panel undocked into a platform window; and the `PlatformWindows` preference takes effect at the next editor start (`Docs/Decisions/0035-m24-contract.md` decisions 18, 20 and 23). No work planned.
- A Game view undocked into its own platform window (M24, Windows only) gets no game input: the engine `Window`'s callbacks see only the main GLFW window (`imgui_impl_glfw` chains user callbacks for the main window only, and `Platform/Window.cpp` owns them), so no native key, mouse or gamepad event reaches the play session while that OS window has the focus or the cursor; the Game view docked in the main window gets its input with platform windows on. Play with the Game view docked (`Docs/Decisions/0035-m24-contract.md` decision 23, W24.1's integration). No work planned.
- Particles have no gameplay collision (M26, ADR 0037 decision 5; plan §6 "M26"): they are a presentation-only CPU simulation that never reads or writes the physics world or the state hash; a game that needs colliding debris uses bodies.
- Particles are not simulated in edit scenes (M26, ADR 0037 decision 5): an edit scene's views draw no particles, so its captures stay deterministic; play or simulate the scene (lockstep for a capture) to see them.
- An emitter's alpha-blended particles sort back to front within the emitter only (M26, ADR 0037 decision 7): emitters draw in canonical entity order, so two overlapping emitters' particles do not interleave by depth; additive emitters need no order.
- Terrains have no holes and no run-time edits (M26, ADR 0037 decisions 20 and 23; plan §6 "M26"): a heightfield is a full square, and only the editor's terrain tools and `terrain.edit` change it, in edit scenes.
- A terrain receives shadows but casts none (M26, ADR 0037 decision 22): its chunks are not drawn into the shadow cascades, the spot atlas or the point faces, so a ridge does not shadow the valley behind it.
- Probes are baked, never dynamic (M26, ADR 0037 decision 8; dynamic GI is won't-do, ADR 0028 decision 2): a moved light, object or probe keeps its last bake until `lighting.bake` runs again, and a bake is one bounce (its captures render without the probes).
- Particles write no velocity (M26, ADR 0037 decision 17): they draw after the prepass, into SceneColor only, so under TAA a moving particle's history is reprojected by the surface behind it and ghosts slightly; FXAA, the default, is unaffected.
- A terrain's velocity is the camera's motion alone (M26, ADR 0037 decision 22): `TerrainItem` has no previous world, so a terrain that moves (under a moving parent, or moved by a script) ghosts under TAA; terrains are expected to stay still.
- A view's temporal state restarts after a device loss (M26, ADR 0037 decision 29): TAA's history and the adapted exposure are dropped with the renderer's state, so the first frames after a recovery may differ from an uninterrupted run (a reset: no history, the exposure converging at once); a capture, which resets anyway, gives the same image.
- A particle's colour and size over its life change at the tick rate (M26, ADR 0037 decision 7, W26.1's integration record): render extraction evaluates the curves at the particle's age as of its last step (it does not know the session's FixedDelta), while its position interpolates by the extraction's alpha, so at a frame rate above the tick rate a fading particle's colour steps once a tick.
- A terrain body's bounds reach one cell past its far edges (M26, ADR 0037 decision 21, W26.1's integration record): Jolt pads an odd sample count up to its block size of 2 with samples that collide with nothing, so `physics.bodyInfo`, `Physics.GetBodyBounds` and `GetColliderBounds`, `PhysicsShape::GetLocalBounds` and the `PHYSICS_ADJACENT_STATIC_BODIES` check see the field one cell longer along its far X and Z edges; raycasts, overlaps and contacts never see the padding (`PhysicsShape.h`, §9.2).
- A view's reflection probes share one cube array (M26, ADR 0037 decision 16, W26.1's integration record): the per-view copy holds every shaded probe's prefiltered cube in one array, so a reflection probe whose Environment's cube differs in format or size from the view's first probe's is dropped from the view, with one warning per renderer; in practice only probes whose Environments were imported with different `Compression` settings on a device with BC support differ, so import every probe's Environment alike.
- Only 3D colour-grading LUTs import (M26, ADR 0037 decision 15, W26.1's integration record): a `.cube` file with `LUT_1D_SIZE` (a 1D table or a shaper) is refused as Unsupported; 3D tables with `DOMAIN_MIN` and `DOMAIN_MAX` or DaVinci Resolve's `LUT_3D_INPUT_RANGE` import.
- SSR traces one mirror ray per pixel, with no roughness cone or blur (M26, ADR 0037 decision 18, W26.2's integration record): a glossy surface's traced reflection is as sharp as a mirror's, and its confidence fades over the upper half of [0, `SsrMaxRoughness`], so surfaces rougher than half `SsrMaxRoughness` fade to the probes' prefiltered reflection instead of a blurred trace. Lifted by a roughness-aware resolve (several rays per pixel, or a blurred mip chain of the traced image sampled by roughness), deterministic like the trace.
- SSR is screen-space only (M26, ADR 0037 decision 18, W26.2's integration record): what is off screen, behind a surface thicker than `SsrThickness` or seen from its back cannot be traced, so the probes' or the environment's reflection stays there (the probe fallback). Lifted only by reflections that see beyond the screen (ray-traced reflections, won't do: ADR 0028 decision 2; or reflection probes placed where it matters).
- Transparent surfaces are neither traced nor reflected by SSR (M26, ADR 0037 decision 18, W26.2's integration record): SSR runs after the skybox and before ForwardTransparent, over the opaque image and depth, so a Blend surface keeps its probe or environment reflection and does not appear in an opaque surface's traced reflection. Lifted by a second trace after the transparent passes, with the transparent surfaces' own depth and roughness.
- Terrains are not drawn by the Overdraw data view, have no wireframe edges and no selection outline (M26, ADR 0037 decision 22, W26.2's integration record): those views draw the mesh items' pipelines only, while a terrain's depth still occludes what is behind them and its pick id still selects it. Lifted by terrain variants of the overdraw, wireframe and selection-mask pipelines (each a startup pipeline, or created on first use like the material debug views).
- FeatureTest's committed probe bakes reproduce byte for byte only on the device class and driver that baked them (M26, ADR 0037 decisions 8 and 25, the milestone review): `Scaffold/Probes.jsonl` and `GoldenProbes.jsonl` run `lighting.bake` in a rendering editor and commit its output, the `.irradiance` and `.hdr` files below `Assets/Lighting/`, which are SceneColor read back from GPU renders, and `Scaffold.py --check` (the automation suite's `test_scaffolds_reproduce_the_project_byte_for_byte`) compares them byte for byte, a stricter rule than the goldens' thresholds; an environment bake stays in the machine's `Library/` cache instead. So a driver or device change, which renames the goldens' device class, also needs a reviewed re-bake: `Tests/Golden/README.md`'s rename procedure runs `Scaffold.py` and reviews the re-baked `Assets/Lighting/` files with the probe goldens as one regeneration before its golden run. Kept: the goldens' device class is held (ADR 0028 decision 9), and a comparison within a tolerance would let a real change of the bake through.
- `prefab.apply` refuses to add an entity added below the instance that another entity references (M27 friction F04, `Docs/Decisions/0038-m27-rolling-ball.md`; §5.5): the added entity becomes a member with a derived ID, so that reference would name no entity, and the apply fails with `InvalidState` naming both. Exempt are the added entities themselves and, when the prefab written is the outermost instance's, that instance's members, whose references are written with the prefab and recorded in its space; at a nested level a member's reference is refused too, since the outermost root's record keeps it in the outermost prefab's space. The way out is to set the reference after the apply, to the member the result's `addedEntities` names. No work planned: retargeting those references would make the apply rewrite entities outside the instance and records of the outermost root.
- A dry run of `edit.batch` hands back no token for its real run (M27, ADR 0038 friction F11): the real run sends the whole batch again (a level's 60-odd ops in Rolling Ball), since a token that applied a validated dry run would hold state across calls, which edits between the two could race, while sending the payload again costs only its size. No work planned.
- No test switches to Exclusive display mode (M28, `Docs/Decisions/0043-m28-game-services.md` decision 3 and Risks): it changes the desktop's video mode, a system setting of the one shared test machine, so the windowed child covers only VSync, Windowed and Borderless, and the mode-list check and the refusal of a mode the monitor does not list; Exclusive mode and a restored choice at the next launch are checked by the World Tree session's Dist export (brief 04). No work planned.
- A restored Borderless or Exclusive display mode opens on the primary monitor (M28, `Docs/Decisions/0043-m28-game-services.md` decision 3; the W28.1 review's follow-ups): `user://Display.json` keeps the mode, size, refresh rate and VSync but not the monitor, so a game a player ran borderless or full screen on a second monitor opens on the primary one at the next launch (`Window::Create`). Lifted by keeping the monitor in the file and creating the window on it when it is still connected. No work planned.
- Display settings do nothing outside a live Runtime session (M28, ADR 0043 decision 3): the editor's game view, headless runs and every fixed-view session (test runs, replays, recordings, lockstep) keep the project's window, so an options menu shows no modes there and its request is refused with the reason; the effect is seen only in a live, windowed Runtime run (an export). No work planned.
- A game's save data is one store of at most 1 MiB of JSON (M28, `Docs/Decisions/0043-m28-game-services.md` decision 8): no slots, binary blobs or cloud saves; a game keeps several slots as keys of the one store. Its numbers are doubles, which a replay's header keeps exactly. No work planned.

## 7. Non-goals for v1

Out of scope by design (§1.2), each open to an ADR. ADR 0028 schedules some, records others as won't do (§8), and leaves the rest out of scope:

- **Graphics:** backends other than NVRHI-Vulkan, ray tracing, bindless and GPU-driven rendering, render-graph aliasing (won't do, §8); clustered light culling and point-light shadows (built by M23, W23.1); TAA, histogram auto-exposure, colour-grading LUTs and SSR (built by M26: auto-exposure and LUTs in W26.1, TAA and SSR in W26.2); GI beyond IBL plus AO (baked irradiance and reflection probes built by M26, W26.1; dynamic GI won't do, §8).
- **Assets:** GPU texture compression (imported textures as BC7 and BC5 since M23, W23.1; environment cubes as BC6H since its W23.2), EXR import (built by M23, W23.2), Ogg Opus import and mesh instancing (built by M23, W23.1).
- **Features:** skeletal and morph animation (built by M23, W23.3, with script-driven blending; an animation state-machine graph stays a non-goal, §1.2), particles and terrain (built by M26: particles and terrain import, physics and queries in W26.1, terrain rendering and its sculpt and paint tools in W26.2); visual scripting (built by M24: graphs, their transpiler to Luau and their edit methods by W24.1, `Docs/Decisions/0035-m24-contract.md` decisions 2 to 13; the Graph Editor canvas, live values in play (`graph.liveValues`) and the graphs skill page by W24.2, decisions 14 and 15) and native gameplay modules (built by M19 on Windows, W19.1 to W19.3, ADR 0030 decisions 25 to 35; on Linux and macOS dropped by the owner, §4); networking (out of scope, stays here: "Networking can stay in the backlog for now").
- **Editor and scenes:** native file dialogs (on Windows since M18, W18.1: nativefiledialog-extended's `IFileDialog` backend behind the FileDialog API, ADR 0029 decisions 19 to 21; their Linux and macOS backends dropped by the owner, §4, so the ImGui picker serves there), ImGui multi-viewport OS windows (built by M24 on Windows, W24.1: platform windows on their own swapchains, registered with M18's recreation protocol, `Docs/Decisions/0035-m24-contract.md` decisions 17 to 21; on Linux and macOS dropped by the owner, §4), a UI framework beyond `TextComponent` (the static UI since M22's W22.1, ADR 0033 decisions 2 to 9, and its interaction since W22.2: focus and navigation, events, the four widgets, the theme, minimal authoring and the interaction state in the hash, decisions 21 to 36; and since W22.3 the text input, fallback fonts, shaping and bidirectional text, and world-space canvases, decisions 42 to 53).
- **Platforms:** mobile and web, native Wayland, cross-OS export, bit-exact cross-OS or cross-compiler determinism (out of scope, stay here: "We are not doing this right now"); consoles, identity code signing and notarization (won't do, §8).
