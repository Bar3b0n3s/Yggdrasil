## 4. Linux and macOS catch-up

The product owner chose "Drop the catch-up" (ADR 0028 decision 10, superseding ADR 0026 decision 1's deferral of 2026-10-14 and the first version of ADR 0028, which scheduled it as M21). Windows is the only verified platform. First-party code stays portable by rule (the `Platform/` layering, no Windows-only shortcuts, the local portability stage's premake generation and clang-cl builds), but Linux and macOS are never verified: the Linux/macOS catch-up was dropped by the product owner, because there is no Linux or macOS machine without GitHub. GitHub is only an off-site backup of the repository: GitHub Actions is not part of the process, and nothing reads or waits for its results.

- The GitHub Actions failures of the M15 milestone commit, and whatever the runs of later pushes report (ADR 0026 decision 1): dropped by the owner (ADR 0028): there is no Linux or macOS machine without GitHub.
- A macOS run of an exported bundle: its signature and loader lookup (ADR 0026 decision 1): dropped by the owner (ADR 0028): there is no Linux or macOS machine without GitHub.
- **ADR 0025 finding M29:** port the Runtime's automation connection to POSIX, so that "RuntimeApp: F1 toggles the stats overlay in a windowed run and the game still receives F1" runs on Linux and macOS (ADR 0025 decision 15): dropped by the owner (ADR 0028): there is no Linux or macOS machine without GitHub.
- **ADR 0025 finding M30:** verify the map check against a real GCC LTO Dist map, and read the executable's ELF symbols beside the map if GNU ld's map misses the symbols the linker plugin internalized (ADR 0025 decision 15; ADR 0024 decision 11): dropped by the owner (ADR 0028): there is no Linux or macOS machine without GitHub.
- GCC 14, Clang 19 with libstdc++ and Apple Clang build only in GitHub Actions, and their failures were to be fixed here (ADR 0013 decision 25's third limit): dropped by the owner (ADR 0028): there is no Linux or macOS machine without GitHub.

The designs for these (the bundle probe, the M29 port and the M30 ELF reader) stay in the gitignored `bin/Reviews/M16-Map.json` of the development machine (ADR 0026 decision 1).

The owner's answer to the plan's open points, "Windows backends only" (ADR 0028 decision 10), also drops the kept items' Linux and macOS backends. Windows backends only: a kept item's platform interface stays, so a later port can add backends, but no Linux or macOS backend is written, and on Linux and macOS the interface reports the capability as unavailable (`ErrorCode::Unsupported`) through the platform layer's existing error path. The rule covers the platform capabilities the program adds in first-party C++: existing POSIX backends (`Platform/Posix/`) keep compiling when their interface changes, and the Python tooling keeps its guarded POSIX branches. Vendored libraries' premake scripts stay portable (the portability stage generates gmake and xcode4 projects from them); their GCC, Clang and Apple Clang builds are never compiled.

- Native file dialogs on Linux: nativefiledialog-extended's xdg-desktop-portal backend, with `libdbus-1-dev` in `Setup.py`'s Linux package check: dropped by the owner (ADR 0028): "Windows backends only", since nothing here can compile or test a Linux or macOS backend. On Linux the FileDialog API falls back to the ImGui picker.
- Native file dialogs on macOS (the macOS backend of M18's dialogs): dropped by the owner (ADR 0028): "Windows backends only", since nothing here can compile or test a Linux or macOS backend. On macOS the FileDialog API falls back to the ImGui picker.
- ImGui multi-viewport OS windows on Linux (X11) and macOS (M24's platform windows outside Windows): dropped by the owner (ADR 0028): "Windows backends only", since nothing here can compile or test a Linux or macOS backend. There the editor keeps every panel docked in its main window.
- The per-game native module on Linux and macOS (M19's module outside Windows: a dlopen backend for the editor's load and hot reload, and the make, GCC, Clang or Xcode native build that building and exporting a game with `Native/` would need): dropped by the owner (ADR 0028): "Windows backends only", since nothing here can compile or test a Linux or macOS backend. There `native.*` build and load, and exporting a game that has `Native/`, return `ErrorCode::Unsupported`; a game without `Native/` is unaffected.

## 6. Accepted limits

Limits accepted for v1. A limit that names a milestone is scheduled by ADR 0028 and leaves this list when that milestone lands; the others have no work planned, and reopening one needs an ADR. Each milestone's ADR adds the kept limits it accepts.

- No render thread; two frames in flight (§4.11). Won't do (§8).
- Device loss, GPU out-of-memory and GPU hangs are fatal: autosave in the editor, a crash report and exit code 4, with no recovery (§8.14). M18 (W18.3, W18.4; ADR 0028 decision 5): device loss and driver-reset hangs are recovered, and GPU out-of-memory after startup is recovered by a trim and retry or fails only its request; a hang with no loss report, out-of-memory at startup and a failed recovery stay fatal, recorded here by M18's ADR.
- A material that leaves the view and returns gets a new binding set (ADR 0013 decision 25; ADR 0025 decision 18). M18 (W18.1).
- Golden images exist for the `nvidia-61x` device class only; every other device class runs them in smoke mode (§15.4; ADR 0013 decision 25). Kept: goldens for other classes won't do (§8). Goldens stay on the nvidia-61x device class only, and the NVIDIA driver's major version is held for the whole program; M18 (W18.2) reports a renamed class (ADR 0028 decision 9).
- `Invariant` on the clip position is not decorated, because Slang 2026.8 cannot; the prepass and forward pipelines agree through `NoContraction` products. The program stays on Vulkan SDK 1.4.350.0 and slangc 2026.8 (`Scripts/Lib/Toolchain.json` unchanged); it is revisited only if an in-scope item needs a newer toolchain, as an approval request at a phase boundary (ADR 0013 decision 25; ADR 0025 decision 18; ADR 0028 decision 3).
- The machine-wide build, GPU and gate locks cover the scripts and the MCP bridge's launches, not processes started by hand: a Tests or Editor binary run directly takes no lock (the build-and-test skill routes GPU test cases through `Test.py --filter`), and an editor that the bridge leaves running with unsaved changes when its MCP client goes away renders without the GPU lock, whose hold ends with the bridge (Architecture §2.3; ADR 0028 decision 16). No work planned.
- The shared vendor-library cache never evicts an entry: every Visual Studio, MSVC or Windows SDK update, change of the per-user property sheet and vendored-library change adds a full set (about 1.5 GB for the Debug, Release, Dist, clang-cl and ASan entries of today's ten libraries), and the old sets stay. The space is reclaimed by hand, removing `<git common directory>/vendor-cache` (or old entries) at a phase end, which is safe only while no build runs in any worktree (`Scripts/Locks.py` lists no build holder; the next builds compile and publish what they need); doing it while builds run makes their links fail (Architecture §2.2; ADR 0028 decision 16). No work planned: an automatic prune would need each entry's last use recorded and the cache's lock against running links.
- A replay's start fingerprint (replay format 3, M19) names only what it records: every entity and serialized component of the starting scene and the assets those components reference directly, so a changed asset that only another asset references (a module that only a script requires, a material's texture) is not named, nor is a change of a game's native module (its code and its resources' starting values are not fingerprinted; its build's `SourceHash` could be, in a later replay format), and a replay migrated from format 1 or 2 carries no fingerprint until it is recorded again; such a failure lists the possible causes, the native module among them, as before (ADR 0030 decision 2; the native module, M19's milestone review). No work planned.
- Kept screenshots (`keep: true`, M19) are never pruned: `Library/Automation/Kept/` grows with every kept file until the user removes files, the one automation output that Architecture §13.4's bounded-output rule does not bound (ADR 0030 decision 9). No work planned: a keep is the builder's explicit choice per screenshot, and `Library/` is local and gitignored.
- The MCP bridge's `editor_status` without a connection (M19) asks each editor running with automation for its renderer over a connection of its own, since a session file (§13.2) holds no renderer: the probe is not transcribed and waits up to 5 s for the connection and 5 s for `session.info`, so an editor that does not answer adds about 10 s and is listed with a null renderer and a `probeError` (Architecture §13.8; ADR 0030 W19.3, the native test game's friction NT-04). No work planned: writing the renderer into the session file would remove the probe, an engine change.
- An export cannot follow an `Assets.Load` whose reference a script computes: with `Export.PruneUnreferenced` (M19) on, an asset that only such a load names is left out of `Game.pak`, and `project.validate` names each such load (`SCRIPT_COMPUTED_ASSET_LOAD`, a warning); without the setting nothing is pruned, and `Engine.pak` keeps every built-in whenever a packaged script computes a reference (ADR 0030 decisions 19 to 21). No work planned: a computed path is known only when the game runs.
- A Luau value converts to JSON (`script.eval`'s value, a Variant field, a binding's JSON argument such as `Scene.Load`'s parameters) only as nil, booleans, finite numbers, strings and tables of them: a vector, `Quat` or other engine value is refused with `ErrorCode::Script`, naming its Luau type and its place in the value (M19: the native test game's friction NT-08, ADR 0030), so a script returns `{v.x, v.y, v.z}`. No work planned: converting vectors and quaternions to arrays would change every Luau entry point that converts to JSON, a script-API change.
- A pak entry larger than 1 GiB is stored uncompressed: the vendored stb's deflate and inflate take `int` lengths, and its deflate grows its output buffer with `int` arithmetic that overflows once its output passes about 1.5 GiB, which incompressible input above about 1.4 GiB reaches (pak version 2, M19; ADR 0030 decision 17). No work planned.
- A game's native module (M19) holds plain data only: its types are trivially copyable structs whose reflected fields are bools, 32-bit integers, floats, glm vectors and quaternions, linear colours, entities and enums, with no string, array, asset reference or nested struct, and a type migrates by field name and `RenamedFrom` only, with no version or migration function (ADR 0030 decisions 26 and 27). No work planned.
- Native components live as JSON in their entity's preserved components, outside the frozen type registry: their data round-trips through its canonical JSON once per NativeStep that touches it; they have no script proxy, inspector drawer or `component.schema` (`native.status` gives their schemas, `native.setComponents` edits them, which automation's other component writes refuse with a hint naming it, `native.getComponents`, `scene.tree`, `entity.get` and `scene.query` read them, and the Native panel shows the selected entity's read-only); `project.validate` does not check them (their findings are load diagnostics); an Entity value inside a prefab is not remapped when the prefab is instantiated; and no prefab override records a native component, so `native.setComponents` refuses a member of a prefab instance in the edit scene (a rebuild from the prefab would restore the prefab's), and a prefab file's native components are canonicalized only when `prefab.create` writes it again with the module loaded (ADR 0030 decisions 26 to 29). No work planned.
- Scripts and test suites cannot read a game's native components or resources (M19): a native component has no script proxy and a resource no Luau view, so `Entity:HasComponent("Native.<Name>")` raises `NotFound` with a hint that names `native.getComponents`, a suite tests a module through the built-in state its systems write (its Transforms), and only automation reads the module's own state (its components through `native.getComponents`, `scene.tree`, `entity.get` and `scene.query`, its resources through `native.status`'s `playResources`) (ADR 0030 decision 26; the native test game's friction NT-05). No work planned: a read-only Luau view, such as `Entity:GetNativeComponent` and `Test.GetNativeResource` returning a value's canonical JSON as a table, would lift it as a script-API change (the add-script-api skill, `Engine.d.luau`, FeatureTest's gate 4).
- A native system (M19) reaches built-in state only through its step context, `INativeStepContext` of `NativeApiVersion` 1: Transforms, the active flag, name, parent, `FindEntity`, `CreateEntity` and `DestroyEntity`, besides its module's own components and resources; never a `Text`, `MeshRenderer`, material, light or sound, so native code cannot show a counter on a HUD or recolour an entity (ADR 0030 decisions 26 and 28; the native test game's friction NT-06). No work planned: generic access to built-in components would be a later `NativeApiVersion`.
- Every export of a game with a native module (M19) builds its Runtime anew, about 20 s, even when its sources are unchanged, and the games suite's Dist half pays it twice (its testing and its plain export): step 3a builds into a new numbered directory below the output directory's `.export-native-<pid>-<tag>` sibling and removes it once the package is in place (ADR 0030 decision 33; the native test game's friction NT-12). No work planned: a cache of Runtime builds below `Library/Native/`, keyed by the source hash (which covers the configuration and `NativeApi.h`) and the engine's build id, would remove the cost.
- A native source that is not clang-format clean is fixed by hand (M19): `native.build` reports it as a `NATIVE_FORMAT_WARNING` that quotes the line clang-format writes there, and the builder rewrites the source with `native.write` and builds again, since no method formats a source (ADR 0030 decision 35; the native test game's friction NT-02). No work planned: a `native.format {path, dryRun}` method writing clang-format's output through `native.write`'s provenance path would fix a source in one call.
- Native code runs inside the editor's and the Runtime's process: an exception that escapes a system stops its play session, but a crash ends the process, the risk the user's "Allow native code" preference accepts; systems read the project's input actions, never devices (ADR 0030 decisions 28 and 29). No work planned.
- Loading a game's native module (M19) with a layout other than the loaded one's (every first load, one after an unload included) clears the open scene's undo history, even when its migration changed nothing: the history's entity snapshots hold the previous layout's values or, recorded without a module, the values as written, which undo would restore whole, so the edits made before a module's first load can no longer be undone; `native.load` reports it (`undoCleared`) (ADR 0030 decision 31). No work planned.
- Cancelling a native build (`native.build`'s disconnect or cancel, an export's cancelled NativeBuild step) kills `Scripts/BuildNative.py`, but the MSBuild it started runs to its end, writing only into that build's own output directory (`Library/Native/Builds/<sequence>/` or the export's numbered one), whose record is never read and which no later build reuses: the next export skips a leftover it cannot remove yet, and removes it once it can, or a later editor does once this one has exited; a Windows job object would also end an `mspdbsrv` shared with builds in other worktrees (ADR 0030 decision 30). No work planned.
- The native module builds, loads and exports on Windows only, and the export of a game with `Native/` builds its Runtime, so the exporting machine needs the Windows toolchain; on Linux and macOS its build, load and export are `Unsupported` (ADR 0030 decisions 30, 33 and 34; §4). No work planned.
- A collider event reaches one piece where Jolt's manifold reduction merges a body pair's contacts: a body resting flat across two coplanar pieces gathered into one body, or a ball on the seam between two bricks, gives only the piece of the first sub-shape pair its own `OnCollisionEnter` and `OnCollisionExit`; pieces whose contacts face different ways each get theirs, and a piece with its own `Static` body gets one event per piece at a seam (§9.4; ADR 0031 decision 2). No work planned: a piece that needs its own event at a seam keeps its own `Static` body.
- A prefab override of one script slot follows the slot's index in the prefab entity's Script list: a prefab edit that reorders slots, or inserts one before an overridden slot, moves the override to whichever slot then has that index, while appending slots (the inspector's Add script) keeps every index; an override whose slot the prefab no longer has is dropped as stale (`PREFAB_STALE_OVERRIDE`) (§5.5; ADR 0031 decision 19). No work planned.
- A change of an entity's script slots (the inspector's Add script, Up, Down and Remove, or a whole-list `entity.update`) rewrites the whole Script list, which checks every value it writes, so it is refused, changing nothing, while any slot of the entity holds a field value its script rejects (an unknown field name or a wrong type), the error naming that value. A wrong-typed value can be corrected in the inspector first; an unknown field name cannot be removed there, as before M20, but an automation client can remove it by writing the list without it (ADR 0031 "Integration (W20.2)"). No work planned.

## 7. Non-goals for v1

Out of scope by design (§1.2), each open to an ADR. ADR 0028 schedules some, records others as won't do (§8), and leaves the rest out of scope:

- **Graphics:** backends other than NVRHI-Vulkan, ray tracing, bindless and GPU-driven rendering, render-graph aliasing (won't do, §8); clustered light culling and point-light shadows (M23, W23.1); TAA, histogram auto-exposure, colour-grading LUTs and SSR (M26: W26.1 and W26.2); GI beyond IBL plus AO (baked irradiance and reflection probes in M26, W26.1; dynamic GI won't do, §8).
- **Assets:** GPU texture compression, EXR import, Ogg Opus import (M23, W23.1 and W23.2) and mesh instancing (M23, W23.1).
- **Features:** skeletal and morph animation (M23, W23.3), particles and terrain (M26: W26.1, W26.2); visual scripting (M24: W24.1 and W24.2) and native gameplay modules (built by M19 on Windows, W19.1 to W19.3, ADR 0030 decisions 25 to 35; on Linux and macOS dropped by the owner, §4); networking (out of scope, stays here: "Networking can stay in the backlog for now").
- **Editor and scenes:** native file dialogs (M18, W18.1, on Windows; their Linux and macOS backends dropped by the owner, §4), ImGui multi-viewport OS windows (M24, W24.1, on Windows; on Linux and macOS dropped by the owner, §4), a UI framework beyond `TextComponent` (M22, W22.1 and W22.2).
- **Platforms:** mobile and web, native Wayland, cross-OS export, bit-exact cross-OS or cross-compiler determinism (out of scope, stay here: "We are not doing this right now"); consoles, identity code signing and notarization (won't do, §8).

## 8. Won't do

Items the product owner decided not to build (ADR 0028, 2026-10-19). Reopening one needs a new decision by the product owner.
