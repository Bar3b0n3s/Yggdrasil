## 1. Planned milestones

Milestones run in phases: the milestones of a phase are developed in parallel, each on its own branch in its own worktree, and their milestone-end `CI.py` runs go one at a time on the one GPU. ## 4. Linux and macOS catch-up

The product owner chose "Drop the catch-up" (ADR 0028 decision 10, superseding ADR 0026 decision 1's deferral of 2026-10-14 and the first version of ADR 0028, which scheduled it as M21). Windows is the only verified platform. First-party code stays portable by rule (the `Platform/` layering, no Windows-only shortcuts, the local portability stage's premake generation and clang-cl builds), but Linux and macOS are never verified: the Linux/macOS catch-up was dropped by the product owner, because there is no Linux or macOS machine without GitHub. GitHub is only an off-site backup of the repository: GitHub Actions is not part of the process, and nothing reads or waits for its results.

## 6. Accepted limits

Limits accepted for v1. A limit that names a milestone is scheduled by ADR 0028 and leaves this list when that milestone lands; the others have no work planned, and reopening one needs an ADR. Each milestone's ADR adds the kept limits it accepts.

- No render thread; two frames in flight (§4.11). Won't do (§8).
- The GPU failures that M18 does not recover stay fatal: autosave in the editor, a crash report and exit code 4 (§8.14 item 6). M18 (ADR 0028 decision 5; ADR 0029 decisions 25 and 40 to 46) recovers a device loss in process at the frame boundary, a hang that the driver or the operating system resets during the bounded wait's reset wait (like a loss), and GPU out-of-memory after startup (trimmed and retried once, then only the request fails with `OutOfMemory`). What stays fatal, each with its reason: a hang with no loss report after the 10 s budget and the reset wait (`--gpu-reset-wait`, 15 s by default: Vulkan cannot cancel submitted work, a device with pending work cannot be destroyed, and a second device on the same GPU would queue behind it; `project.open {recover}` restores the editor's autosave); out-of-memory at startup (nothing has rendered) and in a recovery's recreation (a second startup); out-of-memory in the swapchain's acquire and present and in the application frame's UI draw (no request there can fail alone); a Vulkan out-of-memory error that vulkan.hpp throws out of NVRHI's internals on a healthy device, at the frame boundary or in an automation method (the throw unwinds the frame or the method in the middle of a recording, with no request boundary to trim and retry at; Architecture §4.6 item 2); a loss before the first frame, a recovery whose device creation fails again after its one retry, a second loss during the recovery, an owner whose recreation fails on the recreated device, and a GPU object still alive after every owner released. No work planned. A swapchain recreation that runs out of memory again after its trim leaves the window black until its size changes or it is minimized and restored, since Vulkan retires the old swapchain: a window whose size never changes (a fullscreen game whose alt-tab does not minimize it, a fixed-size window) stays black for the rest of the run while the game goes on (ADR 0029 decision 44). No work planned: a retry without a size change would have no presented frame to pace it.
- The shader reload (`shaders.reload`, the editor's Tools > Reload shaders, M18) reloads the scene renderer's pass list only: ImGui's per-format pipelines and the Runtime's blit keep the shaders the library cached for them before the reload, also for a pipeline created after it, so a change to them needs a restart; exported games never reload shaders (ADR 0029 decision 3). No work planned.
- A hand-edited `.spritesheet` whose frame extends past its texture (or a texture reimported smaller than its frames) is accepted by the importer, and the frame samples clamped edge texels: `asset.create` and `asset.setProperties` refuse such a frame, where the texture's size is at hand (ADR 0029 decision 14 and risk 6), and M21 decided it by reporting it: `project.validate` warns `SPRITE_FRAME_OUTSIDE_TEXTURE` on the sheet's frame and on each tilemap palette entry that names it, against the imported texture's width and height, while the renderer draws it as before (ADR 0032's milestone review). No work planned.
- Recovery from a really lost device is exercised only by injection: the injected losses and the injected reset hang leave the Vulkan device alive, so `Recover`'s release on a really lost device (NVRHI's in-flight command lists retired without querying the device, `vkDeviceWaitIdle` and the timeline query answering `VK_ERROR_DEVICE_LOST`, a `vk::SystemError` thrown out of the middle of a recording) and a real driver reset (a Windows TDR) have never run here; that code is written not to rely on the device answering, and the injected tests answer the timeline with `VK_ERROR_DEVICE_LOST` through the dispatcher where they can (ADR 0029 risk 8 and decisions 39 and 40). No work planned: no test suite provokes a real TDR.
- Golden images exist for the `nvidia-62x` device class only; every other device class runs them in smoke mode (§15.4; ADR 0013 decision 25). Kept: goldens for other classes won't do (§8). Goldens stay on the nvidia-62x device class only, and the NVIDIA driver's major version is held at 62x for the rest of the program: the goldens were `nvidia-61x`'s until the product owner took driver 621.14 on 2026-11-10 and they were renamed (ADR 0028 decision 9, amended 2026-11-10); since M18 (W18.2) a renamed class is reported: a device class without an image's golden next to a same-vendor class that has it fails the golden run instead of smoke-testing, and `Tests/Golden/README.md` holds the rename procedure (ADR 0029).

The program stays on Vulkan SDK 1.4.350.0 and slangc 2026.8 (`Scripts/Lib/Toolchain.json` unchanged); it is revisited only if an in-scope item needs a newer toolchain, as an approval request at a phase boundary (ADR 0013 decision 25; ADR 0025 decision 18; ADR 0028 decision 3).

- The 2D world's polygons are Jolt convex hulls, whose corners Jolt rounds by its default convex radius (up to 0.05 m) for contacts and overlaps, while rays meet the sharp hull and a BoxCollider2D's corners stay sharp: a box slides off a square PolygonCollider2D's corner earlier than off an equal BoxCollider2D's, almost a pixel at 16 pixels per unit. The frozen `PhysicsShape.h` has no way to set the radius (M21, ADR 0032 decision 8). No work planned.
- The 2D world extrudes each box and polygon along Z by the diagonal of its bounding rectangle, so contact normals stay in the plane; the depth counts against `PhysicsShape::MaxColliderSize`, so a 2D box or polygon whose bounding rectangle's diagonal exceeds 50 km is refused, where the 3D world takes colliders up to 100 km (M21, ADR 0032 decision 8). No work planned.
- 2D picking takes the sprite a pixel shows from the draw order on the CPU, before the GPU mesh pick: sprites write no depth or EntityId, so the editor's click and `viewport.pick` pick a sprite even where a mesh in front of it covers it; texture alpha is not sampled, so a transparent texel inside a sprite's quad still picks the sprite (M21, ADR 0032 decision 14). No work planned.
- In the scene view's 2D mode the grid in the plane z = 0 draws over sprites: it is editor debug draw, which the EditorOverlay stage draws after the output stage at the view's resolution, depth-tested against the scene depth that only meshes write, while sprites draw earlier, into the scene colour, without writing depth. Drawing it beneath them would put an editor overlay into the scene image before the post chain and the pixel-art upscale, which no stage does; the grid's lines are thin and fade with distance, and the view's Grid option hides them (M21, ADR 0032's W21.1 integration). No work planned.
- 2D lights cast no shadows: a Light2D lights every lit sprite and tile within its radius, through every sprite, tile and collider (M21, ADR 0032 decision 20; plan §6 "M21"). No work planned.
- A lit pixel takes the 2D lights with the normal of the topmost lit sprite or tile drawn there: the Lights2D pass accumulates the light at the scene resolution from one normal per pixel, so where lit items overlap, those beneath a normal-mapped one (or a flat one above a normal-mapped one) are lit with the top item's normal, as in other engines' screen-space 2D lighting. A view draws at most 1,024 2D lights, the first in canonical order among those that reach it (a light off the view never counts), and logs the first light it skips (M21, ADR 0032 decision 22). No work planned.
- A view draws at most 524,288 tiles (`SceneRenderer::MaxTileQuadsPerView`, two `QuadBatcher` batches), the first in its 2D draw order (each tilemap's rows from the top down), of the chunks that meet it; the tiles past it are left out with one warning per view, while every sprite still draws, so the renderer's CPU memory stays bounded however far a view of huge tilemaps zooms out; a 1920 x 1080 view that shows that many tiles gives each about 2 x 2 pixels, a zoom only an editor view reaches (M21, ADR 0032's milestone review). No work planned.
- Tilemap v1 has no per-cell flips or rotations: a tile is its palette entry's frame as authored, so a mirrored or turned tile is a palette entry of its own frame (M21, ADR 0032 decision 23). No work planned.
- Lit tiles take the flat normal: neither a TilemapRenderer nor a Tilemap's palette entry has a normal map (Tilemap v1), so a lit tilemap takes each 2D light whole, as a lit sprite without a normal map does; a normal-mapped surface is drawn with sprites (M21, ADR 0032 decisions 21 and 24). No work planned.
- A collider's asset that is missing or not yet registered when the physics system builds its body (a MeshCollider's mesh, whose body takes the placeholder mesh's shape, M11; a TilemapCollider's tilemap, whose body is refused with `PHYSICS_INVALID_SHAPE`, M21) keeps asset version 0 until something loads it: the version check every PreStep makes (`AssetManager::GetVersion`) picks up an asset added later only once a renderer, a script or another body has loaded it, and otherwise the body is rebuilt with it at the next change of a component or of the hierarchy that rebuilds it. An edit, reimport or hot reload of a loaded mesh or tilemap (a `tilemap.paint` included) rebuilds the shape at the next PreStep (ADR 0032 decision 25 and W21.2's integration). No work planned.
- A UI element's rectangle never follows its content (M22, ADR 0033 decision 6): a UiText's or a UiImage's rectangle is its UiRect's, or its UiLayout container's placement of its UiRect Size, so a label is not sized to its text, an image not to its frame, and a container not to its children; text wraps and aligns inside the rectangle it is given and may overflow it. Scene's layout reads no asset, as render extraction reads none (§8.2), so it needs no font metrics. No work planned.
- The locale is fixed for a play session's life (M22, ADR 0033 decision 11): `Loc.Get` reads every string table in the project's `Localization.Locale`, which a script reads with `Loc.GetLocale` and cannot change, so a game's language menu takes effect at the next play session or export. No work planned.
- The glyphs a font's `Ranges` add are not kerned in the Text component (M22): its frozen, unshaped `TextLayout` (ADR 0013 decision 11) kerns only between the glyphs of ASCII and Latin-1, because the TrueType kerning reader (`Utils::ReadTrueTypeKerning`) holds a dense table of every ordered pair of the glyphs it kerns, which 65,536 range glyphs would make about 17 GB (§7.4; ADR 0033 decision 6 and "Integration (W22.1)"). UI text (`UiText`) no longer has this limit: since W22.3 the measurement layer shapes it with HarfBuzz, which kerns every glyph of a FontImporter version 5 font through its GPOS or `kern` table (ADR 0033 decisions 43 and 44, "Integration (W22.3)"). No work planned.
- Input that automation or the capture's release (`input.inject`, `QueueReleaseAll`) queues for a tick ahead of a device event that the frame view already previewed (M22's same-frame preview, live play only) reaches the frame view only as the state the tick leaves, not as its own edges: a tap made only of such injected events is not reported by the frame view, while the step view sees it as before (§4.3; ADR 0033 decision 12 and "Integration (W22.1)"). No work planned: only live play mixes injected and device input in one tick, and lockstep, recording, replay and test sessions never preview.
- The editor's UI authoring is minimal (M22 C22.2, ADR 0033 decision 34): the scene viewport's UI preview draws the elements' outlines, selects the topmost element at a click, moves and resizes the selected element's UiRect with its edge and corner handles, and the UiRect inspector sets anchor presets; there is no snapping, no guide, no multi-element alignment and no rotation or scale of UI elements. No work planned.
- The UI widgets are minimal (M22 C22.2, ADR 0033 decisions 21 to 24): the pointer is the mouse's left button (no touch, no second pointer, no right or middle button for the UI); a press on a widget inside a scroll view goes to that widget, so a scroll view is dragged only by its own background or content area, without inertia, elastic overscroll or scrollbars; held navigation moves focus once per press (no repeat while held; the left stick once per crossing of one half); toggle groups (radio buttons) are not built, a script keeps one toggle of several on from `OnUiValueChanged`; a widget's state tint multiplies only its own element's UiImage, never its texts or its children's images; and there is one theme per canvas: a widget cannot override its canvas's tints (another canvas or a script colour gives another look). No work planned.
- The text input is minimal (M22 C22.3, ADR 0033 decisions 45 to 48): it takes committed characters only (GLFW's character callback, no IME composition display), edits by codepoint rather than grapheme cluster, has no selection, no clipboard and one line (Enter submits), its editing keys act once per press (no repeat while held, as the other UI commands), its caret does not blink, and typing reaches at most 1,024 codepoints (`MaxLength`'s limit, so the longest typed text fits the 4,096 bytes a script's write of a component holds; the review of C22.3). No work planned.
- A gamepad cannot type into a text input (M22, ADR 0033 decision 47, amended by W22.3's review): it focuses, submits and leaves one, but characters come only from a text source (the keyboard's committed characters) and the editing keys are keyboard keys, so typing by gamepad would need an on-screen keyboard, which M22 does not build (a departure from Roadmap M22's "every widget works by keyboard and gamepad" for typing alone). No work planned: a gamepad on-screen keyboard for text input is new scope.
- A time scale of 0 stops the UI (M22, ADR 0033 decision 24's amendment at the milestone review): UI input, events and callbacks run in the fixed step from latched input, for determinism, so `Time.SetTimeScale(0)`, which runs frames but no tick, lets no hover, click, navigation or typing reach a widget and runs no `OnUi*` callback until ticks run again, and a slow time scale delays the UI's response by the same factor. The pattern: a pause menu keeps the time scale and pauses gameplay with a flag its behaviours check, so its widgets stay interactive (the game-building skill's `ui` page, luau-gameplay's UI section; "PlaySession: with a time scale of 0 live play runs no tick, so a click fires nothing until the scale returns" pins it). Running UiInput from the frame view while the time scale is 0 would be new scope, with a determinism decision of its own.
- Fallback fonts are per font and none is built in (M22 C22.3, ADR 0033 decision 42): a text falls back through its font's `FontImportSettings.Fallbacks`; the built-in default font has none (the reserved built-in handles 0x01c2 to 0x01c4 stay free, since a useful CJK font would put megabytes into every export), so a game that draws CJK, Arabic or Hebrew imports its fonts with `Ranges` and names them in its UI font's fallbacks. The Text component keeps its frozen layout (ADR 0013 decision 11): no fallback chain, no shaping and no bidirectional reordering; UI text (`UiText`) has all three. No work planned.
- Shaping and bidirectional text take four simplifications (M22 W22.3, ADR 0033 decision 43 and "Integration (W22.3)"): a line break inside a shaped run keeps the forms the whole run was shaped with (its pieces are not shaped again); `MeasureText` creates its HarfBuzz faces and fonts for each call and caches nothing (risk 14; not measured); a right-to-left run draws a mirrored glyph only for a mirrored codepoint the font maps (FontImporter version 5 bakes the mirrored forms of the codepoints it bakes); and a codepoint that no font of the chain draws takes no part in the bidirectional algorithm. No work planned.
- World-space canvases are flat and unlit (M22 C22.3, ADR 0033 decisions 49 to 51 and the review of C22.3): no billboard, no lighting or fog, untonemapped like world Text, depth-tested without depth writes, so two World canvases overlap in their centres' back-to-front order rather than per pixel, and a World canvas draws over world Text where they overlap, whichever is nearer (world Text is recorded first, in the Text row, also without depth writes); the pointer reaches them through the primary camera only, within its clip range, and is not occluded by scene geometry (UiInteraction makes no depth or physics query, so a World canvas behind a mesh or a collider takes the pointer where the ray meets it, though the depth test hides it there; a game that needs occlusion casts the pointer's ray with `Physics.Raycast` before it acts; ADR 0033 decision 50, amended by W22.3's review); and the editor's UI preview leaves their elements out (no outline, pick or rect tool: a World canvas is placed by its entity's Transform and its elements are edited in the inspector or with `entity.update`). No work planned.
- Rigid node animation is not imported (M23, C23.3, `GltfImporter` version 3; ADR 0034 decision 25): skeletal animation imports a glTF animation's channels that target a skin's joints or a skinned node's morph weights; a channel that animates another node (a rigid node animation: a door, a propeller) is skipped with `ASSET_CONTENT_SKIPPED`, and a joint node becomes a Skeleton joint, never an entity, so scripts attach objects to joints through `Animator:GetJointTransform`. The reason: an AnimationClip's channels name a Skeleton's joints, or a SkinnedMesh's morph weights by its entity path from the Animator, and the AnimationSystem writes only its Animator's pose and, with root motion, the Animator entity's own Transform. What would lift it: a Transform channel that names an entity by its path from the Animator, as the morph-weight channels do, written to that entity's Transform in the AnimationSystem phase (scene data, so the serialization and the state hash cover it), with the importer keeping an animated node as an entity below the Animator. No work planned.
- An Animator's pose is sampled once per fixed step and not interpolated between ticks: a frame between two ticks draws the last tick's pose while the entity's transform interpolates, so animation shows at the tick rate (60 Hz by default; ADR 0034 risk 11). No work planned.
- A skinned vertex's normal and tangent are transformed by the blended joint matrix itself, not its inverse transpose, so a joint with a non-uniform scale shades approximately, on the GPU and in the CPU reference alike (ADR 0034 decision 27). No work planned.
- CPU raycasts (`scene.raycast`) test a skinned mesh's bind-pose triangles, not its deformed ones; GPU picking (`viewport.pick`, the editor's click) reads the deformed render, and physics colliders are never animated (ADR 0034 risk 12). No work planned.
- An animation clip is a single pose (duration 0) or at least 1 ms long (`MinAnimationClipDuration`; the glTF importer skips a shorter animation with `ASSET_CONTENT_SKIPPED`), a looping layer counts at most 8 ends of its clip in one fixed step (`MaxAnimationWrapsPerStep`: its time stays exact, the events and root motion of the cycles beyond are dropped), and an Animator delivers at most 256 events a step (`MaxAnimationEventsPerStep`, the rest dropped with one warning for the entity), so a short clip of many events played fast (a broken or hostile file) cannot exhaust memory in the fixed step (ADR 0034 decisions 24, 26 and 29). No work planned: no clip that plays visibly reaches these bounds.
- glTF skins that resolve to one Animator merge into one Skeleton (M23, `GltfImporter` version 3), whose joints keep the first listing skin's inverse binds; each skinned mesh is moved into that Skeleton's bind space by each vertex's heaviest joint's correction, which is exact when the skins share one bind pose (as exporters write them) and approximate for a vertex whose influences disagree when a skin was bound in a different pose of the shared joints (ADR 0034, "Stream A notes (W23.3)" and the W23.3 integration record). No work planned: an exact rebind needs per-mesh inverse binds in the frozen mesh and palette formats.
- A skinned vertex takes at most four joint influences (M23): a glTF primitive's `JOINTS_1` and `WEIGHTS_1` are reported with `ASSET_CONTENT_SKIPPED` and ignored, and the four influences of `JOINTS_0` are renormalized (`MeshSkinVertex`, ADR 0034 decision 25). No work planned.
- A glTF mesh on a joint node is reported with `ASSET_CONTENT_SKIPPED` and not placed (M23): joint nodes become Skeleton joints, never entities, so nothing holds the mesh; a model attaches it to a non-joint child node instead, which the importer places under the Animator at its rest transform (ADR 0034 decision 25). No work planned.
- A glTF animation's morph-weight channels play only on a node at or below a skin's Animator (M23): a glTF of morph targets without a skin imports its meshes' morph targets and its nodes' SkinnedMesh weights, but its animations' weights channels are skipped with `ASSET_CONTENT_SKIPPED`, since no Animator plays them (ADR 0034 decision 25). No work planned: the AnimationSystem poses only an Animator whose Skeleton loads, so a morph-only rig would need an Animator that poses without one.
- A deformed item that casts shadows (M23) is deformed once a frame whenever any shadow is planned, even when every cascade, spot tile and point face then culls it: the Prepare stage prepares the shadow casters, acquiring each deformed caster's deformation, before the per-face culling, so an off-screen skinned shadow caster costs its Skinning dispatch whether or not a shadow draws it (`Docs/Decisions/0034-m23-contract.md` decision 36, stream C's design the lead accepted). No work planned: culling the casters per face before acquiring their deformations changes the Prepare stage's order of the shadow passes, which no milestone of the program schedules.

## 7. Non-goals for v1

Out of scope by design (§1.2), each open to an ADR. ADR 0028 schedules some, records others as won't do (§8), and leaves the rest out of scope:

- **Graphics:** backends other than NVRHI-Vulkan, ray tracing, bindless and GPU-driven rendering, render-graph aliasing (won't do, §8); clustered light culling and point-light shadows (built by M23, W23.1); TAA, histogram auto-exposure, colour-grading LUTs and SSR (M26: W26.1 and W26.2); GI beyond IBL plus AO (baked irradiance and reflection probes in M26, W26.1; dynamic GI won't do, §8).
- **Assets:** GPU texture compression (imported textures as BC7 and BC5 since M23, W23.1; environment cubes as BC6H since its W23.2), EXR import (built by M23, W23.2), Ogg Opus import and mesh instancing (built by M23, W23.1).
- **Features:** skeletal and morph animation (built by M23, W23.3, with script-driven blending; an animation state-machine graph stays a non-goal, §1.2), particles and terrain (M26: W26.1, W26.2); visual scripting (M24: W24.1 and W24.2) and native gameplay modules (built by M19 on Windows, W19.1 to W19.3, ADR 0030 decisions 25 to 35; on Linux and macOS dropped by the owner, §4); networking (out of scope, stays here: "Networking can stay in the backlog for now").
- **Editor and scenes:** native file dialogs (on Windows since M18, W18.1: nativefiledialog-extended's `IFileDialog` backend behind the FileDialog API, ADR 0029 decisions 19 to 21; their Linux and macOS backends dropped by the owner, §4, so the ImGui picker serves there), ImGui multi-viewport OS windows (M24, W24.1, on Windows; on Linux and macOS dropped by the owner, §4), a UI framework beyond `TextComponent` (the static UI since M22's W22.1, ADR 0033 decisions 2 to 9, and its interaction since W22.2: focus and navigation, events, the four widgets, the theme, minimal authoring and the interaction state in the hash, decisions 21 to 36; and since W22.3 the text input, fallback fonts, shaping and bidirectional text, and world-space canvases, decisions 42 to 53).
- **Platforms:** mobile and web, native Wayland, cross-OS export, bit-exact cross-OS or cross-compiler determinism (out of scope, stay here: "We are not doing this right now"); consoles, identity code signing and notarization (won't do, §8).
